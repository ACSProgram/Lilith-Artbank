# 维护与批量工作流

维护任务都是显式触发的长任务：有进度、可取消、失败有清单。它们不改变“原图不可变”的原则，只清理可重建缓存或用户明确要求删除的内容。

本域覆盖的长任务：重建缩略图（走任务总线，可选重算 pHash / 主色）、图片空间优化（估算与执行两阶段）、永久删除与清空回收站的待释放标记与后台释放任务（`ReleaseGarbage`）、库检查（快速检查与完整 BLAKE3 校验）、孤儿移入回收站（可撤销）、导出到目录、缩略图包空闲回收。入口都在工具栏「任务 → 维护与检查…」的四个分区里（`src/app/MaintenanceDialog.tsx`）。

描述导出/回填整条**不做**：真实库只有 1.7% 的图片缺描述，导出要复制 10–20 GB，且 `output/` 里全是 64 位哈希文件名，对外部打标工具不友好。特征包只统计、不回收：模型切换会让整包作废重算，压了没有意义。

## 描述导出/回填（不做）

原软件的「导出无描述图片 → 外部打标 → 回填描述」流程不再实现。需要批量描述时用 AI 服务的批量任务；手工补写走详情面板。

## 库检查

一次目录遍历同时产出四类结论，不重复走盘（`src-tauri/src/library/inspect.rs`）。范围可选当前选择 / 文件夹 / 集合 / 视图 / 全库；临时文件夹不参与。

- **遍历方式**：从 `folders` 表取范围内 `kind = 'normal'`、未进回收站且不在释放中的文件夹（临时文件夹与回收站等系统目录不是图库的一部分），拼绝对路径逐个 `read_dir`。不做整库递归 `walkdir`，避免把 `.artbank` 里的 pack 也数进来。内存是 O(最大单文件夹)：每个目录的行与文件集在内存里比对，孤儿是否属于别的文件夹靠逐条反查（孤儿本来就少），不预载全库哈希表。
- **判据**：文件名必须是 `<64 位小写十六进制>.<扩展名>`。哈希在本文件夹的行里且大小一致 → 正常；大小或扩展名不一致 → **大小不符**；哈希在别的文件夹或库里根本没有 → **孤儿**；行在、文件不在 → **缺失原图**；文件名不符合规范 → 非内容寻址文件，只计数（`desktop.ini`、用户手工放进来的东西，移动它们风险高于收益）。
- **快速检查**：只看存在性与大小，不读文件内容，39 万行量级在二十秒上下（实测见[性能基准](../guides/performance.md)的「库检查」）。
- **完整校验**：在快速检查基础上重算 BLAKE3 与 `content_hash` 比较，分条流式读（1 MB 缓冲），几十 MB 的原图不整个进内存。按范围进行；「全库」是单独选项，勾上才出现耗时确认。
- **不持路径锁**：全库完整校验要读二三十分钟，长期占根路径读锁会挡住导入与编辑。改为容忍漂移——扫描开始记时间水位，`modified_at` 不早于它的行跳过哈希校验并计入「扫描期间变动」。与「不承诺任意时刻的全库快照一致」同一口径。
- **进度与取消**：单位是张数（与压缩、embedding 同口径）；准备段只给文案「正在准备…」，扫描段按张推进，完整校验接着同一批单位继续、不重置分母；每 256 张查一次取消，已扫到的部分保留在报告里。
- **报告**：四份清单各最多 5000 条，超出时 `truncated` 为真、界面写明「最多保留 N 条」。报告按任务 id 缓存在内存（最近 5 条），被挤掉时提示重新扫描。导出走 `save_inspection_report(taskId, path, group?)`，后端直接写 CSV（列 `kind,path,image_id,expected_size,actual_size,detail`），几万行不经过 IPC。
- 检查结果不自动改数据：缺失与大小不符只报告；孤儿可以移入回收站（见下）。
- 命令：`start_batch_task` 的 `kind = "checkFast" | "checkFull"`；报告用 `get_inspection_report(taskId)` 读。

## 清理孤儿文件

入口是检查报告里的「移入回收站」，**必须基于一份当次扫描的报告**：`move_orphans(reportTaskId, paths)` 会校验每个路径都在报告的孤儿清单里，否则拒绝。不接受任意路径列表，否则就成了「按用户给的路径随便搬文件」的口子。

- 目标 `recycle/orphans/<原文件名>`，重名追加 `-1`、`-2`；同卷 `rename`，跨卷退化为复制 + 删源；单个失败记入失败清单，不中断整次操作。
- 顺序是**先搬文件、再用短事务记账**：单写连接不会被几百 GB 的搬移长期占住，导入 flush 与元数据写入不必等整次清理跑完。记账失败时把已搬走的文件逆序搬回原位；进程在两步之间被强杀会留下「文件已在回收站但没有记录」，这类文件仍可手工找回，不影响库内一致性。
- 整次操作写**一条** `orphanMove` 记录，`data` 是 `(源绝对路径, 目标绝对路径)[]` 的 JSON 数组，撤销一次退回整次清理；撤销时原路径已被占用就跳过该条并计入「无法恢复」。
- 中途取消时记录只包含**实际已搬走**的文件，未处理的留在报告里等下次，撤销永远不会指向一个没搬的文件。
- 这些文件在数据库里没有记录，移走后图库看不出任何变化；清空回收站之后文件就真的没了。界面文案必须说清这一点。

## 缩略图维护

- **重建缩略图**：工具栏「任务 → 批量任务…」，范围可选当前选择 / 文件夹 / 集合 / 视图 / 全库；默认只补缺失，可勾选重做已有并顺带重算 pHash / 主色。对话框先显示“范围 N 张 / 将处理 M 张”；不勾选重做时已有缩略图不计入 M，开始后任务 `total` 等于 M。重新解码原图、生成 512px、追加到 pack、在事务里更新指针与 `thumb_version`；连续失败 5 张自动停止。
- **缺失缩略图**：`thumb_segment=0` 或读取失败时，详情/网格显示占位；用同一条批量任务补建。打开图库时会把段长度短于 `thumb_segments.size` 的越界指针清成 `thumb_segment=0`，所以掉电丢掉的尾部字节不会变成永久 404。
- 包格式只追加，`append` 只往段末尾写、段满才开新段，**从不回头找空洞**。所以编辑一张图留下约 23 KB 空洞，跑一次全库重建会让旧包整份变成空洞——不是慢慢涨，是跳着涨（一次重建多占约 9 GB）。

### 缩略图包空闲回收

统计是只读的，回收是写任务，两者分开：`get_pack_stats` 一条 SQL 出全部段（`garbage = size − 16 − used`，16 是段头），特征包同样一条聚合，只显示不回收。

- **阈值**：段垃圾率 > 20% 才动手。没有单独的停止阈值：一次回收压的是**整段**，压完这一段就回到接近 0，不存在「压到一半停手」的状态。20% 意味着最坏常驻浪费约 1.8 GB（9 GB 的 20%）；再往下压（如 5%）回收更干净，但每次都要重写接近整个包，写放大会明显变大。
- **空闲判定**：`app/activity.rs` 只记一个时间戳（`AtomicI64`），`touch()` 的落点是 `trace::read/write/write_async` 三个包装（覆盖全部命令）、`thumb://` 与 `img://` 协议入口（纯滚动不发命令，只发缩略图请求）、MCP 请求入口。不监听鼠标键盘、不查窗口是否最小化、不加窗口事件。
- **动手条件三条同时满足**：`idle_for() >= 3 分钟`、任务总线没有运行中或排队中的任务、缩略图包垃圾率 > 20%。前两条是内存判断、零成本，只有它们都满足才去查第三条的 SQL——平时一次数据库查询都不跑。
- **循环**：`app/idle.rs` 一个线程每 30 秒醒一次（1 秒切片，关库不必等满 30 秒），开库时启动、关库时退出。条件满足就提交一个 `TaskKind::PackCompact`，然后回到等待——任务在跑期间第二条不满足，自然不会重复提交。不做「一次空闲窗口只跑一批」的代次计数：任务压到干净或被打断就结束，天然自限。
- **让位**：每复制 2000 个 blob 检查一次 `idle_for()`，小于 3 分钟说明人回来了，放弃当前段——删掉本次新写的段文件，数据库一个字没改，旧段原样保留，所以能在 1–2 秒内响应。任务相位落新增终态 `TaskPhase::Yielded`（前端文案「已让位」），不复用 `Cancelled`：用户没点取消，胶囊上写「已取消」会误导。已提交的段保留、不回退；用户手动点取消仍落 `Cancelled`，两条路径只在终态相位上不同。
- **手动「立即回收」**：提交同一个 `TaskKind::PackCompact`，只是不等空闲条件；仍受任务互斥，有导入在跑时会排队。没有超过阈值的段时按钮不可点。
- **压多少**：不设固定段数。只要还有段的垃圾率超过 20% 就继续压下一段，直到没有这样的段或被打断。离开 10 分钟就压 10 分钟的量，离开一小时一次压干净。
- **回收算法**（`src-tauri/src/library/pack_gc.rs`）：新建下一个段号的文件 → 按 `images.id` 升序读该段仍被引用的 blob，逐条复制并记录新偏移 → 数据写 + `sync_all` → 一个事务里批量更新 `images.thumb_segment/thumb_offset` 与 `thumb_segments.size`，并删掉旧段行 → 延迟 2 秒删旧段文件。发布顺序与图片压缩同源，失败或让位时数据库根本没动过，只需删掉新文件。段里一条有效指针都没有时整段删掉，不再造一个只有段头的文件。
- **与内存写指针的关系**：压缩完成后调用 `ThumbPack::reload_from_disk()` 重新读最新段头，让 `append` 落到新段末尾。压缩占内容写者 + 根路径原地替换（`Access::Replace`），与导入、编辑、重建缩略图互斥——这些正是唯一会 `append` 的路径，所以压缩期间不会有新的 append 进来。查看器与 MCP 拼图读缩略图不受影响。
- **旧段的读窗口**：提交后延迟 2 秒再删，期间新到的读请求已全部指向新指针；仍失败的请求由 `thumb://` 现有的 404 重试兜底。删除失败只记日志，留待下次回收。
- **残留清理**：打开图库时扫一遍 `thumbs/`，凡是不在 `thumb_segments` 表里的 `.pack` 直接删。覆盖三种来源：让位时没删成的、提交失败留下的、进程崩溃留在磁盘上的。9 个段的目录扫描是毫秒级。顺序必须是「读库 → 清残留 → 打开缩略图包」：`ThumbPack::open` 会读编号最大的 `.pack` 的头，磁盘上留着 `9999.pack` 就会让图库直接打不开。这段逻辑在 `library::service::open` 里，不在 `AppState`。
- 设置项 `maintenance.autoCompactThumbs`（默认开）关掉之后空闲循环不再动手，「立即回收」仍然可用。

## 特征包维护

- embedding/pose 存放在 `features/<kind>-<model>-<dim>-<dtype>-<hash>.pack`，`feature_blobs` 记录 model/dim/offset/length。
- 模型变更后，旧向量保留但标记为不兼容；重算走批量任务。
- 特征包同样只追加，但**不做压缩**：维护页只显示每个包的条数、已用与垃圾字节。模型切换会让整包作废重算，压了没有意义。

## 图片空间优化

两步：只读估算 → 确认执行。执行会替换原图，且不可撤销。

### 估算（只读）

- 入口：工具栏「任务 → 优化图片空间…」，范围可选当前选择 / 文件夹 / 集合 / 视图 / 全库。
- 参数：质量档位（极高 / 高 / 中）、输出格式（JPEG / WebP）、长边上限（留空表示不限，合法范围 64–65535；输出 WebP 且超过 16383 时界面提示会被跳过）、三个重算开关、是否跳过已处理过的图片、抽样档位。
- 抽样只有五档：50 / 200 / 500 / 1000 / 2000，默认 200。滑块按档位索引走，五个标签与五个停靠点一一对应；后端仍接受 50 的倍数，五档只是界面限制。
- 档位提示：本次会话里有过同一 `(输出格式, 长边上限, 档位)` 的完成估算时，滑块右侧显示「覆盖 X 体积 · 约 Y」——X 是该次估算的覆盖率（按 0.01% / 0.1% / 1% 三档精度，否则默认档的 0.08% 会被显示成 0），Y 用 `sampleElapsedMs / sampleCount × 当前档位` 折算。没有实测就不显示这一行。这个提示只描述抽样本身，与结果页的总预计耗时是两件事。
- 只读：估算只占会话读，逐张拿文件夹读锁与图像预算许可，不写数据库、不写操作记录、不改文件，也不产生临时文件；可取消，结果只缓存在内存（最近 10 条），同时充当执行凭证。
- 进度：统计候选只报百分比、不报张数（这一段读的是整个范围，按张数显示会让人以为在重跑全库）；编码样本才按张显示 `k / n`。百分比按阶段耗时加权，统计占前 25%、编码样本走到 100%，只前进不回退；汇总阶段直接满格并显示「正在汇总结果…」。
- 误差区间：以**切片**为单位重抽 300 次（切片等体积，方差估计才有意义）。覆盖 100%（`sampleCount ≥ candidateCount`）时两个区间都直接报 0——抽样就是全体时不存在抽样误差，旧实现即使估算与实际逐字节相等也会报 ±8%…±18%。耗时区间 = `sqrt(抽样波动² + (0.5 × (write + finish))²)`：抽样波动是重抽得到的 `work` 的 1.96σ，逐张累加的耗时先按线程数折算成墙钟再外推（与点估计同口径）；写入与提交侧没有抽样，用校准值的 ±50% 当固定项。区间只描述已抽到的部分与抽样误差，不覆盖机器负载波动，未覆盖体积由覆盖率单独显示。
- 结果读取：前端以任务 id 与阶段为依赖，不再因任务快照每 150ms 刷新而丢弃在飞请求；超过 5 秒未返回显示「读取估算结果超时」与「重试读取」；缓存被新的估算挤掉时提示「估算结果已被新的估算覆盖，请重新估算」。
- 任务接管：结果自带 `options`、`scope`、`scopeLabel`、`sampleSize` 与 `libraryId`，接管时不依赖前端内存。重新打开对话框按「执行中 → 估算中 → 本次结果 → 已完成估算 → 默认配置」决策；执行始终用结果里的范围与参数，不按当前浏览状态重拼。换库、关库或结果属于别的图库时不接管；「返回修改」放弃过的结果不会再自动弹出；应用重启后任务中心为空，不承诺跨重启恢复。
- 设置与结果一致：估算运行中改参数，结果回来时签名已变就丢弃并提示重新估算；展示中的结果与当前设置不符时也会作废。
- 打开延迟：对话框先出现、范围计数后补（`get_library_stats` 的 `summary` profile 只做计数），不再为了一个总数跑完整分面统计。
- 统计口径（漏斗）：
  - 范围 `total`：当前范围解析出的未删除图片。
  - 未纳入候选（只看数据库列，与执行共用 `optimize::prefilter`）：`bpp < 0.12`、勾选「跳过已处理过」时 `optimized_at > 0`、输出 JPEG 时带 alpha、输出 WebP 时单边超过 16383、GIF（动画/多帧保守跳过）。
  - 候选 `candidate`：通过前置判据、会进入解码与编码评估的图片。
  - 候选内跳过：非 sRGB 色彩、16 位源、画质不达标、省得太少、动画/多帧/多页（APNG、动画 WebP、多页 TIFF）、读取或解码失败。透明 / bpp 低 / 超 WebP 尺寸这三条在扫描时用的是数据库列（`has_alpha`、`file_size`、宽高），解码后换成真实值；两者不一致时会在解码后失败，单列「解码后判定」。
  - 处理 `process`：候选减去候选内跳过。
- 不变量（外推后各桶会先按比例收窄再算 `process`，四条都严格成立）：`totalCount = prefilterCount + candidateCount`、`totalBytes = prefilterBytes + candidateBytes`、`candidateCount = processCount + candidateSkipCount`、`candidateBytes = processBytes + candidateSkipBytes`。
- 动画/多帧/多页判据：GIF 只看数据库里的格式列；APNG 认 PNG 的 `acTL`、动画 WebP 认 RIFF 的 `ANIM`、多页 TIFF 看 IFD 链长度，都只读文件头，不解码全部帧。估算与执行共用 `optimize::multiframe_guard`。
- 抽样：按「有损源 / 无损源 × 6 个 bpp 桶」交叉分层，样本量按候选体积分配且每层至少 3 张；**层内按累计体积等分切片**，每份随机取一张代表整份（`slice_indices`）。切片让样本的体积与像素构成由构造贴合总体：某张图独占若干份时会合成一份并被必然抽到，尾部不会整体缺席。每张样本带 `(weight_bytes, weight_count)`，即它代表的整份切片。层内候选不足档位时退化为全取。样本真实解码并按阶梯质量编码，回解码后计算 PSNR 与局部坏点占比；PSNR 底线随源类型分两套（有损 / 无损），坏点占比只作诊断，不参与裁决。样本还会真实执行 BLAKE3 与勾选的重算（缩略图 / pHash / 主色），结果直接丢弃，只保留耗时。切片合并会让实际样本数偶尔略少于档位，此时界面不显示「候选不足」（那个标记只看候选张数是否少于档位）。
- 外推：每层按**切片字节加权**的节省率（`Σ 切片字节 × 单张节省率 / Σ 切片字节`，夹到 0–1，`MAX_SIZE_RATIO = 0.95` 是替换阈值，不是节省率上限），再乘以该层候选总体积；跳过分类直接累加切片权重，不再按张数等比例放大。切片权重之和恒等于层体积与层张数，所以漏斗仍然严格闭合。
- 预计耗时：`work = max(样本墙钟 × 放大倍率, 候选读取字节 / 读取带宽, 分段耗时 / 线程数)`、`write = 预测输出字节 × 每字节写盘秒数 + 处理张数 × 每张 fsync`、`finish = 批次数 × 每批提交 + 处理张数 × 每张删除`，三项之和是总预计耗时。放大倍率**按层计算**：每层用「该层候选像素 / 该层样本像素」放大该层的编码耗时，再汇总。样本量按体积分配，高 bpp 层拿到的样本远多于它的像素份额；用全局像素比会把「这层分到的样本少」和「这层像素本来就少」混在一起，实测会整体放大一倍以上。写入侧参数优先取本库上次执行的实测校准（`meta` 表的 `optimize.calibration.v1`）：每字节写盘秒数不含 fsync，fsync 按张单独计，两者不会重复。没有记录时用“普通 SSD”量级的保守常数：写入 300 MB/s、每张落盘 1.5 ms、每批提交 20 ms、每张删除 0.5 ms。校准只在处理 ≥20 张、有输出字节、且四项都落在合理量级时更新；记录损坏或数值异常会被忽略，保留上一次的值。慢盘（机械硬盘）的第一次估算会偏低，从第二次起按本库校准。
- 输出：范围与候选两行短信息、样本张数与覆盖率（含 ≥32 MP 大图被抽到的张数）、候选池的「处理 / 候选内跳过」环图与细分图例、未纳入候选单独一组、预计节省与误差、预计耗时与误差及三项拆分、样本质量分布、收益曲线、分文件夹明细、样本失败清单（最多 20 条）。覆盖率低于 1% 时在耗时下固定一行提示「抽样只读取了 X% 的候选体积，实际误差可能大于上面的 ± 值」。
- 收益曲线：横轴是**已处理的候选张数占比**（与执行时的进度条同源），纵轴是累计节省；按执行顺序（bpp 从高到低）累加。横轴刻度取 0/20/40/60/80/100%，与五个里程碑点一一对齐。每个点的耗时按三段各自加权：`work` 按像素、`write` 按该层的预测输出字节、`finish` 按该层张数。界面上标注 20% / 40% / 60% / 80% / 100% 五个里程碑（图上只给首尾标数值，其余看右侧表格）。前 20% 的图片的累计节省不到总节省的 10% 时，曲线下方补一句预告「前 20% 的图片预计…开始阶段进展可能较慢」，因为同批里混着会跳过的图时，开头可能很久看不到空间变少。
- 命令：`start_batch_task` 的 `kind = "optimizeEstimate"` 携带 `optimize` 与 `estimateSampleSize`；结果用 `get_optimize_estimate(taskId)` 读取。
- 实现：判据、阶梯编码、PSNR/坏点、EXIF/ICC 搬运与去 Orientation 在 `src-tauri/src/imageops/optimize.rs`；分层、抽样、外推、漏斗与耗时拆分在 `src-tauri/src/library/optimize_estimate.rs`；任务与结果缓存在 `src-tauri/src/app/state.rs`；界面在 `src/app/OptimizeDialog.tsx`，占比环图与收益曲线在 `src/app/OptimizeCharts.tsx`。
- 未做：分文件夹明细每行的「只处理这个文件夹」按钮（范围切换不支持任意 folderId，见 `src/app/taskScope.ts`）。

### 执行（写路径）

- 元数据：JPEG 输出搬运源 JPEG 的 EXIF（删 Orientation）与 ICC；**WebP 输出不搬运任何元数据**（`webp` 库只提供简单编码接口，没有写 ICCP/EXIF chunk 的能力），界面在输出格式处提示。PNG/BMP/TIFF 源转 JPEG 同样不搬运。
- 色彩配置：输出装不下 ICC 时，只有源配置名里带 sRGB 才放行（丢掉 sRGB 配置不改变显示），其余一律跳过并计入「非 sRGB 色彩」，避免颜色变样。判断只看 ICC 的 `desc` 名称，PNG 只看 `iCCP` 的配置名。
- 命令：`start_batch_task` 的 `kind = "optimize"`，必须带 `estimateId`。凭证缺失、被缓存淘汰、参数指纹不符、重新解析出的候选张数/体积与估算相差超过 10%，或**候选集合指纹不一致**（张数与体积都对得上、但换了一批图）时直接拒绝，要求重新估算。界面在「确认执行」前再弹一次确认：说明会损失一点画质、原图无法恢复，但执行中可以取消。
- 排队后复核（三道关）：执行任务默认排队，提交时校验一次；worker 真正拿到资源（内容写者 + 根路径原地替换）后再重新解析范围、收集候选，依次核对（1）参数指纹与张数/体积、（2）候选集合指纹、（3）**逐张 `stat` 原图**（8 线程并行，实测约 19 µs/个，十几万候选在热缓存下几秒）并确认涉及的文件夹还在。文件夹消失直接拒绝；原图缺失或大小不符的比例超过 1% 也拒绝并给出张数，低于 1% 则把这几张从候选里剔除、在任务摘要里说明「N 张原图缺失或已变化未纳入」。不做内容哈希校验——执行阶段本来就要读一遍，大小 + 集合指纹已能挡住实际会遇到的漂移。
- 范围与过滤：按同一范围重新解析 id，与估算共用前置判据（GIF、bpp、已处理、透明、WebP 尺寸）；16 位源与非 sRGB 色彩在解码后跳过，动画/多帧/多页源在读文件后按 `multiframe_guard` 跳过——GIF、APNG、动画 WebP、多页 TIFF 不会被替换成单帧。候选行在 worker 开始时一次性读进内存，用于 bpp 全局排序与凭证核对。
- 原图缺失容错：编码前读原图失败（被外部删掉或挪走）单独计入 `source_missing`，**不累加连续失败**——否则 5 张缺失就会把整任务停掉，而压缩不可撤销、已提交的批次不会回滚。连续失败阈值只用于解码器/磁盘异常这类系统性故障。任务摘要会分别显示「N 张原图缺失已跳过」与「失败 N 张」。
- 进度口径：分母是候选**张数**（`jobs.len()`），每张推进一格；分子是「已替换 + 已跳过 + 失败」——跳过在编码结束时就结算，提交成功的张数在批次结束时补上。执行前就被排除的图片（已处理过、bpp 太低、超出 WebP 尺寸）不进分母也不进「已完成」：它们不需要任何工作，算进去会让进度条开局就冲到六成，之后十几分钟只挪一点，看起来像卡死；这部分只在估算视图与任务摘要的「未纳入候选」里列出。bpp 降序把小图排在前面，按像素计权会让最前面几千张只推进零点几个百分点，看起来像卡死；按张计与 embedding 同口径，速度与 ETA 也一并统一。代价是前期小图多、进度比时间跑得快，后期大图慢、显得越走越慢——这是按张计的固有性质。准备段（`resolve` + 读候选 + 逐张 `stat` 复核，十几万候选要十来万次 stat）只给文案「正在核对原图…」，这一段没有百分比。已提交张数、条形、百分比与速度都只在批次结束时前进，所以编码期间靠 message 给批内计数：「正在编码… 第 k 批 m/256」，每 16 张更新一次（5 张/秒约 3 秒一跳），提交期间换成「正在写入第 k 批」。
- 顺序与并发：候选按 bpp 从高到低处理；`TaskKind::Optimize` 占内容写者与根路径**原地替换**（`Access::Replace`），和导入、编辑、移动、AI 任务以及所有会改路径的文件夹操作互斥，但不再挡住读者——压缩期间查看器、MCP 拼图与复制照常可用。编码与提交双缓冲：编码下一批时提交上一批，提交/删旧期间进度继续前进；最后一批提交完才到 100%。编码时显示「正在编码… 第 k 批 m/256」，提交前显示「正在写入第 k 批」。取消后批次内剩余的图立即停止编码且不再计入进度，但已编码并送入通道的批次仍会提交——进度停在真实张数，不会回退。取消只改显示：收到请求后任务相位切到 `cancelling`（前端文案「取消中」），压缩面板与任务胶囊的取消按钮禁用并说明「等当前批次提交完成，已执行的部分不会撤销」，进度条换成静态斜纹；通道仍是 `sync_channel(1)` 上的阻塞 `send`，committer 仍会提交已取走的批，复核段仍不检查取消，所以取消延迟不变。
- 单张：读原图一次（色彩配置判断、动画判据、解码与 EXIF 搬运共用这份字节）→ 阶梯编码与 PSNR 裁决 → 写入 `.artbank/temp/optimize-*.{jpg|webp}` 并 `sync_all`。阶梯先判体积再算 PSNR：当前质量已经缩不到 95% 就直接按「省得太少」早退，不再往高质量爬。
- 发布顺序（断电保护）：每 256 张或 256 MiB 一批（先到者为准），顺序固定为「文件数据 fsync → 持久化 rename → 目录 flush → 事务提交（`synchronous = FULL`）→ 删旧图」。
  - rename 走 `platform::fs::rename_durable`：Windows 用 `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`，其他平台用标准 rename 再补目录 fsync。
  - 每个目标目录只 flush 一次（`FlushFileBuffers` 目录句柄；系统/文件系统不支持时按“依赖 write-through”处理并记调试日志，其他错误中止本批）。
  - 事务在写连接临时提到 `FULL`，结束后无论成败恢复 `NORMAL`；只有提交返回后才删旧图与查看器预览。
  - 提交失败或目录 flush 失败时删掉本批已发布的新文件，数据库不变、旧图不动。
- 孤儿恢复：目标内容文件已存在时不直接当“内容重复”。先查有没有行引用该 `content_hash`；没有行引用就按 BLAKE3 校验目标文件——内容一致则接管（删临时文件、照常更新行），不一致（上次崩溃留下的截断文件）则删掉重发。只有这条罕见路径才读目标文件算哈希。导入的发布路径用同一套判断。
- 批内重复：本批两张图编码出完全相同的字节时只落盘一份，另一张计为「内容重复」跳过，唯一约束不会因此报错。
- 线程与批次：编码线程数来自全局图像预算 `workerThreads`（默认逻辑核数 − 1，上限 128）；估算与执行共用同一预算。批次 256 张 / 256 MiB，编码结果放入深度 1 的通道，内存峰值是「正在编码的一批 + 等待提交的一批」。
- 执行界面：就是同一张估算视图，用实际数据填充，不再有第二套面板。**进度与曲线只用一种计量单位：候选张数**；体积只出现在「已省 / 体积」区块，不参与任何进度或横轴。
  - 顶部一行状态：进度条、`已完成 k / n`、已用时与预计还需、速度、当前文件。百分比 = `(已替换 + 已跳过 + 失败) / 候选张数`，任务未结束时上限 99%（≥99% 给一位小数，`99.8%`），只有 `finishedAt` 有值才显示 100%。这个式子是环图中心、实线终点横坐标与里程碑横轴的同一个数；胶囊与对话框也读它（压缩任务不再暴露计量器的加权百分比）。
  - 速度 = 已结算张数 / 已用时，与「已完成」同一个和——跳过的图同样消耗了完整工作量，全跳过时速度仍然有值。
  - 环图在执行时换成「已替换 / 已跳过 / 失败 / 未处理」四段（互斥，和为候选张数），中心显示**已处理占比**（不再是「已替换」），标签写「已处理」；「已替换」下沉为图例第一行。「已跳过」下面按 6 个原因展开子行（非 sRGB 色彩 / 16 位源 / 画质不达标 / 省得太少 / 动画多页 / 解码后判定），执行中就可见。
  - 体积行标签是「已替换体积」，右侧预计值写「全范围预计 X」，避免与正上方的总预计节省撞成两个一样的数字。
  - 收益曲线用虚线画预估、实线画实际，两条线共用 `已结算张数 / 候选张数` 这条横轴，末点都到 100%；里程碑表多一列「实际」，五行都会在走到时填值。前期收益提示与抽样覆盖率提示只在执行中显示。
  - 任务结束后顶部换成一行结论「已替换 N 张 · 省 X · 用时 Y」，环图去掉「未处理」段，曲线下方保留一行「实际 vs 预计：耗时 · 处理张数 · 节省空间」（取消或失败补「已停止」）。
  - 字节只算已提交批次；实际耗时从真正进入编码起算，不含排队、准备与执行前复核。
- 旧图删除：提交后并行执行，不持有数据库写锁；路径校验的根目录只 canonicalize 一次、父目录按文件夹缓存。删除失败只记日志并计入 `deleteFailed`，留给后续维护清理。
- 行更新只改内容列：`content_hash`、`file_ext`、`file_size`、`format`、`has_alpha`、`width`/`height`（取缩放后的像素尺寸）与 `optimized_at`。`score`、`description`、标签、集合、`imported_at`、`modified_at`、`feature_blobs`，以及未勾选重算时的 `phash`/`colors*`/`thumb_*` 都保持原值。
- 重算开关：缩略图按压缩后的像素重建并 `thumb_version + 1`；pHash、主色同理重算。三者默认关闭，缩略图默认沿用旧图。
- 失败：单张失败进入任务自动生成的失败清单（报告最多 50 条，任务胶囊显示前 20 条）；连续 5 张失败自动停止，已提交批次保留。
- 执行报告：除处理/跳过/失败与字节数，还带 `prefilterSkipped` / `candidateSkipped` / `duplicateSkipped`（三者之和等于 `skipped`），候选内跳过另按原因分六个桶（`skipColorProfile` / `skipNotSmaller` / `skipQuality` / `skipDepth` / `skipMultiframe` / `skipLate`，之和恒等于 `candidateSkipped`），以及 `elapsedMs`、`encodeMs`、`hashMs`、`recalcMs`、`writeMs`、`fsyncMs`、`publishMs`、`commitMs`、`deleteMs`、`deletedFiles`、`deleteFailed`。执行结束后用这些实测值更新本库校准记录，供下次估算替换保守常数。
- 收尾口径：任务与界面用的「已跳过」只取候选池内的数（`candidateSkipped + duplicateSkipped + sourceMissing`），**不含**执行前被排除的图片；`skipped` 里那段执行前排除只留给报告本身。任务摘要按段写「已替换 N 张 · 省 X · 已跳过 N 张 · 未纳入候选 N 张」（未纳入候选 = 前置排除 + 执行前复核剔除，失败另起一段），跑完那一刻不会再把「已跳过」从 1.7 万跳到 7 万、「已完成」也不会超过候选张数。
- 操作记录：`kind = 'optimize'`，`affected` 是实际替换的张数，不写撤销数据；完成后标题改写为「优化图片空间 · N 张 · 省 X」。撤销/重做会返回“压缩操作不可撤销，原图已删除”，记录面板在撤销链中含压缩记录时禁用撤销。
- 崩溃恢复：已提交批次的 `affected > 0`，打开图库时按通用规则标为 `applied`；未提交批次的临时文件由文件守卫删除；rename 后、提交前崩溃留下的目标文件在下一次执行或导入时按内容哈希接管或替换。
- 断电边界：不承诺磁盘自身缓存撒谎、文件系统损坏、外部程序改文件时的恢复，也不承诺任意时刻的全库快照一致；不做启动时的全库孤儿扫描。没有做过拔电注入测试——只验证了发布顺序、提交失败回滚、孤儿接管与平台层调用（本机目录 flush 可用）。
- 实现：写路径、发布与孤儿恢复在 `src-tauri/src/library/optimize.rs`；持久化 rename 与目录 flush 在 `src-tauri/src/platform/fs.rs`；校准记录在 `src-tauri/src/library/calibration.rs`；任务启动在 `src-tauri/src/app/state.rs`；两阶段界面在 `src/app/OptimizeDialog.tsx`。

## 临时文件

- `.artbank/temp/` 只放原子写入与编辑中间文件；打开图库时清理一次。
- 导入/保存崩溃后可能留下 temp 文件；清理只删除 temp 目录内文件，不触碰原图。
- 删除类操作先写待释放标记；记录过期或清空操作记录后，`ReleaseGarbage` 任务按批次删行、删文件；图片处理完后自底向上删除已空且无子项的回收站文件夹行与空目录（目录里仍有未纳管文件时保留并记警告），失败留下标记并在下次任务中重试。
- 一次释放按 400 张一块：块内先提交删行事务，再删文件；释放任务本身不可取消，卡在块边界也不会留下半删的行。
- `.artbank/undo/` 存放编辑等操作的暂存文件；打开图库时删除没有对应 `operations.id` 的目录。

## 图库管理

- 添加/打开/切换/关闭/移除见 [图库与元数据](library.md)。
- 移除只移除列表项，不删除文件；UI 必须明确提示。
- 重命名只改显示名与清单名称，不改目录名。
- 不支持在应用内删除整个图库目录；用户可在资源管理器中自行处理。

## 导出

入口在维护页的「导出」分区，走 `start_batch_task` 的 `kind = "export"`（范围 + 选项的形状与批量任务一致，单开一个命令会让范围解析、预览、取消、进度各写两遍）。实现 `src-tauri/src/library/maintenance_actions.rs`。

- 复制原图到用户选的目录，保留库里的文件名（`<content_hash>.<ext>`）。8 MB 缓冲流式复制，几百 MB 的原图不整个读进内存。
- 目标已存在同名文件：**跳过并计数**，不覆盖、不改名——用户的目录里可能已经有同一次导出的结果，覆盖会悄悄吃掉别的东西。
- `includeManifest = true` 时写 `manifest.csv`：`content_hash,file_ext,width,height,folder_path,score,description`，开头写 UTF-8 BOM（没有它 Excel 会把中文读成乱码）。不写 JSON：CSV 能被 Excel 和脚本同时吃。
- 占根路径读锁（`Access::Read`）并申请内容写者与元数据写者：导出期间导入、编辑、移动、删除与改评分都被拒绝，导出结束后恢复。这条后果写在「开始导出」按钮下面一行，全库导出会挡很久。
- 进度按张数，附带已复制字节；可取消，已复制的文件保留在目标目录。
- 导出不修改图库，不写操作记录。

## 验收要点

- 孤儿扫描只移动孤儿，不误伤正常文件；DB 行缺失原图时能显示；非内容寻址文件只计数。
- 缩略图回收后所有指针有效，旧 segment 被删除，`thumb_version` 不受影响，查看器与 MCP 拼图照常读图。
- 完整校验能发现人为改坏的原图；快速检查不会误报大小相同的篡改；扫描期间被改动的行不算问题。
- 导出同名跳过不覆盖；manifest 列顺序固定、中文不乱码；取消后已复制的文件保留。
- 所有长任务可取消，取消后图库一致、临时文件可清理。
- 真实窗口的手工验收步骤见[待办](../planning/todo.md)的「维护与检查」一节。
