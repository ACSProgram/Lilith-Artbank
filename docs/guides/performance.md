# 性能基准

本文件是性能数字的唯一维护处：预算、当前实测、结论与仍需复测项。逐轮原始记录（含当时的判断与全部单次值）在[性能实测明细](../planning/archive/2026-10-27-性能实测记录明细.md)。

- **不同轮次受系统负载影响可达约 2 倍**，跨时段只能比同一序列内的相对值；跨机器墙钟不可比。

## 真实库（39 万行）

索引 A/B 在库副本上做，`CREATE INDEX idx_images_visible_facets ON images(deleted_at, purge_operation_id, folder_id, file_ext, score)`：

| 查询 | 加索引前 | 加索引后 |
| --- | --- | --- |
| `counts()`（排除回收站与临时区） | 620.9 ms | **19.7 ms** |
| `list_folders`（`GROUP BY folder_id`） | 683.4 ms | **27.1 ms** |
| `list_tags LIMIT 100`（旧形状，逐张回表） | 1 162.7 ms | 784.6 ms |
| `list_tags` 新形状（`image_tags` 聚合 + 回连 `tags`） | 23.7 ms | **23.7 ms** |
| `image_tags` 覆盖扫描 `GROUP BY tag_id` | 23.9 ms | 23.9 ms |
| `filter_counts` 无筛选（五分支） | 1 815.0 ms | 618–824 ms |
| `filter_counts` 有子树筛选（`人体`，约 8.5 万张） | — | **160.1 ms** |
| `count_tags` | 0.3 ms | 0.3 ms |
| 首屏 150 / 按 id 取 150 行 | 0.4 / 0.5 ms | 0.4 / 0.2 ms |

索引成本（390,542 行）：建索引 533 ms、库体积 +7.0 MB、1000 行改评分 50 → 24 ms、1000 行改文件夹 40 ms。

- 聚合的查询计划都是 `SEARCH images USING INDEX idx_images_active_pixels (deleted_at=?)`：按像素索引顺序回表 39 万次。换成覆盖索引即 20–27 ms，**瓶颈是索引形状而不是聚合写法**。
- `filter_counts` 剩下的 620–824 ms 全在标签分支：39 万活跃 id 与 46 万关系求交集，属于这类连接的地板（`CROSS JOIN` 强制顺序只有 5–10% 收益）。有筛选时降到 160 ms。
- 20 万行合成库上记录的 69 ms 分面计数**不能代表真实库**；真实库每次全表聚合都要重读约 1 GB。

同一批改动在 20 万行合成库上的复测（用于确认形状没退化，不能替代真实库结论）：

| 项 | 现状 | 对照 | 说明 |
| --- | --- | --- | --- |
| `counts()` | 5.75 ms | 去掉索引 5.66 ms | 整库在页缓存里，看不出真实库 620 → 20 ms 的收益 |
| `list_folders`（10,221 行） | 17.8–18.1 ms | 58.5–59.1 ms | 3.3× |
| `list_tags_page` 100 | 15.6–17.1 ms | 旧形状 225.3 ms | 13.5× |
| `filter_counts` 无筛选 | 318.7 / 325.7 ms | 去掉索引 243.1 ms | **合成库上反而慢 30%**（5 列覆盖索引更宽，`matched` 物化要多扫页） |
| v7 → v8 建索引 | 316–319 ms（含 `ANALYZE`） | — | 真实库 `CREATE INDEX` 533 ms |

**结论：分面收益只能由真实库判断，合成库不作为回归门槛。**

## 相似度与向量

常驻视觉索引（20 万行，pHash + 4/8 色预转 OKLab）：

| 路径 | 预算 | 实测 |
| --- | --- | --- |
| 索引构建 | ≤1 s | 289.12 ms |
| 索引代次检查（`count(*) + max(id)`） | ≤5 ms | 9.13 ms |
| pHash 目标扫描 | ≤50 ms | 2.07 ms |
| 主色目标扫描 | ≤100 ms | 54.81 ms |
| 全库 pHash 分组（阈值 6） | ≤2 s，不退化成 O(n²) | 127.58 ms |

- 代次检查超 5 ms 预算，但每次打开图库只跑一次；若以后改成每次扫描都校验，要换成 O(1) 近似。
- 索引内存按结构估算 232 字节/行：20 万行约 46 MB、50 万行约 116 MB，是当前唯一随库常驻的相似度状态（向量仍走 mmap）。
- 分组先用 8×32 位分段索引收窄候选（阈值 ≤7 时鸽巢原理保证不漏），完全相同哈希先并组；单组 >4096 张或总检查数超上限时只标 `truncated`。

向量扫描与 AI 冷启动（20 万 × 1536 fp16，CPU 版 torch）：

| 项 | 耗时 |
| --- | --- |
| 语义搜索全库扫描（中心化余弦） | 449.26 ms（预算 500 ms） |
| 均值：整段单线程 | 417.3 ms |
| 均值：rayon 4096 行分块 | **42.5 ms**（9.8×，结果差异 0.0000） |

历史列表与裁剪只读操作表，与图片数量无关；标记与释放都是后台任务，分别占元数据写与内容写资源。

分页查询对待释放行的处理（同机 A/B）：

| 查询 | 无条件加 `purge_operation_id IS NULL` | 只在需要的视图加 |
| --- | --- | --- |
| 单级 folder 首页 150（id 列表） | 81.07 ms | 39.26 ms |
| 单级 importedAt 首页 150 | 0.63 ms | 0.64 ms |
| 6 级排序首次建 id 列表 | 197.94 ms | 197.94 ms |

原因是 `purge_operation_id` 不在排序 id 列表的覆盖索引里，无条件加条件会让文件夹排序退化为逐行回表。现在只有回收站视图与全库搜索显式加，普通视图与集合视图靠 `deleted_at IS NULL` 挡住（待释放行一定有 `deleted_at`）；新增视图或改变删除语义时必须确认这条不变量仍成立。

排除临时图片的写法（20 万行，同一时段连续三次取一次完整序列）：

| 查询 | 无过滤 | `NOT IN (子查询)` | `<> COALESCE(标量子查询, -1)` |
| --- | --- | --- | --- |
| 单级 folder 首页 150 | 40.65 ms | 53.60 ms | 44.79 ms |
| 单级 importedAt 首页 150 | 0.67 ms | 0.72 ms | 0.68 ms |
| 6 级排序首次建 id 列表 | 208.55 ms | 221.92 ms | 207.81 ms |

`NOT IN (SELECT …)` 在 SQLite 里按行探测临时索引（20 万次），非相关标量子查询只求值一次。条件收敛在 `temp::EXCLUDE_SQL` / `temp::ONLY_SQL` 一处，`COALESCE(…, -1)` 兜住“还没有临时文件夹行”的库。

## 并发与资源锁

- 任务准入改为资源表后，每次读原图多一次短路径读锁；锁表用互斥量 + 条件变量，等待者按资源排队。`concurrency::resources::tests::concurrent_stress_leaves_table_idle` 用 8 线程跑 10 万次读写交替，要求无死锁、无残留锁。
- 图像预算默认 `max(1, 逻辑核数 − 1)`，上限 1-128；预算只限制同时进行的解码/编码数量，不改变各任务自己的循环。多任务并发时的吞吐、峰值内存与路径锁开销尚未在真实库上实测；`perf_path_lock` / `perf_thread_budget` / `perf_optimize_tail` 本批未补，已记入[待办](../planning/todo.md)。
- 导入的尾部改善来自动态单文件队列与 128 深度通道；压缩的尾部改善来自编码/提交双缓冲。两者的新墙钟与末尾 5% 数据都还没有取得，不能把“感觉更快”写成结论。

## 图片空间优化

编码与写路径（16 核、NVMe、开发档）：

| 项目 | 结果 |
| --- | --- |
| 编码线程 4 / 8 / 12 / 15 | 9.7 / 16.4 / 15.2 / 16.4 张/秒（16 张 1200×900） |
| 线程策略 | 全局图像预算默认 `核数−1`，可在设置里改成 1-128；本机 8 是吞吐拐点，但没有写死成默认 |
| 批次 500 / 1000 / 2000（600 张 320×240，553 张实际处理，双缓冲之前） | 0.87 / 1.32 / 1.01 s |
| 批次上限（当前） | 256 张或 256 MiB，先到者为准；双缓冲的新基线未实测 |
| 其中发布（rename + 目录 flush） | 242 / 376 / 340 ms，约 0.4–0.7 ms 一张 |
| 其中事务提交 | 7 / 9 / 7 ms |
| 其中删旧图与预览 | 88 / 121 / 117 ms |
| 预计 vs 实际（400 张 800×600，无校准记录） | 预计 13.0 s，实际 11.4 s，比值 0.88 |
| 实际分段（同上） | 编码 86.6 s（8 线程折算约 10.8 s 墙钟）、写盘 559 ms、发布 173 ms、提交 4 ms、删除 108 ms |

估算误差：

| 场景 | 节省空间偏差 | 耗时偏差 |
| --- | --- | --- |
| 232 张合成库、50 张档位连抽 10 次 | −0.1%…+0.1%（极差 0.3 个百分点） | −9.1%…+9.1%（受 1 秒取整限制） |
| 301 张真实图片副本、同上 | −7.1%…+10.2%（中位 +0.6%） | +15.3%…+34.5%（中位 +21.7%，未达 ±5% 目标） |
| 同一份 232 张合成库、机器有负载 | 稳定在 ±0.3% | −16.7%…+94.4% |

- 断电保护的代价主要是 rename + 目录 flush（约 0.4 ms/张），提交本身可忽略；批次上限改为 256 张 / 256 MiB，提交与删旧和下一批编码重叠，新的墙钟与末尾 5% 基线尚未实测。
- 首次估算在无校准记录时略偏高（约 14%），来自保守的写入常数；执行一次后校准记录接管，误差来源只剩编码耗时外推。
- 耗时外推完全继承采样那一刻的墙钟，误差区间只覆盖抽样误差、不覆盖负载；跨机器或跨负载比较耗时偏差没有意义。
- 节省空间的剩余偏差来自「有损源 bpp ≥ 0.50」这一层内部每像素成本异质，按层放大消不掉（拆分方案见[待办](../planning/todo.md)）。

## 结论

1. **SQLite 不是瓶颈**。首屏、深分页、文件夹、FTS 都在毫秒级，不需要自研元数据索引。
2. **缩略图包优于逐文件**。随机读快约 16 倍，且避免 20 万小文件对备份、扫描与冷启动的压力。
3. **浏览器解码满足门槛**。150 张 512px 冷加载约 0.44–0.46 s，远低于 3 s 底线，也低于 1 s 目标；不需要 DDS/WebGPU 自绘网格。
4. **WebP 已定稿**。`webp` 0.3 + `libwebp-sys` 0.9.6 静态编译，debug exe 无额外 DLL，缩略图统一 WebP q80。
5. **导入吞吐达标**。合成图 47.7–50.0 张/秒，瓶颈在解码、WebP 编码与 k-means，不在 SQLite 写入。
6. **分面计数有明确边界**。普通视图在预算内；FTS 搜索约 133 ms，2 字搜索与超大集合约 0.8 s，靠筛选面板加载态兜底。进一步优化要拆请求或换数据形状，不是调 SQL。
7. **7 个排序指标都在预算内**。单级 0.66–0.76 ms；多级首次建 20 万 id 列表 213 ms，后续翻页与深页 0.83 ms，深分页不随页数变慢；文件夹排序走同一通道 42 ms。
8. **操作记录不随图库规模变慢**。500 条记录列表 0.88 ms、裁剪 1.64 ms；20 万行待释放统计 26 ms，标记与释放都是后台任务。
9. **子树筛选与树计数达标**。1 万文件夹下子树页 4 ms、`get_folders` 25–29 ms、文件夹分面 62–66 ms；文件夹分面已接近 100 ms 上限，加载态必须保留。
10. **真实库的“卡”来自索引形状**。聚合计划全是按 `idx_images_active_pixels` 回表 39 万次；一张 5 列覆盖索引把 `counts` / `list_folders` 降到 19.7 / 27.1 ms，代价 +7 MB 与 533 ms 建索引。标签聚合要从“逐张回表”换成 `image_tags` 覆盖聚合（1 163 → 24 ms）。
11. **合成库只能验证形状，不能验证 I/O**。整库在页缓存里时回表几乎免费，`filter_counts` 甚至反向变慢；性能结论必须以真实库为准。
12. **向量方案可行**。fp16 落盘 + f32 计算、mmap 分块扫描：20 万条 1536 维扫描 449 ms，不常驻 1.6 GB 向量，也不需要首版 ANN；均值用 rayon 分块快 9.8×。
13. **AI 冷启动的时间几乎全在依赖导入**，优化点是“启动时预热导入 + `ensure` 末尾 warmup forward”，不是缩短模型加载本身。
14. **文件夹概览是只读轻查询**。20 万行合成库、1 万张子树 p50 17.7 ms，字节与分组都走覆盖索引；前端按“profile + 范围 + 筛选”缓存 48 条并先显示旧值，切文件夹不闪空。真实库耗时仍待复测。
