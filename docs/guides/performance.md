# 性能基准

## 原始基线

原 C++ 图库的参考表现（用户描述）：

- 二进制元数据/缩略图数据加载吞吐约 100 MB/s 到 >1 GB/s（不含解压）；
- 一页 150 张缩略图加载并渲染在 1 秒内。

新程序的最低要求是达到原性能的 **1/3**：一页 150 张缩略图从请求到可见 ≤3s；目标仍是 ≤1s。元数据侧不要求复刻“整库载入吞吐”，因为新结构不整库载入；我们看首屏查询与翻页延迟。

### 图片空间优化写路径（2026-10-26）

三个临时库基准，都不写真实库，也不跑 release：

- `perf_encode_threads`：16 张 1200×900 确定性 PNG，在内存里解码并阶梯编码到 JPEG，比较 4 / 8 / 12 / 核数−1 线程的吞吐。只衡量解码 + 编码 + PSNR 的并行扩展性，不含磁盘。
- `perf_optimize_batch_size`：600 张 320×240 PNG 的临时库，分别按 500 / 1000 / 2000 张一批执行完整写路径，每档都用新库（同一批图压第二次会被判「省得太少」而全部跳过）。
- `perf_estimate_vs_actual`：400 张 800×600 PNG 的临时库，先估算再执行，比较预计耗时与实际墙钟，并打印执行报告的分段耗时。

```bash
cargo test --manifest-path src-tauri/Cargo.toml --lib -- --ignored --nocapture perf_encode_threads
cargo test --manifest-path src-tauri/Cargo.toml --lib -- --ignored --nocapture perf_optimize_batch_size
cargo test --manifest-path src-tauri/Cargo.toml --lib -- --ignored --nocapture perf_estimate_vs_actual
```

本机（16 核、NVMe、开发档）实测：

| 项目 | 结果 |
| --- | --- |
| 编码线程 4 / 8 / 12 / 15 | 9.7 / 16.4 / 15.2 / 16.4 张/秒（16 张 1200×900） |
| 线程策略 | `min(核数−1, 8)`：8 已是吞吐拐点，再多只增加每线程整图缓冲 |
| 批次 500 / 1000 / 2000（600 张 320×240，553 张实际处理） | 0.87 s / 1.32 s / 1.01 s（差异主要是缓存与调度噪声） |
| 其中发布（rename + 目录 flush） | 242 / 376 / 340 ms，约 0.4–0.7 ms 一张 |
| 其中事务提交 | 7 / 9 / 7 ms（1000 张一批也只有个位数毫秒） |
| 其中删旧图与预览 | 88 / 121 / 117 ms |
| 预计 vs 实际（400 张 800×600，无校准记录） | 预计 13.0 s（work 11 s、write 2 s、finish 0 s），实际 11.4 s，比值 0.88 |
| 实际分段（同上） | 编码 86.6 s（8 线程折算约 10.8 s 墙钟）、写盘 559 ms、发布 173 ms、提交 4 ms、删除 108 ms |

结论：

- 写入侧的断电保护代价主要是 rename + 目录 flush（约 0.4 ms/张），提交本身可忽略；批次大小对总耗时没有决定性影响，保留 1000。
- 首次估算在无校准记录时略偏高（约 14%），来自保守的写入常数；执行一次后校准记录接管，误差来源只剩编码耗时外推。
- 这些是开发档、合成图的数字，只用于同机对比；真实库的预计/实际对比仍要由用户手工跑。

### 查看器与保存（S4）

尚无自动基准；S4 只在单测中断言正确性，性能由真实窗口手工测量：

- 大图预览：首次打开 >2400 万像素、TIFF/TGA 或带 EXIF 方向的图片时，记录 Rust 生成 4096px WebP 的耗时与缓存体积；再次打开的命中耗时；
- 查看器滚动/缩放/平移的帧率与 WebView2 内存；原图直接加载与预览路径分别记录；
- 保存：4K/8K 图片从点击保存到列表缩略图刷新的端到端耗时，含解码、几何、编码、BLAKE3、缩略图重算与事务；
- 保存期间导入/切库被维护守卫拒绝的行为，以及失败后旧原图与数据库行保持一致。

前端虚拟化不跑自动基准；S2/S3 用浏览器预览的 4,000 行 mock 做 DOM 结构与交互检查（见下）。真实 WebView2 的滚动帧率、内存与编辑/回收站文件操作由用户手工验收。

解释：

- 翻页搜索使用 OR-EXISTS，`LIMIT 150` 能在命中率较高时提前停止；2 字搜索的翻页只需约 1.4 ms。
- 分面计数必须求出完整命中集。搜索/集合视图用单条 `MATERIALIZED` CTE 求一次命中集，再分五个 `UNION ALL` 分支聚合；这比逐分面重复求命中集快数倍，但 20 万级命中仍会超过 100 ms。
- 2 字搜索回退 `LIKE` 全表扫描 `description`，无法利用 trigram 索引；超大集合的标签分面需要扫描命中集并聚合 60 万条标签关系。
- 计数只在筛选面板打开时请求，面板内有 160 ms 防抖与加载态；不会阻塞网格翻页、编辑或滚动。
- 普通视图的分面计数 69.54 ms，在 100 ms 预算内。
- 语义搜索在开发档（本 crate opt-level 1、依赖 2）实测：20 万条 1536 维 fp16 向量、单 pack、rayon 扫描、中心化余弦，449.26 ms；向量只在 mmap 中读取，不整体载入堆。基准会生成约 614 MB 临时向量包，默认忽略，运行方式见 `ai::embedding::perf_tests`。50 万条按线性估算约 1.1 s。

前端 S3 交互（浏览器预览，Chromium 代理，724×712 CSS，4,000 行 mock）：搜索/范围切换、扩展筛选、详情与批量编辑、集合 CRUD/运算、回收站、标签重命名、右键菜单、Ctrl+A 与窄窗口覆盖层均走通；DOM 仍只挂载视口附近的行。该检查不代表 WebView2 性能；真实窗口的编辑/回收站文件操作与 20 万行滚动仍需手工验收。

### 相似度检索（S7，2026-10-24）

基准代码在 `library::perf::perf_metadata_200k`：pHash 与主色都按行用 splitmix 分散生成，避免全部相同让分段索引退化成单一大组。20 万行实测（2026-10-25 复跑）：

| 路径 | 预算 | 20 万行实测 |
| --- | --- | --- |
| 视觉索引构建（pHash + 4/8 色 OKLab） | ≤1s | 289.12 ms |
| 索引代次检查（`count(*) + max(id)`） | ≤5ms | 9.13 ms |
| pHash 目标扫描（常驻索引） | ≤50ms | 2.07 ms |
| 主色目标扫描（常驻索引） | ≤100ms | 54.81 ms |
| 全库 pHash 分组（阈值 6） | ≤2s，且不退化成 O(n²) | 127.58 ms |

- 索引代次检查 9.13 ms 已超出 5 ms 预算：它是 `count(*)`（20 万行 6.3 ms）加一次 `max(id)`，每次打开图库只跑一次，可以接受；若以后改成每次扫描都校验，需要换成 `max(id) + 行数` 的 O(1) 近似。
- 索引内存按结构估算：每行 id 8 + pHash 32 + 4 色 64 + 8 色 128 = 232 字节，20 万行约 46 MB、50 万行约 116 MB，随图库线性增长；实际常驻内存未单独采样。这是当前唯一随库常驻的相似度状态（向量仍走 mmap）。
- pHash 目标扫描是纯位运算遍历常驻数组，不查库；主色扫描每行做 4×4 或 8×8 的最近色比较。
- 分组先用 8×32 位分段索引收窄候选（阈值 ≤7 时鸽巢原理保证不漏），完全相同的哈希先并组，再对候选做距离判定；随机哈希几乎不产生候选，退化数据受单组上限与总检查数上限保护。
- 全库 embedding 复核组随候选组规模增长；单组 >4096 张直接跳过并标记截断。
- 运行方式：`cargo test --lib -- --ignored --nocapture perf_metadata_200k`（建 20 万行临时库，不触碰真实仓库）。

### 多级排序与 id 列表游标（P4，2026-10-25）

排序指标扩到 7 个后，单级排序仍在原索引上走键集游标；多级或文件夹排序改为先算出完整有序 id 列表（进程内最多缓存 2 份），后续页按 `token:offset` 切片。20 万行实测（与上面几张表不是同一次运行，同机同规模，绝对值受缓存与负载影响）：

| 路径 | 预算 | 20 万行实测 |
| --- | --- | --- |
| 单级 importedAt / modifiedAt / score / size / pixels 首页 150 | ≤50 ms | 0.66 / 0.67 / 0.71 / 0.76 / 0.68 ms（p95 ≤0.95 ms） |
| 单级 folder 首页 150（走 id 列表） | 按 id 列表预算 ≤400 ms | 42.06 ms（p95 43.32 ms） |
| 6 级排序首次（建 20 万 id 列表） | ≤400 ms | 212.98 ms（p95 223.50 ms） |
| 6 级排序后续翻页（切片 + 回行） | ≤60 ms | 0.83 ms（p95 1.13 ms） |
| 6 级排序 offset 199 850 的深页 | ≤60 ms | 0.83 ms（p95 1.00 ms） |
| schema v3 → v4 建两个索引 | — | 459.05 ms |
| id 列表内存 | — | 20 万 id ≈1.6 MB，最多缓存 2 份 |

- 6 级排序省略了「集合内顺序」：该指标只在集合视图可用，集合视图另有手工顺序专项（0.70 ms）。7 级同时用满时多一级的比较，量级不变。
- **文件夹排序按 id 列表预算，不是 50 ms 预算**：`folders.path` 是文本列，做不到行值比较的键集游标，所以文件夹排序每次都先建一份有序 id 列表（20 万行 42 ms，比 6 级排序快是因为少 5 级比较且没有集合 JOIN）。39 万行的真实库约为两倍量级（≈85 ms），仍在 400 ms 内；要压到 50 ms 需要 `(deleted_at, path)` 索引并把游标值改成文本，暂不做。
- schema v4 为修改时间与 `width * height` 各补一个索引（`width * height` 是表达式索引），单级排序因此都落在 1 ms 内；20 万行建这两个索引合计 459 ms，39 万行的真实库首次打开按同量级估算在 1 s 左右。
- id 列表在会改变图片集合、排序字段或筛选字段的写入后整体失效（`AppState::mutate` 与导入收尾统一清空），旧 token 再被使用时返回“排序结果已过期”；前端同时通过刷新令牌重新取第一页。
- 运行方式仍是 `cargo test --lib -- --ignored --nocapture perf_metadata_200k`。

### 排除临时图片（MCP 批次 5，2026-10-26）

普通视图与全库搜索要把临时文件夹（`folders.kind='temp'`）里的图片排掉。同机同一时段 A/B（20 万行，三次连续运行取一次完整序列）：

| 查询 | 无过滤（基线） | `NOT IN (子查询)` | `<> COALESCE(标量子查询, -1)` |
| --- | --- | --- | --- |
| 单级 folder 首页 150（id 列表） | 40.65 ms | 53.60 ms | 44.79 ms |
| 单级 importedAt 首页 150 | 0.67 ms | 0.72 ms | 0.68 ms |
| 6 级排序首次建 id 列表 | 208.55 ms | 221.92 ms | 207.81 ms |

- 原因：`NOT IN (SELECT …)` 在 SQLite 里按行探测那个临时索引，20 万行就是 20 万次探测（+13 ms）；非相关标量子查询只求值一次，代价只剩比较 `folder_id`（+4 ms）。

- 注意：这台机器在不同时段整体快慢差近 1.8 倍（同一次改动里 6 级排序在 208 ms 与 352 ms 之间波动），跨时段只能比同一序列内的相对值，不要拿单次绝对值下结论。

- `counts()` 的计划在合成库上仍是 `SEARCH images USING COVERING INDEX idx_images_active_pixels (deleted_at=?)`——`count(*)` 不需要列，任何以 `deleted_at` 开头的索引都够用，所以计划文本不能用来断言“新索引被选中”；真实库的差异来自 `folder_id <> temp` 触发的回表。
- v7 → v8 建索引：**316–319 ms**（含 `ANALYZE`，20 万行）；真实库单条 `CREATE INDEX` 533 ms（39 万行、未含 `ANALYZE`）。`reopen` 16.6–20.2 ms，`counts()` 单独 7.3–7.5 ms——开库不再同步算计数。
- 其余既有指标未退化：首屏 0.63 ms、深键集页 4.9 ms、子树页 2.0 ms、`selection_tags` 20 万选中 92.3 ms、6 级排序建 id 列表 199 ms、v3→v4 两个索引重建 430–436 ms。

| 项 | 耗时 |
| --- | --- |
| 均值：整段单线程 | 417.3 ms |
| 均值：`rayon` 4096 行分块 | **42.5 ms**（9.8×） |
| 结果最大差异 | 0.0000（该数据集可精确表示） |

按行数线性外推到真实库 364 056 行：均值约 0.76 s → 0.08 s。计划阶段估的“单线程 2–3 s”偏高，实际单线程只要 0.4 s 量级（`decode_f16` 走批量转换），但并行收益仍然接近线程数。

## 结论与决策

1. **SQLite 不是瓶颈**。首屏、深分页、文件夹、FTS 都在毫秒级；不需要自研元数据索引。
2. **缩略图包优于逐文件**。随机读快约 16 倍，且避免 20 万小文件对备份、扫描和冷启动的压力。
3. **浏览器解码满足门槛**。150 张 512px 缩略图冷加载约 0.44-0.46s，远低于 3s 底线，也低于 1s 目标。
4. **WebP 已定稿**。`webp` 0.3 + `libwebp-sys` 0.9.6 静态编译，构建可接受，debug exe 无额外 DLL；缩略图统一 WebP q80。
5. **不需要 DDS/WebGPU 缩略图管线**。浏览器解码已达标，自绘网格的复杂度与风险不值得。
6. **导入吞吐达标**。1000 张合成图 47.7–50.0 张/秒，高于 20 张/秒的阶段下限；瓶颈仍在解码、WebP 编码与 k-means，而不是 SQLite 写入。
7. **查询引擎在预算内**。S2 的完整查询路径（含 JOIN、标签摘要、筛选分面）仍在毫秒级；S3 的搜索/集合翻页也都低于 50 ms。
8. **分面计数有明确边界**。20 文件夹数据集上普通视图 69.54 ms 在预算内；FTS 搜索约 133 ms、2 字搜索与 20 万条集合约 0.8 s，筛选面板显示加载态。搜索/集合计数用单条 `MATERIALIZED` CTE，避免逐分面重复扫描；进一步优化需要拆分计数或按分区懒加载。10,221 文件夹数据集上无筛选计数复测为约 0.55 s，原因待定位（见“仍需复测”）。
9. **虚拟化只证明 DOM 有界**。浏览器预览中 150–300 行只挂载十几到二十几个单元格；真实 WebView2 的滚动帧率与内存尚待手工验收。
10. **fp16 存储、f32 计算可行**。批量 `convert_to_f32_slice` 让 20 万条扫描从 699.8 ms 降到 449.3 ms；不需要把 1.6 GB 向量常驻堆，也不需要首版 ANN。
11. **子树筛选与树计数达标**。1 万文件夹下子树页 4 ms、`get_folders` 25-29 ms、文件夹分面 62-66 ms；子树条件只展开 `folders` 并命中 `folder_id` 索引，没有退化为逐图路径匹配。文件夹分面已接近 100 ms 上限，筛选面板必须保留加载态。
12. **7 个排序指标都在预算内**。单级排序 0.66-0.76 ms；多级排序首次建 20 万 id 列表 213 ms，后续翻页与深页都是 0.83 ms，深分页不随页数变慢；文件夹排序走同一条 id 列表通道，20 万行 42 ms。schema v4 的两个新索引让修改时间与像素尺寸也走键集游标。
13. **操作记录不随图库规模变慢**。500 条记录列表 0.88 ms、裁剪 1.64 ms；20 万行待释放统计 26 ms，标记 2.8 s、数据库删行 26.8 s 都是后台 write lane 任务。
14. **真实库的“卡”来自索引形状，不是 SQL 写法**。`counts()` 620.9 ms、`list_folders` 683.4 ms、`filter_counts` 1 815.0 ms，计划全是 `idx_images_active_pixels` 回表 39 万次；一张 `(deleted_at, purge_operation_id, folder_id, file_ext, score)` 覆盖索引把前两者降到 19.7 / 27.1 ms，代价只有 +7.0 MB 与 533 ms 建索引。
15. **标签聚合要换驱动方向**。`list_tags` 从“tags → 关系 → 逐张回表”改成“`image_tags` 覆盖聚合 + 回连 `tags`”，1 162.7 → 23.7 ms 且结果逐行相同；剩下的 `filter_counts` 标签分面（620–824 ms）是 39 万 id 与 46 万关系求交集的地板，靠异步化解决体感，不靠继续调 SQL。
16. **AI 冷启动的时间几乎全在依赖导入**。`import torch` 1.8–2.0 s + `import transformers` 2.4–2.5 s + 取 SigLIP 具体类 3.4–3.5 s = 7.7–8.0 s（RSS 420 MB），而这段代码在 `/v1/models/ensure` 请求内；后台有负载时同一脚本涨到 17 s。另外 `ensure` 只 mmap 权重（RSS 499 MB），首次 forward 还要 2.37 s 把 2.83 GB 拉进物理内存——所以优化点是“启动时预热导入 + ensure 末尾 warmup forward”，不是缩短模型加载本身。
17. **合成库只能验证形状，不能验证 I/O**。实现后在同一台空闲机器上用 20 万行合成库复测：`list_folders` 58.5 → 17.9 ms（3.3×）、`list_tags` 225.3 → 16.2 ms（13.5×）、均值 417 → 42.5 ms（9.8×），但 `counts()` 在两态都是 5.7 ms，`filter_counts` 反而从 243 变 319 ms。合成库整库在页缓存里、回表几乎免费，真实库（1 GB、随机 IO）才体现 620 → 20 ms 的收益——**性能结论必须以真实库为准，合成库只用来防止形状退化**。
