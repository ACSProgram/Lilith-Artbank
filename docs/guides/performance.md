# 性能基准

## 原始基线

原 C++ 图库的参考表现（用户描述）：

- 二进制元数据/缩略图数据加载吞吐约 100 MB/s 到 >1 GB/s（不含解压）；
- 一页 150 张缩略图加载并渲染在 1 秒内。

新程序的最低要求是达到原性能的 **1/3**：一页 150 张缩略图从请求到可见 ≤3s；目标仍是 ≤1s。元数据侧不要求复刻“整库载入吞吐”，因为新结构不整库载入；我们看首屏查询与翻页延迟。

## 方法

运行：


### 应用内缩略图基准（S1 前半）

开发构建的工作区工具栏有“缩略图基准”。它用 Rust 生成 150 张 512px 确定性图片，经正式管线编码为 WebP q80、写入临时追加式 pack，然后让 WebView2 通过 `thumb://` 加载：

- 冷加载：每次使用新的 `?run=<n>`，浏览器缓存必然未命中；
- 热加载：复用同一 URL，测浏览器缓存路径；
- 计时从创建 `<img>` 到 150 张全部 `decode()` 完成后再等两帧 rAF；
- 同时显示 Rust 侧 pack 读取 p50/p95 与包体积。

```bash
npm run tauri dev
# 打开任意图库 → 工作区右上角“缩略图基准” → 生成样本 → 冷加载 / 热加载
```

真实 WebView2 的数字由用户在本机手工验收；用户已确认冷/热加载满足 ≤1s 门槛，具体数字尚未记录。浏览器预览不支持该基准。

### 查询引擎（S2）

`perf_metadata_200k` 在原有索引基准之后，直接调用 `library::query::query_page`、`filter_counts` 与 `query_ids`，覆盖真实 SQL 构造、文件夹 JOIN、标签摘要批量查询与参数绑定：

- 首屏：导入时间降序 150 条；
- 深分页：评分降序，游标 `(score, id) < (2, 150000)`；
- 文件夹、标签筛选各 150 条；
- 筛选分面计数（文件夹/扩展名/评分/标签）；
- 全选 id：一个标签约 3,000 个 id；无筛选 200,000 个 id。

```bash

```

### 搜索、集合与分面计数（S3）

同一基准在 S3 追加：

- 描述搜索：FTS5 trigram（"素材"）与 2 字 `LIKE`（"参考"）各 150 条；
- 标签名搜索（"标签17"）与文件夹路径搜索（"folder7"）各 150 条；
- 集合视图：临时集合放入全部 20 万张图片，按 `collectionPosition` 升序取 150 条；
- 以上每种查询的 `filter_counts`（总数/文件夹/扩展名/评分/标签五个分面）各跑 10 轮；
- 搜索/集合计数在 SQL 内使用 `WITH matched AS MATERIALIZED`，只求一次命中集。

集合视图采样前先创建 20 万条 `collection_items`，用于观察极端规模下的手工排序与计数。

### 查看器与保存（S4）

尚无自动基准；S4 只在单测中断言正确性，性能由真实窗口手工测量：

- 大图预览：首次打开 >2400 万像素、TIFF/TGA 或带 EXIF 方向的图片时，记录 Rust 生成 4096px WebP 的耗时与缓存体积；再次打开的命中耗时；
- 查看器滚动/缩放/平移的帧率与 WebView2 内存；原图直接加载与预览路径分别记录；
- 保存：4K/8K 图片从点击保存到列表缩略图刷新的端到端耗时，含解码、几何、编码、BLAKE3、缩略图重算与事务；
- 保存期间导入/切库被维护守卫拒绝的行为，以及失败后旧原图与数据库行保持一致。

前端虚拟化不跑自动基准；S2/S3 用浏览器预览的 4,000 行 mock 做 DOM 结构与交互检查（见下）。真实 WebView2 的滚动帧率、内存与编辑/回收站文件操作由用户手工验收。

### 查询引擎与虚拟网格（S2，2026-10-23）

同一台机器、Rust 1.97.1、开发档（本 crate opt-level 1，依赖 opt-level 2），20 万行合成库、20 个文件夹、200 个标签、60 万条标签关系、4 个读连接：

| 路径 | p50 | p95 | 预算 |
| --- | --- | --- | --- |
| 查询引擎首屏 150（导入时间降序） | 0.62 ms | 0.79 ms | ≤50 ms |
| 查询引擎深分页 150（score/id 游标） | 1.08 ms | 1.24 ms | ≤50 ms |
| 查询引擎文件夹 150 | 0.58 ms | 0.83 ms | ≤50 ms |
| 查询引擎标签 150 | 2.91 ms | 3.16 ms | ≤50 ms |
| 筛选分面计数（4 个分面） | 27.36 ms | 40.32 ms | ≤100 ms |
| Ctrl+A 取 20 万 id | 17.61 ms | — | 未设硬门槛 |

补充数据：

- 同期原始 SQL 基准仍为：首屏 0.10 ms、深分页 0.46 ms、文件夹 0.08 ms、标签 1.97 ms；
- 一个标签筛出约 3,000 个 id 的全选耗时 44.70 ms（包含标签 JOIN 与排序）；无筛选的 20 万个 id 为 17.61 ms；
- 计数包含四个 GROUP BY 分面，比单一只读查询慢，但仍低于 100 ms 预算；
- 打开图库并读取计数 23.67 ms。

前端虚拟化（浏览器预览，Chromium 代理，724×712 CSS，4,000 行 mock）：

- 加载 150 行时同时挂载 12–24 个网格单元格（取决于滚动位置与视口/缓冲）；
- 加载 300 行并滚到中段后约 18 个单元格；
- 列表加载 150 行时约 24 行；
- 滚动到底自动追加下一页；筛选/排序切换后回到第一页，无旧行残留；
- 窄窗口下列表隐藏“导入时间/文件夹”列，无横向溢出。

这些数字只证明 DOM 有界与分页行为，不是 WebView2 帧率；真实 20 万行的滚动帧率、内存与一页 150 张缩略图仍需在真实窗口复测。已加载页不会回收，长时间滚动到全库末尾时前端内存会随已加载行增长，留待 S9。

### 搜索、集合与分面计数（S3，2026-10-23）

同一台机器、Rust 1.97.1、开发档（本 crate opt-level 1，依赖 opt-level 2），20 万行合成库、600,000 条标签关系、20 万条集合关系、4 个读连接。表中为最近一轮；不同轮次受系统负载影响约 2 倍，趋势与相对关系稳定：

| 路径 | p50 | p95 | 预算 |
| --- | --- | --- | --- |
| 查询引擎首屏 150（导入时间降序） | 0.70 ms | 1.31 ms | ≤50 ms |
| 查询引擎深分页 150（score/id 游标） | 2.59 ms | 5.36 ms | ≤50 ms |
| 查询引擎文件夹 150 | 1.55 ms | 3.74 ms | ≤50 ms |
| 查询引擎标签 150 | 5.65 ms | 7.87 ms | ≤50 ms |
| 查询引擎集合 150（手工顺序） | 1.65 ms | 2.53 ms | ≤50 ms |
| 查询引擎搜索 150（FTS trigram） | 8.78 ms | 14.15 ms | ≤50 ms |
| 查询引擎搜索 150（2 字 LIKE） | 1.40 ms | 4.93 ms | ≤50 ms |
| 查询引擎搜索 150（标签名） | 5.78 ms | 11.46 ms | ≤50 ms |
| 查询引擎搜索 150（文件夹路径） | 7.12 ms | 9.32 ms | ≤50 ms |
| 筛选分面计数（普通视图） | 69.54 ms | 96.66 ms | ≤100 ms |
| 筛选分面计数（FTS 搜索） | 132.56 ms | 144.38 ms | 超预算，显示加载态 |
| 筛选分面计数（标签搜索） | 99.86 ms | 107.71 ms | 预算边缘 |
| 筛选分面计数（文件夹搜索） | 79.85 ms | 109.96 ms | 预算边缘 |
| 筛选分面计数（2 字搜索） | 825.88 ms | 878.44 ms | 超预算，显示加载态 |
| 筛选分面计数（20 万条集合） | 778.83 ms | 819.69 ms | 超预算，显示加载态 |
| Ctrl+A 取 20 万个 id | 41.36 ms | — | 未设硬门槛 |
| 语义搜索向量扫描 200k×1536 fp16（中心化余弦） | 449.26 ms | — | ≤500 ms |

解释：

- 翻页搜索使用 OR-EXISTS，`LIMIT 150` 能在命中率较高时提前停止；2 字搜索的翻页只需约 1.4 ms。
- 分面计数必须求出完整命中集。搜索/集合视图用单条 `MATERIALIZED` CTE 求一次命中集，再分五个 `UNION ALL` 分支聚合；这比逐分面重复求命中集快数倍，但 20 万级命中仍会超过 100 ms。
- 2 字搜索回退 `LIKE` 全表扫描 `description`，无法利用 trigram 索引；超大集合的标签分面需要扫描命中集并聚合 60 万条标签关系。
- 计数只在筛选面板打开时请求，面板内有 160 ms 防抖与加载态；不会阻塞网格翻页、编辑或滚动。
- 普通视图的分面计数 69.54 ms，在 100 ms 预算内。
- 语义搜索在开发档（本 crate opt-level 1、依赖 2）实测：20 万条 1536 维 fp16 向量、单 pack、rayon 扫描、中心化余弦，449.26 ms；向量只在 mmap 中读取，不整体载入堆。基准会生成约 614 MB 临时向量包，默认忽略，运行方式见 `ai::embedding::perf_tests`。50 万条按线性估算约 1.1 s。

前端 S3 交互（浏览器预览，Chromium 代理，724×712 CSS，4,000 行 mock）：搜索/范围切换、扩展筛选、详情与批量编辑、集合 CRUD/运算、回收站、标签重命名、右键菜单、Ctrl+A 与窄窗口覆盖层均走通；DOM 仍只挂载视口附近的行。该检查不代表 WebView2 性能；真实窗口的编辑/回收站文件操作与 20 万行滚动仍需手工验收。

## 结论与决策

1. **SQLite 不是瓶颈**。首屏、深分页、文件夹、FTS 都在毫秒级；不需要自研元数据索引。
2. **缩略图包优于逐文件**。随机读快约 16 倍，且避免 20 万小文件对备份、扫描和冷启动的压力。
3. **浏览器解码满足门槛**。150 张 512px 缩略图冷加载约 0.44-0.46s，远低于 3s 底线，也低于 1s 目标。
4. **WebP 已定稿**。`webp` 0.3 + `libwebp-sys` 0.9.6 静态编译，构建可接受，debug exe 无额外 DLL；缩略图统一 WebP q80。
5. **不需要 DDS/WebGPU 缩略图管线**。浏览器解码已达标，自绘网格的复杂度与风险不值得。
6. **导入吞吐达标**。1000 张合成图 47.7–50.0 张/秒，高于 20 张/秒的阶段下限；瓶颈仍在解码、WebP 编码与 k-means，而不是 SQLite 写入。
7. **查询引擎在预算内**。S2 的完整查询路径（含 JOIN、标签摘要、筛选分面）仍在毫秒级；S3 的搜索/集合翻页也都低于 50 ms。
8. **分面计数有明确边界**。普通视图 69.54 ms 在预算内；FTS 搜索约 133 ms、2 字搜索与 20 万条集合约 0.8 s，筛选面板显示加载态。搜索/集合计数用单条 `MATERIALIZED` CTE，避免逐分面重复扫描；进一步优化需要拆分计数或按分区懒加载。
9. **虚拟化只证明 DOM 有界**。浏览器预览中 150–300 行只挂载十几到二十几个单元格；真实 WebView2 的滚动帧率与内存尚待手工验收。
10. **fp16 存储、f32 计算可行**。批量 `convert_to_f32_slice` 让 20 万条扫描从 699.8 ms 降到 449.3 ms；不需要把 1.6 GB 向量常驻堆，也不需要首版 ANN。

| 打开图库 | ≤1s（不含首次迁移） |
| 首屏 150 条元数据 | ≤50ms |
| 深分页 | ≤50ms |
