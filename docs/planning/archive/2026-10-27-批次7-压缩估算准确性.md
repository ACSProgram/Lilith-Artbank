范围对应《[使用反馈整改计划](2026-10-27-使用反馈整改计划.md)》的编号 15（压缩耗时估算偏低，特别是大图多时）与补充反馈（节省空间同时偏乐观，怀疑样本抽到小图），以及批次 7 小节。不把估算变成全量预编码，不承诺精确值，不引入新的临时文件依赖。

## 结论摘要

1. **偏差已经复现，而且两个症状同源**：在按真实构成复制的 301 张图库上，默认档位附近（50 张样本）连抽 10 次，节省空间落在 **85–270 MB**（真值 210 MB，−59%…+29%，中位 +17%），耗时落在 **12–20 s**（真值 15.5 s，−23%…+29%，中位 −16%）。同一次抽样同时给出“省得比实际多、时间比实际短”。抽样张数补到覆盖 73% 后两者分别变成 −0.2% 与 +3.2%。
2. **根因不是“样本抽到小图”这么简单，而是“层内按张数均匀抽 + 按体积加权外推”**。真实库默认档位 200 张只覆盖候选体积的 **0.078%**；最重的层（有损源、bpp ≥ 0.50）里，按体积排前 5% 的 11 446 张占该层 **36.9%** 体积，而 200 张档位分给这一层 146 张，期望只抽到其中 **7.3 张**。样本的“体积构成”与总体的“体积构成”是两次独立的重尾抽样，样本一偏，节省率与像素均值一起偏。
3. **耗时偏低有确定的传导路径**：`work = 样本墙钟 × candidate_pixels / sample_pixels`。`sample_pixels` 是样本的像素总和，在重尾分布下波动极大，且被 1:1 放大到全库——样本像素均值偏大时整体时间偏低。节省空间的方向则由同一份样本的字节加权节省率决定。两个偏差都来自同一次抽样，所以“同时出现”。
4. **耗时模型本身在满样本下只有 +3% 误差**（大图组 22 s vs 实际 21.4 s；混合组 16 s vs 15.5 s；小图组 2 s vs 1.87 s）。因此本批次不需要重做编码耗时模型，需要修的是**抽样与加权**。
5. **误差区间目前既不可信也不可用**：`bootstrap_margin` 在样本覆盖 100%、估算值与实际值逐字节相等时仍报 **±7.7% / ±15.2% / ±17.9%**；在真正缺样本时又报不出来（混合组一次 −59% 的抽样只给了 ±27% 的区间）。它既不是置信区间，也不是误差上界。
6. **执行凭证只比张数与总体积（±10%）**：同数量同体积但换成另一批图片、文件内容被原地替换、单个目录消失都可能通过校验；真正的坏情况（原图缺失）要等执行到一半才以“连续 5 张失败即停止”的形式暴露。
7. **逐张校验原图是可行的但必须并行**：串行 stat 全库 390 541 个文件 30.6 s；8 线程 7.45 s（19 µs/个），274 068 个候选折算约 **5.2 s**。全量串行校验不能放进执行路径，并行可以。
8. **实现后复测**（同一份 301 张真实图片副本）：50 张档位连抽 10 次，节省空间 **−7.1%…+10.2%**（中位 +0.6%，原 −59.5%…+28.7% / 中位 +17.3%）；耗时 **+15.3%…+34.5%**（中位 +21.7%，原 −23%…+29% / 中位 −16%）。节省空间已达标；耗时方向从“偏低”翻成“偏高”，极差收窄但中位偏差超出 ±5%，未完全达标（见第十二节）。实现中还发现并修掉一处独立缺陷：耗时外推原本用**全局**像素比，把“这层分到的样本少”与“这层像素本来就少”混在一起，实测会把耗时放大一倍以上，已改成**按层各自放大**。

## 一、现状与代码定位

### 1.1 分层、抽样与外推

- 分层键是「有损源 / 无损源 × 6 个 bpp 桶」共 12 层，bpp 边界 `[0.10, 0.15, 0.22, 0.32, 0.50]`（`src-tauri/src/library/optimize_estimate.rs:35`、`:398`、`:405`）。`lossless_source` 定义为“不是 jpeg/jpg/webp”（`src-tauri/src/library/optimize.rs:82`）。
- 扫描阶段逐块（400 张）读候选行，累计每层的张数、字节、像素，并把每层的 id 收进 `strata_ids`（`optimize_estimate.rs:437`–`:478`）。
- 样本量分配：每层先给 `MIN_PER_STRATUM = 3` 张（`:39`、`:956`），余量按**层字节份额**分（`:963`–`:978`）。所以“跨层按体积”这一层是对的。
- **层内抽取是等概率按张数**：`choose_indices(length, take, rng)` 在整个层的 id 列表里均匀取（`:1002`、`:503`）。层的 id 列表按扫描顺序排列（大致是 id 序，与体积无关）。这一步把“跨层的体积加权”在层内丢掉了。
- 节省率：每层 `rate = 1 − Σnew / Σold`，样本内按字节加权（`:1026`–`:1043`），再乘该层候选总体积（`:1046`）。跳过样本 `new = old`，所以跳过等于“零节省”，不额外扣减。
- 跳过比例：`cumulative_skips` 用 `scale(total.count, part, sample_count)` 按**张数**外推（`:1166`–`:1179`、`:1184`），前提是层内样本按张数均匀——这与上面的抽样方式一致，但一旦改成体积加权抽样，这里必须同步改（见 3.4 与方案 S1）。
- 覆盖率：`coverage = sample_bytes / candidate_bytes`（`:673`），界面直接显示（`src/app/OptimizeDialog.tsx:926`–`:929`）。

### 1.2 耗时模型

`estimate_seconds`（`optimize_estimate.rs:1247`）三段：

```
wall     = 样本编码墙钟 × candidate_pixels / sample_pixels      // :1265
segments = 样本分段耗时和 / 线程数 × candidate_pixels / sample_pixels  // :1267-1271
io       = candidate_bytes / (sample_bytes × 线程数 / 读取秒数)   // :1273-1279
work     = max(max(wall, segments), io)
write    = 预测输出字节 × 每字节写盘秒数 + 处理张数 × 每张 fsync   // :1282-1284
finish   = 批次数 × 每批提交 + 处理张数 × 每张删除                // :1286-1288
```

- 唯一的外推轴是**像素**，且用的除数是 `sample_pixels`（样本像素总和）。样本像素均值的任何波动都会 1:1 传进 `work`。
- `write` / `finish` 用 `calibration`（`src-tauri/src/library/calibration.rs:60`、`:105`）：来自**本库上一次执行**的实测，只要那次处理 ≥ 20 张、有输出字节、四项都在合理量级就会覆盖。它不区分范围，也不区分图片尺寸。
- 线程数取 `cores − 1` 夹到 8（`src-tauri/src/library/mod.rs:53`、`:56`）。

### 1.3 误差区间

- `bootstrap_margin`（`optimize_estimate.rs:1191`）在每层**已抽到的样本内**有放回重抽 300 次，重算 `Σ 层字节 × rate`，取 1.96σ。
- 它不重抽“没抽到的部分”，所以对“尾部整体缺席”这种偏差不敏感；反过来，即使样本就是全体（覆盖 100%），重抽仍然产生方差，于是报出一个并不存在的 ±。
- 界面只在 `savingsBytes > 0` 时显示 `± margin`，`margin = 0` 时显示“误差可忽略”（`OptimizeDialog.tsx:968`–`:976`）。耗时没有任何区间（`:985`–`:988`）。

### 1.4 执行凭证与执行前复核

- `verify_grant`（`src-tauri/src/library/optimize.rs:153`）只检查两件事：参数指纹一致；**候选张数与候选总体积**都在估算值的 ±10% 内（`:178`）。
- `eligible_summary`（`:140`）用同一套前置判据重算张数与字节，`collect_candidates`（`:101`）只返回 `deleted_at IS NULL` 的行。
- 真正开始执行前会再跑一次 `recheck_optimize_scope`（`src-tauri/src/app/state.rs:1860`–`:1875`），它同样只比张数与体积。
- 没有检查：候选 id 集合是否变化、原图是否还在、文件大小是否变了、目录是否被删。
- 执行阶段单张读文件失败记 `failed` 并累加 `consecutive_failures`，达到 `MAX_CONSECUTIVE_FAILURES = 5` 就整任务停止（`optimize.rs:50`、`:407`–`:421`）。也就是说“原图被外部删掉”会以“连续多张处理失败，任务已停止”的形式出现，已经提交的批次不会回滚。

### 1.5 界面

- 档位标签是绝对张数：`50（快）/ 200（默认）/ 500 / 1000 / 2000（准）`（`OptimizeDialog.tsx:64`–`:70`），默认索引 1（`:71`）。提示语是“样本越多越准，也越慢。”（`:824`）。
- 结果页显示“样本 N 张（候选不足）· 覆盖 X% 的候选体积”，`X` 在真实库默认档位是 **0.08%**。
- 抽样等待提示用上次同参数实测折算（`sampleWaitLabel`，`:104`），只描述“抽样要等多久”，与总预计耗时无关。
- `sampleSize` 记录的是**档位**，`sampleCount` 是实际抽到的张数（`optimize_estimate.rs:669`–`:671`），候选不足时两者不等。

## 二、问题判定

按“用户能感知的顺序”：

| 现象 | 直接原因 | 证据 |
| --- | --- | --- |
| 节省空间偏乐观 | 层内按张数均匀抽 → 样本的**体积构成**是一次独立抽样；节省率又按样本字节加权 → 样本偏向“省得多”的那部分时整体偏高 | 混合组 10 次抽样中位 +17.3%，最好一次 +28.7% |
| 偶尔严重偏低 | 同一机制的反面：样本几乎不含大图时，字节加权率被大量“省得太少”的小图拉低 | 混合组最低一次 −59.5% |
| 耗时偏低 | `work` 按 `sample_pixels` 反比外推；样本像素均值偏大时整体偏低 | 混合组 10 次 −23%…+29%，中位 −16% |
| 大图多时更明显 | 大图集中在重尾层；该层字节的 36.9% 由前 5% 的图片持有，而 200 张档位只给该层 146 张样本，期望覆盖其中 7.3 张 | 3.2、3.3 |
| 误差提示不可信 | bootstrap 只在已抽样本内重抽 | 覆盖 100% 仍报 ±7.7%…±17.9% |
| 估算“过期”判不出来 | 凭证只比张数与体积 | 1.4 |
| 执行到一半停止 | 原图缺失按普通失败计，连续 5 张即停 | 1.4 |

不是主要原因的部分（有数据支撑）：

- **耗时模型**：满样本下三组分别是 +2.9% / +3.2% / +7.0%，量级正确。
- **像素常数假设**：单张 decode+encode 的每像素成本确实随尺寸与阶梯重试变化（12–103 ms/MP，见 3.8），但在满样本下没有形成系统性偏差；它放大的仍是抽样误差。
- **写入侧校准**：三组回测里 `write + publish + commit + delete` 合计只占实际耗时的 3–5%，即使偏 2 倍也不影响结论。

| 10 | 76.9 MB | 15.4% | 270.32 MB | +28.7% | ±87.0 MB | 13 s |

- 节省空间：中位 **+17.3%**，均值 +2.6%，极差 −59.5%…+28.7%。均值接近真值但中位明显偏高——重尾比率估计的典型形态：多数抽样略高，少数抽样塌到很低。**用户看到的是一次抽样，所以他看到的是“偏乐观”。**
- 耗时：中位 13 s（−16%），极差 12–20 s。方向与节省空间相反但同源：样本像素均值偏大时时间偏低。
- 报出的 ± 与真实误差不匹配：第 5、9 次真实误差 82 MB / 125 MB，区间只有 ±56 MB / ±43 MB；第 3 次真实误差 36.8 MB，区间却给到 ±118 MB。

### 3.6 覆盖 100% 时的误差区间

| 组 | 覆盖 | 估算 vs 实际 | 报出的 ± |
| --- | --- | --- | --- |
| 小图 | 100% | 完全相等 | ±4.00 MB（7.7%） |
| 大图 | 100% | 完全相等 | ±101.83 MB（15.2%） |
| 混合 | 100% | 完全相等 | ±37.51 MB（17.9%） |

抽样就是全体时不存在抽样误差，`bootstrap_margin` 仍然报出 8%–18%。这说明它度量的不是“估算可能错多少”，而是“如果把样本当成从某个假想总体里抽出来的，它会抖多少”。把它当置信区间展示会同时误导两个方向。

### 3.7 逐张校验原图的成本

对 390 541 个内容文件逐个 `stat`（只读，热缓存）：

| 方式 | 耗时 | 每张 |
| --- | --- | --- |
| 串行 | 30.60 s | 78 µs |
| 8 线程 | 7.45 s | 19 µs |
| 16 线程 | 6.95 s | 18 µs |

274 068 个候选按 8 线程折算约 **5.2 s**。全量串行校验不能放进执行路径；并行可以，且只占整次执行耗时的百分之几。

### 3.8 每像素成本的分布（代理测量，159 张真实图）

用 PIL 复刻“解码 + 阶梯质量编码 + 回解码算 PSNR”，只用来确认每像素成本是否随尺寸/重试变化：

| 情形 | 每像素成本 |
| --- | --- |
| 无损源 0–1 MP | 90–147 ms/MP |
| 无损源 8–25 MP | 21–46 ms/MP |
| 有损源，q85 一次通过 | 14–25 ms/MP |
| 有损源，需要 q90/q95 或三档都不达标 | 60–103 ms/MP |

单张节省率在 0%–90% 之间，与尺寸没有稳定的单调关系；决定它的是源本身（是否已经压得很紧、是否触发“省得太少”跳过）。所以本批次不引入“按尺寸的节省率曲线”，只解决**抽样代表性**。

### 3.9 本次测量的局限

1. 回测库是真实图片的**子集**（150–301 张），不是 39 万张全库。真实库默认档位的覆盖率只有 0.078%，无法在可执行规模上直接复现；本文件用“同一档位、同一构成、多次抽样”的方式复现偏差形态，量级可能更大而不是更小。
2. 回测参数只有默认档（高档 / JPEG / 不缩放）。WebP 输出、长边缩放、重算缩略图未覆盖。
3. 大图组是小样本（150 张、24 MP 均值），单个异常图片就能影响 ±5%。
4. 代理测量用 PIL，不是 `image` + `jpeg-encoder` 的实际实现，只用于说明形状。
5. 未测真实窗口：界面在长估算中的表现、抽样等待提示的准确性、结果页在 0.08% 覆盖下的观感都需要手工验收。

## 四、方案

### S1 层内改为“按体积等分抽取”（核心）

现状：层内按张数等概率抽。改成：

1. 扫描阶段每层已经收集了 `(id, bytes)`；按 `bytes` 排序（228 926 行排序约 20 ms 量级）。
2. 把该层的候选按**累计体积**切成 `take` 份（每份 ≈ 层体积 / take），在每份里随机取一张。
3. 每张样本带上它代表的 `(slice_count, slice_bytes)`，跳过比例与耗时外推改用切片权重，不再假设“层内按张数均匀”。
4. 层内候选数 ≤ take 时退化为全取（保持现状）。

效果（预期，需实现后复测）：

- 样本的**体积构成**由构造保证贴合总体，节省率的字节加权不再依赖运气；
- `sample_pixels` 贴合 `candidate_pixels`，`work` 的外推轴变稳；
- 小图不再因为“张数多”而占满样本，大图一定被抽到；
- 不增加样本张数，不增加抽样耗时（排序是毫秒级）。

代价：`choose_indices` 的均匀抽样假设被移除，`cumulative_skips` 的外推方式必须同步改，否则跳过比例会失真（大图跳过率与小图不同）。这是本批次唯一有回归风险的改动，需要 S1 的测试覆盖。

### S2 误差区间重做

1. 覆盖 100%（`sample_count == candidate_count`）时区间直接为 0。
2. 抽样单位从“样本”改成“切片”：bootstrap 重抽切片，重算 `Σ 切片字节 × 切片内样本的节省率`。切片等体积，方差估计才有意义。
3. 额外输出一个“未覆盖体积占比”，在界面上与 ± 并列，用于说明“这个区间只覆盖了已抽到的部分”。
4. 耗时也给出区间：同一套重抽同时算 `work` 的分布（按切片像素加权），`write` / `finish` 用校准值的 ±50% 作为固定项合成。

### S3 档位语义与呈现

1. 保留五档与滑块，标签改成“张数 + 该档在真实库的典型覆盖率”，例如 `200 张 · 约 0.1% 体积`（覆盖率由估算结果回填，不写死）。
2. 结果页把“样本 N 张 · 覆盖 X%”扩成“样本 N 张 · 覆盖 X% 体积 · 覆盖最大的 K 张（≥ 32 MP）”，让用户看到尾部有没有被代表。
3. 覆盖率低于某个阈值（例如 1%）时，在“预计节省”旁固定一行说明“抽样很浅，误差可能大于 ± 显示值”，不再依赖“误差可忽略”。

### S4 执行前校验扩展

在 `recheck_optimize_scope` 里补三件事（都在拿到写 lane 之后、开始编码之前）：

1. **候选集合指纹**：对排序后的 id 列表做一次 BLAKE3（或 64 位折叠），与估算时记录的值比对。张数/体积相同但换了图片时能立刻发现。
2. **原图存在性与大小**：8 线程并行 `stat`，与 `images.file_size` 比对。274 068 个候选约 5.2 s；缺失或大小不符的比例超过阈值（建议 1%）就拒绝执行并提示“有 N 张原图缺失或已变化，请重新估算”；低于阈值则把这些行从候选里剔除并在任务摘要里说明。
3. **目录存在性**：候选涉及的 `folders.path` 逐个 `is_dir`（445 个目录，毫秒级）。目录被删时不再等到逐张失败。

不做：内容哈希校验（274 068 个文件全量哈希是分钟级，且执行阶段本来就要读一遍；大小 + 集合指纹已经能挡住实际会遇到的漂移）。

### S5 执行阶段容错

- 单张“文件不存在 / 无法读取”单独计数，**不累加** `consecutive_failures`，避免 5 张缺失就把整任务停掉；连续失败阈值只用于“解码器/磁盘异常”这类系统性故障。
- 任务摘要里区分“失败（解码/写入）”与“原图缺失”。

### S6 校准值分档（可选，视测量结果）

`calibration` 目前只按“上一次执行”覆盖，且不区分图片尺寸。若实现后回测显示 `write` 段仍有系统性偏差，再考虑按输出体积档位分别记录；本批次先不改，避免引入新的失效面。

### 不做

- 不做全量预编码（那等于把估算变成执行）。
- 不承诺精确值：目标是“同档位下误差可解释、不系统性偏乐观”，不是“误差 < 5%”。
- 不引入临时文件、不写数据库（估算仍然只读）。
- 不改压缩判据、PSNR 底线、阶梯质量、发布协议。
- 不改 `MAX_SIZE_RATIO` 与“省得太少”的语义。
- 不改 `tags_modify` / MCP 相关路径；压缩仍不开放给 MCP。

1. **S1 抽样与权重**（含 `cumulative_skips` 的切片外推、`sample_pixels` 的代表性）——先做，其它都依赖它。
2. **S2 误差区间**（100% → 0、切片 bootstrap、未覆盖占比、耗时区间）。
3. **S4 + S5 执行前校验与容错**（互不依赖，可并行）。
4. **S3 界面**（依赖 S2 的字段）。

退出标准（括号内是实现后复测结果）：

- 在“按真实构成复制的 301 张库”上，50 张档位连抽 10 次，节省空间与耗时的极差都收窄到 ±15% 以内（现状 −59%…+29% / −23%…+29%），且中位偏差 ≤ 5%。
  - 节省空间：**−7.1%…+10.2%，中位 +0.6%**，达标。
  - 耗时：**+15.3%…+34.5%，中位 +21.7%**，未达标（方向偏保守，见第十二节）。
- 覆盖 100% 时 `±` 为 0；覆盖 73% 时真值落在 ± 内。（实测：100% → `±0`；83% 覆盖时 `±66.7 MB`、真值误差 +1.7%，落在区间内。）
- 估算后人为删掉 2% 的原图、或替换成同体积的另一批图片，执行前必须被拒绝并给出张数。（单测 `source_check_reports_missing_and_changed_files`、`grant_requires_matching_fingerprint_and_stable_candidates` 覆盖。）
- 原图缺失 3 张（低于阈值）时执行继续，任务摘要显示“原图缺失 3 张”，不再整任务停止。（单测 `missing_sources_are_counted_without_stopping_the_run`：连删 6 张仍然继续。）
- 抽样耗时增加不超过 10%（排序 + 切片）。（未单独基准。切片只做一次排序 + 一次归组，22.9 万条量级是几十毫秒，相对秒级的样本编码可忽略；样本张数没有增加。）

## 六、自动测试与基准设计

Rust（`cargo test`）：

- `allocate_samples`：层内候选 ≤ take、层内全部同尺寸、层内极端重尾（1 张占 90% 体积）三种边界。
- `slice_indices`（新）：切片数量正确、每张只被选一次、每份体积接近等分、`take == count` 时全取。
- 权重外推：同一份数据用“均匀抽样”与“切片抽样”两种权重算 `cumulative_skips`，结果在合成均匀分布上应一致（防止权重公式写反）。
- `bootstrap_margin`：覆盖 100% 返回 0；单层单样本返回 0 或明确的上界；切片重抽结果单调（样本越多区间越窄，允许噪声）。
- `verify_grant`：指纹一致 + 集合指纹一致通过；张数/体积在 ±10% 但 id 集合不同时拒绝；原图缺失 2% 时拒绝、0.5% 时通过并返回剔除数。
- `recheck_optimize_scope`：目录被删、文件被删、文件大小变化三种情形。
- 执行容错：3 张缺失后继续、连续 5 张解码失败才停。

基准（`cargo test --lib -- --ignored`）：

- `perf_estimate_vs_actual` 扩成两组构成（大图占比高 / 低），并把档位从单一 200 扩成 `50 / 200 / 全量`，输出三个偏差比例；这是本批次的正式回测口径。
- 新增 `perf_estimate_sampling_spread`：同一份库、同档位连抽 N 次，打印节省空间与耗时的 min / 中位 / max / 标准差。
- `perf_metadata_200k` 追加：20 万行上的层内排序 + 切片耗时（确认抽样开销 ≤ 10%）。

前端（`npm run test:web`）：

- 结果页：覆盖 100% 时不显示 ±；覆盖率低时显示提示行；耗时区间与三段拆分同时出现。

## 七、用户手工验收

1. 全库跑一次估算（默认档）：记录“样本张数 / 覆盖体积 / 覆盖的最大图张数”，确认覆盖数字与档位标签一致。
2. 同一个范围连跑 3 次估算（不改参数）：记录三次的节省空间与耗时，确认波动比现在小。
3. 把档位从 50 拉到 2000：确认覆盖率与耗时按比例变化，界面不出现“误差可忽略”但实际覆盖 0.1% 的情况。
4. 估算完成后，在资源管理器里删掉 2–3 张候选原图，再点“确认执行”：确认被拒绝并给出张数；随后删掉 1 张（低于阈值）再执行：确认任务继续、摘要显示“原图缺失 1 张”。
5. 估算完成后，用外部工具替换同一批图片（体积接近）：确认执行被拒绝（集合指纹不一致）。
6. 大图占比高的范围（例如某个以 4000 万像素为主的文件夹）跑一次估算 + 执行：对比预计耗时与实际，记录偏差。
7. 小图占比高的范围（例如缩略图目录）同样跑一次。

## 八、风险

- **切片抽样改变了跳过比例的外推口径**：如果权重写错，`candidate = process + skip` 的漏斗会破。必须保留现有漏斗不变量测试。
- **切片抽样会让样本偏向大图**：对“省得太少”的小图估计变粗，跳过张数可能偏离。用切片 `count` 外推可以修正，但方差会比现在大（小图样本变少）。这是有意取舍：字节与像素的估计更重要。
- **执行前并行 stat 会与后续编码争 IO**：274 068 张 5.2 s 是热缓存；冷盘会显著更慢。建议在拿到写 lane 后做，且允许用户取消。
- **集合指纹只能发现“换了图片”，发现不了“内容变了但大小没变”**：这是明确的能力边界，需要写进提示文案。
- **耗时区间可能与用户直觉冲突**：同一档位给两个区间（节省与耗时），界面会更满；需要按“后果优先”只保留必要说明。
- 校准值分档若在后续加入，会让“上一次执行”的语义变成“上一次同档执行”，可能长时间不更新。

### 11.2 S1 切片抽样的实际形态

方案写的是“按累计体积切成 `take` 份，每份随机取一张”。实现时改成**按“最后一个字节落在第几份”归组**（`slice_indices`）：

- 每张按 `bytes` 升序排列，累计体积的第 k 份区间是 `[T·k/take, T·(k+1)/take)`，元素按自己的最后一个字节归组；
- 每份随机取一个成员代表整份，权重是**这一份的字节与张数之和**；
- 各份字节之和恒等于层体积、张数之和恒等于层张数，所以外推不需要再按比例放大，漏斗仍然严格闭合。

这么改是因为“逐段收束”的写法在重尾下会失效：若某张图独占 90% 体积，累计量一次跨过 9 条边界，只会切出 1 份，那张图被抽中的概率仍是 1/1000。按末字节归组时它会自成一份并被必然抽到，同时它的权重等于它实际覆盖的体积。

代价：某张图独占多份时会合并成一份，**实际样本数可能少于档位**。真实库不会出现（22.9 万张分层，每份上千张），只在几十张的极小库或极端重尾下可见。界面的“候选不足”因此改成按候选张数判定，不再用实际样本数。

### 11.3 S2 误差区间的实际形态

- 覆盖 100%（`sampleCount ≥ candidateCount`）时两个区间直接返回 0。
- 重抽单位是切片：每层有放回重抽 `n_s` 次，重算 `Σ 切片字节 × 单张节省率`。
- 耗时区间：同一套重抽里同时累加每层的工作秒数与像素，重算放大倍率后得到 `work` 的分布，取 `1.96σ`；写入与提交侧没有抽样，用 `0.5 × (write + finish)` 当固定项，与抽样波动按平方和合成。
- “未覆盖体积占比”没有新增字段：`coverage` 本来就是“实际读取的候选体积占比”，界面直接用它，并在低于 1% 时固定提示一行。

### 11.4 实现中新发现并修掉的问题：耗时外推用了全局像素比

原实现 `work = 样本墙钟 × candidate_pixels / sample_pixels` 用的是**全局**像素比。样本量按体积分配，高 bpp 层拿到的样本远多于它的像素份额，于是 `sample_pixels` 被拉低、倍率被拉高，把“这层分到的样本少”和“这层像素本来就少”混在一起。

在 232 张合成库上实测：全量估算 11 s，50 张档位估算 17–18 s（+54%…+64%），而样本覆盖了 76% 的体积。换成**按层各自放大**（`scaled_work = Σ_s 该层工作秒数 × 该层候选像素 / 该层样本像素`）后变成 10–12 s（−9.1%…+9.1%）。真实图片组也受益：见 12.2。

这一条不在原方案里，是复测时暴露的独立缺陷；它同时解释了准备阶段“满样本准确、缺样本就偏”的一部分现象。

### 11.5 S4 执行前校验

`recheck_optimize_scope` 现在是三道关，顺序固定：

1. `verify_grant`：参数指纹 → 候选张数/体积 ±10% → **候选集合指纹**（`blake3(排序后的合格 id 列表)`）。
2. `verify_sources`：8 线程并行 `stat` 合格候选，与 `images.file_size` 比对；同时逐个 `is_dir` 候选涉及的文件夹。
3. 阈值：文件夹缺失直接拒绝；缺失 + 大小不符超过 **1%** 拒绝并给出张数；低于 1% 则剔除这几张，把数量带回任务摘要。

旧估算没有集合指纹时（升级后第一次执行）不因指纹为空而拒绝。

### 11.6 S5 执行容错

`encode_one` 读原图失败返回 `EncodeOutcome::SourceMissing`，执行循环里单独累加 `report.source_missing`，**不累加** `consecutive_failures`；失败清单仍然记一条（最多 50 条），任务摘要分别显示“原图缺失已跳过”和“失败 N 张”。

### 11.7 收尾复查修正：耗时区间用了串行耗时

点估计的 `work` 用样本编码的**并行墙钟**（`elapsed`），而区间重抽把每张样本的 `read + encode + hash + recalc` **逐张累加**后塞进同一套外推公式。两者差一个线程数：区间会围绕“串行总和”展开，比点估计大出约 8 倍（本机 8 线程）。12.2 里 50 档报出的 ±19–24 s（约 ±100%）主要来自这里，不是抽样波动。

修正：`margins` 在重抽后按线程数把 `total_secs` 折算回墙钟，再加 `write` / `finish`，与点估计同口径。合成组复跑（覆盖 76%）的耗时区间变成 **±1–2 s / 估算 15–18 s**，修正前同一份数据是它的 8 倍左右。真实图片组没有重跑；12.2 的区间宽度仍是修正前的值，按同一比例推算约收窄到 ±2–3 s。

同一轮复跑还暴露一条与抽样无关的敏感性：同一份数据、同一档位，样本编码墙钟在 10–25 s 之间波动（整机负载不同），点估计随之从 15 s 漂到 35 s，节省空间却稳定在 −0.2%…+0.3%。区间只反映抽样误差，不覆盖机器负载，这条记入[待办](../todo.md)。

## 十三、未达标项与后续

1. **耗时中位偏差 +21.7%（目标 ≤5%）**。已确认不是抽样代表性造成的（节省空间已达标），而是层内每像素成本异质 + 写入侧保守常数。若要继续压，最小改动是把“有损源 bpp ≥ 0.50”这一层再按 bpp 拆细（例如 0.50–0.80 / ≥0.80），让每层内每像素成本更齐；代价是分层数从 12 变成 18，`STRATUM_COUNT` 与相关测试要一起改。本批次没有做，留作后续。
2. **抽样耗时增加未单独基准**。切片只增加一次排序 + 一次归组，量级毫秒，但没跑 `perf_metadata_200k` 追加项。
3. **真实窗口未验收**：低覆盖率提示、耗时区间的观感、档位标签回填覆盖率、执行前 5 s 校验的等待反馈，都需要手工走一遍（第七节的 1–7 条）。
4. **真实库未复测**：真实库默认档覆盖率只有 0.078%，无法在可执行规模上直接对比；本次只用 301 张真实副本 + 232 张合成库。
5. **耗时估算对机器负载敏感**：同一份数据、同一档位，样本编码墙钟在 10–25 s 之间波动时点估计从 15 s 漂到 35 s，而节省空间稳定在 −0.2%…+0.3%。区间只覆盖抽样误差，不覆盖负载。若要压，得把外推轴从“墙钟”换成分段耗时（encode / hash / recalc 分别外推），代价是丢掉读盘等待的真实占比。
