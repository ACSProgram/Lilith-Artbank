## 零、结论摘要

- **开始前计数**：当前批量任务对话框只有范围总数；“将处理多少”要等任务开始后由 AI 的 `filter_missing` 改写 `total`，缩略图任务则始终把已有缩略图的图片算在分母里。本批新增只读预览命令，返回“范围 N 张 / 将处理 M 张”，并让任务开始时用同一套过滤，`total` 与预览一致。
- **执行进度**：任务快照只有张数、百分比与当前图片 id；压缩执行没有原始字节、已节省字节、当前文件、速度与 ETA。本批扩展快照，压缩把已结算像素喂给 `WorkMeter`，前端显示张数、字节、速度、ETA 与当前文件。
- **压缩面板**：估算结果页在执行时仍留在下方，执行态只有一条小进度条。本批执行时切换为动态面板，预计值保留为对照；完成后显示实际 vs 预计，并保留原收益曲线作为预估参考。
- **查询方案**：读连接带 `PRAGMA query_only=1`，不能建临时表；选择集不能用小块 `IN` 逐块统计。20 万行合成库上，逐块 `IN(400)` 需要 12–14 秒，范围聚合 143–291 ms，选择集 `json_each` 196k 约 250 ms。预览主路径用单条聚合，选择集用 `json_each`。
- **不做**：不改压缩判据与估算公式（批次 7）；不换任务总线与资源锁；不把运行时曲线写进快照；不新增图表库；不建持久化统计表。

### 1.6 读连接与查询约束

- 读连接统一设置 `PRAGMA query_only = 1`（`src-tauri/src/library/db.rs:36-40`）。实测在该连接上 `CREATE TEMP TABLE` 直接报 “attempt to write a readonly database”，所以**不能**用临时表承载选择集。
- SQLite 的参数上限不适合把 39 万个 id 直接塞进 `IN (?, ?, …)`。
- rusqlite 0.37 使用 bundled SQLite，JSON1 可用；`json_each(?)` 在 `query_only` 连接上可读，实测通过。
- 20 万行合成库（196k 可见、29.4k 缺 embedding、28k 缺缩略图、130.7k 缺描述，页缓存热）的结果：

| 方法 | 结果 | 结论 |
| --- | --- | --- |
| 范围 id 解析（`SELECT id … ORDER BY id`） | 217 ms | 只用于任务开始，不用于预览主路径 |
| 逐块 `IN(400)` 统计缺失 | 11.95 s（embedding）/ 14.15 s（缩略图） | 不可用 |
| 逐块 `IN(4000)` 统计缺失 | 244 ms | 可用但有参数上限，不作为首选 |
| 范围单条聚合（count + SUM） | embedding 291 ms / 缩略图 143 ms / 描述 162 ms | 预览主路径 |
| 选择集 `json_each`（196k id） | 统计 249 ms / 取 id 244 ms | 预览与任务过滤 |
| 选择集临时表 | 被 `query_only` 拒绝 | 不用 |

上表是 SQLite 查询形状的可行性测量，不是最终基线：Python sqlite3 3.45.3、合成库、页缓存热；真实 39 万行、约 1 GB 的库仍需在实现后复测。

## 二、计数口径（本批的契约）

### 2.1 两个数字

- **范围 N（`total`）**：当前范围在浏览口径下的图片数。文件夹 / 集合 / 视图 / 临时区 / 全库复用 `PreparedQuery` 的可见性与筛选；回收站视图按 `PreparedQuery` 的实际可见行数（排除待释放；全库搜索按全库口径叠加）；当前选择的 N 是“仍存在的选中行数”，包含已进回收站的选中行。
- **将处理 M（`willProcess`）**：范围里**未删除**且确实需要处理的图片数。回收站里的行永远不计入 M；因此回收站视图或只选中回收站图片时 M = 0。
- 任务开始后，AI 与缩略图任务的 `total` 使用 M，而不是范围 N；优化执行仍使用自己的候选总数（它已有独立口径，不混用）。
- M = 0 时禁用开始并显示“没有需要处理的图片”。
- 预览是开始前的快照；开始与预览之间图库可能发生变化，任务开始时会重新过滤，任务 `total` 才是最终口径。

### 2.2 各类型的待处理条件

`PendingFilter` 的 SQL 条件如下，统一带 `images.deleted_at IS NULL`：

| 类型 | 条件 |
| --- | --- |
| 全部（`All`，重做类） | `images.deleted_at IS NULL` |
| 缩略图 | `images.deleted_at IS NULL AND (images.thumb_segment = 0 OR images.thumb_length <= 0)`。与 `thumbs::load_pointer` 的判定一致（`src-tauri/src/library/thumbs.rs:238-263`） |
| Embedding | `images.deleted_at IS NULL AND NOT EXISTS (SELECT 1 FROM feature_blobs f WHERE f.image_id = images.id AND f.kind = 'embedding' AND f.model = ? AND f.dim = ?)` |
| 姿势 | `images.deleted_at IS NULL AND NOT EXISTS (… f.kind = 'pose')`；与现有过滤一致，不看模型 |
| 描述（不重做） | `images.deleted_at IS NULL AND length(trim(images.description)) = 0` |
| 描述（重做） | `images.deleted_at IS NULL AND images.description_source <> 'user'` |

说明：

- “重新生成已有描述”沿用现有语义：手写描述（`description_source='user'`）一律不覆盖，导入与 AI 描述可以重做。
- 描述的“空”以 SQLite `trim` 为准。现有任务过滤在 Rust 里用 `text.trim()` 判断；本批让任务与预览都走同一条 SQL，避免两套判断。描述写入前会 `trim`（`src-tauri/src/library/metadata.rs:538`、`:573`），实际数据不会出现只含制表符/换行的描述。
- Embedding 的模型与维度必须来自当前 AI 服务；服务离线或没有返回维度时不能计算 M，前端显示“—”，不显示一个可能错的数字。
- 计划原文把 embedding 与 pose 都写成“按当前模型与维度”统计；代码核对后 pose 一直只按 `kind='pose'` 判断，不看模型（`src-tauri/src/ai/job.rs:411`）。本批保持现有语义，否则旧姿势特征会被整体判成缺失。这是一处有意保留的差异。
- 姿势与描述的计数本身不依赖模型，但按计划仍在 AI 服务离线时显示“—”，因为任务无法开始；服务恢复后由状态轮询触发重算。

### 2.3 范围与选择集的查询形状

非选择范围复用 `PreparedQuery`（`src-tauri/src/library/query.rs:1315-1401`）与现有筛选：

```sql
WITH scope AS (
  SELECT images.id AS id,
         CASE WHEN <pending> THEN 1 ELSE 0 END AS pending
  FROM images {join_sql}
  WHERE {filters}
)
SELECT count(*) AS total,
       coalesce(sum(pending), 0) AS will_process
FROM scope;
```

- `{filters}` 已包含视图可见性、搜索与全部筛选；`{join_sql}` 只用于集合视图。
- 参数顺序必须按 SQL 文本顺序：`pending` 里的模型/维度参数在前，`join_sql` 参数其次，`filters` 参数最后。这里容易写错，测试要覆盖两个不同模型/维度的绑定。
- 这个 CTE 只扫一次图片表；`total` 是范围行数，`pending` 在已删除行上为 0。

选择集用 `json_each`，不建临时表：

```sql
WITH selected_ids AS (
  SELECT DISTINCT value AS id FROM json_each(?)
),
scope AS (
  SELECT images.id AS id,
         CASE WHEN <pending> THEN 1 ELSE 0 END AS pending
  FROM images
  JOIN selected_ids ON selected_ids.id = images.id
)
SELECT count(*) AS total,
       coalesce(sum(pending), 0) AS will_process
FROM scope;
```

- 参数顺序：JSON 数组在前，`pending` 的模型/维度在后（JSON 在第一个 CTE，pending 在第二个 CTE 的 SELECT 列表）；与上面的范围聚合相反，实现时按 SQL 文本顺序绑定，并用两个不同模型/维度的测试锁住。
- `DISTINCT` 解决重复 id；不存在的 id 不会计数；`total` 包含已删除的选中行，`pending` 把它们排除。
- 任务过滤用同一形状的 `SELECT id FROM scope WHERE pending = 1 ORDER BY id`；Rust 侧再按输入 id 顺序过滤一次，保持原来的处理顺序并去重。
- 选择集上限沿用 `MAX_SCOPE_IDS = 1_000_000`（`src-tauri/src/app/tasks.rs:46`、`:1001-1004`）。

### 2.4 为什么不加索引

本批先不加 schema 索引。20 万行合成库上范围聚合 143–291 ms，远低于会导致界面不可用的量级；预览有 250 ms 去抖、加载态与缓存。真实 39 万行库如果 p95 超过约 1.5 s，再按实测决定是给缩略图缺失加部分索引，还是把预览限制在当前范围。没有测量前不加索引，避免把写路径与迁移一起改。

## 三、后端设计

### 3.1 `PendingFilter` 与查询函数

在 `src-tauri/src/library/query.rs` 增加：

```rust
pub enum PendingFilter {
    All,
    Thumbnail,
    Embedding { model: String, dim: u32 },
    Pose,
    Description { overwrite: bool },
}

pub struct PendingStats {
    pub total: u64,
    pub will_process: u64,
}

pub fn pending_stats(database: &LibraryDb, query: LibraryQuery, filter: &PendingFilter)
    -> AppResult<PendingStats>;

pub fn selected_pending_stats(database: &LibraryDb, ids: &[i64], filter: &PendingFilter)
    -> AppResult<PendingStats>;

pub fn selected_pending_ids(database: &LibraryDb, ids: &[i64], filter: &PendingFilter)
    -> AppResult<Vec<i64>>;
```

- `pending_stats` 用于非选择范围的预览；内部 `normalize` 后构建 `PreparedQuery`，按 2.3 的 CTE 聚合。
- `selected_pending_stats` / `selected_pending_ids` 用 `json_each`；JSON 数组由 `serde_json::to_string(ids)` 生成。空数组直接返回 0，不查库；非法 id（≤0）与数量上限按 `resolve` 同样的规则报错。
- `selected_pending_ids` 返回按输入顺序过滤后的 id；实现上把查询结果收进 `HashSet`，再遍历输入，顺带去重。
- 不新增 `pending_ids` 的非选择范围版本：任务开始时仍先 `TaskScope::resolve`，再走 `selected_pending_ids`；这样任务与预览共用同一套 pending 条件，且改动面最小。
- 所有函数只走读连接；`json_each` 已在 `query_only` 连接上验证。

### 3.2 `TaskScope` 到 `LibraryQuery` 的映射

在 `src-tauri/src/app/tasks.rs` 增加只读映射，供预览使用：

| `TaskScope` | `LibraryQuery` |
| --- | --- |
| `Selected` | 无（走 `selected_pending_stats`） |
| `Folder { id, include_subfolders }` | `view: All`，`filters.folder_ids = [id]`，`filters.folder_direct = !include_subfolders` |
| `Collection { id }` | `view: Collection`，`collection_id = Some(id)` |
| `View { query }` | 直接复制 |
| `Temp` | `view: Temp` |
| `Library` | 默认查询（`view: All`） |

- 文件夹 id、集合 id 的合法性在这里校验（与 `resolve` 相同的错误文案）；`Selected` 不走这个映射。
- 临时文件夹用 `Temp` 范围，不通过 `Folder` 范围传它的 id；界面本来就分开提供这两个选项。
- 这个映射只用于预览；估算、移动、撤销仍用现有 `resolve`，不改它们的语义。

### 3.5 任务快照扩展

`TaskSnapshot` 增加字段（`src-tauri/src/app/tasks.rs:158-179`、`src/app/taskTypes.ts:143-164`）：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `runStartedAt` | `i64 \| null` | 第一次进入 `Running` 的时间；排队与准备阶段不算。用于实际耗时与速度 |
| `currentFile` | `string \| null` | 当前处理的相对路径（`文件夹/<content_hash>.<ext>`，根目录下只有文件名）；没有时前端回退为 `#图片id` |
| `originalBytes` | `u64` | 已提交（真正替换）的原图字节；仅压缩任务非 0 |
| `savedBytes` | `u64` | 已提交的节省字节；仅压缩任务非 0 |
| `ratePerSecond` | `f64 \| null` | 运行以来的平均完成张数/秒；未开始或完成为 0 张时为 `null` |
| `etaSeconds` | `u64 \| null` | 预计剩余秒数；优先用 `WorkMeter` 的单位吞吐，没有时按完成张数平均速度折算 |

实现要点：

- `TaskHandle` 增加 `run_started_at: Mutex<Option<i64>>`、`current_file: Mutex<Option<String>>`、`original_bytes/saved_bytes: AtomicU64`。
- `set_phase(Running)` 首次写入 `run_started_at`；另提供 `mark_work_started()`，把 `run_started_at` 重置为当前时刻。压缩在真正调用 `optimize(...)` 前调用它，把排队、准备与执行前逐张 `stat` 复核排除在实际耗时之外（见 3.6）。
- `finish` 清空 `current_file` 与 `currentImageId`。
- `snapshot` 计算：
  - 没有 `run_started_at` 时，`ratePerSecond` 与 `etaSeconds` 都是 `null`，不用排队时间凑；
  - `elapsed = (finished_at ?? now) - run_started_at`；
  - `worked = completed + failed`（跳过项不一定消耗时间，尤其是压缩的前置跳过，所以不进入速度）；
  - `ratePerSecond = worked > 0 && elapsed >= 0.5s ? worked / elapsed : null`；
  - `remaining = total - (completed + failed + skipped)`；
  - `etaSeconds = meter.eta().map(secs)`；为空且 `remaining > 0 && rate > 0` 时用 `ceil(remaining / rate)`；
  - 终态不返回 ETA。
- 速度为“运行以来平均”，不为每个任务再加一套采样锁；压缩的 ETA 由下面的像素计量器提供，AI/缩略图用张数平均速度兜底。
- 快照每 150 ms 复制一次；新增一个短字符串与几个整数，开销可忽略。**不把运行时曲线放进快照**。

`TaskCapsule` 只增加一项：运行中且 `etaSeconds > 0` 时在元信息行显示“还需 X”；不铺开字节、速度与文件（`src/app/TaskCapsule.tsx:52-61`）。

### 3.6 压缩进度：像素计量、字节、当前文件与计数

**`BatchReporter`**（`src-tauri/src/library/mod.rs:39-50`）增加带默认实现的回调，测试里的旧 reporter 不用改：

```rust
fn current(&self, _image_id: Option<i64>, _path: Option<&str>) {}
fn bytes(&self, _original: u64, _saved: u64) {}
fn skipped_count(&self, _skipped: usize) {}
fn failed_count(&self, _failed: usize) {}
```

`TaskHandle` 把 `current` 落到现有的 `set_current`（`currentImageId`）与新的 `set_current_file`；其余三个落到 `set_bytes`、`set_skipped`、`set_failed`。AI 任务照旧在循环里 `set_current(Some(id))`，并在加载到内容行后补 `set_current_file`；缩略图任务只有 id。

**`optimize_with_batch_size`**（`src-tauri/src/library/optimize.rs:483-724`）调整：

1. 开始：前置跳过统计完成后调用 `reporter.skipped_count(prefilter_skipped)`；`reporter.report(0, total_all)` 不变。真正进入编码前调用 `worker.mark_work_started()`，把执行前复核排除在实际耗时之外。
2. 计量器：保留 `meter.set_total_units(total_units)`，只调用一次 `enter_phase(0, 90)`；**删除 `enter_phase(90, 8)`**。
3. 编码：每个候选结算后调用 `meter.advance_units(row.pixels().max(1))`；不再用单独的 `settled_units` 原子计数，也不再为编码阶段调用 `set_percent`。这样 `meter.percent()` 自然给出 0–90，`meter.eta()` 有像素吞吐。
4. 提交：提交线程用 `meter.done_units()` 作为已结算单位，调用 `meter.set_percent(90 + settled * 8 / total_units)`。显式百分比是单调的，编码结束时最多到 90，提交阶段推进到 98。这里仍沿用批次 5 的“已结算像素”口径（不是已提交像素），本批不改提交阶段的分母。
5. 当前文件：编码线程在 `encode_one` 前调用 `reporter.current(Some(row.id), Some(相对路径))`，同时更新 `currentImageId` 与 `currentFile`；提交线程开始一批时调用 `reporter.current(None, None)`，让界面显示“正在写入第 k 批”而不是停在某张图上。
6. 字节：每批提交后读取报告里的累计 `old_bytes/new_bytes`，调用 `reporter.bytes(old_bytes, old_bytes.saturating_sub(new_bytes))`。只有真正发布的图片计入，和 `completed` 一致。
7. 计数：每批提交后调用 `reporter.failed_count(report.failed)` 与 `reporter.skipped_count(prefilter + candidate + duplicate + source_missing)`。这样运行中的失败/跳过不再等到收尾才出现；收尾时 `state.rs` 仍以最终报告覆盖一次（`src-tauri/src/app/state.rs:2049-2050`）。
8. 末尾：`meter.set_percent(99)` 保留；`finish` 时 `meter.finish()` 给出 100。

进度数字的口径（运行中与完成时）：

| 字段 | 来源 | 完成时关系 |
| --- | --- | --- |
| `total` | `total_all` = 前置跳过 + 候选 | 不变 |
| `completed` | 已发布张数 | `completed + failed + skipped = total` |
| `failed` | 解码/磁盘失败 | 同上 |
| `skipped` | 前置 + 候选内 + 内容重复 + 原图缺失 | 同上 |
| `originalBytes` | 已发布图片的旧字节和 | 与 `completed` 同集合 |
| `savedBytes` | 旧字节 − 新字节 | 与 `completed` 同集合 |
| `progressPercent` | 编码 0–90，提交 90–98，末尾 99，完成 100 | 取消/失败时停在真实进度 |
| `etaSeconds` | 像素剩余 / 像素滚动吞吐 | 提交尾段可能为 0，界面显示“正在收尾” |

取消与失败：

- 取消只停止取新批次；已编码并送入通道的批次仍提交。`completed/savedBytes` 反映真正入库的部分；未处理部分留在 `total - done`，进度不回退。
- 提交失败或连续失败停止时，已提交批次保留；`failed`/`skipped` 反映实际；面板不显示 100%。

### 4.4 运行时收益曲线

- 前端按执行任务累积采样点，不进快照、不加事件通道：
  - `{ elapsedSeconds, savingsBytes, processed }`；`elapsedSeconds` 用 `runStartedAt`（没有则退到 `startedAt`）到当前时刻，和“预计 vs 实际”的耗时口径一致；
  - 每个任务最多每 2 秒取一个点，且只在 `processed` 或 `savingsBytes` 相比上一个点有变化时取；`runStartedAt` 变化时重置采样，避免执行前复核阶段产生时间倒退的点；
  - 超过 240 个点时隔点丢弃一半，再继续采样；
  - 对话框隐藏时只要执行任务还在就继续采样，重新打开能看到完整曲线；任务切换、重新估算或关闭图库时清空。
- 图表 `OptimizeProgressChart`（`src/app/OptimizeCharts.tsx` 新增）：
  - 横轴“已用时”（秒），纵轴“累计节省”。选时间而不是执行百分比，是因为估算曲线只有每个点的累计耗时，没有与执行百分比一一对应的横轴；时间能同时比较实际与预估。
  - 实际线用 `savedBytes`；
  - 预估线用估算曲线每个点的 `(elapsedSeconds, savingsBytes)`；
  - 只在实际点 ≥ 2 或任务已结束且 `savedBytes > 0` 时显示；
  - 原“覆盖体积 vs 累计节省”曲线保留在估算明细里，标题明确“预估”。
- 纯函数 `appendRuntimePoint(points, sample, { minIntervalSeconds: 2, maxPoints: 240 })` 与 `compareOptimizeEstimate(estimate, execution)` 放在 `src/app/optimizeProgress.ts`，用 `node --test` 覆盖采样间隔、降采样与差异计算。
- 不引入图表库；沿用现有 SVG 与 `.optimize-chart-*` 样式，新增 `.is-actual` / `.is-estimate` 两个线型。

### 6.1 与计划原文的差异

| 计划原文 | 本设计 | 原因 |
| --- | --- | --- |
| embedding/pose 按当前模型与维度统计缺失 | embedding 按模型 + 维度；pose 仍按任意模型判断 | 现有 pose 过滤不看模型（`src-tauri/src/ai/job.rs:411`），改了会把旧姿势特征整体判缺失 |
| 计数结果先显示旧值、后台刷新 | 同一数据版本内复用；跨版本直接加载 | 旧 M 可能让用户拿过期数字判断要不要开始；与文件夹统计的“旧值先显示”目标不同 |
| 进度面板横轴“进度/时间” | 运行时曲线固定用时间 | 估算曲线只有每点的累计耗时，没有与执行百分比一一对应的横轴 |
| 完成后对照预计与实际 | 对照的实际耗时从 `mark_work_started` 起算，不含排队、准备与执行前 `stat` 复核 | 否则小任务的实际耗时会被复核时间放大，对照失真 |
| 计划未单列回收站/已删除选择 | 范围 N 可包含，将处理 M 一律排除已删除 | “将处理”必须是会真正处理的图片；回收站视图 M=0 |
| 计划未单列预览加载期 | 加载中也禁用开始 | 避免用户在 M 未定时启动一个 0 张任务 |
| 计划未规定选择集实现 | 用 `json_each`，不用临时表 | 读连接 `query_only` 拒绝临时表；逐块 `IN` 在 20 万行上 12–14 秒 |
| 计划未单列缩略图分母 | 开始前先过滤缺失，任务 `total` 等于 M | 原实现把已有缩略图算进分母；不先过滤就无法做到“预览与任务 total 一致” |

## 九、用户手工验收

1. 打开批量任务，类型选“重建缩略图”，范围“整个图库”：范围行显示 N 与将处理 M；勾选“重新生成已有缩略图”后 M 变成 N；取消勾选后恢复。
2. 点击开始：任务面板的总数等于刚才的 M；完成后重新打开对话框，M 减少（全部成功时为 0），开始按钮在 M=0 时禁用并提示“没有需要处理的图片”。
3. 切换到文件夹 / 集合 / 当前视图 / 临时区 / 当前选择：范围行随之变化；开始后任务总数与预览 M 一致。若能在回收站视图或多选中包含回收站图片，确认 N 包含它们而 M 不包含，M=0 时不能开始。
4. AI embedding 在线：M 与后端缺失数一致；停止 AI 服务后，范围行显示“将处理 —”和“连接 AI 服务后计算”，开始按钮禁用；服务恢复后（最多约 8 秒）M 自动出现。
5. 模型缺失维度或服务未返回维度：显示“AI 服务未返回模型维度”，不显示错误数字；开始按钮禁用。
6. 姿势与描述在线：M 正常；描述勾选“重新生成已有描述”后，手写描述不计入 M，导入/AI 描述计入；取消勾选后只计空描述。
7. 快速连续切换类型、范围、跳过已有：旧请求的答复不会覆盖新数字；加载时显示“正在计算…”；切换回来时命中缓存，不重复请求。
8. 在批量任务对话框打开期间导入图片、改评分或改标签：预览数字在后台更新，不出现旧值或空白。
9. 批量任务执行中：面板显示张数、速度、预计还需与当前文件；快速任务没有 ETA 也不报错；任务胶囊显示 ETA。
10. 图片空间优化：估算完成后开始执行；执行中显示完成百分比、已处理/总数、已省/原图字节、速度、ETA、当前文件；关闭再打开对话框仍能接上同一执行任务。
11. 优化执行取消：任务状态为已取消，进度条不跳到 100%，已省字节与已处理张数只反映已提交部分；对照表显示实际部分，不显示“失败”结论。
12. 优化执行完成：对照表显示预计/实际/差异，耗时不含排队；估算明细可以展开；运行时收益曲线有实际线与预估线，原“覆盖体积”曲线仍在估算明细里。
13. 深色主题下新的对照表、当前文件省略与两条曲线可读；窗口较窄时不横向溢出。

真实库只用于只读预览；开始任务、压缩执行与取消验收请用复制样本或测试库（`G:\Lilith Test Library`），不要写 `G:\Lilith Image Library`。代理不启动应用、不截图，界面由用户验收。

## 十、边界、风险与后续

不做：

- 不改 `optimize_estimate.rs` 的外推、抽样与误差公式（批次 7）。
- 不改压缩判据、质量梯子、跳过策略、批次大小与双缓冲内存上限。
- 不换任务总线/资源表，不改 lane、准入、排队与取消规则。
- 不新增进度事件通道；运行时曲线只从现有快照采样。
- 不建持久化计数表、不做增量计数、不加 schema 索引（测量后再定）。
- 不引入图表库；不因预览去改浏览列表的查询与缓存。
- 不把批量任务改成非模态；不自动取消其他任务。

风险：

- **真实库计数可能比合成库慢**：1 GB 库、冷页缓存或复杂搜索会放大到秒级。预览必须异步、去抖、有加载态与缓存；超过预算先收窄默认范围或加索引，不能靠“后台刷新”掩盖。
- **`json_each` 依赖 JSON1**：bundled SQLite 默认带；用单测在 `query_only` 连接上跑一次选择集查询，若未来替换 SQLite 构建会直接失败。
- **选择集 IPC 体积与内存**：39 万全选的预览请求仍会携带 id 列表（与开始任务相同）；任务过滤还会在准备阶段建一个 pending `HashSet`（39 万约 10 MB 量级，1M 约 30 MB 量级）。去抖与缓存避免重复发送；若实测 IPC 或峰值内存成为瓶颈，再评估选择集令牌，本批不做。
- **预览与任务开始之间数据变化**：M 可能过期；任务开始时重新过滤，任务 `total` 是最终口径。界面不在任务开始后回头改预览行，避免两个数字互相追赶。
- **AI 模型/维度变化**：预览用状态里的模型与维度，任务开始用 `ensure_capability` 的实际值；两者不一致时任务 `total` 不同。状态每 8 秒刷新，缓存键含模型/维度，正常不会长期错位。
- **缩略图过滤改变“跳过”语义**：已有缩略图不再进入分母，任务胶囊的跳过通常为 0。若用户依赖“跳过 N 张”判断已有缩略图数量，需要改看范围 N 与 M 的差。
- **压缩 ETA 在提交尾段为 0**：像素都已结算、提交尚未完成时，ETA 会贴近 0；界面用阶段文案“正在写入第 k 批/正在收尾”兜底，不把它写成“已完成”。
- **运行中字节只算已提交批次**：编码完成但未提交的图片不计入 `savedBytes`，这是有意的磁盘真相；面板数字会略滞后于进度条。
- **快照字段增加**：每 150 ms 多复制一个短字符串；不要把曲线或失败清单继续扩进快照。
- **参数顺序错误**：范围聚合的 `pending` 参数出现在 SELECT 列表，早于 WHERE 参数；测试必须覆盖两个不同模型/维度，避免“数字碰巧对”。
- **回收站视图 M=0**：这是有意行为；若用户希望在回收站里重建缩略图，需要单独的产品决定，本批不做。

后续（不阻塞本批）：

- 按真实库测量决定是否为缩略图缺失加部分索引。
- 若选择集 IPC 成为瓶颈，引入短期选择集令牌。
- 若真实窗口里 `start_batch_task` 的同步 `resolve` 造成明显卡顿（39 万约 400 ms），再把启动命令改成 `run_blocking`；本批不为此改命令签名。
- 批次 7 用本批的实时吞吐与字节字段做分层 ETA/估算回测；本批只保证字段口径与展示自洽。
