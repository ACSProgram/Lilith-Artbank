## 结论摘要

这 17 条里，真正需要动架构的只有 3 处，其余是界面与交互返工：

1. **任务系统**：导入、AI、相似分组是三套互不相通的实现，且相似分组没有进度和取消。要抽成统一的任务总线（第 2 条），这是最大的一块。
2. **拖放全线失效**：`dragDropEnabled: true` 让 WebView2 接管了拖拽，前端 HTML5 拖放收不到事件。所以“图片拖进文件夹”“文件夹拖动排序”在真实窗口里从来没工作过（浏览器预览里是好的，所以一直没被发现）。
3. **主题体系**：现在只有一套浅色变量，查看器/编辑器几十处硬编码深色，`settings.ui.theme` 字段存在但从未被应用。

另外发现 7 个用户没提但确实存在的问题（见「额外发现」），其中“设置项 `thumbnailCacheMb` 完全没有消费者”和“Modal 没有焦点陷阱”建议顺手修掉。

实际执行时的偏差：

- **全屏连查看器自身界面一起收起**：计划只写了“隐藏标题栏”，实现里全屏同时隐藏顶栏、工具面板、状态栏、侧栏与胶片带，只留画布（计划里“左侧工具面板自动折叠”的意图）。Esc 退全屏、再按一次才关查看器；`Ctrl + 双击` 切全屏没有做（双击已用于适应/1:1），只保留 F11 与顶栏按钮。
- **体积预估不取消旧编码**：计划写“新请求取消旧的”。实现改为“同一时间只跑一次编码 + 只保留最新一份请求 + 按代次丢弃过期结果”，效果等价，但不需要给编码线程加中断检查。
- **胶片带没有做 `[` / `]` 快捷键**：←/→ 已经能切换，增加第二套按键只添冲突。
- **标签筛选的跳转有取舍**：`apply`/`append` 时目标图自身带这个标签，可以确认它在新结果里，于是用锚点游标跳过去并保持选中；`remove` 会放宽结果、无法确认目标图是否还在，按常规清空选择（否则会把不符合筛选条件的行插到页首）。集合内顺序没有行字段可当游标，此时只保留选择、不跳转。
- **姿势面板只留可见点数与不透明度**：计划里的节点编号、置信度数值、线宽滑块没有做——置信度已经体现在“低于 0.5 半透明”上，编号与线宽对看图没有决策价值。

### P4 · 文件夹与排序（11、17）

状态：**已完成（2026-10-25），用户手工验收通过**。实现、验证与两处验收后修复见 [体验整改 P1–P4 实现记录](2026-10-25-体验整改P1-P4记录.md) 的 P4 一节。

范围：

- 指针事件拖放（`useDragSort`）：图片拖入文件夹、文件夹拖动换父级/排序、悬停自动展开、Esc 取消、边缘自动滚动。
- 文件夹排序菜单（手动/名称/数量，升降序）+ `reorder_folders` 命令 + `sort_index` 持久化。
- 图片排序：
  - 指标扩展到 7 个（导入时间 / 修改时间 / 评分 / 文件大小 / 像素尺寸 / 文件夹 / 集合内顺序）；
  - **多级排序不设人为上限**，可加到指标数量上限；键集游标改为 `sortValues[]`，条件按级别展开；
  - **新增 id 游标通道**：多级排序或无索引指标时，一次性算出有序 id 列表并缓存（token + offset 切片），避免每页重排整个命中集；
  - 排序是**全局一套**，叠加到全部图库视图（全部/回收站/集合/文件夹/搜索）；**相似与语义结果固定按相似度，不参与排序**；
  - 排序弹层 + 排序方案（全局共享，存设置，数量上限 50 是**存储**上限，不是级数上限），方案可随时手动切换，不按视图自动套用。
- 列表视图列头点击直接改排序（复用同一套 `SortSpec`），列显示/隐藏留到后续。

完成指标：

- 真实窗口（非浏览器预览）里能把 3 张图拖到文件夹行上，图片物理移动、树计数更新。
- 拖文件夹到自己子孙上被拒绝并给出提示；拖到行上 1/4、下 1/4 分别插到前后。
- 手动排序重启应用后保持。
- 多级排序跨页无重复、无遗漏（单测：重复主键值 + 混合升降序 + 跨页 + 5 级以上）。
- 多级排序下连续翻 20 页，第 20 页耗时与第 1 页同一量级（验证 id 游标没有每页重排）。
- 排序在“全部/回收站/集合/文件夹/搜索”之间切换时保持一致；进入相似/语义结果时恢复按相似度降序。
- 20 万行基准：每个指标的 1 级排序首页 ≤50ms；7 级排序首次（建 id 游标）≤400ms、后续翻页 ≤60ms。超标先加索引，仍超标才在 UI 标注“该组合较慢”。

实际执行时的偏差：

- **排序旁的升降序快捷按钮已删除**（用户验收后反馈）：排序弹层每一级本来就有自己的方向切换，再放一个“只改第一级”的图标按钮既重复又容易误以为是全局方向。计划原文写的“升降序快捷按钮保留”作废。
- **导入预填当前文件夹**（用户验收后反馈）：从资源管理器拖文件进窗口时，导入对话框的“目标文件夹”原来固定为空；现在预填当前单选中的文件夹（多选或根目录时留空）。点击“导入”与拖入共用这一默认值。
- **文件夹排序指标在全库搜索里仍可用**：计划原写“文件夹在全库搜索时不可用”，实现里没有禁用——`folders.path` 对全库结果同样有定义，禁用只会少一个可用维度。
- **锚点游标改为包含目标行**：标签筛选后跳转时，游标从“目标行之后”改为“从目标行的排序位置开始”，这样即使目标行不在结果里，也不会把一张不匹配的图插到页首；筛选条件仍会把它排除。
- **相似结果没有“恢复排序”动作**：相似/语义结果固定按相似度，排序按钮置灰；退出结果视图后沿用进入前的全局排序。没有另做一套结果内排序状态。
- **20 万行排序基准未实测**：`library/perf.rs` 已更新多级排序与 `sortValues` 的记录结构，但本批没有在 20 万行上跑新的排序基准；数字待补。

## 风险与对策

| 风险 | 对策 |
| --- | --- |
| 多级排序破坏键集分页 | 先补 keyset 单测（重复值/混合方向/跨页），再改查询；分页不退回 OFFSET |
| id 游标与库内容不一致（导入/编辑/删除后顺序变了） | 数据变更统一走已有的 `invalidate_similarity` 一类钩子失效 token；前端收到 `refreshToken` 变化时重新取第一页 |
| id 游标占用内存 | 只保留当前一个 token（+ 上一个用于回退），20 万 id ≈1.6 MB；超过上限时丢弃最旧的并让对应请求回退到键集路径 |
| 新增排序指标无索引导致全表排序 | 每个指标先跑 20 万行基准，超标就加表达式索引或限制可用条件 |
| 指针拖放替换 HTML5 拖放后，OS 拖入导入仍要保留 | 只替换内部拖放，`dragDropEnabled` 保持 true；补一条“从资源管理器拖文件进窗口”的回归检查 |
| 任务总线改动面大 | 先做总线与导入迁移（行为不变），再迁 AI，最后接相似分组与缩略图；每步都保留旧事件名一版 |
| 深色主题遗漏硬编码色 | tokens 化后用 grep 卡口 + 两套主题截图逐页检查 |

## 2. 批量任务与后台任务总线

### 现象

- “AI 任务”“相似分组”“导入”各自一套界面和进度实现，互不相通，也没有统一的“批量任务”入口。
- 任务范围只有“选中 / 当前视图 / 整个图库”，没有“当前集合”“当前文件夹”。
- 没有“生成/重建缩略图”这类任务。
- 同时只能跑一个任务；冲突时报错文字互不相同；关掉对话框就看不到进度；失败清单只在当次对话框里。

### 定位

1. **两套任务系统，第三套是裸命令**
   - 导入：`src-tauri/src/import/job.rs` + `app/state.rs:109-174`（`import_job` 单槽位）。
   - AI：`src-tauri/src/ai/job.rs` + `ai/runtime.rs:464-543`（`inner.job` 单槽位，事件 `ai-job-progress` / `ai-job-finished`）。
   - 相似分组：`aiApi.findSimilarGroups`（`src/modules/ai/api.ts:124-135`）是同步命令，`SimilarityGroupsDialog.tsx:39-56` 只有一个 `busy` 转圈，没有进度、没有取消；全库扫描期间界面完全无反馈。
2. **互斥靠一个全局标志，错误信息分散**
   - `app/state.rs:176-187` `ensure_no_activity`：maintenance / import / ai job 三者互斥，文案是硬编码字符串。
   - `ai/runtime.rs:471-473` 又有自己的“已有 AI 任务在运行”。
   - 前端只能把错误当 toast 弹出来，没有“排队/替换”的选择。
3. **范围模型不完整**
   - `AiJobRequest`（`ai/job.rs:114-123`）只有 `image_ids` 和 `query`；`resolve_ids`（`:447`）在两者都为空时直接全库。
   - `AiTaskDialog.tsx:29` `type Scope = "selected" | "view" | "all"`，没有集合/文件夹语义；“当前视图”实际是 `query`，而 `query` 已经包含 `filters.folderIds` 与 `collectionId`，所以能力上做得到，只是 UI 没暴露。
4. **没有缩略图任务**
   - 只有导入时生成缩略图（`import/pipeline.rs:325` `thumbnail::encode`）。
   - `library/thumbs.rs` 只有 `append` / `read` / `load_pointer`，没有“重建单张缩略图并更新指针”的领域函数。
   - `docs/modules/maintenance.md` 的“重建缩略图/包压缩”仍只是文档，没有实现。
5. **前端没有任务中心**
   - `AiTaskDialog` 自己 `listen("ai-job-progress")`（`:100`），对话框一关监听就没了；`ImportDialog` 同理。
   - 任务状态只存在对话框局部 state 里，切换视图/重开对话框会丢失失败清单。

### 方案

**Rust：通用任务总线 `src-tauri/src/app/tasks.rs`**

- `TaskKind`：`import`、`thumbnail`（重建缩略图）、`aiEmbedding`、`aiPose`、`aiDescription`、`similarityGroups`、`folderMove`、`permanentDelete`、`emptyTrash`。
- `TaskLane`（互斥组）：
  - `write`：导入、缩略图重建、永久删除、清空回收站、文件夹移动 —— 需要 `MaintenanceGuard`，独占，阻止关库/导入/编辑。
  - `ai`：embedding / pose / description —— 独占 AI 服务，串行。
  - `scan`：pHash 相似分组 —— 只读，可与 `ai` 并行，不可与 `write` 并行。
  - 规则：`write` 与任何 lane 冲突；`ai` 与 `scan` 可并行；同 lane 内串行排队。
- `TaskScope`：`selected(ids)` / `folder(folderId, includeSubfolders)` / `collection(id)` / `view(query)` / `library`，由 `query::query_ids` 在 Rust 侧解析，前端只传语义，不传全量 id（避免 50 万 id 过 IPC）。
- `TaskBus`：任务注册表（保留最近 50 条，含已结束）、排队、取消、冲突处理。启动任务时若冲突，返回 `TaskConflict { active: TaskSummary }`，前端弹“排队等待 / 取消现有任务 / 取消”。
- 事件统一为 `task-progress` / `task-finished`，payload 统一 `TaskSnapshot { id, kind, label, scope, phase, total, completed, failed, skipped, message, currentImageId, startedAt, finishedAt, failures[], cancellable }`。现有 `ai-job-*`、`import-*` 事件保留一个版本作为兼容层，随后删除。
- 缩略图任务：新增 `library/thumbs.rs::rebuild(database, thumbs, root, image_id, options)`，复用 `imageops::thumbnail::encode` + `phash::compute` + `colors::dominant`，追加 blob、更新 `images.thumb_*`、`thumb_version += 1`、可选重算 pHash/主色；单张失败记入失败清单，不中断。
- 任务不因为关库而静默丢失：关库前若有 `write` 任务，走 `ensure_no_activity` 的既有保护；`ai`/`scan` 任务在关库时被取消并标记 `cancelled`。

**前端：任务中心**

- `src/app/TaskCenterProvider.tsx`：全局唯一，启动时订阅事件，暴露 `startTask()`、`tasks`、`cancelTask()`。
- `src/app/TaskCenterPanel.tsx`：右下角任务胶囊（有任务时出现，显示“2 个任务 · 43%”）→ 点击展开面板；每条显示类型、范围、进度条、已完成/失败/跳过、耗时、取消按钮、失败清单（可复制）。
- `src/app/BatchTaskDialog.tsx`：统一入口，替换 `AiTaskDialog` 与 `SimilarityGroupsDialog` 的“启动”部分：
  1. 任务类型（生成缩略图 / 重建缩略图 / Embedding / 姿势 / 描述 / 相似分组）；
  2. 范围（当前选择 / 当前文件夹（含子文件夹）/ 当前集合 / 当前视图 / 整个图库），不适用项置灰并给出原因（与第 3 条同一套能力判断）；
  3. 类型相关选项（覆盖、提示词、阈值、是否重算 pHash/主色）；
  4. 预计数量（先用 `queryImageIds` 取数量，或轻量 `count` 命令，避免拉起全量 id）；
  5. 开始后对话框可关闭，进度转到任务胶囊。
- 相似分组的“结果查看”仍保留独立弹窗（结果需要浏览），但扫描动作改走任务总线。

### 决策

- 不做“无限并行”。图片任务是磁盘/CPU/服务瓶颈，串行 + 明确排队比并行更快也更可预期。
- 任务历史只保留本次会话（内存），不落库：重启后的任务没有意义，失败项已经体现在图片状态上。

## 3. 能力置灰

### 现象

- 没有姿势/embedding/主色的图片，右键仍然能点“找相似 · 姿势”，点了才报错。
- 语义搜索、相似分组在服务离线或没有向量时也可点，点了才失败。

### 定位

1. `src/modules/library/LibraryContextMenu.tsx:90`：`canFindSimilar` 只判断 `menu.items[0]?.deletedAt == null`，与图片是否具备该特征无关。
2. `ImageRow`（`src/modules/library/types.ts:47-66`）不含任何特征存在性字段（无 `hasPose` / `hasEmbedding` / 主色），前端无从判断。
3. 后端缺失时会直接报错：`library/similarity.rs` 的 `target_visuals` 只接受哈希/主色完整的图片，`ai/pose.rs` 无 pose 时同样报错（`ai/runtime.rs` 的 `find_similar_images` 分支）。这些错误以 toast 形式弹出。
4. 语义搜索按钮（`LibraryView.tsx:1014-1022`）只判断 `!similarity`；相似分组（`:1024-1033`）只判断 `!onOpenSimilarityGroups`；AI 任务（`:1067-1081`）只判断 `!onOpenAiTasks`，与 `aiStatus.mean.count`、`aiStatus.health` 无关。
5. `FilterPanel` 的“内容状态”三行（`:312-337`）永远可点，即使全库没有 embedding。

### 方案

- 新增命令 `get_image_capabilities(image_ids)` → `[{ imageId, pose, embedding, colors, phash }]`（布尔）。只在打开右键菜单/详情侧栏时对目标图调用，不进入列表查询，避免给 150 行列表加 3 个 EXISTS。
- 前端 `src/shared/capability.ts`：把“动作是否可用 + 不可用原因”收敛成一个函数，返回 `{ enabled, reason }`；所有禁用控件都带 `title={reason}`，不用“灰了但不知道为什么”。
- 右键菜单“找相似”五项按第一张图的 `capabilities` 置灰：没有 pose → “姿势”灰，提示“这张图片还没有姿势数据，可在批量任务里生成”。
- 工具栏：语义搜索在 `aiStatus.mean.count === 0` 或服务离线时灰（提示“还没有 embedding，先跑批量任务”）；相似分组在 AI 离线时仅禁用 embedding 模式，pHash 模式仍可用；AI 任务按钮不再整体禁用，改为打开对话框后按能力逐项置灰。
- 筛选面板“内容状态”在对应特征全库为 0 时置灰并说明。

## 4. 右键菜单

### 现象

- 五项都写成“找相似 · pHash”“找相似 · 主色（8 色）”…… 前缀重复，扫读困难。
- “在侧栏查看详情”多余：单击图片本身就会打开详情侧栏（`LibraryView.tsx:384` `setInspectorOpen(true)`）。
- 菜单整体是 12 个平铺项，没有分组，危险操作和复制操作混在一起。

### 定位

- `LibraryContextMenu.tsx:107-156`：五项重复前缀，且用 `<em>首张</em>` 表示“只对首张生效”，语义不清。
- `LibraryContextMenu.tsx:103-106`：“在侧栏查看详情”调用 `onShowDetails` → `LibraryView.tsx:1387-1390`，只是 `setInspectorOpen(true)`，而右键本身已经 `setInspectorOpen(true)`（`:420`）。这个菜单项实际是空操作。

- `LibraryView.tsx:1238-1372`：`.library-main` 是 flex 行，`InspectorPanel` 插入后 `.library-canvas` 宽度变小。
- `VirtualGrid.tsx:71-79`：`ResizeObserver` 监听容器宽度，宽度一变 `columns` 重算（`:107-110`），所有 cell 的 `translate3d` 位置全部重排。

## 8. 编辑界面

### 现象

- 没有“保存后大概多大”的预览。
- 裁剪后（未保存）再旋转，裁剪框直接消失。
- 只改 JPG 质量时“保存修改”按钮是灰的，存不了。

### 定位

1. **裁剪被旋转/翻转清空**
   - `ImageViewer.tsx:382-397` `rotateBy` 里 `crop: null, resize: null`；
   - `ImageViewer.tsx:399-415` `flip` 同样清空 `crop` 与 `resize`；
   - `ImageViewer.tsx:428-435` `applyCrop` 也会 `resize: null`。
   - 这三处把“几何操作”当成互斥状态，用户连续操作时前面的结果被丢掉。
2. **只改质量无法保存**
   - 前端 `viewer/model.ts:97-102` `hasPixelChanges` = 几何变化 ∨ 格式变化，没有质量；`ViewerTools.tsx:363` 的 `disabled={!hasChanges}` 因此为真。
   - 后端 `imageops/edit.rs:215-217` `has_changes` 同样只比几何与格式，`library/edit.rs:132-134` 直接返回 `UNCHANGED_HINT`。
   - 注释写着“仅调整质量或重新编码不算修改”，但用户要的正是“重新压缩到更小体积”这个操作。
3. **没有体积预览**
   - `ViewerTools.tsx:313-356` 输出区只有格式与质量滑块，`outputSize`（`model.ts:73`）只算尺寸，不算字节。
   - 没有任何“编码一次取长度”的能力。

### 方案

- **几何状态改为可组合**：旋转/翻转不再清空裁剪，而是把裁剪矩形一起变换：
  - 顺时针 90°：`(x, y, w, h)` → `(H_old - y - h, x, h, w)`；
  - 水平翻转：`x → W - x - w`；垂直翻转：`y → H - y - h`；
  - 缩放保持，重新按新基底 clamp（`resizeFromWidth` 已有能力）。
  - 抽成纯函数放 `viewer/model.ts` 并补单测（旋转 4 次回到原状、翻转 2 次回到原状、旋转后裁剪面积不变）。
- **质量计入“有修改”**：`hasPixelChanges` 增加“有损格式且质量 ≠ 默认 90”；后端 `has_changes` 增加 `quality` 参数，规则一致。保存前提示“重新编码会损失画质，且不会保留原始 EXIF”。
- **最终大小预览**：输出区新增一行
  - `结果 1024 × 1024 · JPEG q60 · 约 148 KB`；
  - 尺寸即时算；体积在几何/格式/质量变化后 500ms 防抖，调用新命令 `estimate_edit_size(image_id, geometry)`，后端在内存里编码一次并丢弃结果，只回字节数（超过 2000 万像素时按 1/4 缩略编码后按面积比外推，并标注“估算”）；
  - 命令带取消（新的请求取消旧的），避免拖滑块时堆积编码任务。
- 输出区增加“与当前文件对比”：`原文件 1.2 MB → 148 KB（-88%）`，让“重新压缩”这件事有反馈。
- **编辑撤销栈**：
  - `src/modules/viewer/useEditHistory.ts`：`{ past: Entry[], present: GeometryState, future: Entry[] }`，`Entry = { state, label }`，`label` 由操作名生成（`裁剪`、`旋转 90°`、`水平翻转`、`调整尺寸 1024×768`、`输出 JPEG q60`）；
  - 所有几何/输出参数变更走 `commit(label, next)`，滑块类连续操作合并成一次（同 label 且间隔 <600ms 合并，松手时提交）；
  - `Ctrl+Z` 撤销、`Ctrl+Shift+Z` / `Ctrl+Y` 重做，最多 50 步，超过丢弃最旧的；
  - 切换图片时清空；**保存成功后清空且不可撤销**（保存是“新内容发布”，旧原图已删除，要支持撤销保存就得保留旧文件版本，2026-10-24 确认不做）；
  - 工具面板底部显示最近一步的可撤销标签，按钮在无可撤销时置灰。

### 决策（2026-10-24 已确认）

- 第 8 条最后一句补的是**编辑撤销栈**，与“最终大小预览 + 与原文件体积对比”一起做。

## 9. 筛选零值

### 现象

- 筛选面板里评分 6 个档位永远都在，没有图片的档位显示“—”。
- 标签列表把所有标签都列出来，当前视图里 0 张的标签也照列。

### 定位

- 评分：`FilterPanel.tsx:236-249` 固定渲染 `[0,1,2,3,4,5]`，缺失时 `scoreCounts.get(...) ?? "—"`。后端 `query.rs:959-974` 只返回实际存在的评分分组，所以 0 张的档位就是 `—`。
- 标签：`FilterPanel.tsx:377-391` 遍历 `visibleTags`（全部标签，来自 `getTags`），计数 `tagCounts.get(tag.id) ?? 0`，0 也渲染。
- 扩展名分面已经是“只显示存在的值”（`counts.extensions` 直接来自分组查询），所以评分和标签是特例，不是统一规则。

### 方案

- 统一规则：**计数为 0 且未被选中**的分面项不渲染；已被选中的项即使当前计数为 0 也保留（否则用户无法取消选择）。
- 评分档位同理：只渲染 `scoreCounts` 里存在的值，加上已选中的值。
- 计数尚未加载（`counts == null`）时不要把所有项都当成 0：此时按“未过滤”处理，全部渲染，避免面板打开瞬间闪一下。
- 如果某个分组全部为 0，整段隐藏（例如没有任何评分时，评分段直接不出现），而不是显示 6 个“—”。

## 11. 文件夹排序与拖放

### 现象

- 文件夹树只能按名称字母序，不能按数量/时间，也不能手动调整顺序。
- 文件夹拖不动，图片也拖不进文件夹（浏览器预览里能拖，真实窗口里不行）。

### 定位

1. **排序写死**
   - `folderTreeModel.ts:55-59`：`sortNodes` 用 `Intl.Collator` 按名称排序，没有任何可选项。
   - `folderTreeModel.ts:64-74` `flattenVisible` 只是按树遍历，顺序完全由上面的排序决定。
   - `folders` 表（`library/schema.rs`）没有顺序字段，`get_folders` 返回的 `FolderInfo` 也没有 `sortIndex`。
2. **拖动失效的根因（关键）**
   - `src-tauri/tauri.conf.json` 里 `"dragDropEnabled": true`。
   - Tauri 在 Windows 上启用原生拖放后，WebView2 会把拖拽交给宿主，**HTML5 drag-and-drop 事件不会正常触发**（Tauri 文档明确要求：Windows 上要用前端 HTML5 拖放，必须设 `dragDropEnabled: false`）。
   - 代码里的拖放链路本身是完整的：`VirtualGrid.tsx:217-218` 设 `draggable` + `onDragStart` → `LibraryView.tsx:372-379` 写入 `IMAGE_DRAG_MIME` → `FolderTree.tsx:276-300` 的 `dropProps` 接收 → `moveImagesTo`（`:240-254`）→ `move_images_to_folder`。
   - 所以“拖不进文件夹”不是没写，而是在真实窗口里根本收不到事件；批次记录里“浏览器预览已完成拖放检查”的结论正好解释了为什么预览正常、真机不行。
   - 同理，文件夹拖动换父级（`FolderTree.tsx:362-366`）也一起失效。
3. **缺少同级排序**：即使拖放能用，现在的拖放语义只有“移动成为子级”，没有“插到某个兄弟之前/之后”（旧程序 `Lilith Artworks` 的 `LibraryTreeView.tsx:99-124` 用 `positionFor` 分上/中/下三段，分别对应 before/inside/after）。

### 方案

- **拖放能力**：保留 `dragDropEnabled: true`（否则会失去“从资源管理器拖文件进窗口导入”），把内部拖放改成指针事件实现：
  - `src/shared/useDragSort.ts`：`pointerdown` + 6px 阈值启动、`pointermove` 跟手 ghost（`position: fixed`）、`elementFromPoint` 命中目标、`pointerup` 提交、Esc 取消、靠近容器边缘自动滚动。
  - 这套实现不依赖 HTML5 DnD，在 WebView2 与浏览器预览里行为一致，也顺便解决“图片拖到文件夹”与“文件夹拖动排序”。
  - 统一 drop 语义：目标行上 1/4 = 插到之前，下 1/4 = 插到之后，中间 1/2 = 放入（图片则是移入该文件夹）。
- **持久化手动顺序**：schema v3 给 `folders` 加 `sort_index INTEGER NOT NULL DEFAULT 0`；新增 `reorder_folders(folder_ids, parent_id, index)`；`get_folders` 返回 `sortIndex`。
- **排序选项**：文件夹区标题右侧加排序菜单：`手动`（默认，按 `sort_index`）/ `名称` / `图片数（含子文件夹）` / `图片数（直接）`，各支持升降序。非“手动”模式下禁用拖动排序（但“拖入文件夹”仍然可用），并在菜单里说明。
- 树节点拖放时的自动展开（悬停 600ms 展开子级），以及“拖到自己子孙上”的禁用判断（`isSameOrDescendant` 已有）。

### 决策（2026-10-24 已确认）

- 内部拖放**自己实现**（指针事件），`dragDropEnabled` 保持 `true`，保留“从资源管理器拖文件进窗口导入”。

## 13. 全屏

### 现象

### 定位

## 14. 姿势节点

### 现象

- 姿势骨架太细、太淡，几乎看不见。

### 定位

- `PoseOverlay.tsx:60-61`：`stroke = min(width, height) * 0.0025`、`radius = min(width, height) * 0.004`，用的是**原图显示尺寸**（`ImageViewer.tsx:818-822` 传 `source.displayWidth/displayHeight`），不是屏幕尺寸。
- SVG 放在被 `zoom` 缩放的 `.viewer-image-wrap` 里，所以缩略显示时（`zoom` 常常是 0.2-0.4）线宽和圆点会一起缩小到 1-2 屏幕像素。
- 颜色：线 `rgba(104,226,181,0.85)`、点 `rgba(240,255,248,0.95)`，在浅色/复杂画面上对比度不足；没有描边外发光，也没有遮罩。

### 方案

- 线宽与半径按**屏幕像素**恒定：传入 `zoom`，用 `strokeWidth = 2 / zoom`、`r = 3.5 / zoom`，缩放时骨架粗细不变。

- 关节分级：躯干/头部节点更大（5px），四肢小节点 3.5px；置信度低于 0.5 的点用虚线或半透明表示。
- 可选开关（姿势面板内）：显示节点编号、显示置信度、线宽滑块、整体不透明度；设置持久化。
- 姿势面板里同时显示“检测到 N/33 个点”。

## 17. 排序指标与方案

### 现象

- 感觉只能切换升降序，选不了按什么排。
- 不能保存常用的排序组合。

### 定位

1. **指标其实有，但只藏在工具栏右端一个原生 `<select>` 里**
   - `LibraryView.tsx:1108-1149`：`<select className="input sort-select">` 提供 `sortOptionsFor(view)`，加一个只有图标的升降序按钮。
   - `model.ts:38-47` `sortOptionsFor` 只有三项：导入时间、评分、文件大小（集合视图多一项“集合内顺序”）。
   - 这个 `select` 没有标签、没有图标、宽度很窄，和旁边一堆按钮挤在一起，实际不可见性很强，所以体感是“只能切顺序”。
2. **指标本身太少**：`types.ts:2` `SortKey` 只有 4 个值；Rust 侧 `query.rs:32-38` 的 `SortKey` 同样是 4 个，`sort_column`（`:599-606`）也只映射 4 列。
3. **没有方案**：`BrowseState.sort`（`model.ts:18-25`）是单个 `SortSpec`，`useLibraryBrowse` 只存在内存里，没有持久化，也没有“保存的排序”概念。
4. **索引**：`schema.rs:55-63` 只有 score / imported_at / file_size 三个排序索引，新增指标要补索引，否则会退化成全表排序。
5. 参考实现：`Lilith Workspace` 音乐库的 `SortDialog`（`MusicPlayerDialogs.tsx:147-263`）就是“多级排序 + 已保存方案（最多 50 个，可另存/更新/删除）+ 优先级上下移”，方案写在本地偏好里。这套交互可以直接搬。

### 方案

**指标（后端 + 前端同步扩展 `SortKey`）**

| 指标 | 列 | 索引 |
| --- | --- | --- |
| 导入时间 | `images.imported_at` | 已有 |
| 修改时间 | `images.modified_at` | 新增 `(deleted_at, modified_at DESC, id DESC)` |
| 评分 | `images.score` | 已有 |
| 文件大小 | `images.file_size` | 已有 |
| 像素尺寸 | `width * height`（表达式） | 新增表达式索引 |
| 文件夹 | `folders.path`（join） | 复用 `idx_folders_path_nocase`，20 万张以上需实测 |
| 集合内顺序 | `collection_items.position` | 已有（仅集合视图） |

- “文件名”不作为指标：原图按内容哈希命名（`<hash>.<ext>`），文件名没有语义。
- “随机”暂不做全库随机（keyset 每翻一页都要重排全表）；改为“打乱当前已加载结果”，只在会话内生效。

**多级排序（不设人为上限）**

- `SortSpec` 从 `{ key, descending }` 扩展为 `sort: SortSpec[]`（数组，第一级为主）。**级数不设上限**，最多能加到指标数量（7 级）；UI 在超过 3 级时给一行轻提示，但不阻止。
- 复合排序本身不是问题：B-tree 索引的列顺序就是排序优先级，`ORDER BY a, b` 只要有 `(a, b)` 索引就能直接走索引顺序。上一版写的“索引只能保证第一级”不准确，准确说法是——**索引能保证的是与索引列顺序一致的前缀**；只建了单列索引时，才只有第一级被保证。
- 真正的问题是“不可能为所有组合建索引”：7 个指标、每级两种方向、任意顺序，组合数量是排列级的。没有匹配索引时 SQLite 走临时 B-tree 排序（`EXPLAIN QUERY PLAN` 里的 `USE TEMP B-TREE FOR ORDER BY`；前缀能命中索引时是 `FOR RIGHT PART OF ORDER BY`），而且 **`LIMIT` 在排序之后才生效，等于每翻一页都要把整个命中集重排一遍**。深分页时这是真正的成本。
- 所以分页策略按“有没有匹配索引”分两条路：
  1. **单级排序且该列有索引**（默认排序、常用排序）→ 继续用现有键集游标（`sortValues[]` 只有一个元素），零额外内存，首页 ≈ 一页的行数。
  2. **多级排序 / 无索引指标** → 新增“结果 id 游标”：第一次查询时在 Rust 里把命中集的 id 按完整排序算一次（`SELECT id ... ORDER BY ...`），存成 `Vec<i64>` 并返回 token；之后每页只按 offset 切 150 个 id，再用现有的 `rows_by_ids` 回填行。200 000 个 id 约 1.6 MB，只保留当前一个 token（加一个上一版用于回退），数据变更时整体失效。
- 这条 id 游标通道和语义搜索已经在用的 `ResultCache` 是同一个模式，不是新概念；它同时解决了“深分页越翻越慢”和“多级排序每页重排”两个问题。
- 键集游标保留（`sortValues: String[]`，条件按级别展开：`(k1 > a1) OR (k1 = a1 AND k2 > a2) OR … OR (全部相等 AND id > aid)`），补 `query.rs` 单测：重复主键值、混合升降序、跨页、5 级以上。

**排序的作用范围**

- 排序是**全局唯一**的一套设置，不是每个视图各记一份：在“全部”里设好排序，切到回收站、集合、文件夹、搜索结果都沿用同一套。
- 作用于所有**图库视图**：全部 / 回收站 / 集合 / 文件夹子树 / 搜索结果（共用 `LibraryQuery.sort`，天然叠加在筛选与搜索之上）。
- **相似与语义结果不参与排序**（2026-10-24 确认）：这两类结果的判定值是浮点相似度，几乎不会相同，排序方案在这里没有实际意义，反而会盖掉“越靠前越像”的默认顺序。它们固定按相似度降序，结果条显示分数。
- 筛选面板的计数（`get_filter_counts`）与排序无关，不受影响。
- 相似/语义结果与当前筛选的关系：保持现状（不叠加筛选），但在结果条提供一个“仅当前筛选内”的可逆开关，勾选后把结果 id 与当前筛选求交集。

**方案（profile）**

- `SortProfile { id, name, sort: SortSpec[] }`，存 `settings.ui.sortProfiles`，**最多 50 个**——这是**存储数量**上限（避免设置文件无限膨胀），与排序级数无关。名称唯一（不区分大小写）。
- 排序弹层（替换现在的 `<select>`）：
  - 上半：当前排序的优先级列表（1…N 行，可滚动），每行可选指标 + 方向 + 上移/下移/删除，底部“添加一级”（指标用尽时置灰）；
  - 下半：`已保存方案` 下拉（含“临时排序”）+ 方案名称输入 + `另存为新方案` / `更新方案` / 删除；
  - 应用后立即生效并写入设置；非法指标自动置灰并说明（“集合内顺序”只能用于集合视图，“文件夹”在全库搜索时不可用）。
- 排序按钮改成带文字的按钮（`排序 · 评分 ↓ + 导入时间 ↓`），点击打开弹层；升降序快捷按钮保留，作用于第一级。（实际执行时已删除该快捷按钮，每级方向在弹层内切换，见 P4 偏差。）

### 决策（2026-10-24 已确认）

- 排序做**多级**，不设人为级数上限（原方案的“3 级”只是保守值）。
- 排序是**全局一套**，叠加到全部图库视图（含筛选与搜索结果）；**相似/语义结果除外**——它们的判定值是浮点相似度，几乎不会有相同值，排序方案在这里没有意义，固定按相似度降序。
- 排序方案全局共享，随时手动切换，不按视图自动套用。
