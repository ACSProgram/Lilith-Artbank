## 2. 必须修（P0/P1）

### 2.1 中文语义搜索几乎失效，工具描述也没提醒用英文

**现象**：三个毫不相关的中文查询（「穿红色长裙的女剑士」「一只橘色的猫」「金属头盔和盔甲」）返回的前几名几乎完全相同，且与查询语义无关；同样的意思换成英文，结果集立刻分开。

**向量层证据**（直接调应用内 embedding 服务，1536 维、已归一化）：

| 对比 | 英文 | 中文 |
| --- | --- | --- |
| 语义无关句之间余弦（4 句两两，均值） | **0.328**（0.29–0.38） | **0.607**（0.53–0.69） |
| 同义句跨语言余弦 | 0.48–0.78 | 同左 |

中文向量彼此挤在 0.53 以上，等于所有中文查询共享一个近乎相同的方向，语义差被压掉了。

**行为层证据**（5 张候选图，用「自己的描述找回自己」）：

| 目标图 | 英文 | 中文 |
| --- | --- | --- |
| 黑白剑柄线稿 `840` | **第 1**（0.2819 vs 次名 0.2078） | 第 2（0.2146 vs 次名 0.2400） |
| 弓箭手人偶 `705` | **第 1**（0.2365） | 第 2（0.2254） |
| 杂志封面 `2425` | **第 1**（0.4080） | 第 1（0.3500，分差变小） |

英文 3/3 排第一，中文 1/3。

**建议**：① 工具描述直接写「语义搜索请用英文短语，中文命中质量明显下降」；② 或对中文查询做一层翻译再编码；③ 长期看换多语言文本塔。这一条不改，AI 用中文语义搜图会持续给出「看起来有结果、其实全靠猜」的答案。

### 2.2 临时区会挡住同内容的图库导入 —— 直接破坏「先看再决定」的用法

**现象**：先把目录导入临时区（`batch-a.png` → 9457、`nested.png` → 9458），再把这个目录导入图库，结果 `imported=1 / duplicates=6`，被跳过的原因全是命中**临时区**的行：

```json
"duplicatePairs": [
  {"imageId": 9457, "sourcePath": "...\\batch-a.png", "trashed": false},
  {"imageId": 9458, "sourcePath": "...\\sub\\nested.png", "trashed": false},
  ...
]
```

9457/9458 只存在于临时区，关库即消失。AI 按描述去 `images_get(9457)` 会看到 `folderPath = ".artbank-temp"`，既不能移动出临时区、也不能加入集合、也没有删除工具 —— 它只能等用户关库清空，再重导一次。

**这正好是临时区最主要的用法**（导入 → 看看 → 决定入库），第二步就被自己挡住了。

**建议**：精确重复检测排除 `kind = 'temp'` 的行；或者命中临时区时在回执里单独给一类 `tempDuplicatePairs`，并在工具描述里写明「关库后失效，重新导入即可」。至少不能让 `duplicates` 静默吃掉真正的入库。

### 2.3 `similarity` 选择器忽略 `limit`，AI 以为只改前 3 张、实际选中 20 张

**现象**：`find_similar(limit=20)` 之后用选择器写入：

```json
{"kind":"similarity","token":"98f3…","limit":3}
```

`dryRun` 返回 `selected: 20`、`willChange: 20`，`sample` 里也是 20 张。`limit` 字段在 schema 里存在、但解析时被忽略，实际取整个结果槽。

**风险**：这是唯一一个「AI 明确限定了数量、系统却放大」的入口，一旦发生在 `images_trash` 或大范围 `images_update` 上，就是真实误伤。**建议**：要么实现 `limit`（按 `offset` + `limit` 切片），要么从 schema 里删掉这个字段并在描述里说明「selector 永远取整个结果槽」。

### 2.4 MCP 导入的图永远进不了语义检索

**现象**：图库导入只算 pHash 与主色，不算 embedding / 描述。`library_info` 反映得很清楚：`images 9449` 但 `embeddings 9447`；`find_similar(kind=embedding, targetId=9459)` 直接报「这张图片还没有 embedding，请先运行 AI 任务」；文本语义搜索的 `total` 恰好等于 embedding 条数，新导入的图不在其中。

而 MCP **不能**给普通图库生成 embedding（`temp_features_generate` 只收临时区 id），所以 AI 导入完之后想「帮你找找库里跟这 20 张相似的」是做不到的，只能让用户自己去界面跑批量任务。

**建议**：① 工具描述写明「新导入的图暂时没有语义特征，语义搜索找不到它们」；② 或给 `library` 开一个与临时区同构、但需要 `confirmedCount` + 确认档的受限特征生成入口。第 ① 条是零成本且立刻能减少误解的。

## 3. 应修（P2）：dryRun 与实际不一致 / 计数语义互相矛盾

这类问题不会造成数据损坏，但会让 AI 白跑一轮，或者得出错误结论。

| # | 位置 | 现象 | 建议 |
| --- | --- | --- | --- |
| 3.1 | `images_update` 评分 | 目标评分与现状相同时，`willChange` 仍等于 `selected`（3 而不是 0），执行后还真写了一条 `affected=3` 的无效历史记录 | `willChange` 按实际变化数算；全无变化时直接 `noop` |
| 3.2 | `collections_membership add` | 已在集合里的图，`dryRun` 给 `willChange=1 / skipped=0`，执行却是 `noop / affected=0` | 与 3.1 同因：dryRun 没算「已在目标状态」 |
| 3.3 | `images_move` | 已在目标文件夹的图，`dryRun` 给 `willChange=1`；任务结果是 `message="移动 0 张，跳过 1 张"` 但 `skipped:0`、`completed:1` | 同一份「跳过」信息在 message 和计数字段里打架 |
| 3.4 | `images_move`（临时图） | 不是同步拒绝，而是返回 `taskId`，再由任务 `phase=failed` 失败，且 `failed:0`、`failures:[]` | 前置校验，和 `collections_membership` 一样同步拒绝 |
| 3.5 | `images_trash`（临时图） | 会先弹确认卡片问用户「是否移入回收站」，批准后才失败 | 明显不可能的操作用户不该被问一次 |
| 3.6 | `import_start`（路径不存在） | 先入确认队列，批准后才在扫描阶段失败 | 入队前做路径存在性校验，直接 rejected |
| 3.7 | `history_list` | 顶层 `canRun:true` + `blockedReason:null`，但条目里 `canUndo:false`「压缩操作不可撤销」 | 顶层 `canRun` 与条目语义不一致，AI 会直接信顶层 |
| 3.8 | `history_undo`（含 optimize 链） | `dryRun` 返回 200 + `preview.blockedReason`，照样给 `steps=14 / affected=7034`；只有真执行才报错 | `dryRun` 直接 `rejected` 更安全，避免 AI 拿过期数字去执行 |
| 3.9 | `cancellable` 字段 | 已完成/已取消的任务大多仍为 `true`，但撤销/重做任务为 `false` | 统一按终态置 false |
| 3.10 | `find_similar.threshold` | 描述说「pHash 是 0-256 距离上限，其它指标是 -1..1 的分数下限」，但 color4/color8 实际也是**距离上限**（0.012 的图，`threshold=0.005` 返回 0 条） | 描述改成「phash 0-256、color4/8 是 0-1 的距离上限、embedding/pose 是 -1..1 的相似度下限」 |
| 3.11 | `find_similar` 回显 | 请求 `kind=embedding, mode=text`，响应 `kind:"semantic"` | 回显请求值或用枚举里真实存在的值 |
| 3.12 | 导入回执 | `merge` 策略下 `duplicates:0` 但 `duplicatePairCount:1` | 两个「重复」口径不同，AI 用 `duplicates` 判断会得出「没有重复」 |
| 3.13 | 拼图 `thumbMissing` | 被 `excludeCells` 排除的格子和「本来就没有图」都返回 `thumbMissing:true` | 区分 `empty` / `excluded` / `thumbMissing` 三种状态 |

## 4. 作为 AI 客户端「只看工具描述」时的误解点

按要求，我在不看模块文档的前提下只用 `tools/list` 的描述 + JSON Schema 试了一遍，这几处会直接导致用错：

1. **语义搜索该用英文**：描述里没有任何提示，全靠自己撞（撞完的结论就是 §2.1）。
2. **`threshold` 的方向对 color 指标是反的**：按描述传 `0.8`（以为是相似度下限）会把全库带回来，传 `0` 会一条都不剩（§3.10）。
3. **`view=library` 不存在**：`search_images` 描述写「view=library 时包含回收站」，但 `QueryView` 只有 `all/trash/collection/temp`，`library` 其实是 `searchScope` 的值。
4. **`similarity.limit` 的语义**：以为是「只取前 N 张」，实际是整个结果槽（§2.3）。
5. **临时区重复阻断**：完全想不到，而且从回执上看不出命中的是临时行（只有 `imageId`，要再查 `images_get` 才知道是 `.artbank-temp`）。
6. **`duplicates` vs `duplicatePairCount` vs `merged`** 三个口径：不读完回执全部字段，很容易把「合并」当成「没有重复」。
7. **`completed` / `total` / `skipped` / `failed`**：导入任务里 `completed` 是「已处理文件数」，移动任务里 `completed` 是「已移动张数」，同一个字段两种含义。
8. **`images_get` 与搜索行的标签形状不同**：搜索行是 `["服装","氿玄花瓣"]`，`images_get` 是 `[{id,name}]`；描述里没提。
9. **回收站图片 `capabilities.embedding=false`**：会以为没算过向量，其实是扫描排除。
10. **分面只给 id**：`facets.folders` 给 `folderId`、`facets.tags` 给 `tagId`，都要再跳一次 `folders_list` / `tags_list` 才能说人话。

## 5. 体验与文案类

- **确认卡片排版**（你现场指出的）：`标签… / 评分… / 重复项合并` 和 `导入图片 / 1 个路径 · 「test」 / 时间` 挤在同一视觉层，第二行信息密度过高；建议把导入专属信息拆成独立一行（小标题或 chips），并与「后果」列表拉开间距。
- **`import_start` 的 `count` 是路径数不是图片数**：卡片上「1 个路径」靠 `unit:"path"` 兜住了，但用户第一眼仍会读成「只导入 1 张」；建议对目录路径显示「1 个目录（预计 N 张）」或直接在批准后回执里说明。
- **`folderPath` 暴露内部路径**：临时图的 `folderPath` 是 `.artbank-temp`，建议展示为「临时」。
- **根目录图片无法从文件夹树发现**：`folders_list` 根层不返回「未分类/根目录」项，本库根目录那 1 张图只能靠搜索发现；`library_info` 也没有根目录计数。
- **`search_images` 行内没有 description**：想批量看描述只能每 50 张调一次 `images_get`。
- **审计日志**：`tasks_cancel` 拒绝审批只记 `status=rejected`，不带 `approvalId`，也没有审批生命周期（创建/批准/过期）单独成行；字段名 `operation=` / `task=` 与文档写作 `operationId` / `taskId`。
- **`library_info.ai.baseUrl`** 把内部 AI 服务地址给了出去，而语义搜索的报错文案是刻意隐藏地址的，两处策略不一致。
- **撤销后新写入会清空灰色分支**：文档写了，但实际感受是「刚撤销的记录直接消失、`history_redo` 变成『操作记录不存在』」。建议在 `history_list` 的 note 里把「下一次写入会删除这些重做记录」说白。
