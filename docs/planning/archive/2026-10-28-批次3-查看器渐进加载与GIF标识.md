## 一、本批次决策

| 问题 | 结论 |
| --- | --- |
| GIF 的播放范围 | 查看器继续播放原图动画；网格、列表与胶片带保持静态首帧，不做动图缩略图。网格与列表给 GIF 加角标，说明“仅在查看器中播放”。 |
| 超过 24MP 的 GIF | 沿用 Rust 生成的静态 WebP 预览；查看器工具面板与状态栏明确写“已生成静态预览，动画不可用”。编辑仍只保留首帧，保留现有警告。 |
| 缩略图层来源 | 用会话项已有的 `thumbVersion` 取 512px 缩略图（`thumbnailUrl`），按原图宽高比铺进 stage；不新增第二套缩略图、不改缩略图包。 |
| 加载态 | 有可用缩略图时不显示整块“正在读取原图”；延迟 150ms 仍加载才显示小 spinner；无缩略图或缩略图失败才回到整块加载态；取图失败仍用现有错误态。 |
| 取图时序 | 核对后 `get_viewer_source` 已是 async + `spawn_blocking`（2026-10-27 批次 6 完成），窗口事件循环不会被预览生成阻塞；本批次不再改命令，只给 `img://preview` 补“文件缺失时兜底生成”。 |
| 切换防闪 | 渲染只接受与当前 `activeId` 一致的 `ViewerSource`；切换后的第一帧不再复用上一张的 source、缩放与姿势。拟合缩放改为 layout effect，避免缓存图先以 100% 显示一帧。 |
| 尺寸一致性 | 缩略图层、高清层、姿势叠加与裁剪选区共用同一套 `displayWidth/displayHeight`、`zoom`、`pan` 与旋转/翻转变换；占位尺寸只用于布局，裁剪坐标仍只按 `ViewerSource` 换算。 |
| 透明图淡入 | 有 alpha 的图片不做交叉淡入：高清层加载完成后直接换层并隐藏缩略图，避免缩略图从透明区域透出。 |
| GIF 角标 | 角标只按导入时识别的 `format = gif` 判断，不看可能被改名的扩展名；APNG、动画 WebP 与多页 TIFF 不在本批次范围。 |
| 不做 | 不在网格播放动图；不新增 GIF/APNG 解码器；不改变编辑输出格式；不提前预加载相邻图片；不在本批次决定“禁止编辑动图”。 |

## 二、现状核对

### 2.1 GIF 从导入到查看

现有链路已经能“显示动图”，缺的是标识与静态预览的说明：

- 导入白名单含 GIF（`src-tauri/src/import/scan.rs:11-13`）。
- 解码走 `DynamicImage::from_decoder`（`src-tauri/src/import/decode.rs:69-75`），GIF 只取首帧；导入生成的缩略图因此也是静态首帧。
- 缩略图最长边 512px、保持宽高比（`src-tauri/src/imageops/thumbnail.rs:5`、`:12-38`、`:72-84`），以 WebP 追加进 `.pack`，`thumb://` 只回静态字节。
- 查看器的浏览器原生格式包含 GIF（`src-tauri/src/library/viewer.rs:31-32`）。≤2400 万像素且无 EXIF 方向时直接加载原文件（`src-tauri/src/library/viewer.rs:91-101`），由 WebView2 播放动画；`img://` 对 GIF 返回 `image/gif`（`src-tauri/src/app/img_protocol.rs:77-90`、`:120-130`）。
- 超过 24MP 或带 EXIF 方向时生成最长边 4096 的静态 WebP 预览（`viewer.rs:17`、`:91-101`、`:145-167`）；GIF 一般不携带可识别的 EXIF 方向，实际触发条件主要是 `preview`。
- 编辑 GIF 只保留首帧的警告已经存在（`src/modules/viewer/ViewerTools.tsx:212-216`）；默认输出格式为 PNG/JPEG/WebP（`src/modules/viewer/model.ts:30-35`）。
- 网格格子的 `title` 只显示尺寸、格式、大小（`src/modules/library/VirtualGrid.tsx:278-280`）；列表的“格式”列只显示 `GIF` 文本（`src/modules/library/VirtualList.tsx:281`）；`LibraryThumbnail` 没有格式角标（`src/modules/library/LibraryThumbnail.tsx:42-76`）。

结论：“增加 GIF 支持”不成立，查看器已经能播放；缺口是网格/列表无法一眼识别动图，以及大 GIF 走静态预览时没有任何说明。

### 2.2 当前打开与加载时序

`src/modules/viewer/ImageViewer.tsx` 的状态与渲染顺序：

- `activeId` 变化后，副作用（`useEffect`，`:196-245`）在**首帧绘制之后**才执行：清空 `source`、把 `sourceStatus` 设为 `loading`、清空姿势/裁剪/历史，并重置 `fitActive` 与 `pan`（`:197-211`）。
- 渲染条件只检查 `source && sourceStatus === "ready"`（`:839`），没有检查 `source.imageId === activeId`。因此切换图片后的第一帧仍可能使用上一张的 `source`；随后副作用把 `source` 置空，画面才切换到加载态。
- `source` 为空期间，画布只显示整块加载态“正在读取原图 / 大图可能需要生成预览…”（`:815-821`）；此时没有任何占位图，切换到下一张会先白一下。
- `source` 就绪后，`<img>` 挂载并等待浏览器解码；`zoom` 由另一个副作用设置（`:281-286`），同样是首帧之后执行。缓存图可能在第一帧以 `zoom = 1` 显示，随后才缩到适应窗口。
- 高清图未加载完时，画布中央显示 `viewer-image-loading` 小 spinner（`:912-916`）；加载失败显示整块错误与“重新加载”（`:918-935`）。
- 左侧工具面板在 `source && geometry` 就绪前显示“正在准备查看器…”（`:768-800`），这属于工具区，不是画布加载态。

结论：闪烁不只来自“没有缩略图占位”，还来自两处时序——旧 source 在新 `activeId` 的首帧仍可见、拟合缩放晚一帧生效。

### 2.3 缩略图是否适合做占位

- 缩略图最长边 512px、严格保持原图宽高比（`thumbnail.rs:12-38`、`:72-84`）；导入时解码已应用 EXIF 方向，数据库 `width/height` 与缩略图方向一致。
- 会话项已经带 `width`、`height`、`thumbVersion`、`format`（`src/shared/viewerSession.ts:5-16`），`LibraryView` 直接把 `ImageRow` 作为会话项（`src/modules/library/LibraryView.tsx:1471-1477`）。因此不需要新增 DTO。
- 大图预览是 `fit_within(width, height, 4096)`（`viewer.rs:145-153`），与原图同比例；用它作为占位尺寸，高清层到达后只需按真实 `displayWidth/displayHeight` 重算，宽高比不变。
- 现有适应窗口计算 `fitZoom` 只依赖 `displayWidth/displayHeight`、旋转次数与视口（`src/modules/viewer/model.ts:271-290`）。把它拆成“按尺寸计算”的纯函数即可在没有 `ViewerSource` 时先算占位缩放。

结论：512px 缩略图适合作为渐进层；占位尺寸可直接用会话项的 `width/height`，不需要新字段。

### 2.4 取图、预览缓存与 `img://`

- `get_viewer_source` 已经是异步命令：先取当前图库句柄，再把 `viewer::source` 放进 `spawn_blocking`（`src-tauri/src/app/commands.rs:702-714`）。这次异步化在 2026-10-27 批次 6 完成，计划核对表里“命令内同步生成”的描述已过时。
- `viewer::source` 在需要预览时同步调用 `ensure_preview`（`viewer.rs:96-101`、`:145-167`）：已存在直接返回，不存在才解码、缩放、编码 WebP，再原子写入 `temp/viewer/<id>-<hash>.webp`（`:138-143`、`:221-238`）。
- 预览缓存单次会话上限 2GB，累计写入每满 256MB 按 mtime 清理（`viewer.rs:21-27`、`:169-219`）；查看路径本身不扫目录。
- `img://preview/<id>` 目前只读取预览文件（`src-tauri/src/app/img_protocol.rs:62-75`）；文件缺失返回 404，前端显示“这张图片打不开”，点“重新加载”会重新走 `get_viewer_source` 才能再生成（`ImageViewer.tsx:918-935`）。
- `img://` 协议本身已在 `spawn_blocking` 中执行（`img_protocol.rs:27-34`），不会阻塞窗口事件循环。

结论：窗口事件循环不会被预览生成卡住；用户感知的“卡住”主要来自空白等待。本批次用缩略层覆盖这段等待，并补“预览文件缺失时协议自己兜底生成”。

### 2.5 网格、列表与格式信息

- 网格格子是纯图，格式只在 `title` 里（`VirtualGrid.tsx:278-280`）；列表缩略图 30×30（`src/styles/index.css:1822-1828`），格式列显示 `GIF` 文本（`VirtualList.tsx:281`）。
- `LibraryThumbnail` 被网格、列表与“找相似”参考图共用（`src/modules/library/FindSimilarPanel.tsx:416-421`），在它内部加角标可以一次覆盖这三处；胶片带与详情缩略图使用自己的 `<img>`（`src/modules/viewer/Filmstrip.tsx:103-109`、`src/modules/library/Inspector.tsx:583`），不在本批次范围。
- 现有缩略图失败态会替换整块内容（`LibraryThumbnail.tsx:48-75`），角标不应覆盖失败占位。

### 2.6 与反馈的对应

- 编号 2：查看器已经播放 GIF，网格/列表始终静态，编辑会丢动画。本批次补“静态首帧”的可见标识与“大 GIF 已转静态预览”的说明，不承诺动图缩略图。
- 编号 4：切换时先清空 `source`、整块加载态、没有缩略图占位，且旧 source 可能多留一帧。本批次同时解决占位、淡入与切换时序，而不只是加一层图片。

## 三、目标行为

### 3.1 GIF

1. ≤24MP、无方向问题的 GIF 在查看器中继续播放动画，行为不变。
2. 超过 24MP 的 GIF 走静态 WebP 预览；工具面板显示“已生成静态预览，动画不可用；保存仍读取原图。”，状态栏显示“静态预览 · 动画不可用”，不再只写“降采样预览”。
3. 网格、列表与“找相似”参考缩略图对 GIF 显示角标 `GIF`；角标只做标识，不播放动画，不改变格子尺寸。
4. 网格格子与列表格式列的 `title` 明确“GIF 动图，仅在查看器中播放”。
5. 编辑 GIF 仍只保留首帧，现有警告保留；本批次不禁止编辑动图。
6. 原图缺失、预览生成失败仍走现有错误态与重试，不把错误伪装成静态预览。

### 3.2 渐进加载

1. 切换图片时立即渲染该图片的缩略图层，按原图宽高比、适应窗口的缩放与居中位置占位；画布不再先白一下。
2. 高清层加载完成后用短淡入覆盖缩略图层；缩略图层保留到高清层首帧绘制完成再隐藏，位置与尺寸不跳动。
3. 快速加载（缓存命中）不出现加载态；超过 150ms 仍加载才显示小 spinner；有缩略图时不显示整块“正在读取原图”。
4. 无缩略图或缩略图加载失败时回到现有整块加载态；取图失败显示现有错误态；高清层失败显示现有“这张图片打不开”与重新加载。
5. 缩放、平移、旋转、裁剪选区、姿势叠加对缩略图层与高清层使用同一套显示尺寸和变换；编辑坐标只按 `ViewerSource` 换算，不使用占位尺寸。
6. 切换、重试、404 后缩略图、高清层、姿势、裁剪、缩放与平移都按当前图片复位，不残留上一张的状态。
7. 有 alpha 的高清图不做交叉淡入，加载完成直接换层，避免透明区域透出缩略图。
8. 不预加载相邻图片；不改变翻页、胶片带与全屏行为。

## 四、实现落点

### 4.1 查看器纯函数：按尺寸拟合与 GIF 静态预览判断

`src/modules/viewer/model.ts`：

```ts
export function fitZoomForSize(
  width: number,
  height: number,
  rotate: number,
  viewportWidth: number,
  viewportHeight: number,
): number {
  const size = transformedSize(width, height, rotate);
  if (size.width <= 0 || size.height <= 0 || viewportWidth <= 0 || viewportHeight <= 0) {
    return 1;
  }
  const padding = 72;
  return clamp(
    Math.min(
      (viewportWidth - padding) / size.width,
      (viewportHeight - padding) / size.height,
    ),
    0.02,
    1,
  );
}

/** 现有调用点保持不变；占位阶段直接传会话项的宽高。 */
export function fitZoom(
  source: ViewerSource,
  rotate: number,
  viewportWidth: number,
  viewportHeight: number,
): number {
  return fitZoomForSize(
    source.displayWidth,
    source.displayHeight,
    rotate,
    viewportWidth,
    viewportHeight,
  );
}

/** GIF 走 Rust 静态预览时，动画不可用。 */
export function gifStaticPreview(
  source: Pick<ViewerSource, "format" | "preview"> | null | undefined,
): boolean {
  return source?.format === "gif" && source.preview === true;
}

/** 占位按原图尺寸、高清按降采样尺寸时，用手动缩放保持屏幕上的实际大小。 */
export function rescaleZoom(
  zoom: number,
  previousDisplayWidth: number,
  nextDisplayWidth: number,
): number {
  if (previousDisplayWidth <= 0 || nextDisplayWidth <= 0) return zoom;
  return clamp(
    zoom * (previousDisplayWidth / nextDisplayWidth),
    0.02,
    8,
  );
}
```

- `fitZoomForSize` 不依赖 `ViewerSource`，供“只有会话项、还没有 source”的阶段使用。
- 占位宽高用 `item.width/height`；预览与原图同比例，默认适应窗口时屏幕上的显示尺寸不随尺寸切换变化。
- `rescaleZoom` 只处理“用户在占位阶段手动缩放、随后高清层换成降采样尺寸”的情况：`displayWidth` 变小，缩放值按比例放大，屏幕上的实际大小不变。默认适应（`fitActive`）不走它，直接按新尺寸重算 `fit`。
- `gifStaticPreview` 只回答“是否 GIF 且使用了静态预览”，不负责生成文案；文案留在查看器组件。

### 4.2 查看器状态：按 `activeId` 归属，避免旧状态串入

`src/modules/viewer/ImageViewer.tsx` 建议把“某张图的加载结果”与“当前活动图”绑定，而不是继续用一组彼此独立的 state：

```ts
type LoadState =
  | { imageId: number; status: "loading" }
  | { imageId: number; status: "error"; error: string }
  | { imageId: number; status: "ready"; source: ViewerSource };

const [load, setLoad] = useState<LoadState>({
  imageId: session.initialId,
  status: "loading",
});
const activeLoad =
  load.imageId === activeId ? load : { imageId: activeId, status: "loading" as const };
const source = activeLoad.status === "ready" ? activeLoad.source : null;
const sourceError = activeLoad.status === "error" ? activeLoad.error : null;
```

媒体状态同样带 id：

```ts
interface MediaState {
  imageId: number;
  loaded: boolean;
  failed: boolean;
  thumbFailed: boolean;
}

const initialMedia = (imageId: number): MediaState => ({
  imageId,
  loaded: false,
  failed: false,
  thumbFailed: false,
});

const [media, setMedia] = useState<MediaState>(initialMedia(session.initialId));
const activeMedia =
  media.imageId === activeId ? media : initialMedia(activeId);
```

取图副作用：

- 开始时 `setLoad({ imageId: activeId, status: "loading" })`，同时重置姿势、裁剪、撤销历史、`pendingStep`，并清空 `cropStart` / `dragRef` 指针手势；这些写入仍然可以放在 `useEffect`，因为渲染已按 id 过滤，不会显示旧 source。
- 媒体状态用函数式更新复位：`setMedia((current) => current.imageId === activeId ? current : initialMedia(activeId))`。不能用无条件 `setMedia(initialMedia(activeId))`：缓存图可能在副作用执行前就触发 `onLoad`，随后这次复位会把“已加载”覆盖回未加载，spinner 不再消失。
- 成功时只在仍为同一 `activeId` 时写 `{ imageId, status: "ready", source }`；失败写 `{ imageId, status: "error", error }`。
- 现有 `disposed` 清理与 `reloadToken/retry` 依赖保留；重试时在点击处理器里先同步写 `media` 为当前 id 的初始值，再递增 `retry`，这样缩略图立即回来，不必等副作用。重试是同一个 imageId 的主动复位，允许无条件写。
- `resetHistory(initialGeometry(next))` 仍在成功回调里执行；渲染时用 `const geometry = source ? history.geometry : null`，加载阶段不读取上一张的几何状态。

拟合与复位改为 layout effect：

```ts
const item = items.find((entry) => entry.id === activeId);
const displayWidth = source?.displayWidth ?? item?.width ?? 0;
const displayHeight = source?.displayHeight ?? item?.height ?? 0;
const rotate = source && geometry ? geometry.rotate : 0;
const fit = fitZoomForSize(
  displayWidth,
  displayHeight,
  rotate,
  viewport.width,
  viewport.height,
);

useLayoutEffect(() => {
  setFitActive(true);
  setPan({ x: 0, y: 0 });
}, [activeId]);

useLayoutEffect(() => {
  if (fitActive) {
    setZoom(fit);
    setPan({ x: 0, y: 0 });
  }
}, [fitActive, fit]);

const placeholderWidthRef = useRef(0);
useLayoutEffect(() => {
  if (source == null && item) placeholderWidthRef.current = item.width;
}, [source, item]);
```

- 两个 `useLayoutEffect` 都在绘制前把新图的缩放与平移准备好，缓存图不会先以 100% 闪一帧。
- 视口尺寸的第一次测量也要在绘制前完成：保留现有 `ResizeObserver` 负责后续变化，但挂载时先在 layout effect 里读一次 `clientWidth/clientHeight`。否则 `viewport` 还是 0 时 `fitZoomForSize` 返回 1，缩略层会先以 100% 尺寸画一帧。
- 现有“视口尺寸变化后重算适应”的行为不变；用户已经手动缩放（`fitActive = false`）时，切图会按现有逻辑回到适应。
- `fitActive` 与 `pan` 的复位从原来的 `useEffect` 移到 layout effect；取图副作用中对应的两行删除，避免两处竞争。
- 大图的手动缩放：用 `placeholderWidthRef` 记录“当前没有 source 时实际用于布局的宽度”（`item.width`），并把 `fitActive` 同步到 `fitActiveRef`（与现有 `activeIdRef` 同法，每次渲染同步）。取图成功、准备写入 `ready` 之前，如果 `fitActiveRef.current === false` 且占位宽度大于 0，调用 `setZoom((value) => rescaleZoom(value, placeholderWidthRef.current, next.displayWidth))`；这样从原图占位切到 4096px 预览时，屏幕上的实际大小不变。`fitActive` 为 true 时不做换算，直接按新的 `displayWidth` 重算 `fit`。

渲染与交互的占位尺寸：

```ts
const thumbItem = item != null && !activeMedia.thumbFailed ? item : null;
const hasThumb = thumbItem != null;
const hasFrame = source != null || hasThumb;
const showStage = hasFrame && activeLoad.status !== "error" && !activeMedia.failed;
const cropping = source != null && cropMode;
const poseVisible = source != null && poseOpen && pose != null && hasPose;
const fullSize = transformedSize(displayWidth, displayHeight, rotate);
const appliedCrop = source != null && !cropping ? geometry?.crop ?? null : null;
```

- 画布只有在 `showStage` 时渲染 `viewer-pan/clip/stage/image-wrap`；否则保留现有整块加载态或错误态。
- `thumbItem` 让 TypeScript 在 JSX 中完成非空收窄，不能再依赖布尔量 `hasThumb` 去访问 `item.id`。
- `cropping` 与 `poseVisible` 把上一张的裁剪/姿势挡在当前 `source` 之外；`cropMode`、`poseOpen` 的存储值仍可在副作用里复位，但渲染首帧不会透出旧覆盖物。
- `handlePointerDown` 的平移分支与滚轮缩放改为只要 `showStage` 就允许，这样缩略图层阶段也能平移/缩放；裁剪分支仍要求 `source && cropping`。
- 所有裁剪、输出尺寸、编辑请求继续只使用 `source` 的 `width/displayWidth`（`cropToOriginal`、`outputSize` 等），占位宽高不得进入编辑换算。

### 4.3 画布结构：缩略图层在下，高清层在上

`viewer-image-wrap` 内同时放两层，缩略图层常驻到高清层首帧完成：

```tsx
<div
  className={`viewer-image-wrap${source?.hasAlpha ? " is-alpha" : ""}`}
  style={{
    width: displayWidth * zoom,
    height: displayHeight * zoom,
    transform: imageTransform,
  }}
>
  {thumbItem ? (
    <img
      className={`viewer-thumb-layer${activeMedia.loaded ? " is-retired" : ""}`}
      src={thumbnailUrl(thumbItem.id, thumbItem.thumbVersion)}
      alt=""
      draggable={false}
      onError={() => {
        if (activeIdRef.current !== activeId) return;
        setMedia((current) => ({
          ...(current.imageId === activeId ? current : initialMedia(activeId)),
          thumbFailed: true,
        }));
      }}
    />
  ) : null}

  {source ? (
    <img
      className={`viewer-image${activeMedia.loaded ? " is-loaded" : ""}`}
      src={withRetry(source.url, retry)}
      alt=""
      draggable={false}
      style={{ imageOrientation: "from-image" }}
      onLoad={() => {
        if (activeIdRef.current !== activeId) return;
        setMedia((current) => ({
          ...(current.imageId === activeId ? current : initialMedia(activeId)),
          loaded: true,
          failed: false,
        }));
      }}
      onError={() => {
        if (activeIdRef.current !== activeId) return;
        setMedia((current) => ({
          ...(current.imageId === activeId ? current : initialMedia(activeId)),
          loaded: false,
          failed: true,
        }));
      }}
    />
  ) : null}

  {poseVisible ? (
    <PoseOverlay
      pose={pose}
      width={source?.displayWidth ?? displayWidth}
      height={source?.displayHeight ?? displayHeight}
      zoom={zoom}
      opacity={poseOpacity}
    />
  ) : null}
</div>
```

说明：

- 缩略图层与高清层都放在同一个 `viewer-image-wrap` 里，因此旋转/翻转、缩放、平移、裁剪（由外层 clip/stage 负责）自动作用于两层，不需要第二套坐标。
- 高清层 `onLoad` 后加 `is-loaded` 触发短淡入；缩略层同时加 `is-retired`，由 CSS 在淡入结束后隐藏（见 4.4），不需要 React 定时器。缩略层保持挂载但透明，避免首帧之间出现空白。
- 不要在高清层 `onLoad` 的同一次渲染里直接卸载缩略层，否则淡入的第一帧会从画布背景开始。
- `onLoad` / `onError` 回调都用 `activeIdRef.current` 复核，防止已卸载的旧图片把新图片的媒体状态覆盖成旧 id；状态本身用 `initialMedia(activeId)` + 函数式更新，不在回调里展开渲染时的 `activeMedia`，否则会丢掉同一次渲染之后发生的 `thumbFailed`。
- 缩略图层的 `onError` 只影响占位；高清层仍会继续加载，避免因为缩略图包缺失把可看的原图判成失败。
- 占位阶段 `poseVisible` 为 false（没有 `source`），上一张的姿势不会挂到缩略层上；source 到达后姿势叠加仍按 `source.displayWidth/Height` 与 `zoom` 绘制，与现有行为一致。
- 画布外的姿势面板、画布 `is-cropping` 类、裁剪框 `overlayRect` 与 Esc 的“先退出裁剪/姿势”判断也改用 `poseVisible` / `cropping`；否则切换后的第一帧仍可能显示或响应上一张的裁剪/姿势状态。

### 4.5 延迟 spinner 与加载/错误态

在查看器内增加一个 150ms 的延迟标志，不新增全局 Hook：

```ts
const waitingForSource = activeLoad.status === "loading" && hasThumb;
const waitingForHighRes =
  source != null && !activeMedia.loaded && !activeMedia.failed;
const delayable = waitingForSource || (waitingForHighRes && hasThumb);

const [slow, setSlow] = useState(false);
useEffect(() => {
  setSlow(false);
  if (!delayable) return;
  const timer = window.setTimeout(() => setSlow(true), 150);
  return () => window.clearTimeout(timer);
}, [delayable, activeId, retry]);

const showSmallSpinner =
  waitingForHighRes && !hasThumb ? true : delayable && slow;
```

渲染规则：

- `activeLoad.status === "loading" && !hasThumb`：保留现有整块加载态（`:815-821`）。
- `showSmallSpinner` 为 true：只显示现有 `viewer-image-loading` 小 spinner（`:912-916`），不显示整块文案。
- `source && activeMedia.loaded`：不显示 spinner。
- `activeLoad.status === "error"`：显示现有错误块与重试（`:823-837`），不渲染缩略层与高清层。
- `source && activeMedia.failed`：显示现有“这张图片打不开”与“重新加载”（`:918-935`）。
- 两个重试入口共用一个 `retryLoad()`：先同步写 `load = { imageId: activeId, status: "loading" }` 并把 `media` 复位为当前 id 的初始值，再递增 `retry`，避免错误块和失败层多留一帧。
- 缩略图失败（`thumbFailed`）且 source 仍在加载时，`hasThumb` 变 false，按无缩略图处理，回到整块加载态；source 已就绪但高清层还没加载时，无缩略图则立即显示小 spinner（没有可展示的占位，不需要再等 150ms）。
- 这是“缩略图不可用”而不是原图错误，不应把 `thumbFailed` 当成取图失败。

这样“有缩略图时不显示整块加载态”“延迟 150ms 才显示 spinner”和“失败才回到错误态”三条规则都有明确条件，不会同时出现两个加载提示。

```rust
/// 供 `img://preview` 使用：已有文件直接返回，缺失时按当前行重新生成。
pub(crate) fn ensure_preview_file(
    paths: &LibraryPaths,
    row: &ContentRow,
) -> AppResult<PathBuf> {
    let target = preview_path(paths, row.id, &row.content_hash);
    if target.is_file() {
        return Ok(target);
    }
    let source = row.path(paths)?;
    if !source.is_file() {
        return Err(AppError::message("原图文件不存在，可能已被外部移动或删除"));
    }
    ensure_preview(paths, row, &source)?;
    Ok(target)
}
```

2. 切换到列表视图：30px 缩略图上有缩小版 `GIF` 角标；悬停格式列显示同一说明。
3. 打开“找相似”面板，参考缩略图中的 GIF 也带角标；角标不影响点击与拖动。
4. 滚动网格、切换筛选与排序：角标不出现在非 GIF 上，缩略图加载失败的格子只有重试按钮，没有角标。

### 7.2 查看器 GIF

1. ≤24MP 的 GIF：查看器播放动画；工具面板只有“编辑 GIF 只会保留首帧”的现有提示，没有“动画不可用”。
2. 若测试库有超过 2400 万像素的 GIF（例如 5000×5000、两帧；没有样本时先用图像工具在临时目录生成再导入）：查看器显示静态画面；工具面板出现“已生成静态预览，动画不可用；保存仍读取原图。”，状态栏出现“静态预览 · 动画不可用”。
3. 对上面的大 GIF 进入裁剪/旋转：坐标与静态预览一致；保存时仍只保留首帧。
4. 原图删除后重新打开：显示现有“无法打开图片”错误；重试后仍失败，不显示假的静态预览说明。

### 7.3 快速切换与渐进加载

1. 在已有缩略图缓存的网格中快速按 ←/→ 切换 10–20 张：每次立即看到新图的缩略图，不出现空白画布，不出现整块“正在读取原图”。
2. 切换瞬间不应看到上一张的高清图停留一帧；不应看到新图先以 100% 尺寸闪一下再缩到适应窗口。
3. 缩略图到高清图的替换没有位置跳动；高清层出现时没有第二次闪烁。
4. 用胶片带切换与用键盘切换表现一致。

### 7.4 慢速大图与加载态

1. 打开一张首次查看的大图或非浏览器原生格式：缩略图先出现；150ms 内画布不出现 spinner；超过 150ms 才出现画布中央的小 spinner，且没有整块加载文案。左侧工具面板在 source 就绪前仍显示“正在准备查看器…”，这是工具区，不计入画布加载态。
2. 在缩略图阶段滚轮缩放、拖拽平移：缩略图跟随；高清层加载完成后保持同样的缩放与位置。
3. 大图生成预览期间窗口仍可操作（顶栏、下一张、侧栏按钮可点）；预览完成后工具面板从“正在准备查看器…”恢复。
4. 全屏模式下重复上述步骤，行为一致。

### 7.5 一致性、失败与重试

1. 加载完成后旋转、翻转、裁剪、显示姿势骨架：缩略层已退役，高清层与覆盖物对齐；裁剪框尺寸与图像尺寸一致。
2. 打开一张有透明区域的 PNG：高清层出现时不应透出缩略图；如仍有残影，记录图片与复现步骤。
3. 把当前图的原图移走或改坏，切换离开再切回：出现现有“无法打开图片”错误；恢复文件后点“重试”应能重新打开，不残留旧缩略层或旧姿势。
4. 协议兜底（可选，难以稳定复现）：在切换到大图的同一时刻删除测试库 `.artbank/temp/viewer/` 中对应的预览文件，使 `<img>` 请求先于重新生成；画面应能恢复，而不是一直 404。做不到稳定复现时以单元测试为准，并在实现记录里写“协议兜底未手工覆盖”。
5. 编辑保存一张图：查看器重新载入后使用新的 `thumbVersion` 占位；旧图内容不应在切换后残留。

## 八、风险、边界与后续

- **占位比例与数据库一致**：占位宽高来自会话项；若数据库宽高与实际文件不一致（外部换文件未重新导入），source 到达后画面会按真实比例修正。这是可接受的过渡，不在本批次引入二次探测。
- **缩略图缺失**：缩略图 404 或包损坏时没有可用的渐进层，回到整块加载态；不能为了“看起来渐进”用空白图或上一张缩略图冒充。
- **透明图残影**：有 alpha 时关闭交叉淡入，直接换层；这是本批次对“短淡入”的唯一例外，避免透明区域透出缩略图。
- **z-index 绘制顺序**：缩略层是绝对定位，高清层必须显式定位或抬高层级，否则缩略层可能盖住高清层；姿势层再高一档。CSS 改动后要在真实窗口检查裁剪框、姿势线与两层的关系。
- **切换首帧**：source 按 id 过滤、layout effect 拟合复位是“无旧图一帧、无 100% 闪帧”的关键；如果只加缩略层而不改这两处，用户仍可能看到旧图或闪缩。手工验收要专门盯切换的第一帧。
- **不预加载**：缩略图未缓存的图片仍可能先显示骨架色再出现缩略图；这是浏览器缓存与网格预载的自然结果，不引入相邻图预加载。
- **性能**：本批次不新增全量扫描或额外磁盘 IO。缩略层复用网格已经请求过的 `thumb://` 资源，高清层仍只请求一次原图/预览；不新增基准。若真实窗口发现切换变慢，再单独测 `<img>` 请求与解码耗时，不先改算法。
- **大 GIF 预览生成时间**：`get_viewer_source` 仍是预览的主生成路径，缩略图层只改善等待观感；协议只在文件缺失时兜底，避免常规查看路径变成两处解码与两套错误口径。
- **协议兜底的并发**：预览缺失时由协议生成，两个并发请求可能同时解码同一张图；现有 `write_preview` 用唯一临时文件与原子重命名处理冲突，不新增锁。批次 5 若引入路径读锁，再按资源矩阵接入。
- **角标可读性**：列表缩略图只有 30px，7px 的 `GIF` 角标可能偏小；先按共用组件实现，真实窗口验收后若不可读，改为格式列追加“动图”标签，不放大缩略图。
- **GIF 静态提示只在普通模式可见**：全屏会隐藏工具面板与状态栏，大 GIF 的“动画不可用”说明在全屏不可见。本批次不在画布上再加一层提示；若用户认为全屏也需要，后续用与网格一致的 `GIF` 角标补。
- **GIF 编辑**：仍只保留首帧；是否禁止编辑动图是计划中的待决策项，本批次不改。
- **不做**：不在网格播放动图；不新增 GIF/APNG 解码器；不改变编辑输出格式；不预加载相邻图片；不改 `DataChange`、任务进度、并发锁或数据库。
- **文档同步**：实现后更新 `docs/modules/viewer-and-editor.md`（查看器显示与导航 `:14`、协议 `:17`、GIF 输出 `:33`，新增渐进层与静态预览说明）、`docs/modules/browse-and-query.md`（缩略图条目 `:295-296` 的角标与 title）。`docs/modules/import.md:11` 的“GIF（首帧）”不变，可补一句“网格/列表缩略图为首帧静态”。同时在 `docs/planning/todo.md` 增加真实窗口验收项，验收通过后再写“已完成”。

与准备稿的差异：

- 三处 `setMedia` 的重复展开合并为组件内的 `patchMedia(imageId, patch)`，仍按 id 归属，行为不变。
- 占位宽度没有单独用 ref 保存，而是在取图效果开始时读取当时的 `sourceRef` 与 `itemsRef`：切换图片时 `source` 已按 id 过滤为空，直接读会话项宽高；同一张图重试或保存后重载时 `source` 不为空，不做换算。
- 保存成功后显式回到适应窗口：新内容尺寸与裁剪可能变化，不再沿用旧的缩放与平移；旧实现是在每次取图副作用里复位，切图与重试现在的复位规则按本文 4.2。
