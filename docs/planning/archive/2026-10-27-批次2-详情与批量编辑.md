# 使用反馈整改 批次 2：详情与批量编辑

日期：2026-10-27
状态：已实现并归档；自动检查通过，等待用户手工验收。本文件保留已确认决策、实现方案、前置测量、实现记录与验收口径。正文行号为准备阶段快照，实现后已变化。

范围对应《[使用反馈整改计划](2026-10-27-使用反馈整改计划.md)》的编号 1、3。批次 2 只做详情布局、描述编辑态、主色展示、批量标签与导入标签输入；不改标签 schema、不改批量操作的撤销记录粒度、不做标签层级或 MCP 标签管理。

## 已确认决策

| 问题 | 结论 |
| --- | --- |
| 描述什么时候写入数据库 | 只点“保存”（或 Ctrl/Cmd+Enter）才写入；失焦、切换区块都不保存；“取消”明确丢弃草稿。 |
| 描述编辑态里的 AI 生成 | 沿用现有后端：AI 文本直接写入并保留 `ai` 来源，成功后回到只读并提示已保存；取消只丢弃手工草稿。 |
| AI 生成会覆盖未保存草稿时 | 先确认“会覆盖当前未保存的描述修改”；确认后才调用 AI。 |
| 已有手写描述时的 AI 生成 | 禁用按钮并说明“已有手写描述，AI 不会覆盖”（后端本来就拒绝覆盖）。 |
| 空描述 | 只读态显示“还没有描述”，保留“编辑描述”；不显示来源标签。 |
| 切换图片时的草稿 | 未保存描述按图片 id 暂存在当前详情组件内；切走再回来恢复编辑态；关闭侧栏才整体丢弃。 |
| 批量移除标签的候选 | 同时列出“全部选中图片都有”的共同标签和“部分图片有”的标签，并显示 `拥有数/选中数`。 |
| 批量移除的点击语义 | 点共同标签从全部选中图片移除；点部分标签只从拥有它的那些图片移除（后端对没有该标签的图片是 no-op）。每次点击一条操作记录，可撤销。 |
| 标签输入方式 | 三处统一为 chip 编辑器：输入框逐个提交标签、自动补全、去重、可移除 chip；**不把逗号、分号、空格当分隔符**，标签名里允许这些字符。 |
| 标签数量上限 | 详情单图最多 64 个（含已有）；批量添加一次最多 64 个；导入初始标签最多 32 个（后端既有上限）。 |
| 主色点击 | 点击色块复制 `#RRGGBB`；悬停 `title` 与 `aria-label` 显示 `#RRGGBB · 百分比 · rgb(...)`。 |
| 详情顺序 | 评分、标签、主色、文件夹、描述、文件；临时视图隐藏文件夹，其余顺序不变。 |

## 一、现状

### 1.1 详情信息栏的顺序

`ImageInspector` 当前渲染顺序（`src/modules/library/Inspector.tsx`）：

1. 缩略图与尺寸/格式/大小/透明信息（`:463`、`:479`）
2. 评分（`:486`）
3. 标签（`:515`）
4. 描述（`:652`）
5. 文件夹（`:705`，`inTemp` 时隐藏）
6. 主色（`:759`）
7. 文件（`:767`）
8. 临时提示或回收站/集合操作（`:792`）

反馈要求顺序为评分、标签、主色、文件夹、描述、文件。当前主色在文件夹之后、描述在文件夹之前，两项都要移动。

查看器侧栏复用同一个 `InspectorPanel`（`src/app/ViewerHost.tsx:117`），所以详情顺序、描述编辑态与主色展示会同时影响主界面侧栏和查看器侧栏。

### 1.2 描述编辑

- 描述始终是一个 `textarea`（`:659`），下方常驻“保存描述”“AI 生成”“复制描述”三个动作（`:672-701`）。
- 保存只比较 `descriptionDraft.trim()` 与 `detail.description.trim()`（`:280-294`）；保存后没有就地更新 `detail.description`，依赖 `version` 变化重新取详情。
- `getImageDetail` 的 effect 依赖 `[imageId, version]`，每次数据变化都会 `setDescriptionDraft(next.description)`（`:212-235`）。批次 1 让评分/标签/描述等写入都会推进 `detailVersion`（`src/modules/library/LibraryView.tsx:600`、`:2432`），因此后台变化或一次评分都会把正在编辑的描述草稿替换掉。
- AI 生成调用 `ai_describe_image`（`:296-327`），后端在 `src-tauri/src/ai/runtime.rs:492-531` 直接写入 `set_ai_description`；手写描述不会被覆盖（`src-tauri/src/library/metadata.rs:392-510`）。成功后前端更新 `detail` 与草稿并通知图库；当前没有“AI 成功后退出编辑态”的概念。
- `descriptionSource` 默认是 `user`（`src-tauri/src/library/schema.rs:43-46`），空描述也会显示“手工”来源（`:657`）。

### 1.3 主色

- `ColorRow` 把 4 色与 8 色都渲染成等宽色块（`:823-841`）；CSS 为 `.color-swatch { flex: 1; min-width: 14px }`（`src/styles/index.css:2995-3001`），所以比例不可见。
- 精确百分比只放在 `title` 里（`:832-834`），没有点击行为。
- 主色权重是每个 palette 内部按最大余数法合计 255（`src-tauri/src/imageops/colors.rs:12`、`:134-170`）；`parse_palette` 固定返回 4/8 项（`src-tauri/src/library/metadata.rs:222-232`），颜色簇不足时会出现权重为 0 的占位项。当前这些 0 权重项也会以最小宽度显示，看起来像存在该颜色。

### 1.4 批量标签

- 批量编辑侧栏（`BatchInspector`，`:843` 起）只有两个文本框：添加标签与移除标签，都用 `splitTags` 按 `,，;；\n` 拆分（`:917-921`），提示文案是“用逗号分隔多个标签”（`:1064`、`:1088`）。
- 移除标签没有读取选中图片的现有标签：用户必须自己记住并输入标签名；后端 `remove_tags_from_images` 对选中集合逐标签删除（`src-tauri/src/library/metadata.rs:689-760`）。
- 添加标签走 `add_tags_to_images`，会创建不存在的标签（`src-tauri/src/library/metadata.rs:582-679`），一次调用一条操作记录。
- 目前没有任何“读取一次选中集合的标签及计数”的后端能力。`get_image_detail` 只返回单张标签（`src-tauri/src/library/metadata.rs:112-220`），逐张读取对几万张选择不可行。
- `BatchInspector` 不接收数据版本，只在自身操作成功后清空输入；外部标签变化、标签改名/删除时不会刷新候选。
- 批量标签写入的变化对象已经带 `fields: ["tags"]` 与 `tagAction`（`:923-965`），批次 1 的 `planDataChange` 会按变化刷新列表/选择/分面/详情（`src/modules/library/dataChange.ts:178-215`），但不会单独推进“标签候选”版本。

### 1.5 导入标签

- `ImportDialog` 用 `tagsText` 字符串保存初始标签（`src/modules/import/ImportDialog.tsx:104`），打开时清零（`:157`），提交时用 `parseTags` 按 `[,，;；\s]+` 拆分（`:53-58`、`:288`）。

## 二、目标行为

### 2.1 详情顺序

单张详情固定为：

1. 评分
2. 标签
3. 主色（4 色、8 色两行）
4. 文件夹（`inTemp` 时隐藏）
5. 描述
6. 文件
7. 临时提示 / 回收站、集合操作

批量编辑的区块顺序不变（评分、添加标签、移除标签、文件夹、集合、操作），只替换标签输入与移除候选。

### 2.2 描述

只读态：

- 标题右侧只在描述非空时显示来源（`AI` / `导入` / `手工`）；描述为空时不显示来源。
- 正文用只读块展示，保留换行与空白，高度随内容自适应；空值显示“还没有描述”。
- 动作：`编辑描述`、`复制描述`（空描述时禁用复制）。

编辑态：

- 正文换成可调整高度的 `textarea`；`Ctrl/Cmd+Enter` 等同保存。
- 动作：`保存`（主按钮）、`AI 生成`（有回调且可用时）、`取消`、`复制描述`（复制当前草稿）。
- 保存只在点按钮或快捷键时发生；失焦不保存。
- 草稿与已保存文本不同时显示“未保存”标记。
- 保存成功后立即把 `detail.description` 乐观更新为 trim 后的文本、`descriptionSource = "user"`、`descriptionModel = ""`，删除草稿并退出编辑；随后 `version` 刷新只做兜底。
- 取消：删除该图草稿，回到已保存文本。
- 草稿按图片 id 保存在当前 `ImageInspector` 内。切到别的图片时草稿保留；切回来恢复编辑态。关闭详情侧栏时整体丢弃。数据版本刷新不会覆盖已有草稿；没有草稿时只读文本跟随 `detail.description`。

AI 生成：

- 只在编辑态显示。
- 无回调、`busy`、图片在回收站、或已有非空手写描述时禁用；手写描述时 `title` 说明“已有手写描述，AI 不会覆盖”。
- 草稿与已保存文本不同且点 AI 生成时，先用现有 `confirm` 确认“AI 生成会覆盖当前未保存的描述修改”。
- 成功后沿用后端直接写入的行为，更新 `detail` 与草稿，删除该图草稿，退出编辑态，提示“AI 描述已生成并保存”。
- 失败时留在编辑态，草稿不变。

### 2.3 主色

- 色块宽度按权重比例分配：`flex-grow = max(weight, 1)`、`flex-basis: 0`，最小宽度 14px；4 色与 8 色使用同一规则。
- 过滤 `weight === 0` 的占位颜色；过滤后没有颜色时显示“未计算”。
- 悬停与 `aria-label` 显示 `#RRGGBB · 百分比 · rgb(r, g, b)`；百分比按 `round(weight / 255 * 100)`。
- 色块改为 `<button type="button">`，点击复制 `#RRGGBB` 并提示“已复制颜色”；补充 `:focus-visible` 样式。
- 权重合计仍是 255 的语义，过滤 0 权重不改变百分比基数。

### 2.4 批量标签

新增一条只读查询，返回选中集合内每个标签的“拥有该标签的选中图片数”。前端在“移除标签”区块分成两组：

- **全部 N 张都有**：`count === total`，按名称排序；点击从全部选中图片移除。
- **部分图片有**：`count < total`，按拥有数从高到低、再按名称排序；默认折叠，展开后提供搜索框与可滚动的 chip 列表。每个 chip 显示 `名称` 与 `count/total` 计数；点击只从拥有该标签的图片中移除。
- `total` 使用去重后的选中 id 数（见 3.1 的边界说明）。
- 没有共同标签时显示“没有共同标签”，但部分标签仍可展开。
- 整个选中集合没有任何标签时显示“所选图片还没有标签”。
- 查询失败时显示“读取选中标签失败”与重试入口；不阻塞评分、文件夹等其它区块。
- 查询中显示加载态；已有结果时保留旧列表并显示轻量加载指示，不清空。

交互：

- 点击 chip 立即调用 `remove_tags_from_images(imageIds, [name])`；成功后从本地候选移除并触发刷新，失败则恢复并提示。
- 每次点击一条操作记录，可撤销；不做二次确认（操作可撤销，且计数已说明范围）。
- 点击期间禁用其它移除 chip，避免并发写入。

添加标签：

- 用统一 chip 编辑器暂存多个标签，点“添加”一次提交，一条操作记录。
- 不存在的标签沿用后端行为直接创建。
- 添加成功后清空暂存并刷新候选（通过 `tagVersion`）。
- 一次最多暂存 64 个；已达到上限时禁用输入并显示“最多 64 个”。

### 2.5 统一标签输入

新增 `src/shared/components/TagInput.tsx`，只做 UI，不直接调用 Tauri：

- 受控 `value: string[]`，渲染可移除 chip。
- 单行输入：`Enter` 或右侧加号把当前文本作为一个标签提交；**不按逗号、分号、空格拆分**。
- `trim`、忽略空串、按小写去重；`exclude` 中的标签不再提交或出现在建议里。
- 支持中文输入法组合态：`isComposing` 时回车不提交。
- 输入为空时 `Backspace` 删除最后一个 chip。
- 自动补全由外部注入 `searchSuggestions(query) => Promise<string[]>`；去抖 160ms，最多 12 条，过滤已选/排除项；点击建议即提交。
- `max` 控制 chip 数；达到上限时禁用输入并显示上限提示。
- 草稿模式可开启 `commitOnBlur`（批量添加、导入），保证点“添加/开始导入”时输入框里没回车的文本不会丢；详情即时模式不开启，避免误加。
- 不解析标签名里的任何分隔符；标签名允许空格、逗号等字符，最终由后端校验长度与控制字符。

三处用法：

- 详情：`value={[]}`，提交一个就用 `set_image_tags` 把“已有 + 新增”一次写入，立即生效；`exclude` 为已有标签，`max` 为 `64 - 已有数量`，不开启失焦提交。
- 批量添加：chip 暂存，点“添加”一次提交。
- 导入：chip 暂存，随导入请求提交；`max = 32`。

## 三、数据与接口

### 3.1 新增只读命令 `get_selection_tags`

在 `src-tauri/src/library/metadata.rs` 增加：

```rust
#[derive(Debug, Clone, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct SelectionTag {
    pub id: i64,
    pub name: String,
    /// 拥有该标签的选中图片数；不是全库数量。
    pub count: u64,
}

#[derive(Debug, Clone, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct SelectionTags {
    /// 去重后的选中图片数，用于判断“全部都有”。
    pub total: u64,
    pub tags: Vec<SelectionTag>,
}

pub fn selection_tags(database: &LibraryDb, image_ids: &[i64]) -> AppResult<SelectionTags>;
```

契约：

- `imageIds` 去重、校验正整数，最多 1,000,000 个；空数组返回 `{ total: 0, tags: [] }`。
- 返回选中集合内至少被一张图片拥有的标签；`count` 是选中集合内的数量。
- 排序：拥有数降序，再按标签名忽略大小写升序（在 Rust 侧用 `to_lowercase` 比较，不用 SQL `NOCASE`，后者只折叠 ASCII）。
- 不按回收站/临时区过滤：临时视图和回收站视图的选中标签都要能参与批量编辑。
- 不返回全库标签数量，也不改变 `list_tags` 的 500 上限。
- `total` 是去重后的请求 id 数。若个别 id 在请求前已被永久删除，计数会自然忽略它，`total` 可能偏大，结果只会少报共同标签，不会误报；调用方按批次 1 的契约应已清理失效 id。

算法（按选择规模在两条路径中选一条，避免 39 万次随机主键探测）：

1. 先读 `SELECT count(*) FROM image_tags` 得到关系总数。
2. 如果 `关系数 > 选中数 × 16`，选择相对较小：按 4000 个 id 一块执行
   `SELECT tag_id, count(*) FROM image_tags WHERE image_id IN (…) GROUP BY tag_id`，在 Rust 里合并计数。
3. 否则选择相对较大或关系表很小：构造 `HashSet<i64>`，扫描覆盖索引
   `SELECT image_id, tag_id FROM image_tags`，只在 `image_id` 属于选择时累加。真实库 46 万条关系的一次覆盖索引扫描约 20ms（SQL 侧），比 39 万次随机探测便宜。
4. 取出 `count > 0` 的标签 id，批量查 `tags.id/name`，组装并按 3.1 的规则排序。
5. 不做“存在图片数”的逐 id 查询：真实库实测这部分比标签聚合本身还慢（见四），而结果只用于判断共同标签；`total` 偏大只会少报共同标签，不会造成误删。

命令与适配：

- `src-tauri/src/app/state.rs` 增加 `pub fn selection_tags(&self, image_ids: &[i64]) -> AppResult<SelectionTags>`，走 `query_source()` 读连接，不改写连接。
- `src-tauri/src/app/commands.rs` 增加薄命令 `get_selection_tags` 并注册。
- `src/modules/library/api.ts` 增加 `getSelectionTags(imageIds)`；浏览器预览用 `mock.ts` 计算交集与计数。
- `src/modules/library/types.ts` 增加 `SelectionTag`、`SelectionTags`。
- 不新增写权限、不进入操作记录、不影响 MCP。

### 3.2 标签候选的刷新

新增一个只服务于批量标签候选的版本号，避免用 `detailVersion` 导致评分/描述变化也重算：

- `LibraryView` 增加 `tagVersion` 状态。
- `applyChanges` 中，只要本次变化满足 `touchesTags(change)`（`kind` 是 `tagCatalog` 或 `unknown`，或 `fields` 包含 `tags`），就递增 `tagVersion`。
- `InspectorPanel` 新增可选 `tagVersion` 并传给 `BatchInspector`；查看器侧栏只有单张详情，不传也不会触发。
- `BatchInspector` 的候选查询 effect 依赖 `[imageIds, tagVersion]`：
  - 选择变化或标签写入/改名/删除时重算；
  - 评分、描述、文件夹等变化不重算；
  - 120ms 去抖合并快速连点选择；
  - 用代次/`disposed` 丢弃过期响应；
  - 卸载或选择清空后忽略结果。

不把候选塞进批次 1 的 `DataChangePlan`：它是批量侧栏的局部展示状态，不是全局查询失效；用独立版本更简单，也不会让详情/列表多一次查询。

### 4.2 聚合耗时（Node 24.19 + `node:sqlite` 3.53.3，只读真实库）

这是实现前的 Node 只读测量，用于比较方案与量级；实现后的 Rust 基准见 4.3。

| 方案 | 10 | 100 | 1,000 | 5,000 | 20,000 | 50,000 | 100,000 | 200,000 | 390,542 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 按 id 分块（4000/块） | 0.1ms | 0.1ms | 3.1ms | 11.6ms | 35.8ms | 93.3ms | 191.6ms | 375.7ms | 692.3ms |
| 全表 `GROUP BY tag_id`（基线） | — | — | — | — | — | — | — | — | 19.5ms |

其他一次性连接方案在 390,542 选中下：

| 方案 | 中位耗时 | 备注 |
| --- | --- | --- |
| `json_each` 单查询 | 875.5ms | 需要 JSON 序列化 39 万 id |
| `json_each` + `JOIN` | 1,240.7ms | 同上 |
| 临时表 + `JOIN` | 654.7ms | 含 39 万行临时表插入 |
| 分块 + 逐块 `count(*)` 查存在 | 约 2,343ms | 存在性查询是大头，必须避免 |

结论：

- 小选择（几万以内）用分块主键探测已经足够快。
- 大选择用“扫描 `image_tags` + Rust `HashSet` 过滤”更稳；基线显示扫描 46 万条关系本身只要约 20ms（SQL 侧），Rust 逐行读取预计远低于分块 692ms。
- 因此实现采用 3.1 的混合路径；阈值最终取“关系数 > 选中数 × 16”，依据见 4.3 的 Rust 基准。
- 不自动在每次数据变化时重算：只随选择与 `tagVersion` 变化，并加 120ms 去抖与加载态。

### 4.3 实现后的 Rust 基准

`perf_metadata_200k` 追加了 `selection_tags`，同一 20 万行合成库、600,000 条标签关系（每图 3 个标签）、4 个读连接：

| 选中数 | 路径 | p50 | p95 |
| --- | --- | --- | --- |
| 2 | 分块探测 | 0.21 ms | 4.07 ms |
| 1,000 | 分块探测 | 3.13 ms | 12.13 ms |
| 20,000 | 分块探测（4,000/块） | 56.13 ms | 62.63 ms |
| 200,000 | 扫描 `image_tags` + Rust 过滤 | 204.95 ms | 211.89 ms |

阈值校准过程：同一基准下把阈值临时调到 8，20,000 选中走分块约 60 ms；调到 32，20,000 选中走扫描约 168 ms。最终取 16：让标签密度较高的 20,000 选中仍走分块，200,000 选中继续走扫描。真实库平均 1.46 个标签/图，全表扫描的交叉点更靠前；200,000 与 390,542 选中都会走扫描，符合 4.2 的预测量级。

## 八、边界、风险与后续

不做：

- 不改标签 schema、标签层级或分类；不改变标签/批量操作的撤销记录粒度。
- 不把“读取选中标签”做成写入或 MCP 工具；不放开 500 条标签列表上限。
- 不重写描述后端；AI 仍直接写入并保护手写描述。
- 不引入 UI 框架或全局状态库；不启动界面做代理侧验收。
- 不修复与本反馈无关的 `folderDraft` 被 `version` 刷新重置的问题；只修描述草稿。若要一起修，需单独确认。

风险与已知边角：

- `add_tags_to_images` 目前只校验一次提交的标签名数量，不校验每张图片加完后的总数是否超过 64；详情 `set_image_tags` 有 64 总数校验。批次 2 的 UI 上限不能保证每图总数不超 64，这是既有缺口，本批次不修，只记录；若需要严格上限，另开后端校验修复。
- 部分标签的点击只影响拥有它的图片；计数与 `title` 必须明确，避免用户以为从全部选中图片移除。
- 大选择候选查询是 O(关系数) 或 O(选中数)，最坏在几十万选中时仍有数百毫秒；用加载态、去抖与独立 `tagVersion` 控制触发频率。若实现后基准超预算，再评估按当前查询复用分面计数。
- 标签名允许空格/逗号后，从旧习惯粘贴“a,b”会得到一个标签；这是“用 UI 而不是文本分隔”的直接结果，需在验收时确认。
- 描述草稿按图片 id 留在 `ImageInspector` 内存中；关闭侧栏即丢弃。只有一张图时内存可忽略，但不要在详情组件外复制这套状态。
- 主色最小宽度会让极小权重略宽于真实比例；这是可读性取舍，精确值仍在 `title` 与点击复制的十六进制里。
- `selection_tags` 的 `total` 不逐个复核 id 是否存在；失效 id 只会让共同标签少报，不会误报。若未来需要在结果里显示“N 张已失效”，再补只读状态查询。
