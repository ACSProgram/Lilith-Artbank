## 已确认决策

| 问题 | 结论 |
| --- | --- |
| 长任务并发 | 导入、缩略图重建、AI、扫描、空间优化估算/执行、移动图片、永久删除、清空回收站、释放删除文件等长任务，冲突时自动排队并显示“排队中”；评分、标签、描述、集合/文件夹元数据、编辑保存、移入回收站/恢复等短写仍立即失败。 |
| 撤销/重做与清空记录 | 不排队。它们依赖当前操作记录时间线，排队后会在未来记录上执行；继续在有任务时立即失败或按钮禁用。MCP 的 `history_undo` / `history_redo` 同样快速失败。 |
| MCP 长任务 | 移动、导入、临时区特征生成等长任务与界面一致，返回 `taskId` 并排队，AI 用 `tasks_get` 轮询；短写仍立即失败。 |
| “历史缓存”对象 | 指操作记录/撤销数据，不是任务中心的内存快照。操作记录面板显示记录数、逆数据字节与 `.artbank/undo/` 暂存字节；清空入口沿用现有“清空记录”。不新增任务中心清空入口。 |
| release panic | 移除 `panic = "abort"`，改为 unwind；任务边界 `catch_unwind` 把 panic 变成任务失败并记录日志；全局 panic hook 把位置与消息写进日志。主线程/非任务线程 panic 只保证记录，不强承诺应用继续。 |
| 任务历史裁剪 | 只裁剪已结束任务；运行中与排队中的任务永不因 50 条上限被移出列表。任务中心保留最近 50 条已结束记录，不新增清空入口。 |
| AI 服务崩溃 | 本批只评估，不实现自动重启。崩溃后状态显示失败，由用户手动启动；避免模型加载风暴与崩溃循环。 |
| `ai::job` 偶发失败 | 5 次全量并发与 5 次 32 线程压力运行均未复现；本批只做 mock 服务隔离与失败信息增强，不把未复现现象写成已修复。 |

## 一、现状

### 1.1 任务总线的生命周期

- `TaskBus` 有三条 lane：`write` 与任何 lane 冲突且只能一个，`ai` 与 `scan` 可以并行（`src-tauri/src/app/tasks.rs:105`、`:414`）。
- `TaskHandle` 的终态由 `finish` / `finish_from` 写入（`:326`、`:338`）；`set_phase` 不会从终态再跳回运行态（`:261`）。
- `spawn_worker` 是裸线程启动，线程起不来时会把任务标成失败并返回错误（`:631`）；线程体 panic 时没有任何兜底。
- `spawn_pump` 也是裸线程，每 150ms 克隆一次快照并推送；只有看到终态才退出（`:708`）。它持有 `Arc<TaskHandle>`，所以单靠 `TaskHandle::Drop` 无法兜底。
- `run_write_task` 用 `begin_write_task` 立即占 write lane，再把任务体放进 `spawn_blocking`（`src-tauri/src/app/commands.rs:483`）；任务体 panic 时 Tokio 会把 JoinError 返回给命令，但 `TaskHandle` 永远停在 Running，写 lane 虽然随 guard 释放，任务中心仍显示进行中。
- `register` 先 `push_back` 再无条件 `pop_front` 到 50 条（`src-tauri/src/app/tasks.rs:612`）。任务超过 50 条时，最早的任务即使仍在运行也会被移出列表；`active()`、`cancel()` 与 `conflicting()` 都看不到它，但 lane 仍被占用。

### 1.2 panic 后的实际表现

- 导入线程自己捕获了 `pipeline::run` 的 panic（`src-tauri/src/import/mod.rs:185`），但收尾、事件与 `finish_live` 都在 catch 之外（`:212`、`:219`）；收尾自身 panic 仍会留下未完成状态。
- AI 任务在 `spawn_worker` 内部捕获 `job::execute` 的 panic（`src-tauri/src/ai/runtime.rs:646`），但 `job::execute` 的 `finish_live` 在 `run_job` 之后（`src-tauri/src/ai/job.rs:152`、`:161`）；`run_job` 内 panic 时操作记录停在 `pending`。
- 空间优化没有任务级 catch；`begin_live` 在执行前创建（`src-tauri/src/app/state.rs:1658`），任务体 panic 时记录停在 `pending`。
- 撤销/重做 panic 时 `undo_runs` 会停在 `running`，操作可能停在 `undoing` / `redoing`；现有恢复只在下次打开图库时由 `recover_on_open` 处理（`src-tauri/src/library/history.rs:1152`）。
- release 配置是 `panic = "abort"`（`src-tauri/Cargo.toml:54`）。release 下 panic 直接结束进程，不会留下“永远运行中”的任务，但用户会丢失当前窗口状态，且没有任务失败状态可看；开发/测试档默认 unwind，问题表现不同。
- 当前没有全局 panic hook，panic 位置与消息不会进入 `lilith-artbank.log`。

### 1.3 并发与冲突

- `launch` 先用 `conflicting` 查正在运行的任务条目；`Fail` 直接返回 `Conflict`，`CancelActive` 逐个请求取消，`Queue` 继续（`src-tauri/src/app/tasks.rs:648`）。
- `conflicting` 只看任务条目（`:511`）。短操作（编辑保存、文件夹元数据、MCP 短写）只占 lane、没有任务条目（`src-tauri/src/app/state.rs:306`、`:351`、`:1374`）。因此 `Fail` 在“短操作占着 lane、但条目为空”时会绕过冲突检查，实际落入排队路径。
- `CancelActive` 忽略取消失败（`src-tauri/src/app/tasks.rs:662`）；撤销/释放任务不可取消时，前端点“取消现有任务并开始”仍会排队，用户看到的语义与实际不一致。
- 排队线程各自轮询 `Condvar`，没有 FIFO；`notify_all` 后所有等待者竞争 lane。队列中只要还有 AI/扫描任务，write 可能长期得不到执行。
- `ensure_no_activity` 只看 lane 计数（`src-tauri/src/app/state.rs:293`）。排队中的任务不占 lane，打开/创建/关闭图库可能在队列即将启动时通过检查。
- 导入入口在 `start_import_inner` 一开始调用 `ensure_no_activity`（`src-tauri/src/app/state.rs:175`），所以导入目前不能排队；移动/永久删除/清空回收站通过 `begin_now` 立即占 lane，冲突直接报错（`:1392`）。
- 前端现状：批量任务与优化对话框默认 `fail`，冲突后展示“排队等待 / 取消现有任务并开始”；相似分组固定 `queue`；导入、移动、删除、清空回收站、撤销/重做、MCP 写都直接报错。

### 1.4 操作历史占用

- 任务中心的历史只在内存里：后端 50 条快照、每任务最多 200 条失败（`src-tauri/src/app/tasks.rs:32`、`:33`），前端同样保留 50 条（`src/app/TaskCenterProvider.tsx:24`）。它没有清空入口。
- 操作记录在 SQLite 的 `operations` / `operation_chunks` 与 `.artbank/undo/`；`HistoryPage` 目前只有 `entries`、`maxSteps`、`pendingPurgeCount/Bytes`、`canRun/blockedReason`（`src-tauri/src/library/history.rs:887`），没有记录数与数据占用。
- 操作记录面板底部只显示“待释放 N 张 · X”和“保留最近 N 步”（`src/modules/library/OperationHistoryPanel.tsx:347`）；清空确认只解释不能撤销与待释放文件（`src/shared/confirm.ts:77`）。
- `history::clear` 删除全部操作行并删除撤销暂存目录（`src-tauri/src/library/history.rs:1298`），随后由释放任务删除待释放原图。

### 1.5 AI 服务崩溃与任务测试

- `AiRuntime::status` 在健康检查失败、`auto_start` 开启、未手动停止、启动配置完整且进程状态为 `Stopped` 时才拉起监督线程（`src-tauri/src/ai/runtime.rs:384`）。
- 托管进程崩溃后 `poll_child` 把状态标成 `Failed`（`src-tauri/src/ai/process.rs:238`）；`status` 不会在 `Failed` 状态自动重启，只有 `start_service` 或保存新设置会重启。
- `ai::job` 端到端测试使用本地 mock 服务（`src-tauri/src/ai/test_support.rs`）。历史记录过“端口与线程时序”偶发失败；本次 5 次全量并发与 5 次 32 线程压力运行均通过，未复现。

## 二、目标行为

### 2.1 panic 与终态兜底

- 所有任务线程在框架层捕获 panic：

  - 任务标为 `Failed`，消息为“任务异常终止：…”；panic 位置与负载写入日志。
  - `LaneGuard` 随栈展开释放，lane 一定归还。
  - 进度推送线程看到终态后退出，不再每 150ms 推送一个永远运行的任务。
  - 任务体正常返回但没有写终态时，同样标为失败，避免“跑完了还显示进行中”。

- release 改为 unwind；全局 panic hook 把 panic 位置与消息写进 `lilith-artbank.log`。主线程或 Tauri/WebView 回调里的 panic 仍可能让应用不稳定，日志只保证可定位，不承诺继续运行。
- 长任务的操作记录用 RAII 收尾：

  - 导入、AI 描述、空间优化在创建 `pending` 记录后持有 `LiveOperation`。
  - 正常结束、取消、失败与 panic 都调用 `finish_live`；空记录删除，有内容的记录转为可撤销并写入错误信息。
  - 排队中被取消、线程起不来时，闭包被丢弃，`LiveOperation` 同样会收掉记录。
  - 进程被强杀或 release 断电式退出时 Drop 不执行，仍由下次打开图库的 `recover_on_open` 恢复。

- 撤销/重做增加 run guard：panic 时把 `undo_runs` 的 `running` 行标为失败；`undoing` / `redoing` 的操作保留给下次打开恢复。本次不自动重试，避免 panic 循环；操作记录面板显示“上次撤销/重做异常中断，请重新打开图库恢复”。
- 任务历史裁剪只移除已结束任务；运行中/排队中的任务永远保留在列表与 `active()` 中。前端合并快照时也优先保留活跃任务。

### 2.2 长任务队列

- 默认 `Queue` 的长任务：

  - 导入（界面与 MCP）。
  - 缩略图重建、AI embedding/pose/description、相似分组。
  - 空间优化估算与执行。
  - 移动图片、永久删除、清空回收站。
  - 释放删除文件（原本就是 `Queue`）。
  - MCP 移动、MCP 导入、临时区特征生成。

- 保持快速失败的操作：

  - 评分、标签、描述、集合/文件夹元数据、编辑保存、移入回收站/恢复。
  - 撤销、重做、清空记录（界面与 MCP）。
  - MCP 的 `images_update`、`images_trash`、`images_restore`、`collections_*`、`folders_modify` 等短写。

- 队列语义：

  - 同 lane FIFO；新任务不插队。
  - write 优先：队列里出现 write 等待者后，不再放行新的 ai/scan；正在运行的 ai/scan 自然结束，write 随后启动。
  - ai 与 scan 可以在没有 write 等待者时并行。
  - 短操作仍立即占 lane，不进入长任务队列；这是为了让编辑、评分等交互不被导入/扫描拖住。
  - 排队任务显示“排队中”，可以取消；取消后不占 lane、不写操作记录。
  - 不合并同类请求；重复提交就是多个排队任务，由用户取消。

- `ensure_no_activity` 同时检查 lane、运行中任务与排队任务；打开/创建/关闭图库在存在任何排队任务时按现有文案拒绝。导入不再预先要求“全库空闲”，而是直接排队。
- 关闭/退出时取消排队中的任务，避免退出过程中队列突然启动；运行中的 write 任务仍按现有规则拒绝关闭或留到下次启动。

- 空间优化执行排队后，候选收集、估算凭证与指纹校验移到 worker 开始时重新执行；排队期间文件或范围变化会让任务失败并提示重新估算，不使用排队前的过期候选。

### 2.3 操作记录占用

- `HistoryPage` 增加 `storage`：

  - `recordCount`：全部操作行数。
  - `chunkCount` / `chunkBytes`：逆数据条数与字节数。
  - `undoFiles` / `undoBytes`：`.artbank/undo/` 下的文件数与字节数。
  - `totalBytes`：逆数据 + 撤销暂存。

- 操作记录面板底部显示“记录 N 条 · 撤销数据 X”；有暂存文件时同时显示文件数。清空确认补充会删除多少撤销数据，并说明数据库文件不会立即缩小、空间会留给后续写入。
- 只做展示与确认，不改清空语义；不引入 `VACUUM`，不在清空后重写数据库。

### 2.4 AI 服务崩溃

- 本批不实现自动重启。评估结论：

  - 只在用户手动启动或保存新设置时重启，符合当前“所有权明确”的模型。
  - 自动重启容易在模型文件损坏、显存不足、端口冲突时形成崩溃循环；模型加载本身昂贵。
  - 若后续要做，只对托管进程、`auto_start` 开启且未手动停止的情况，按有限次数与退避重试，并在重试期间保持状态“失败/重试中”，不能在任务运行中静默替换服务。
- 本批只补日志与状态文案，不改 `AiRuntime::status` 的重启触发条件。

### 2.5 `ai::job` 测试隔离

- 未复现偶发失败，不宣称修复根因。本次只做：

  - mock 服务启动后增加就绪信号；`Drop` 时唤醒 accept 循环并 join。
  - 失败断言附带已收到的请求路径，便于下次定位是端口、线程还是请求时序。
  - 若后续再次出现，再考虑用模块级互斥把网络测试串行化，不默认降低全量测试并行度。

## 三、数据与接口

### 3.1 TaskBus 调度与终态

```rust
struct WaitEntry {
    task_id: String,
    lane: TaskLane,
}

struct LaneState {
    write: usize,
    ai: usize,
    scan: usize,
    waiters: VecDeque<WaitEntry>,
}
```

- `launch`：

  1. 计算冲突条目。
  2. `Fail` 发现 lane 忙或冲突条目非空时返回 `Conflict`；短操作占 lane 时也返回冲突，不再静默排队。
  3. `Queue` 先注册任务与进度推送线程；只有队列为空且 lane 可启动时立即运行，否则追加等待者并启动排队线程。
  4. 排队线程被取消时移除等待者、标 `Cancelled`，不执行任务体。

- `begin_queued(app, handle)`：给 `run_write_task` 使用。注册任务与推送线程，尝试立即启动；否则追加等待者并阻塞等待 lane。被取消时返回错误，调用方不执行任务体。
- `acquire_immediate` 保持给短操作使用，允许在长任务队列存在时插队，保证交互响应。
- `cancel` / `cancel_lanes` 同时清理等待者并唤醒；`wait_idle` 与 `is_idle` 把等待者也计入。
- `register` 裁剪时只从头部移除已结束任务；没有已结束任务时允许列表暂时超过 50 条，保证活跃任务不丢。
- `TaskRunGuard`：

```rust
struct TaskRunGuard {
    handle: Arc<TaskHandle>,
}

impl Drop for TaskRunGuard {
    fn drop(&mut self) {
        if !self.handle.is_finished() {
            self.handle.set_message("任务异常终止");
            self.handle.finish(TaskPhase::Failed);
        }
    }
}
```

- `spawn_worker` 用 `catch_unwind(AssertUnwindSafe(run))` 包住任务体；panic 时提取 `&str` / `String` 负载写日志并标失败。正常返回但未写终态时同样标失败。
- `launch` 的立即执行路径也包一层 `catch_unwind`，避免任务启动闭包自身 panic。
- `run_write_task` 在 `spawn_blocking` 内先 `begin_queued`，再用 `catch_unwind` 包住任务体；panic 时返回“任务异常终止”给命令，同时任务进入失败终态。

### 3.2 操作记录 RAII

```rust
pub struct LiveOperation {
    database: Arc<LibraryDb>,
    id: i64,
    finished: bool,
}

impl LiveOperation {
    pub fn begin(database: &Arc<LibraryDb>, op: NewOperation<'_>) -> AppResult<Self>;
    pub fn id(&self) -> i64;
    pub fn finish(mut self, error: &str) -> AppResult<()>;
}
```

- `Drop` 在未 finish 时调用 `finish_live(..., "任务异常终止")`，失败只记日志。
- 导入：`start_import_inner` 创建 `LiveOperation`，把 id 交给 `ImportSource`，把 guard 移入导入线程；线程结束、启动失败或排队取消都会收尾。
- AI 描述：`job::execute` 在创建 `pending` 后持有 guard，`run_job` 返回后 finish；panic 时 Drop 收尾。
- 空间优化：guard 在 worker 内、复核凭证与候选之后创建；排队取消不会留下空记录。
- 撤销/重做：增加 `HistoryRunGuard`，Drop 时把当前 `undo_runs` 行标为失败；正常路径仍写 `completed` / `cancelled`。

### 3.3 操作记录占用

```rust
#[derive(Debug, Clone, Default, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct HistoryStorage {
    pub record_count: u64,
    pub chunk_count: u64,
    pub chunk_bytes: u64,
    pub undo_files: u64,
    pub undo_bytes: u64,
    pub total_bytes: u64,
}
```

- `HistoryPage.storage` 新增字段；`get_operation_history` 一次返回。
- 逆数据字节用 `SELECT count(*), coalesce(sum(length(data)),0) FROM operation_chunks`；BLOB 长度是 O(1) 读取头，不读内容。
- `.artbank/undo/` 递归统计普通文件；跳过符号链接，读取失败按 0 处理并记日志。
- `total_bytes = chunk_bytes + undo_bytes`。

### 3.4 前端

- `TaskStartResult` 与 `ConflictPolicy` 去掉 `cancelActive`；批量任务与优化对话框直接发送 `queue`，冲突面板删除，排队状态由任务进度区显示。
- 任务合并保留活跃任务：活跃任务全保留，已结束按新到旧补到 50 条。

## 七、用户手工验收

1. 启动一个长导入，再启动 AI/缩略图任务：第二个显示“排队中”，前一个结束后自动开始；排队期间可取消。
2. 长任务运行时发起移动/永久删除/清空回收站：进入队列而不是报错；任务胶囊能看到排队与执行两段状态。
3. 长任务运行时点撤销/重做/清空记录：按钮禁用或立即失败，不排队。
4. 用测试构建触发任务 panic：任务显示失败，写 lane 立即释放，后续任务能开始；操作记录没有停在 pending；重新打开图库能恢复中断的撤销。
5. 操作记录面板显示记录数与撤销数据占用；清空后记录清空、待释放文件被删除；数据库文件没有立即变小。
6. AI 服务运行中崩溃：状态显示失败，不自动重启；手动启动后可用。
7. MCP 并发提交移动/导入：第二个返回 taskId 且 phase 为 queued；短写仍立即失败；`tasks_get` 能看到排队与完成。
8. 有排队任务时关闭/切换图库：按文案拒绝或取消排队后继续，不发生换库后旧任务启动。

## 八、边界、风险与后续

不做：

- 不改 SQLite 单写连接；不引入外部任务队列或跨进程队列。
- 不把长时间写任务拆成无协调的并行写。
- 不实现 AI 服务崩溃自动重启；不实现任务队列持久化。
- 不新增任务中心清空入口；不对数据库执行 `VACUUM`。
- 不编译 release，不启动界面或浏览器。

风险与已知边角：

- 自动排队会让“提交即开始”变成“提交后等待”；任务胶囊与对话框必须明确显示排队，否则用户会误以为卡住。
- 排队后执行的空间优化必须重新校验估算凭证；否则排队期间的文件变化会让统计与候选脱节。
- 短操作插队保证交互，但极端情况下持续短写仍可能推迟长 write；当前按单用户桌面场景接受。
- panic 被捕获后，进程内可能仍有未释放的第三方状态；数据库事务与操作记录尽量收尾，但出现重复 panic 时应提示重启，而不是无限重试。
- `LiveOperation` 的 Drop 需要写数据库；如果 panic 发生在写连接持锁期间，Drop 可能失败，只记日志，仍由下次打开恢复。
- release unwind 的体积/性能变化未测量（不编译 release）。
- 撤销/重做 panic 后不在当前会话自动续做；用户需要重新打开图库，避免 panic 循环。
- 操作记录占用的目录扫描在大量暂存文件时可能变慢；本次实测很小，若后续出现数千文件再考虑缓存。

## 十、实现记录（2026-10-27）

状态：已实现，自动检查通过；等待用户按第七节手工验收。

### 10.1 落地内容

- 任务总线的等待者队列：`LaneState.waiters: VecDeque<WaitEntry>`，同 lane 先来先得；队列里一旦出现 `write` 等待者，后面的 `ai` / `scan` 都不再启动，`write` 拿 lane 要求“排在最前且全空闲”。`ai` 与 `scan` 在没有 `write` 等待者时可以并行。
- `is_idle` 把 lane 计数、等待者与未结束任务一起判断：`any_busy`、`ensure_no_activity`、`wait_idle`、`close_library`、`shutdown` 都据此拒绝或等待。
- 长任务默认排队：`launch(..., Queue)` 先注册任务与进度线程，队列空且 lane 可启动时立即跑，否则置 `Queued`、入队并在独立线程等 lane；`begin_queued` 给 `run_write_task` 用，同样注册、排队、阻塞等 lane。`Fail` 仍保留给撤销/重做/清空记录，lane 忙或有等待者时直接返回 `Conflict`。
- `cancel` / `cancel_lanes` 同时清理等待者并唤醒；退出与换库前 `cancel_queued` 取消所有排队任务，避免关闭过程中队列突然启动。
- 终态兜底：`spawn_worker`（任务体线程）与 `spawn_launcher`（排队线程）共用 `spawn_guarded`，后者用 `finish_on_return` 区分“正常返回即结束”；任务体 panic 提取 `&str` / `String` 负载，写日志并把任务标成 `Failed`；正常返回但没写终态同样标失败；立即执行路径的启动闭包也用 `catch_unwind` 包住。
- `register` 只裁剪已结束任务：超过 50 条时找一条已结束的移除，没有就允许暂时超限，运行中/排队中的任务永不丢。前端合并快照时同理，活跃任务全保留，已结束按新到旧补到 50 条。
- `LiveOperation`：`begin` 建 `pending` 记录，`finish(error)` 正常收尾，`Drop` 兜底；导入、批量 AI 描述与空间优化都改用它。导入的 guard 随线程闭包移动，排队取消、线程起不来或 panic 时由 Drop 收尾；空间优化在 worker 里复核凭证之后才建记录。
- `HistoryRunGuard`：撤销/重做的 `undo_runs` 行在 panic 时标 `failed`，`undoing` / `redoing` 的操作留到下次打开图库续做。
- 空间优化执行在 worker 拿到 lane 后重新解析范围、收集候选并核对凭证（`recheck_optimize_scope`），排队期间文件或参数变化会让任务失败并提示重新估算。
- 导入：`import_job` 单槽位改为 `import_jobs: VecDeque`（运行中的不淘汰），`ImportPhase` 增加 `Queued`，`progress()` 在阶段仍为 `Queued` 时回落到任务总线的终态，排队取消能正确显示 `cancelled`。
