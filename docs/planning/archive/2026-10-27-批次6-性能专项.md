# 使用反馈整改 批次 6：性能专项（调查、测量与方案）

日期：2026-10-27（正式测量：同日空闲环境复测）
状态：已实现并归档（P1–P4 全部落地），自动检查通过，等待用户按“十一、实现记录”里的“用户手工验收”验收。收尾后在空闲环境补跑了 20 万行合成库的聚合与均值基准（见“十一、基准复测”）：`list_folders` 3.3×、`list_tags` 13.5×、均值 9.8×，但 `counts` 与 `filter_counts` 的收益只能由真实库体现；第四节数字仍是实现前在空闲环境做的方案验证。

范围对应《[使用反馈整改计划](2026-10-27-使用反馈整改计划.md)》的编号 7、8 与批次 6 小节，外加 `todo.md` 中并入测量的计数/内存项。本批次只做“先测量、再改查询与线程模型、最后按需加缓存/索引”；不提前上 ANN，不做全量内存化，不用跨机器墙钟比较，不改动真实库。

## 结论摘要

1. **主要瓶颈不是 SQL 写得慢，是“全表聚合没有覆盖索引”**。`images` 上的活跃索引都以 `deleted_at` + 像素/评分/时间开头，任何要 `folder_id`、`purge_operation_id` 的聚合都得回表 39 万次。真实库空闲环境实测：`counts()` 620 ms、`list_folders` 683 ms、`filter_counts` 1 815 ms。在库副本上建一张覆盖索引后变成 **20 / 27 / 620–820 ms**；索引只多占 **7 MB**、建一次 **533 ms**——远低于准备阶段的估算 25–40 MB / 1–3 s。
2. **标签链路还有一层可修的形状问题**。`list_tags` 现值 1 163 ms，瓶颈不是 SQL 写法而是“tag → 关系 → 逐张回表”。改成“从 `image_tags` 直接 `GROUP BY tag_id`（覆盖扫描）+ 回连 `tags`”只要 **24 ms**，且与现查询逐行相同（100 行、计数合计 457 405）。`filter_counts` 的标签分面仍要 620–820 ms，因为它是“活跃集合 ∩ 关系表”的交集，属于这类连接的地板；有筛选时降到 ~160 ms。
3. **这些查询全挂在 Tauri 同步命令上**，Windows 下由 WebView 的 IPC 回调（事件循环线程）直接执行。开库、开筛选面板、任何文件夹增删改、移动后的收尾都在这条路径上。索引只缩短卡的时间，**不卡窗口要靠线程模型**（D2 已确认）。
4. **语义搜索冷启动的大头是 Python 导入，而且导入比之前估计的更贵**。空闲环境实测：`import torch` 1.8–2.0 s（RSS 204 MB）、`import transformers` 2.4–2.5 s（272 MB）、再取 `AutoTokenizer/SiglipTextModel` 等具体类 **3.4–3.5 s（420 MB）**，合计 **7.7–8.0 s**。同一脚本在非空闲环境下是 17 s——后台负载能把它翻倍，这正是“有时一分钟”的放大机制。
5. **“加载完成”不等于“可用”**：文本塔权重是 fp32 零拷贝 mmap，`ensure` 后只占 499 MB；**首次 forward 才把 2.83 GB 真正拉进物理内存，2.37 s**，之后每条 163 ms。所以现在的 `/v1/models/ensure` 返回后，第一次搜索还要再卡 2.4 s，而且 UI 在这段时间没有任何提示。
6. **均值仍然按用户口径“开库时算”**，但现在有两个真问题：`ensure_mean` 在 `Computing` 状态不等后台线程、而是**同步再算一遍**（重复 1–3 s）；`mean` 是单线程标量循环，而均值遍历的是 1.12 GB / 364 056 行 fp16 包。修法：开库后**后台**算（不阻塞打开）、`Computing` 时等待、`rayon` 并行。
7. **移动图片本身不慢**：同盘 rename 空闲环境实测 0.169 ms/张（2000 张 338 ms）。慢的是收尾链路（重拉文件夹 + 重算计数 + 整页刷新）。
8. **前端两个独立问题**：刷新把已加载行硬截到 3000 行；滚到全库末尾约 213 MB JSON 常驻。

## 一、现状与代码定位

### 1.1 计数与聚合：没有覆盖索引

- `LibraryDb::counts()`：`count(*) FROM images WHERE deleted_at IS NULL AND folder_id <> ?`（`src-tauri/src/library/db.rs:98`、`:106`）。打开图库与每次 `refreshStatus` 都走它（`src-tauri/src/app/state.rs:144`、`:617`）。
- `query::list_folders`：`SELECT folder_id, count(*) FROM images WHERE deleted_at IS NULL AND purge_operation_id IS NULL GROUP BY folder_id`（`src-tauri/src/library/query.rs:626`、`:629`）；同函数内还有 `all_folders`（`:1613`）与一条 `SELECT id, sort_index FROM folders`（`:643`）。
- `query::list_tags_page`：`tags JOIN image_tags JOIN images`，带临时区排除（`query.rs:689`、`:699`；排除条件 `src-tauri/src/library/temp.rs:27`）。
- `query::filter_counts` → `build_materialized_counts`：一条 `WITH matched AS MATERIALIZED (…)` 加五个 `UNION ALL` 分支（`query.rs:1425`、`:1508`）；每个分面用 `filters_only(filters, Some(Facet::X))`，即**排除自己那一维**的筛选（`query.rs:1445`–`:1449`）。
- 现有索引：`idx_images_active_imported / _modified / _pixels / _score / _size`（都以 `deleted_at` 开头的部分索引）、`idx_images_folder_imported(folder_id, imported_at)`、`idx_images_trash`、`idx_images_purge`、`idx_image_tags_tag`。
- 查询计划（真实库）：`counts` / `list_folders` / `filter_counts` 的基表段都是 `SEARCH images USING INDEX idx_images_active_pixels (deleted_at=?)`——按像素排序取行，再逐行回表拿 `folder_id`、`purge_operation_id`；`list_tags` 同样从 `images` 驱动，再对每一张图探测 `image_tags`。
- 结论：缺的是“可见性 + 分面列”的覆盖索引，不是 SQL 退步。

### 1.2 同步命令阻塞窗口事件循环

- 这些重读命令都是同步 `#[tauri::command]`（`src-tauri/src/app/commands.rs`）：
  `query_images:281`、`query_image_ids:286`、`get_filter_counts:294`、`get_query_total:302`、`get_folders:307`、`create_folder:312`、`rename_folder:317`、`move_folder:326`、`reorder_folders:335`、`place_folders:352`、`apply_folder_order:362`、`delete_folder:378`、`get_tags:386`、`search_tags:391`、`get_library_status:116`。
- Tauri 2 的同步命令在 IPC 回调里直接执行（`tauri-macros` 的 `body_blocking`），Windows 下该回调来自 WebView2 事件循环；异步命令走异步运行时。所以上面任何一条 620 ms 的查询都会同时卡住窗口。**这条来自宏与运行时实现，最终以“命令执行时拖动窗口”的真实验收为准。**
- 前端触发点：
  - 开库：`AppRuntimeProvider` 的 `refreshStatus`（`src/app/AppRuntimeProvider.tsx:178`）+ `LibraryWorkspace` 的 `reloadFolders`（`src/app/LibraryWorkspace.tsx:176`、`:190`）。
  - 打开筛选面板：`loadOptions`（`getTags`）+ 160 ms 后 `getFilterCounts`（`src/modules/library/FilterPanel.tsx:65`、`:91`）。
  - 任何文件夹操作：`folder_service` 每个写路径结尾都 `query::list_folders`（`src-tauri/src/library/folders.rs:110`、`:195`、`:300`、`:395`、`:648`、`:755`、`:820`），把 683 ms 的聚合塞进了写命令。
  - 移动图片后的收尾：`planDataChange` 的 `folders: true`（`src/modules/library/dataChange.ts:236`）→ `LibraryView` 里的 `await onFoldersChanged()`（`src/modules/library/LibraryView.tsx:614`）→ 又一次 `getFolders`。

### 1.3 移动图片与移动文件夹

- 图片移动：`metadata::move_images_with_id`（`src-tauri/src/library/metadata.rs:1180`）在一个事务内逐张 `content_path` + `fs::rename`（`:1267`）+ `UPDATE images SET folder_id, modified_at`（`:1275`），全部成功后写一条操作记录（`:1307`）。命令走 `run_write_task` + `spawn_blocking`（`commands.rs:533`、`:494`），本身不阻塞窗口。
- 文件夹移动：目录 `rename` 一次（`folders.rs:260`）+ `update_subtree_paths`（`:270`）+ `query::list_folders`（`:300`）。命令是同步的（`commands.rs:326`）。
- 操作记录收尾：每次写入后 `after_history_write` 做 `history::trim` + `cleanup_undo_dirs`（`src-tauri/src/app/state.rs:1203`）。
- 数据变化后还会 `clear_page_cache()`（`state.rs:754`），深排序的 id 列表要重建。

### 1.4 语义搜索冷启动与均值

- `semantic_search`（`src-tauri/src/ai/runtime.rs:674`）是同步串行长链：`health` → `ensure_capability("textEmbedding")`（触发服务端加载文本塔）→ `embed_text` → `ensure_mean`（`:735`）→ `resolve_similarity_scope` → `embedding::search_with_total`（`:739`）→ 返回 token，前端再取第一页（`src/app/useSimilarityBrowse.ts:94`、`:108`）。
- 命令是 `async fn`，不阻塞主线程；但前端只有 `busy` 一个状态（`useSimilarityBrowse.ts:92`、`:111`），没有阶段提示。`/v1/models/ensure` 超时 600 s（`src-tauri/src/ai/client.rs:12`），`embed` 60 s（`:9`）。
- 服务端导入位置：`ClipCache._load_locked` 内的 `import torch` / `from transformers import …`（`server/clip_cache.py:117`、`:118`）——**发生在第一次 `/v1/models/ensure` 请求里**。`main.py` 顶部只导入标准库与本地模块（`_torch()` 是延迟导入，`server/main.py:37`），所以进程启动本身很快。
- 塔的驻留：同一时间只驻留一个塔，**加载另一个塔会先卸载当前的**（`clip_cache.py:91`–`:92`）；空闲卸载默认 300 s（`_reap_loop` `:264`，参数默认值见 `:59`、`:65`；应用启动未传 `--idle-unload-seconds`，`src-tauri/src/ai/process.rs:51`）。用户澄清：实际使用中没有观察到“反复卸载”，慢的是**进程冷启动**；本批次因此不改卸载策略，但要记录“图片塔 ↔ 文本塔切换”会重付一次加载（见 4.7）。
- 均值：`library_opened` 无条件 `spawn_mean`（`runtime.rs:346`、`:366`）；`spawn_mean` 先 `distinct_groups` 再 `embedding::mean`（`:1182`、`:1205`–`:1206`）。`ensure_mean`（`:1135`）只在 `Ready` 且 model/dim 匹配时复用，**在 `Computing` 状态会覆盖槽位并同步再算一遍**（`:1154`、`:1155`），与后台线程重复。
- `embedding::mean`（`src-tauri/src/ai/embedding.rs:527`）是单线程标量循环（逐条 `record_slice` + `decode_f16` + 累加，`:549`–`:573`）；`rows()`（`:91`）先查 34.5 万条指针（带 `JOIN images`）。`rayon` 已在依赖里（`src-tauri/Cargo.toml:30`，`embedding.rs:4` 已 `use rayon::prelude::*`）。
- 均值失效边界：只有临时区特征生成完成会失效（`runtime.rs:654`–`:658`）；普通 embedding 任务只清相似结果（`:660`），均值保持旧值直到重开图库——这是 `docs/modules/ai-service.md` 的既有口径，但 UI 文案没体现。
- UI 门禁：语义搜索按钮以 `aiStatus.mean.count === 0` 判定禁用，理由写“还没有图片 embedding”（`src/app/LibraryWorkspace.tsx:480`–`:484`）。均值正在计算时 `count` 也是 0，文案是错的；状态轮询 8 s 一次（`src/modules/ai/useAiStatus.ts:44`）。

## 二、瓶颈判定

按“用户能感知的顺序”排（括号内为正式测量，见第四节）：

| 现象 | 直接原因 | 现在 | 加索引/改形状后 |
| --- | --- | --- | --- |
| 打开图库、切库慢 | `counts()` + `get_folders` 都是全表回表聚合，且在主线程 | 620 + 683 ms | 20 + 27 ms |
| 打开筛选面板卡 | `getTags` 1 163 ms + `getFilterCounts` 1 815 ms，都在主线程 | 约 3 s | 24 + 620～820 ms（无筛选）／约 190 ms（有文件夹筛选） |
| 移动/删除/导入结束后“卡一下” | `plan.folders` → `getFolders`；`plan.status` → `counts()` | 683 + 620 ms | 27 + 20 ms |
| 文件夹新建/改名/排序卡 | 写命令结尾返回整棵文件夹树 | 683 ms | 27 ms（异步后不再阻塞窗口） |
| 语义搜索第一次要十几秒 | 请求内导入 7.7–8.0 s + tokenizer 0.9 s + 首次 forward 2.4 s + 均值 1–3 s + 扫描 | 13–15 s（CPU、空闲） | 预热后 4–5 s，且分阶段可读 |
| 语义搜索“有时特别慢” | 后台负载把导入翻倍（17 s）、CUDA/冷盘/Defender、图片塔↔文本塔切换重付一次加载 | 无上限 | 导入预热后不再受进程冷启动影响 |
| 深滚动后改一张图，列表变短 | `refreshKeepingRows` 截到 3000 行 | 立即 | 同（P4 修） |
| 滚到全库末尾内存升高 | 已加载行与缩略图解码缓存都不回收 | 213 MB JSON + ≤1 GB 解码 | 同（D5 先不做） |

不是瓶颈的部分（有数据支撑）：

- 首屏 150 条 0.4 ms、按 id 取 150 行 0.5 ms。
- 图片移动的 rename 本身 0.169 ms/张；写 1000 行 `UPDATE` 加索引前后 50 / 24 ms（噪声内）。
- `count_tags` 0.3 ms（`EXISTS` 短路）。
- 向量扫描（numpy 单线程代理 0.90 s，Rust 走 rayon 会更快）。
- 建索引 533 ms、体积 +7 MB——一次性成本可以接受。

## 三、方案

分四组，前两组解除全局阻塞，后两组是各专项。每组独立验收，允许按组落地。

### P1 命令线程模型（不改任何查询与数据）—— D2 已确认

1. 所有重读命令改为异步（`spawn_blocking` 执行数据库部分），清单见 1.2。保持同步签名的只留真正需要主线程的（窗口/平台调用）。
2. 写命令结尾不再顺带返回整棵文件夹树：返回受影响文件夹的 `FolderInfo`（新增/改名/移动/排序涉及的 id 与其父级），前端按 id 就地合并；`get_folders` 只在开库与“结构无法推断”时调用。
3. `counts()` 不再挂在 `get_library_status` 上每次重算：`status()` 返回缓存值 + 数据变化事件驱动刷新（或拆出 `get_library_counts`，前端按需拉）。开库首帧不等待计数。
4. 语义搜索把阶段写成事件（`semantic-stage`：加载文本模型 / 预热 / 计算均值 / 扫描向量 / 读取结果），前端在搜索框下方显示；均值计算中也允许点搜索。
5. 修正“均值计算中显示还没有 embedding”的文案：区分 `computing` / `missing` / `failed`。

### P2 查询形状与索引（schema v8）—— D1 已确认

1. 新增覆盖索引（已实测，见 4.4）：

```sql
CREATE INDEX idx_images_visible_facets
  ON images(deleted_at, purge_operation_id, folder_id, file_ext, score);
```

- 效果：`counts()` 620 → 20 ms、`list_folders` 683 → 27 ms、`filter_counts` 1 815 → 620～820 ms（标签分支见下）。
- 代价（实测，不是估算）：库 +7.0 MB、建索引 533 ms、1000 行 `UPDATE` 无可见退化。
- 不用部分索引：同一批 SQL 有的带 `purge_operation_id IS NULL`、有的不带，部分索引会让其中一半无法命中。

2. `list_tags_page` 改形状（实测 24 ms，结果与现查询逐行一致）：

```sql
SELECT tags.id, tags.name, cnt
  FROM tags JOIN (SELECT tag_id, count(*) AS cnt FROM image_tags GROUP BY tag_id) x ON x.tag_id = tags.id
 ORDER BY cnt DESC, tags.name LIMIT ?1 OFFSET ?2;
```

- `image_tags` 是覆盖扫描（`GROUP BY tag_id` 24 ms），不再逐张回表。
- **必须先做有界减法**：临时区与回收站的图片仍可能有关系行。真实库当前 `deleted_at IS NOT NULL` 与临时区图片都是 0 张（关系行 0 条），但代码不能依赖这一点——用一条 `image_id IN (SELECT id FROM images WHERE deleted_at IS NOT NULL OR folder_id = :temp)`（有界集合）减去其 `tag_id` 计数，再排序。总数 `total` 与“有图标签数”同理。
- 若减法集合很大（例如刚清空回收站前），退回现形状——条件：dead 关系行数 > 5 万时走旧 SQL。

3. `filter_counts` 的标签分面：实测 620～820 ms，已接近“390 000 × 463 666 交集”的地板（`CROSS JOIN` 强制连接顺序只有 5～10% 收益，不采用）。保持现形状；由 P1 的异步化保证不阻塞窗口。若实现后仍想更快，可加“无任何筛选时标签分面复用全局直方图”（那 24 ms 的结果就是答案），但会多一个缓存失效面，本批次不做，记入 `todo.md`。

4. `list_folders` 的 `purge_operation_id IS NULL` 与 `deleted_at IS NULL` 语义重复，但覆盖索引已把它变成索引内的常量条件，保留以免依赖不变量。

5. 失效与一致性：新索引不改语义；迁移只建索引，不重建表。

### P3 语义搜索冷启动（按 D3 修订）

1. **导入预热**：AI 服务启动后起一个后台线程 `import torch` + `from transformers import AutoTokenizer, Siglip*`，把 7.7–8.0 s 从“第一次搜索”挪到“应用启动、用户在看图”。实测代价 RSS 420 MB（torch 204 + transformers 68 + siglip 具体类 148）。
   - 这 420 MB 不是净增：任何 AI 功能（图片塔、文本塔、批量索引）都要付同样的导入成本，预热只是提前支付。
   - 只有“整场会话完全不用 AI”时才是纯浪费，所以做成设置项 `ai.prewarmImports`（默认开）；另外在预热前检查 `aiStatus`：AI 服务被手动停止时不预热。
   - 不做“隐藏 sklearn”这类小动作：`transformers` 的 sklearn 导入被 `is_sklearn_available()` 守护，实测隐藏后 7.7 → 6.88 s、RSS 420 → 347 MB，收益不足一次点击，且要污染 `sys.modules`。
2. **加载即预热（warmup forward）**：`/v1/models/ensure` 现在只搬权重（499 MB RSS），首次 forward 还要 2.37 s 把 2.83 GB 文件页拉进物理内存。在 ensure 末尾对 1 条固定文本做一次 forward，让“加载完成”= 真正可用；用户看到的是“加载文本模型（约 3 s）”一个阶段，而不是“加载完成”之后再卡一次。之后每条 163 ms。
3. 不改空闲卸载策略（用户澄清没有反复卸载）。但要记录：**切换塔要重付一次加载**（加载文本塔会卸载图片塔，反之亦然），若经常在“批量生成 embedding”和“语义搜索”之间来回，每次切换约 3.3 s。这一条先只观察，不改。
4. 均值（按 D4 修订：开库时算，但放到后台，不阻塞打开）：
   - 保持 `library_opened` 触发，但**不阻塞开库**（现在是 `spawn_mean` 后台线程，需要确认开库路径上没有任何地方等它），并且 `ensure_mean` 在 `Computing` 时**等待后台结果**而不是覆盖槽位重算（当前 `runtime.rs:1154`–`:1155` 会重算，实测多花 1–3 s）。
   - `embedding::mean` 改 rayon 并行（实测遍历 364 056 × 1536 fp16 的包，numpy 单线程 1.15 s；Rust 标量单线程估计 2–3 s，16 线程应降到 0.3 s 量级）。
   - 不做持久化（用户已否掉）：均值仍只活在内存里，换库/换模型就重算。
5. 扫描侧：`rows()` 的指针查询改为只取 `feature_blobs`（不再 `JOIN images` 判断可见性），可见性交给扫描时已有的 id 集合；避免 34.5 万行 JOIN。

### P4 前端与缓存收尾

1. `refreshKeepingRows` 按“已加载页数”重取（保留当前行数，不硬截 20 页）；深滚动时按锚点页 + 相邻页重取，保证滚动位置与列表长度都不跳。
2. 已加载页回收：**先不做**（D5）。先把满滚动内存量出来，再决定是否按 6000 行上限窗口化。
3. `temp/viewer/`：加 2 GB 上限 + 按 mtime LRU，在打开图库时顺手清理（D6，不增加查看路径 IO）。
4. 缩略图解码缓存：先测真实 WebView2 内存（1024 vs 512），再决定是否下调默认值；不先改。

### 不做

- 不上 ANN、不做向量常驻堆、不做全量内存化。
- 不引入增量计数表（写放大 + 易漂移），计数仍以 SQL 聚合为准。
- 不做均值持久化（D4 修订）。
- 不改空闲卸载策略、不用 `sys.modules` 技巧缩短导入。
- 不改三档权限、不改 MCP 工具集；MCP 的 `tags_list` / `folders_list` 只受益于索引与 P2.2，不改口径。
- 不改图片文件布局、不改操作记录模型。
- 不为性能问题放宽任何正确性检查。

## 八、风险

- **覆盖索引**不是免费的：写路径（评分、标签、移动、回收站、导入）每次多写一棵索引。实测 1000 行 `UPDATE` 没有可见退化，但批量导入 20 万张时仍需在 `perf_metadata_200k` 里复核；若退化明显，退到“只给计数加一张窄索引”。
- **异步命令**会放开并发读：读连接池只有 4 条，深滚动 + 筛选 + 状态轮询可能排队；需要观察排队时延，必要时按命令限流。
- **导入预热**会让 AI 服务进程在启动后常驻约 420 MB（用任何 AI 功能都要付，只有完全不用 AI 的会话才是净浪费）；做成设置项，并在 AI 服务被手动停止时不预热。
- **warmup forward** 会让 `ensure` 变慢约 2.4 s（CPU）——但这段时间本来就要花，只是从“搜索等待”变成“加载等待”，所以必须在 UI 上把它显示成一个阶段，否则用户会觉得“加载变慢了”。
- **均值等待**会改变 `ensure_mean` 的时序：搜索会等后台线程而不是自己重算。若后台线程卡住，需要一个退化策略（超时后同步算）。
- **P1.2 的增量返回**改变文件夹命令的返回契约，前端合并逻辑要覆盖新建/改名/移动/删除/排序五种情形。
- 语义搜索仍无超时与取消：模型加载卡住时用户只能等 600 s。建议同批加“取消”或在 ensure 前给 30 s 的快速失败。

### P2 索引与查询形状（schema v8）

- `schema.rs`：`SCHEMA_VERSION = 8`，新增 `idx_images_visible_facets(deleted_at, purge_operation_id, folder_id, file_ext, score)`；`migrate_v7_to_v8` 只建索引 + 标版本，`IF NOT EXISTS` 幂等，不改任何行。测试 `migrates_v7_to_v8_and_adds_the_visible_facets_index` 覆盖“索引存在、现有行不变、再跑一次不报错”。
- `query::list_tags_page` 换形状：`image_tags GROUP BY tag_id` 覆盖聚合 + 回连 `tags`，排序与分页在 Rust 侧完成。回收站/临时区的关系行用 `dead_tag_counts` 做有界减法；死亡图片数超过 `MAX_TAG_DEAD_RELATIONS = 50_000` 时退回旧 SQL（`list_tags_page_legacy`）。
- `filter_counts` 保持原形状（标签分面是交集地板），靠 P1 的异步化解决体感。
- `db::counts` 与 `query::list_folders` 的聚合 SQL 提成 `ACTIVE_COUNT_SQL` / `FOLDER_COUNTS_SQL` 常量，测试用 `EXPLAIN QUERY PLAN` 断言“不得再用 `idx_images_active_*` 回表”。
- 结果一致性由三条测试守住：`list_tags_page_matches_legacy_shape`（回收站 / 临时区 / 阈值回退）、`list_tags_page_search_and_offset_match_legacy_shape`（名称搜索与分页）、`folder_infos_returns_only_the_requested_ids`（增量返回与整树计数一致）。

### P1 命令线程模型

- `commands.rs` 新增 `run_blocking`（`tauri::async_runtime::spawn_blocking` + `app.state::<AppState>()`）。改为异步的重读命令：`get_library_status`、`query_images`、`query_image_ids`、`get_filter_counts`、`get_query_total`、`get_folders`、`get_tags`、`search_tags`，以及全部文件夹写命令（`create_folder` / `rename_folder` / `move_folder` / `reorder_folders` / `place_folders` / `apply_folder_order` / `delete_folder`）。
- 文件夹写命令返回 `FolderChange { folders, removedIds }`：`query::folder_infos` 只取受影响 id（新建/改名/移动取子树，移动再补两侧祖先，排序取受影响同级行，删除只回 `removedIds`）。前端 `applyFolderChange` 按 id 就地合并，`planDataChange` 用 `foldersAlreadyLoaded` 跳过整树重取。
- 计数从状态查询里拆出：`state.status()` 只返回缓存，`LibraryInfo` 的三档计数在开库时为 0，新命令 `get_library_counts` 重算并写回缓存。前端 `AppRuntimeProvider.withCounts` 在开库/切库/`refreshStatus` 后补拉；`plan.status` 仍由数据变化驱动。
- 语义搜索加阶段事件：`semantic_search` 把 `stage` 回调透传进 `AiRuntime::semantic_search`，通过 `semantic-stage` 事件发出“加载文本模型 / 生成查询向量 / 计算均值 / 扫描向量”；`useSimilarityBrowse` 订阅并在加载态里显示（`SimilarityBrowseState.stage`）。

### P3 语义搜索冷启动与均值

- `server/clip_cache.py`：新增 `prewarm_imports()`（导入 torch/transformers 与 SigLIP 具体类，返回耗时）；`_load_locked` 在 `eval()` 之后调用 `_warmup_locked` 做一次前向（文本塔 1 条 64 token，图片塔 1×3×image_size 零张量），日志把 warmup 时间单列；warmup 抛错按加载失败处理。
- `server/main.py`：新增 `--prewarm-imports`；启动后 `start_prewarm()` 起后台线程，没有模型目录时跳过；导入失败只记 warning，首次使用时会再报一次带上下文的错误。

### 与计划的差异

1. **P1.3 计数刷新**：计划写“缓存值 + 数据变化事件驱动刷新（或拆出 `get_library_counts`）”，实现选了后者：前端在开库与 `plan.status` 时显式拉一次，后端不做推送。
2. **P1.5 文案**：均值 `computing` 时不拦搜索（点击后由 `ensure_mean` 等待），只有 `failed` 与 `missing` 才禁用并说明原因。
3. **P3.1 预热开关**：“AI 服务被手动停止时不预热”由实现结构保证——只有应用自己拉起服务时才传 `--prewarm-imports`；外部已启动的服务不受影响。
4. **P3.4 均值等待**：加了 15 s 上限，超时后退回同步计算，作为计划风险项里“后台线程卡住”的退化策略。
5. **P3.5 可见性**：计划说“可见性交给扫描时已有的 id 集合”，但全库范围没有 id 集合；实现改成先取两个小集合（回收站、临时区）再在内存里减，真实库这两个集合为空，代价接近零。
6. **P4.3 上限位置**：计划写“打开图库时顺手清理”，但开库本来就整目录清空 `temp`；上限改在写路径按 256 MB 粒度触发，才能真正约束单次会话。
7. **顺手放宽文件批量上限**：`metadata.rs` 的 `MAX_FILE_BATCH_IDS`（1 万）并入 `MAX_BATCH_IDS`（100 万），`LibraryView` 删除“一次永久删除最多 1 万张”的前端拦截。文件操作本就按 400 张分块，与元数据批量共用同一上限。

### 基准复测（2026-10-27 空闲环境，20 万行合成库）

实现期间机器在跑 CPU 任务，所以本批收尾时没跑基准。收尾后在空闲环境（CPU 2%、可用 17.6 GB）补跑，并把追加项写进基准代码：

- `perf_metadata_200k` 追加：`counts()` 三档、`list_tags_page` 新旧形状对比、无筛选 `filter_counts`、v7→v8 建索引耗时与**交替两轮**的索引 A/B（有 → 去掉 → 重建 → 再有），另外把开库后的 `reopen` 拆成“开库”与“`counts()`”两段（开库不再算计数）。
- `perf_embedding_scan_200k` 追加：同一份 20 万 × 1536 fp16 包上的单线程均值 vs `rayon` 分块均值。为此把并行归并抽成 `mean_parallel`，`mean()` 与基准共用。

| 项 | 结果 |
| --- | --- |
| `counts()` 三档 | 5.75 ms（去掉索引 5.66 ms）——合成库看不出真实库的 620 → 20 ms |
| `list_folders` | 17.8–18.1 ms（去掉索引 58.5–59.1 ms），3.3× |
| `list_tags_page` 100 | 15.6–17.1 ms（旧形状 225.3–225.6 ms），13.5× |
| `filter_counts` 无筛选 | 318.7 / 325.7 ms（去掉索引 243.1 ms）——**合成库上反而慢 30%** |
| v7→v8 建索引（含 `ANALYZE`） | 316–319 ms |
| `reopen` / `counts()` 单独 | 16.6–20.2 ms / 7.3–7.5 ms |
| 均值 单线程 → rayon | 417.3 → 42.5 ms（9.8×），结果最大差异 0.0000（计划阶段估的“单线程 2–3 s”偏高） |

结论：`list_folders` 与 `list_tags` 的形状改动在合成库上同样成立；`counts` 与 `filter_counts` 的收益依赖真实库的随机回表，合成库整库在页缓存里、回表几乎免费，反而让更宽的覆盖索引吃亏（`filter_counts` 从 243 变 319 ms，两轮可复现）。因此**合成库只作为形状回归门槛，分面与计数的收益仍以真实库数字为准**。数字与解释已写入 `docs/guides/performance.md` 的“批次 6 实现后复测”。
