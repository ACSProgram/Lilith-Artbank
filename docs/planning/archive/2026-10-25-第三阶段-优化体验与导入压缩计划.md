# 第三阶段：压缩体验整改与导入即压缩

阶段：**已完成并归档（2026-10-25）**；实施与计划的差异见 [当前阶段状态](../current-handoff.md)
前置：图片空间优化批次 1–2 已完成（见 [图片空间优化计划](2026-10-25-图片空间优化计划.md) 第 13 节实测结果）
范围：四项——长边输入、抽样滑块、估算卡死、进度条跳批、导入时自动压缩

## 1. 问题与定位

| # | 现象 | 定位结论 |
| --- | --- | --- |
| 1 | 长边只能选 4 个固定值，抽样只能选 3 个固定值 | 纯界面限制，后端也是硬校验 |
| 2 | 估算有时卡在末尾，有时永远停在「正在读取估算结果…」 | **已定位为确定性 bug**，见 3.3 |
| 3 | 执行进度一次跳 1000 张，中间不动 | **已定位**：`report()` 在整批编码完成后才调用 |
| 4 | 导入时没有压缩选项，只能导完再跑一遍全库 | 缺功能；导入时已经解码过，可零成本复用 |

关键事实：导入管线的 `build_prepared()` 在写文件前**已经解码整张图**（算缩略图、pHash、主色都用它）。这意味着「导入即压缩」不需要额外解码，比事后批量压缩少一次完整读盘 + 解码。

## 2. 3.1 长边上限改为自由输入

### 现状

`OptimizeDialog.tsx` 的 `MAX_EDGES` 是四个固定项：不限 / 4000 / 3000 / 2400。后端 `OptimizeOptions::validate()` 只挡住 `< 64`，没有上限。

### 设计

- 控件从下拉框换成**数字输入框**，右侧单位 `px`，留空表示不限。
- 保留三个快捷按钮（4000 / 3000 / 2400 / 不限）贴在输入框下方，点一下填入。熟手用按钮，特殊需求直接输。
- 合法范围 **64–65535**：
  - 下限 64 沿用后端现有判据，避免误输入把整库缩成缩略图
  - 上限 65535 对齐 `import/decode.rs::MAX_DECODE_EDGE`，超过这个值的图本来就解不进来
- 输入过程中的空值与中间态（例如刚敲了一个 `4`）不报错，只在失焦和点「估算」时校验；非法值就地标红并禁用估算按钮。
- **与 WebP 尺寸上限联动**：输出选 WebP 且输入值 > 16383 时，在字段下方显示一行提示——

  > 超过 16383 px 的图无法编成 WebP，会被跳过。设为 16383 或更小可让它们先缩放再编码。

  这条直接解决批次 2 遇到的那个坑（391×17799 只能跳过）。用户只要把长边设到 16383 以内，超大图就会进缩放流程，而不是整张放弃。

### 后端

- `imageops/optimize.rs::validate()` 增加上限校验：`max_long_edge > 65535` → 报错「长边上限不能超过 65535」。
- 前端与后端用同一组边界常量，避免各写一套。

## 3. 3.2 估算抽样改为离散滑块

### 现状

`SAMPLE_SIZES = [100, 200, 500]`（前端下拉框），`SAMPLE_CHOICES = [100, 200, 500]`（后端硬校验，`state.rs` 里拒绝其他值）。后端采样预算另外 `clamp(1, 2000)`。

### 设计

- 控件换成 `<input type="range">`，**离散刻度**：
  - 范围 **50–2000**，步长 **50**
  - 默认 200
  - 关键刻度标注：50（快）· 200（默认）· 500 · 1000 · 2000（准）
- 数值实时显示，并附**预计耗时**：按实测吞吐换算，JPEG 约 61 张/秒、WebP 约 12.7 张/秒。
  - 50 张 ≈ WebP 4 秒 / JPEG 1 秒
  - 2000 张 ≈ WebP 2 分 40 秒 / JPEG 33 秒
- 拖动时**不启动估算**，只在松手后（防抖 300ms）才允许点「估算」；避免每拖一格就重算。
- 说明文案保持克制：只写「样本越多越准，也越慢」，不承诺精度百分比（批次 2 实测 200 张样本平均误差 14.6%，写死了会被当成承诺）。

### 后端

- `SAMPLE_CHOICES` 换成三个常量 `SAMPLE_MIN = 50`、`SAMPLE_MAX = 2000`、`SAMPLE_STEP = 50`。
- `state.rs::start_optimize_estimate` 的校验改为：值在 `[SAMPLE_MIN, SAMPLE_MAX]` 内且能被 `SAMPLE_STEP` 整除，否则报「估算抽样必须是 50–2000 之间、步长 50 的整数」。
- `optimize_estimate.rs` 里的 `sample_budget.clamp(1, 2000)` 上限已一致，不需要改。

## 4. 3.3 估算卡住：两个症状，两个根因

### 症状 A：永远停在「正在读取估算结果…」

**根因（确定性 bug）**

`OptimizeDialog.tsx` 的取结果 effect 依赖的是整个 `task` 对象：

```ts
const task = taskId ? find(taskId) : null;
useEffect(() => { ... }, [task]);
```

而 `TaskCenterProvider` 每 150ms 用一份**新快照对象**替换任务列表（`merge` 里 `previous.map(...)`）。于是：

1. 任务完成 → effect 触发 → 发起 `get_optimize_estimate`
2. 下一次进度事件（任何任务都算）到达 → `task` 变成新对象 → effect 重跑
3. 重跑前 React 执行上一轮的 cleanup，把 `disposed = true`
4. 在飞的 promise 稍后 resolve，`then` / `finally` 都因 `disposed` 直接 return
5. `loadingEstimate` 永远停在 `true`；而 `fetchedEstimate.current` 已置位，重跑直接 return，**永远不会重试**

这就是「有时候」卡住的原因——取决于那次请求有没有撞上 150ms 的进度事件。

**修法**

- 依赖从对象引用改成原始值：`[task?.taskId, task?.phase]`
- `disposed` 只在 taskId 真的变了时置位，不再因为快照刷新而废弃
- 加 5 秒超时，超时后显示「读取估算结果超时」+「重试」按钮，而不是无限转圈
- 结果缓存 `MAX_ESTIMATES` 从 5 提到 10；如果确实被挤掉，错误文案明确写「估算结果已被新的估算覆盖，请重新估算」

### 症状 B：卡在末尾（进度 99%/100% 不动）

**根因（部分定位）**

- 估算的进度只在「编码样本」阶段上报（`report(completed, sample_total)`）。样本编完之后还有汇总、缩放、构造结果，这段没有进度，进度条就停住。
- 扫描阶段一开始是 `report(0, 0)`，`taskPercent` 对 `total <= 0` 返回 0，所以大库扫描期间进度条完全静止，看起来像卡死。

**修法**

估算改成**四段式进度**，每段都有文案和推进：

| 阶段 | 文案 | 进度 |
| --- | --- | --- |
| 1 统计候选 | 正在统计候选图片… | 按已扫描行数 / 总数（`collect_candidates` 已按 400 分块，每块上报一次） |
| 2 抽样 | 正在挑选样本… | 立即完成，跳到该段末尾 |
| 3 编码样本 | 正在编码样本 k / n 张 | 按样本数 |
| 4 汇总 | 正在汇总结果… | 直接跳到 100% |

**验证方式**：A 修完后连跑 20 次估算（含中途穿插其他任务制造事件干扰），确认不再出现两种卡死。如果 B 仍复现，再查是否卡在 lane 排队（`TaskLane::Scan` 被长任务占住）或写入阶段。

## 5. 3.4 执行进度：按张上报

### 现状（已定位）

`library/optimize.rs`：

```rust
const BATCH_SIZE: usize = 1000;
for batch in jobs.chunks(BATCH_SIZE) {
    let results = pool.install(|| batch.par_iter().map(...).collect());  // 整批 1000 张跑完才返回
    for (row, result) in batch.iter().zip(results) {
        ...
        reporter.report(completed, total);   // 这里才上报
    }
    commit_batch(...);
}
```

进度条在一次 1000 张的并行编码期间完全不动，整批结束后瞬间跳 1000 张；然后 `commit_batch`（写文件 + 改库 + 删旧图）期间又不动。这正是「一次执行 1000 张，停一会继续下一批」。

### 修法

1. **编码阶段按张上报**：在 `par_iter().map()` 内部用 `AtomicUsize` 计数，每完成一张就调用 `reporter.report(completed, total)`。
   - `BatchReporter: Send + Sync`（`library/mod.rs`），`TaskHandle::report` 只是写共享状态，事件由独立 pump 线程每 150ms 发一次——从 rayon 线程调用安全且几乎零成本，不需要额外节流。
2. **提交阶段单独文案**：`commit_batch` 前发 `message("正在写入第 k 批")`，进度保持不回退。写入比编码快一个数量级，进度条只会轻微停顿。
3. `BATCH_SIZE` 保持 1000 不变——批量提交对事务效率有利，进度问题不该靠调小批量解决。

### 关于取消

`par_iter` 闭包里已有 `reporter.cancelled()` 检查，取消后剩下的图会立刻返回 `Ok(None)`，所以取消本身不慢。但这一批**已经编码完成的图仍会走完 `commit_batch`**，进度条会在取消瞬间再跳一次。按张上报后，用户能看到取消时真实停在哪一张，而不是突然从 3000 跳到 4000。

## 6. 3.5 导入时自动优化

### 定位

导入对话框新增开关，**默认不勾**。勾选后展开两项：

- 输出格式：**JPG** / **WebP**
- 质量档位：**极 / 高 / 中**（复用现有 `QualityTier`，与压缩任务同一套）

### 实现点

改 `import/pipeline.rs::build_prepared()`，位置在 `decode()` 之后、`publish()` 之前。

今天是：把 staged 原文件按 `{原哈希}.{原扩展}` 发布到 `content_file()`。

改成：

1. `optimize::plan()` 过判据 → `optimize::encode_ladder()` 编码（**完整 PSNR 阶梯**，与批量压缩同一份代码）
2. 成功且通过判据 → 把**编码结果**写成内容文件：
   - 文件名用**新字节的哈希**（不是源文件哈希）
   - 扩展名 `.jpg` / `.webp`，`format` 字段同步
   - `file_size` 用新长度，`optimized_at` 写当前时间
3. 任何一步不满足 → **保留原图**，导入照常成功，`optimized_at = 0`

### 不满足就保留原图的情形（已确认）

| 情形 | 处理 |
| --- | --- |
| 带透明通道但选了 JPEG | 保留原图 |
| 源文件带非 sRGB 色彩配置（输出装不下 ICC） | 保留原图 |
| 单边 > 16383 且输出 WebP | 保留原图 |
| 16 位源 | 保留原图 |
| 压完省不到 5% | 保留原图 |
| 编码失败 | 保留原图，计入日志 |

一律不阻塞导入，也不让单张失败影响整批。

### 为什么这个位置最划算

缩略图、pHash、主色都是从 `decoded.image` 算的，压缩前后是**同一张图**，所以这三样**不需要重算**。事后跑批量压缩则要重新解码一次、还可能因为「重算开关」再算一遍。

### 必须处理的三件事

1. **不可撤销**：原图不落盘。勾选框旁必须写明「原图不会保留，无法还原」，口径与批量压缩一致。导入确认按钮的二次确认里再提一次。
2. **去重语义变化**：内容哈希变成压缩后字节的哈希。同一张源图用同样参数重复导入仍然去重；**改了档位或格式会变成两条记录**。导入选项区要有一行说明。
3. **结果可见**：导入完成页增加一行「其中 N 张已压缩，省 X MB」。否则用户无法判断开关是否生效。

### 不做的

- 不生成独立的 `optimize` 操作记录（它是导入的一部分，不该在撤销链里多一条不可撤销记录）；但 `optimized_at` 要写，这样以后跑全库压缩会跳过它们。
- 不做全局偏好设置，只在导入对话框里选。
- 不勾选时行为与今天完全一致。

### 代价

| | 吞吐 | 1000 张耗时 |
| --- | --- | --- |
| 不勾选 | 现有导入速度 | 不变 |
| 勾选 + JPEG | 约 60 张/秒 | 约 17 秒 |
| 勾选 + WebP | 约 12.7 张/秒 | 约 80 秒 |

（含完整阶梯 1–4 次编码，数据来自批次 2 全库实测。）

## 8. 验收

### 自动

1. 长边：空值 = 不限；63 / 64 / 65535 / 65536 的边界行为符合预期。
2. 抽样：49 / 50 / 55 / 2000 / 2050 的校验结果符合预期（越界与不整除都拒绝）。
3. 抽样：后端实际使用的样本数等于请求值（不静默夹紧）。
4. 进度：mock 一个 3000 张的任务，断言 `report()` 的调用次数 > 批量数（证明是按张而非按批）。
5. 估算：`get_optimize_estimate` 超时后返回可重试错误，不挂死。
6. 导入：勾选后内容文件扩展名、`format`、`file_size`、`optimized_at` 一致；不勾选时字段与今天完全相同。
7. 导入：透明图 + JPEG 时保留原 PNG，`optimized_at = 0`。
8. 导入：同一源图同参数导入两次仍判重复；改档位后变成两条。
9. 导入：缩略图/pHash/主色与「不勾选」时一致（证明没有因为压缩而偏移）。

### 手工

1. 连跑 20 次估算，中途故意切标签、启动别的任务，确认不再卡在「正在读取估算结果…」。
2. 全库执行一次，观察进度条是否按张平滑推进、取消是否在 1 秒内生效。
3. 导入 50 张（含透明 PNG、宽色域图、超长图各几张），确认特殊图被保留、普通图被压缩。
4. 导入完成页数字与实际磁盘增量对得上。
