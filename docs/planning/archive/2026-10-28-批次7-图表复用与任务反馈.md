## 一、实测：进度条为什么“卡住”

只读查询主库 `G:\Lilith Image Library\.artbank\library.db`（396,180 张在库），按默认参数（JPEG 输出、跳过已处理、非透明、非 GIF、bpp ≥ 0.12）过滤后候选 **127,837 张 / 179.58 GB / 853.24 GP**，平均 6.67 MP/张。执行顺序按 bpp 从高到低（`src-tauri/src/library/optimize.rs:538`），旧进度条的分母是候选像素总量（`:546` 改前的 `Σ pixels`）：

| 已处理张数 | 占张数 | 占像素（= 进度条） | 占体积 |
| --- | --- | --- | --- |
| 200 | 0.16% | 0.088% | 1.30% |
| 1,000 | 0.78% | 0.339% | 3.74% |
| 5,000 | 3.91% | 2.042% | 15.37% |
| 10,000 | 7.82% | 4.100% | 25.34% |
| 30,000 | 23.47% | 12.665% | 50.03% |
| 60,000 | 46.93% | 27.900% | 72.18% |
| 100,000 | 78.22% | 55.995% | 90.71% |

- bpp 降序把“像素少、细节高”的小图排在前面：最前 2,000 张平均 bpp 16.6、平均 2.93 MP，而候选池平均是 6.67 MP、中位 2.59 MP。
- 于是**跑完 1%（1,278 张）只推进 0.43% 的条**，整数百分比要等到约 2,750 张（2.15%）才第一次变成 1%。
- 更根本的是**分辨率**：12.8 万张候选时 1% ≈ 1,278 张，按 5 张/秒算是 4 分钟一个整数百分点；候选池越大越慢。不管计量单位换成什么，整数百分比在万张量级上都推不动。
- embedding 按张计、分母是张数，且面板上“N / M”在跳，所以“一直在动”。
- 另有一段完全没有上报：点确认后要先 `resolve` + 读候选 + 逐张 `stat` 复核（`src-tauri/src/app/state.rs`），十几万张候选要十来万次 stat，这段时间 `progressPercent` 为空、`completed` 为 0。

**结论**：不是事件丢失，不是后台没跑。是“像素计权 + bpp 排序”让早期进度被摊薄一半以上，再叠上整数百分比的分辨率，观感就是卡死。修法只要两步：单位改成张数，百分比在低值段给一位小数（由张数直接算）。不做权重模型。

## 三、概览环图（15）

**现状**：类型、评分、标签三块共用 `StatBars`（`src/modules/library/FolderInspector.tsx:91-110`）；数据形状已够用（类型合并“其他”`src/modules/library/folderStats.ts:8-23`，评分固定六档 `:25-31`）。

**改法**：

- `folderStats.ts` 加两个纯函数：
  - `donutSegments(items, 5)`：前 5 类 + “其他”，返回 `{ key, label, value }[]`，0 值项剔除。
  - `scoreSegments(scores)`：5→1→未评分六档，0 张的档保留（图例显示 0，不画弧）。
- `FolderInspector` 内新增本地 `StatDonut`（不抽公共组件、不改压缩那张环图）：`<svg>` + 每段一个 `<circle>` 配 `stroke-dasharray`，轨道用 `--border-strong`，弧用分类色；中心两行字。
- `tokens.css` 加 6 个分类色 + 1 个“其他”色，明暗各一套；颜色用完即并入“其他”。
- 中心文案：占比最大那段的百分比 + 段名（`62% / JPEG`、`41% / ★★★★`）。
- 图例：色块 + 名称 + `张数 · 百分比`，两列网格，宽度不够降一列。
- 标签保持现有 `StatTags` 条形，不动宽度基准与数字列。
- 空文件夹与无匹配沿用现有空态；切换文件夹不加过渡动画。

详情面板固定 320 px（`src/styles/index.css:2665-2675`），可用约 296 px：环图 96 px + 间距 10 px + 图例约 190 px，按此排版。

## 四、压缩执行复用估算视图（16）

**现状**：执行时另做了一套 `OptimizeExecutionPanel`（`src/app/OptimizeDialog.tsx:196-313`：进度条、两行事实、字节、速度/ETA、当前文件、时间轴曲线），估算视图被折叠进 `<details>`（`:1137-1301`）。两条曲线的横轴还不一样：执行曲线是“已用时”（`OptimizeCharts.tsx:262-370`），估算曲线是“覆盖率”（`:136-250`）。

**改法**：估算视图始终显示，不再有第二套。

- **执行时只保留一行状态**（这些估算视图里没有）：进度条 + `已完成 3,214 / 127,837` + `已用时 41 分钟 · 预计还需 22 分` + `3.4 张/秒` + 当前文件。原 `OptimizeExecutionPanel` 的其余部分删除，时间轴曲线 `OptimizeProgressChart` 删除。
- **结果块**：`已省 {savedBytes}` 后面跟 `预计 {estimate.savingsBytes}`；`体积 {originalBytes} → {originalBytes - savedBytes}` 后面跟预计体积。两者都已在快照里（`TaskSnapshot.original_bytes` / `saved_bytes`，`src-tauri/src/app/tasks.rs:177-179`）。
- **环图**：段改成“已替换 / 已跳过 / 失败 / 未处理”，前三个取快照的 `completed` / `skipped` / `failed`，分母取**任务自己报的 `total`**（不用 `estimate.candidateCount`：估算与执行前复核可能差几张，混用会把“未处理”夹成 0）；中心显示已替换占比。完成的段数与估算的“会处理 X%”自然可对照。
- **收益曲线**：`OptimizeCurveChart` 加一个 `actual: { coverage, savingsBytes }[]` 属性，用虚线画预估、实线画实际，同一覆盖率轴（分母都是候选总体积，口径一致）。实际点由前端按快照采样：`coverage = original_bytes / estimate.candidateBytes`、`savingsBytes = saved_bytes`，沿用现有 2 秒最小间隔与点数上限。
- **里程碑表**：加一列“实际”，覆盖率达到 20% / 40% / 60% / 80% / 100% 时填，未到达显示 `—`。
- 结束后在曲线下方给一行“实际 vs 预计：耗时 · 处理张数 · 节省空间”，取消或失败时在行尾补“已停止”。

数据全部来自现有快照与估算对象，**不加后端字段、不加事件通道**。

## 五、进度（17）

- `src-tauri/src/library/optimize.rs:546`：`total_units` 从 `Σ pixels` 改为 `jobs.len() as u64`；`:665` 的 `advance_units(row.pixels())` 改为 `advance_units(1)`。
  - 附带好处：百分比、速度、ETA 三者现在口径不一（速度/ETA 按张、百分比按像素），改后统一。
  - 已知代价：前期小图多、单张快，进度会跑得比时间快；后期大图慢，会显得“越走越慢”。这是“按张计”的固有性质，与 embedding 一致，接受。
  - 分母同时收窄到候选池：执行前被排除的图片（已处理过、bpp 太低、超出 WebP 尺寸）不进分母也不进“已跳过”，否则进度条开局就六成。估算视图的“未纳入候选”仍然照常列出它们。
- 准备段只改文案，不改签名：`state.rs` 的 worker 在 `verify_sources` 前调 `worker.set_message("正在核对原图…")`，进入编码前调 `worker.set_message("正在编码… 第 k 批 0/n")`。**不**给这一段加百分比。
- 百分比显示：`OptimizeDialog` 的顶部数字用 `completed / total` 直接算，`<10%` 时给一位小数（`0.4%`），`≥10%` 取整；不依赖后端 `progressPercent` 的精度，不动该字段类型。
- 补充（2026-10-28 用户实测后决定）：`completed` / 条形 / 速度都只在批次结束时前进，256 张一批在 5 张/秒下约 51 秒不动，观感等于卡死。改为在编码期间用现有 message 通道给批内计数「正在编码… 第 k 批 m/256」，每 16 张更新一次（`MESSAGE_STEP`）；不新增快照字段、不改 `completed` 的「已提交」语义。
- 任务胶囊与批量面板保持现有显示（整数百分比），不扩散改动。

## 六、取消中（18）

只做显示，不改取消机制。

- `src-tauri/src/app/tasks.rs`：`TaskPhase` 加 `Cancelling`；`is_terminal()` 不含它；`request_cancel()` 在设置标记后调用 `set_phase(TaskPhase::Cancelling)`（`set_phase` 已带“非终态才写”的保护，`src-tauri/src/app/tasks.rs:303-312`）。排队中被取消同样落到 `Cancelling`，随后由排队等待的取消谓词直接写 `Cancelled`。
- 前端：`TASK_PHASE_LABELS` 加 `cancelling: "取消中"`；`isTaskActive` 已按“非终态”判断，无需改。
- 显示：压缩面板与任务胶囊的标题在 `cancelling` 时显示“取消中”，取消按钮禁用；进度条加一条静态 45° 斜纹（不用无限动画）。
- 文案说明在等什么（`CANCEL_PENDING_NOTE`）：
  > 等当前批次提交完成，已执行的部分不会撤销。
- 不改的部分：通道仍是 `sync_channel(1)` 上的阻塞 `send`；committer 仍会提交已取走的批；复核段仍不检查取消。因此**取消延迟不变**（不在本批缩短）。

## 七、附带改动：压缩期间允许读图

压缩原先独占根路径写锁：执行几十分钟里查看器、MCP 拼图与复制都会报冲突。而压缩只替换图片内容、不改文件夹结构与文件名，这类写不需要挡住读者。

- `concurrency/resources.rs`：路径访问级从“读 / 写”两级扩成“读 / 原地替换 / 写”三级。读与读、读与替换都不互斥；移动、删除、导入与另一个压缩仍是写，与替换互斥。
- `state.rs`：压缩的准入从 `with_paths(vec![PathScope::write("")])` 改成 `ResourceRequest::path_replace("")`。
- 安全性：发布仍是“临时文件 + 原子重命名”，读者要么读到旧图要么读到新图。读者正持着句柄也能替换——Rust 的 `File::open` 带 `FILE_SHARE_DELETE`，Windows 的重命名会成功，旧文件在最后一个句柄关闭后才真正消失。
- 契约同步到[图库与元数据](../../modules/library.md)的“路径锁分三级”一条。

## 十、用户手工验收

1. 选中一个文件夹：类型与评分是环图，中心是最大段占比，图例张数与百分比之和为 100%；标签仍是条形。
2. 只有一种格式的文件夹：类型环图是一整圈，图例一行；评分为 0 的档只出现在图例。
3. 空文件夹与“无匹配”各自的空态正确；切换文件夹不闪。
4. 深色主题下六种分类色可区分，“其他”不抢眼。
5. 压缩执行中：面板就是估算视图，环图随完成增长，`已省` 旁显示预计值；曲线出现实际实线并沿预估虚线走。
6. 进度条：从第一张起就在动，低于 10% 显示一位小数，`已完成 N / M` 持续在变；不再出现“后台在跑、界面停在 0%”。
7. 点取消：立刻显示“取消中”，按钮禁用并转斜纹，文案说明在等当前批；结束后显示“已取消”。**取消耗时与改动前相当**，这是本批的已知取舍。
8. 完成后对照一行给出实际与预计的耗时、张数、节省空间。
9. 压缩执行中打开查看器翻图、复制图片、跑一次 MCP 拼图：都应正常，不再报“正在处理图库内容”冲突；同时改名/移动/导入仍应被拒绝。

压缩与取消请用复制样本或 `G:\Lilith Test Library`；`G:\Lilith Image Library` 只作只读统计。代理不启动应用、不截图，界面由用户验收。

## 十一、边界与未决

不做：

- 不改压缩判据、质量梯子、跳过策略、bpp 排序、批大小。
- 不改估算公式、抽样、误差区间（原批次 7 已放弃）。
- 不缩短取消延迟；不 `abort` 线程；不做取消后的回滚。
- 不为进度引入权重模型或浮点百分比链路。
- 不放开压缩期间会改路径的写（移动、删除、导入、另一个压缩）；不改导入与编辑的访问级。

未决（实现时确认，不阻塞）：

- 进度按张后“越走越慢”的观感是否可接受；若不可接受，再谈按张 × 尺寸分档，而不是现在先加常数。
- 环图图例在 296 px 内两列是否过挤，真实窗口看过后再定，不改面板宽度。
- 压缩期间读图的并发在真实窗口里是否稳定（查看器反复翻图 + 大图解码时），需要用户手工验收第 9 条覆盖。
