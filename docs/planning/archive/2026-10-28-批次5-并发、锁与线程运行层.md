# 使用反馈整改（第二轮）批次 5：并发、锁与线程运行层

日期：2026-10-28
状态：**已落实代码与自动检查，待真实窗口验收**。资源矩阵、目标行为与测试设计保留在本文；实际落点、检查结果与未实测项见末尾“十三、落实记录”，验收清单见 `../todo.md`。范围对应[使用反馈整改计划（第二轮）](2026-10-28-使用反馈整改计划（第二轮）.md)的编号 8、13，以及其中的批次 5 边界与已确认决策。

本轮要解决的不是“把锁去掉”，而是把当前的“全库空闲”换成资源级判断：只有真正读写同一份资源的操作才互相等待；读图任务不再挡住文件夹维护；线程预算、进度与尾部收尾统一到一套运行层。

## 零、先回答两个设计问题

### 0.1 线程预算为什么不按本机指标定 8

一般桌面软件的做法不是给每类任务各定一个魔法数字，而是：

- 后台工作线程默认取“逻辑核数 − 1”，留一个核给界面、输入和系统。
- 线程数作为一个用户设置暴露出来；内存紧张或界面卡顿时由用户调低。
- 每类任务不再各自建不同大小的池，而是共享一个预算或一个工作队列；队列有界，避免无限堆积。
- 专业图像/视频软件会再按“每帧/每张图的峰值内存 × 并发数”做内存预算；这需要可靠的尺寸预估，不属于本批。

本机 16 逻辑核的实测只是证据，不是默认值：编码 4 / 8 / 12 / 15 线程分别是 9.1 / 16.2 / 15.2 / 16.2 张/秒，8 线程是吞吐拐点，15 线程没有更快。这个结论会写进性能文档和设置建议，但**不会**把 `8` 写死成默认。批次 5 采用一个全局图像工作预算，默认 `max(1, 逻辑核 − 1)`，上限由现有 `performance.workerThreads` 设置控制（1–128）。如果统一后 15 线程让压缩/估算的峰值内存明显变差，再按实测结果讨论是否把默认改成 `min(核数 − 1, 8)`；这是测量后的决策，不是本机的先验。

### 0.2 分段锁怎么落地，怎么避免死锁

采用一张**资源锁表**，而不是给每个任务写一套 if：

- 资源分两类：少量全局资源（库会话、操作时间线、内容发布、元数据写、AI 服务）和**按文件夹子树**的路径读写锁。
- 所有锁一次性申请：检查全部资源，全部可用才同时占用；否则一个都不占，等待后重试。这样不存在“拿着一把锁等另一把”的环。
- 任务开始前先拿粗粒度资源（会话、时间线、全局写资源、任务级路径范围），运行中只在读某张原图时短暂拿该图片所在文件夹的读锁；不会拿着细锁再去要粗锁。
- 数据库写连接、缩略图包/特征包的内部互斥始终在资源锁之后获取，持有它们时不再申请资源锁。
- 等待都有超时或取消检查；文件夹维护等当前一次读图最多等 10 秒，超时给出“哪个任务正在读哪个文件夹”的文案。
- 路径锁按子树做，不按每个文件做：读 `/角色/a` 的图片拿 `/角色/a` 的读锁；重命名 `/角色/a` 拿写锁。读者每读完一张就释放，写者等待当前这一张读完即可进入，后续读图按新路径重新解析。

这样既满足计划里“先按根目录或文件夹子树、不做每文件一把锁”的边界，也不会让一次长任务把文件夹操作挡到最后。

## 一、现状审计

### 1.1 任务总线的准入规则

- `TaskKind::lane` 把任务分成 `write` / `ai` / `scan` 三条 lane（`src-tauri/src/app/tasks.rs:61`、`:73`）。
- `TaskLane::conflicts_with` 规定 write 与任何 lane 冲突，ai 与 scan 可以并行（`src-tauri/src/app/tasks.rs:108`）。
- 长任务冲突时默认排队：同 lane FIFO、write 优先、write 等待者会阻止后面的 ai/scan 启动（`src-tauri/src/app/tasks.rs:513`、`:870`）。
- 短操作（编辑保存、评分、标签、描述、集合/文件夹元数据、移入回收站/恢复）不建任务条目，直接 `acquire_immediate(TaskLane::Write)`（`src-tauri/src/app/tasks.rs:700`、`src-tauri/src/app/state.rs:385`）。
- `is_idle` 把 lane 计数、等待者和未结束任务一起判断（`src-tauri/src/app/tasks.rs:605`），打开/创建/关闭图库与文件夹维护都用它。

**后果**：AI/扫描任务占着 `ai` / `scan` lane 时，`acquire_immediate(Write)` 的 `can_start` 为假，所以文件夹重命名、移动、删除一律被挡住。这不是数据库不支持并发，而是应用层把“写的资源”粗化成了“全库写 lane”。

### 1.2 文件夹维护的准入与缺口

- 界面上的文件夹新建/重命名/移动/删除、同级排序、一次性排序都走 `begin_maintenance`：先 `ensure_no_activity`，再占 write lane（`src-tauri/src/app/state.rs:335`、`:801`、`:808`、`:815`、`:822`、`:836`、`:852`、`:864`）。
- 这些操作改名的是磁盘目录：重命名/移动/删除在数据库事务内直接 `std::fs::rename` / `remove_dir`（`src-tauri/src/library/folders.rs:168`、`:265`、`:850`）。
- **MCP 的 `folders_modify` 完全不经过任务总线**：只检查 MCP 模式、拿 MCP 写互斥，然后直接调用文件夹领域函数（`src-tauri/src/mcp/tools/folder.rs:77`、`:82`、`:113`、`:158`、`:221`、`:262`）。它既不占 write lane，也不检查 `is_idle`。导入/压缩进行中，AI 可以通过 MCP 重命名目标文件夹，造成路径与批次状态脱节。这是本批必须补的缺口。
- 文件夹重命名/移动在事务内先改磁盘目录，再更新 `folders.path` 子树（`src-tauri/src/library/folders.rs:168`、`:171`、`:265`、`:275`）。数据库读者在提交前仍看到旧路径，磁盘目录已经是新位置；如果 AI 任务恰好在这个窗口读原图，会读到旧路径失败。当前靠“全库空闲”把这个窗口整体排除。

### 1.3 哪些任务真的读写路径

| 操作 | 路径行为 |
| --- | --- |
| 导入（图库） | 向目标文件夹写新原图；可能创建目标下的子目录；图库导入会丢弃临时区同内容行并删其文件（`src-tauri/src/import/pipeline.rs:203`、`:774`）。 |
| 导入（临时） | 只向临时文件夹写新原图，不写操作记录。 |
| 缩略图重建 | 按图片路径读原图，向缩略图包追加，更新指针（`src-tauri/src/library/thumbs.rs:269`、`:285`、`:294`）。 |
| 移动图片 | 把原图从源文件夹改名到目标文件夹，更新 `folder_id` 与操作记录。 |
| 永久删除 / 清空回收站 | 只写待释放标记，不碰文件；释放任务稍后删原图（`src-tauri/src/library/metadata.rs:1397`、`:1407`）。 |
| 撤销 / 重做 | 可能改名文件夹、恢复/删除原图、追加缩略图、改描述/标签/评分（`src-tauri/src/library/history.rs:2984`、`:3152`、`:3363`、`:3742`）。 |
| 释放删除文件 | 按待释放标记删行、删原图与查看器预览（`src-tauri/src/library/history.rs:4425`）。 |
| 压缩估算 | 读样本原图，不写库、不写文件；样本行里的文件夹路径来自候选收集（`src-tauri/src/library/optimize_estimate.rs:879`、`:894`）。 |
| 压缩执行 | 读原图、写新内容文件、删旧原图，提交事务（`src-tauri/src/library/optimize.rs:614`、`:735`、`:974`）。 |
| 临时区特征 | 读临时区原图，写特征包与特征指针。 |
| AI embedding / pose | 优先读 512px 缩略图；缩略图缺失时回落读原图（`src-tauri/src/ai/input.rs:18`、`:30`）。 |
| AI 描述 | 总是读原图，缩放到 1536px 后上传（`src-tauri/src/ai/input.rs:34`、`:38`）。 |
| 相似分组 | 只读数据库 pHash/embedding 与特征包，不读原图（`src-tauri/src/ai/runtime.rs:955`）。 |
| 查看器预览 | 按需读原图，写 `.artbank/temp/viewer/` 缓存。 |
| MCP 拼图/读图 | 只读缩略图或原图，写 `.artbank/temp` 拼图缓存。 |

结论：真正需要保护的是**原图路径**。数据库读写已经由单写连接 + WAL 处理；缩略图包/特征包是追加式且内部有互斥；临时预览缓存不在文件夹子树里。把路径锁从“全库”缩到“文件夹子树”，就能让读图任务与文件夹维护并行。

### 1.4 线程池与线程数

- 导入：请求里的 `worker_threads`（1–128），为空时用逻辑核 − 1；另起 1 个写线程（`src-tauri/src/import/pipeline.rs:241`、`:250`、`:236`）。
- 压缩/估算：独立 rayon 池，`min(核数 − 1, 8)`（`src-tauri/src/library/mod.rs:53`、`:57`、`:66`）。
- 缩略图重建：单线程循环（`src-tauri/src/app/state.rs:1564`）。
- AI：Rust 侧逐张顺序解码、顺序发 HTTP（`src-tauri/src/ai/job.rs:185`）。
- 相似分组：单线程 CPU 扫描（`src-tauri/src/library/similarity.rs:243`）。
- 设置里的 `performance.workerThreads` 只影响导入；压缩/估算不读它（`src-tauri/src/app/settings.rs:196`、`:327`）。

**后果**：同一台机器上导入可以开 15 个线程，压缩/估算固定 8 个；任务并行时没有统一的“图像工作”上限。用户看到的“木桶效应”不是线程数本身，而是批末屏障、串行提交/删旧与写线程收尾。

### 1.5 压缩执行的尾部构成（编号 8）

- 候选先按 bpp 从高到低排序（`src-tauri/src/library/optimize.rs:473`）。
- 每 1000 张一批；批内 `pool.install(...par_iter())` 编码，**等整批全部完成**才进入提交（`src-tauri/src/library/optimize.rs:486`、`:492`、`:506`）。
- 然后串行 `commit_batch`（发布新文件、事务提交），再并行删旧图（`src-tauri/src/library/optimize.rs:559`、`:572`、`:974`）。
- 编码池在提交/删旧期间空闲；提交/删旧期间进度不再前进，最后一批会停在接近 100% 但仍在写。
- 每批最多 1000 张；最后一批哪怕只剩几十张，也要等“最慢的那张”编码完，再等整批提交与删旧。批次越大，这个尾部越明显。
- 实测：553 张、批大小 1000 时总墙钟 0.93 s，其中发布 291 ms、提交 10 ms、删旧 106 ms；发布 + 删旧约占 43%。这部分目前完全串行在编码之后（见第七节）。

### 1.6 导入的尾部构成（编号 8）

- 工作线程用 `scanned.files.par_iter()` 处理；结果通过深度 256 的有界通道送入唯一写线程（`src-tauri/src/import/pipeline.rs:273`、`:220`、`:40`、`:42`）。
- 写线程每 64 张或 250 ms 提交一次（`src-tauri/src/import/pipeline.rs:646`、`:672`）。
- 工作线程结束时 `pool.install` 先等所有工作线程退出，再 `writer.join()` 等写线程把缓冲区刷完（`src-tauri/src/import/pipeline.rs:281`、`:282`）。
- `ImportJob.inc_processed` 在工作线程送出结果时就增加，不是入库提交后增加（`src-tauri/src/import/job.rs:271`、`:300`）。所以界面可能先到 100%，再进入“收尾”。
- 通道深度 256 允许最多几百个已完成结果堆在写线程前面；如果写线程落后，最后要一次性排空，形成收尾尾巴。
- 静态 `par_iter` 的最后一个文件如果特别大，也会成为最后一张的等待点。

### 1.7 生命周期与现有锁序

- SQLite 单写连接 + 多读连接，读走 WAL，写始终串行（`src-tauri/src/library/db.rs:14`、`:61`、`:92`）。
- 文件夹重命名/移动在持有数据库写连接期间做磁盘改名，事务时间包含文件系统操作。
- 导入在数据库事务内追加缩略图包（`src-tauri/src/import/pipeline.rs:692`、`:719`）；压缩在事务内追加缩略图包（`src-tauri/src/library/optimize.rs:808`、`:838`）；缩略图重建先追加包再写数据库（`src-tauri/src/library/thumbs.rs:294`、`:299`）。包内部互斥与数据库写锁不会同时持有到“等对方”的深度，但顺序不统一；当前靠 write lane 串行化导入/压缩/重建，才没有交叉问题。
- AI 特征包先追加再写数据库（`src-tauri/src/ai/embedding.rs:53`、`:61`），同样不在持有包互斥时等数据库。
- `LiveOperation` 的 `Drop` 会写数据库（批次 4）；它不能在持有数据库写锁时被丢弃，否则可能自锁。当前由任务线程在锁外收尾。
- 临时区、估算缓存、导入回执、MCP 确认队列都在换库/关库时清空；换库/关库目前依赖 `is_idle`。

## 二、资源模型（本批的框架）

### 2.1 设计原则

1. **按资源声明，不按任务名特判。** 每个操作声明自己要读/写哪些资源；冲突判断只看资源集合。
2. **路径按文件夹子树。** 不建每文件锁；读者每次读一张原图时短暂持有该文件夹的读锁。
3. **全局写资源尽量少。** 只有在语义上确实全局互斥的东西才做成全局资源：库会话、操作时间线、内容发布、图片元数据写入、AI 服务。
4. **一次申请全部粗锁。** 拿不到就一个都不拿，等待重试；运行中只追加当前文件夹的短读锁。
5. **锁内不做等待。** 数据库写连接、包内部互斥、图像预算都在资源锁之后获取；持有它们时不再申请资源锁。
6. **保留任务循环与队列。** 不把导入/压缩塞进一个全局调度器；任务体仍是各自线程/循环，资源表只负责准入。
7. **可取消、可超时。** 长任务排队可取消；文件夹操作等待当前读图最多 10 秒；AI 单张读图等待可取消。

### 2.2 资源键

| 资源 | 模式 | 说明 |
| --- | --- | --- |
| `session` | 读 / 写 | 所有任务与短操作持有读；打开/创建/关闭/切换图库申请写，要求没有其他持有者与排队任务。 |
| `timeline` | 共享 / 独占 | 普通内容写入追加操作记录时共享；撤销、重做、清空记录独占。 |
| `content.writer` | 独占 | 发布/替换/删除原图内容的写任务：导入、压缩、移动图片、编辑保存、释放、撤销/重做。全局互斥，保护去重索引、批次原子性、操作记录与内容哈希路径。 |
| `metadata.writer` | 独占 | 图片元数据写入：评分、标签、描述、集合成员、回收站状态、AI 描述。暂不按图片行拆细，避免同一行不同列语义未审计就并发。 |
| `ai.service` | 独占 | AI embedding / pose / 描述 / 临时区特征；模型同一时间只驻留一个。相似分组不占它。 |
| `paths` | 读 / 写，按子树 | 图库内相对文件夹路径；根为 `""`。读者读图时短暂持有；写者改目录时持有整个子树。 |
| `image.budget` | 信号量 | 全局图像工作许可；不是冲突资源，不参与准入判断，只限制同时解码/编码的数量。 |

包（缩略图/特征）不再作为全局锁：它们本身就是追加式并带内部互斥，读者按偏移读，多个写者追加不会互相覆盖。数据库指针提交仍由单写连接串行。

### 2.3 路径锁规则

- 键是图库根目录下的相对文件夹路径，`/` 分隔、去首尾 `/`、统一小写（Windows 路径大小写不敏感），根为 `""`。
- 冲突：两个路径相等，或一个是另一个的前缀（按 `/` 边界），且至少一个是写。
- 读/读兼容；写/写、写/读互斥。
- 根读 `""` 只与根写和任意子孙写冲突，不与子孙读冲突；根写与所有路径冲突。
- **写者优先**：某个路径上有写者在等时，新的读者不再插队；已有读者读完即放行写者。这样一次长 AI 任务的逐张读不会把文件夹重命名饿死。
- 读者拿锁的粒度是“当前图片所在文件夹”，读完立即释放；后续图片重新按数据库里的当前文件夹解析路径。
- 一次操作可以申请多个路径（例如移动图片的源与目标、文件夹重命名的旧路径与新路径），全部按上述规则一次判断。

### 2.4 操作资源矩阵

| 导入（临时） | 读 | — | C | `R /临时`（任务级） | 是 | 排队 |

| 释放删除文件 | 读 | — | C | `W /` | 是 | 排队 |
| 压缩估算 | 读 | — | — | 每张样本 `R /所在文件夹` | 是 | 排队 |
| 压缩执行 | 读 | T | C | `W /`（任务级） | 是 | 排队 |
| 临时区特征 | 读 | — | A | 每张 `R /临时` | 是 | 排队 |
| AI embedding | 读 | — | A | 缩略图缺失时每张 `R /所在文件夹` | 是 | 排队 |
| AI pose | 读 | — | A | 同上 | 是 | 排队 |
| AI 描述 | 读 | T | M、A | 每张 `R /所在文件夹` | 是 | 排队 |
| 相似分组 | 读 | — | — | — | 1 个许可 | 排队 |

#### 短操作与只读路径

| 操作 | S | T | 全局写 | 路径 | B | 准入 |
| --- | --- | --- | --- | --- | --- | --- |
| 文件夹新建/重命名/移动/删除 | 读 | T | — | `W /旧`、`W /新`（新建/删除为单个路径） | 否 | 等最多 10 s，失败即报冲突 |
| 文件夹同级排序/一次性排序 | 读 | T | — | `W /父` 或 `W /目标`（保护排序字段所在子树） | 否 | 等最多 10 s，失败即报冲突 |
| 编辑保存 | 读 | T | C | `W /所在文件夹` | 是 | 立即失败 |
| 评分、标签、描述、集合成员、回收站 | 读 | T | M | — | 否 | 立即失败 |
| 查看器预览 | 读 | — | — | 每张 `R /所在文件夹` | 是 | 尽力而为，失败不弹任务 |
| MCP 读图/拼图 | 读 | — | — | 每张 `R /所在文件夹` | 拼图生成时是 | 尽力而为 |
| 打开/创建/关闭图库 | S! | — | — | — | — | 要求没有任务、短操作与排队任务 |

说明：

- 压缩执行占 `W /`（根写）是因为候选集合可能覆盖全库；它仍然会拒绝所有文件夹维护，符合已确认决策。AI 任务也会被它挡住，因为压缩会替换候选图片的原图，这是真实冲突，不是实现偷懒。以后若要细化，可以把候选文件夹集合作为多路径写锁，但那需要按批重新校验，暂不做。
- 导入只占目标子树读，不占根写：它写的是**新**内容文件，不改已有原图；目标子树读足以阻止目标目录被改名/移动/删除，同时允许 AI 读目标里的已有图片。文件夹操作在目标子树之外可以并行。
- 编辑保存、移动、释放、撤销/重做占内容写或根写；它们与 AI 的冲突范围就是它们实际会改的文件夹。
- `metadata.writer` 目前是全局的：同一图片行不同列的并发语义还没有逐个审计，先保证评分/标签/描述/AI 描述之间不互相覆盖。文件夹操作不占它，所以“AI 描述运行时改文件夹”是允许的。
- 实施补充：所有 AI 图像任务与缩略图重建也占 `content_writer`。原矩阵只按“读原图”考虑路径锁，但 embedding/pose 通常直接读缩略图，编辑/压缩会在任务期间替换缩略图与内容；两者并发会让旧内容算出的特征或缩略图落到新内容上。文件夹操作不占内容写者，所以不影响“AI 运行时改文件夹”。

### 2.5 准入、排队与优先级

- 长任务启动时一次性申请全部粗资源：`session` 读、`timeline`、全局写、任务级路径。拿不到就进入资源等待队列；`ConflictPolicy::Queue` 等待，`Fail`（撤销/重做/清空）立即返回冲突。
- 任务级路径锁在任务开始时拿；运行中读单张原图只追加该文件夹的短读锁。
- 同资源按 FIFO；写者优先只作用于路径锁与时间线独占，不改变现有“write 优先”的直觉。`TaskKind::lane` 保留为排队优先级与前端展示字段：内容/文件夹/删除类仍为 `write`，AI 为 `ai`，估算/相似为 `scan`；但**冲突判断不再看 lane，只看资源**。
- 短操作不排队：文件夹操作最多等 10 秒；评分/标签/描述/编辑保存立即失败。失败文案包含占用者标签与原因，例如：
  - “「导入」正在写入「角色」目标文件夹，请等待完成或取消后再重命名文件夹”
  - “「生成描述」正在读取「角色/a」中的图片，请稍后重试”
  - “「优化图片空间」正在处理图库内容，请等待完成或取消后再移动文件夹”
- 排队任务可取消；取消只移除等待项，不占任何资源。
- 生命周期（打开/创建/关闭/切换）申请 `session` 写：有任务、短操作或等待者时拒绝，错误点名占用者；关闭图库对可取消的 AI/扫描任务先取消再等待，内容写任务仍拒绝关闭。

### 2.6 锁顺序与无死锁论证

申请顺序（防御性规则，实际靠“一次全部申请”保证）：

1. `session` 读
2. `timeline` 共享/独占
3. `content.writer` / `metadata.writer` / `ai.service`
4. 任务级路径范围（按路径排序，读/写）
5. 运行中的单文件夹短读锁（只追加，且只读）
6. 数据库写连接、包内部互斥、图像预算许可

无死锁依据：

- 粗资源一次全部申请；失败时一个都不持有，不存在“持有 A 等 B”的环。
- 细路径锁只在已经持有任务级路径范围之后申请，且不会在持有细锁时申请任何粗资源。
- 数据库写连接、包互斥、预算许可都在资源锁之后获取；持有它们时不再申请资源锁。
- 文件夹操作只申请自己的路径写与全局写，不申请别的任务持有的资源；它等待读图读者时，读者不会反过来要文件夹写的资源。
- 撤销/重做/清空持有 `timeline` 独占后再申请路径与内容资源；普通写入在申请路径/内容之前先拿 `timeline` 共享，顺序一致，且它们不会在持有路径锁时再要 `timeline` 独占。
- 所有等待都检查取消标记（长任务）或超时（文件夹操作）；不会无限等一个已经退出的读者。

### 2.7 超时、取消与公平

- 长任务资源等待：每 200 ms 醒一次，检查取消；取消后不占资源。
- 文件夹操作：等待路径写最多 10 秒；超时返回“哪个任务正在读哪个文件夹”，用户可重试。文件夹操作本身不排队，避免用户在界面上点了没反应。
- 图像预算：等待许可可取消；任务取消后已拿到的许可随 RAII 释放。
- 写者优先：路径上有写者等待时，新读者不插队；已有读者最多持有一次读图的时间。这样长 AI 任务不会让文件夹操作永远排在后面。
- 时间线独占（撤销/重做/清空）仍立即失败，不排队；与批次 4 的决策一致。

### 2.8 分阶段落地

为了避免一次性替换所有准入判断，实施分四步，每步都能独立验证：

1. **资源表 + 路径锁 + 会话**：先只把文件夹维护（界面与 MCP）和读图任务（AI/估算/缩略图/查看器预览）迁到资源表；`content.writer` 与 `metadata.writer` 先承担现有 write lane 的全局互斥语义。此步完成后，AI/扫描不再挡住文件夹操作，导入/压缩仍按路径/内容冲突拒绝。
2. **短写迁移**：评分、标签、描述、集合、回收站从 `acquire_immediate(Write)` 迁到 `metadata.writer + timeline`；它们在 AI embedding/pose、估算、相似分组、缩略图重建与文件夹操作运行时可以并行（互相之间仍串行，AI 描述与撤销仍会挡住它们）。
3. **线程预算 + 进度/ETA + 尾部流水线**：统一预算、加权进度、压缩双缓冲、导入动态队列与收尾进度。
4. **清理**：删除旧的 lane 冲突判断与重复的 `ensure_no_activity` 调用；保留 `TaskLane` 作为优先级/展示字段；补齐模块文档。

每步结束跑对应检查并单独提交；本文只定义目标，不提前写成“已实现”。

## 三、目标行为

### 3.1 AI/扫描运行时允许文件夹操作

1. AI embedding/pose/描述、压缩估算、相似分组、缩略图重建运行时，用户可以重命名/移动/删除空文件夹/新建/排序。
2. 重命名/移动与读图重叠时，文件夹操作最多等当前一张图读完（通常几十毫秒；大图描述编码可能到 1–2 秒）。超时给明确文案，不静默失败。
3. 文件夹操作完成后，AI/估算下一张图按数据库里的新路径读取；不会继续用旧路径批量失败。
4. 互不重叠的文件夹子树上的维护操作可以并行；同一路径或祖先/子孙关系上的操作仍串行（路径写锁）。
5. 导入/压缩/移动/编辑保存/释放/撤销/重做仍会按路径或内容冲突拒绝文件夹操作，并说明是哪个任务、为什么。

### 3.2 仍然冲突的操作

- **压缩执行**：占根路径写，所有文件夹操作都会被拒绝；文案是“优化图片空间正在处理图库内容”，不是“图库忙”。
- **导入**：占目标子树读；目标及其祖先/子孙上的文件夹操作被拒绝；其他子树可以并行。
- **移动图片**：源/目标文件夹上的操作被拒绝；其他子树可以并行。
- **编辑保存**：图片所在文件夹上的操作被拒绝；其他子树可以并行。
- **释放删除文件 / 撤销 / 重做**：占根路径写，所有文件夹操作被拒绝。
- **打开/创建/关闭/切换图库**：仍要求没有任务、短操作与排队任务。

### 3.3 MCP 文件夹操作

- `folders_modify` 的 create / rename / move / delete 与界面使用同一个资源申请入口；dryRun 与审批入队前不做资源等待，真正执行时申请。
- 资源冲突时返回普通工具错误（MCP 客户端看到 reason），审计日志记录冲突；不再绕过任务总线。
- 审批单执行时重新申请资源；审批期间开始的导入/压缩会让执行返回冲突，确认单标为失败，而不是沿用旧状态硬改。

### 3.4 生命周期

- 打开/创建/关闭/切换图库申请 `session` 写，等待/拒绝所有任务与短操作；排队任务也计入占用。
- 关闭图库时，可取消的 AI/估算/相似/缩略图任务先取消并等待；内容写任务仍拒绝关闭，文案点名任务。
- 退出时取消排队与可取消任务，等待 2 秒；来不及清空的临时区留到下次打开图库。

### 3.5 短元数据写入

- 评分、标签、描述、集合成员、回收站状态走 `metadata.writer + timeline`，不再占 write lane；AI embedding/pose、压缩估算、相似分组、缩略图重建运行时可以执行。
- AI 描述、撤销/重做也占 `metadata.writer`，所以它们在运行时，评分/标签/手动描述仍会被挡住；这与当前行为一致。
- 元数据写之间仍串行（同一资源），避免同一图片行的多列写入语义未审计就并发。
- 手动描述与 AI 描述仍互斥；AI 描述运行期间手动改描述会立即失败并提示“生成描述正在进行”。

### 3.6 线程预算

- 一个全局图像工作预算，默认 `max(1, 逻辑核 − 1)`，由 `performance.workerThreads` 覆盖（1–128，空为自动）。
- 导入、压缩、估算、缩略图重建、AI 解码/编码、查看器预览、拼图生成共用这个预算；不再出现导入 1–128、压缩/估算固定 8 两套策略。
- 每个任务仍保留自己的循环与进度；预算只限制同时进行的图像工作数量。
- 设置界面文案改为“后台图像工作线程数”；说明这是全局预算，不是单个任务独占。用户可在导入大图时调低。

### 3.7 尾部与进度

- 压缩：编码与下一批提交重叠；提交/删旧期间进度继续前进；不会出现“100% 但还在写”。
- 导入：写线程收尾期间显示“正在写入最后一批（N 张）”；进度在入库提交后才到 100%；工作线程按单文件动态取任务。
- 进度按像素或预估工作量加权；ETA 用滚动吞吐计算；快照字段在批次 6 暴露，本批先把 meter 建好。

## 四、线程运行层

### 4.1 统一预算

- 新增 `ImageBudget`：一个可配置上限的信号量，提供 `acquire(cancel) -> Permit`、`update_limit(n)`、`current_limit()`。
- 默认值：`workerThreads` 为空时 `max(1, available_parallelism - 1)`；有值时 clamp 1–128。
- 任务开始读取当前预算；运行中的任务保留自己的池，但每次图像工作都要拿许可，所以设置调小后新工作会自然受限，已拿许可的任务不会被强杀。
- 许可只覆盖“读/解码/编码/缩略图/pHash/主色/写临时文件”这一段；发 HTTP、等网络、等数据库写连接、等通道时释放。
- 导入的写线程、压缩的提交线程不占图像许可；它们是 IO/数据库线程，由通道/事务节流。

### 4.2 各任务的池

- 导入：rayon 池线程数 = 预算；每个工作项拿 1 个许可；写线程 1 个。
- 压缩执行：编码池 = 预算；每个编码项拿 1 个许可；提交线程不占许可。
- 压缩估算：池 = 预算；每个样本拿 1 个许可。
- 缩略图重建：保持单线程循环，但每张拿 1 个许可；以后要并行时直接用预算，不需要第二套数字。
- AI：逐张处理；解码/编码时拿 1 个许可，HTTP 期间释放。
- 相似分组：单线程 CPU 扫描，拿 1 个长期许可，避免与 15 线程压缩同时打满 CPU。
- 查看器预览/拼图：生成时拿 1 个许可。

### 4.3 加权进度与 ETA

- 新增 `WorkMeter`：
  - `total_units` / `done_units`（原子）；
  - `enter_phase(base, weight)`：编码 0–90、提交 90–98、删旧 98–100 之类；
  - `percent()`：单调递增，终态前不超过 99；
  - `rate()`：最近 10 秒滚动窗口的 units/秒；
  - `eta()`：剩余 units / rate，样本不足时返回 `None`。
- 压缩的 unit 用候选像素（`width × height`），跳过/失败也消耗 unit；这样大图权重更高。
- 导入的 unit 先用文件数（扫描阶段没有可靠尺寸）；解码阶段 0–90，写线程阶段按已入库数 90–100。批次 6 若要按字节加权，再把 `ScannedFile` 加上 `size`。
- 估算复用现有像素权重与阶段百分比，接到 meter 上即可。
- 事件推送仍由任务总线 150 ms pump；meter 不直接发事件。批次 6 把 `eta`、字节、当前文件加进快照；本批只把它用于 `set_percent` 与文案。

### 4.4 压缩双缓冲

- 编码批次从 1000 降为 256 张或 256 MiB（先到者为准）；批次大小在基准里比较 128/256/512。
- 任务线程作为生产者：按 bpp 顺序取一批，`pool.install` 编码，把 `EncodedChunk` 放进深度 1 的通道。
- 提交线程：按顺序提交（发布 → 事务 → 删旧），把已提交的像素数回填给 meter；提交/删旧与下一批编码重叠。
- 通道深度 1 把内存限制在“正在编码的一批 + 等待提交的一批”；再大就需要更复杂的背压。
- 取消：生产者在张边界停止；已经编码并送入通道的批次仍按现有语义提交；提交线程排空后任务结束为 `Cancelled`。
- 提交失败：生产者停止，未提交的编码结果丢弃（临时文件随 `TempPath` 删除），已提交批次保留；任务失败。
- 进度：`completed` 只统计已提交张数；`percent` 由 meter 给出；最后一批提交完才 100%。
- 删除旧图仍在提交线程内执行；如果基准显示删除成为新瓶颈，再用预算池并行删除，但不改变提交顺序。

### 4.5 导入动态队列与收尾

- 用 `AtomicUsize` 单文件取号替代 `par_iter` 的静态分片：
  - 每个工作线程循环 `fetch_add(1)` 取下一个文件；
  - 取消时在取号前后检查；
  - 保证每张恰好处理一次，进度可精确按文件数。
- 通道深度从 256 降到 128（或 2 × 写批次）；写批次仍 64 张或 250 ms。这样最后最多排空约两批，不会堆几百张。
- 新增 `written` 计数：每提交完一批增加；`TaskHandle` 的 `completed` 在提交后更新（或保留 processed，同时用 meter 做加权 percent）。界面上的“已处理”与“已入库”分开显示时由批次 6 决定；本批先保证进度不早到 100%。
- 工作线程结束后进入 `Finishing`，消息“正在写入最后一批（N 张）”；写线程排空、`join` 完成后再进入终态。
- 取消：工作线程停止；写线程继续把已准备好的批次落库；终态为 `Cancelled`；进度反映真实入库数。
- 文件顺序保持扫描顺序，不为了尾部重新排序；如果基准显示“最后一张特别大”是主因，再评估按大小做前瞻调度，不先改变导入顺序。

### 4.6 线程预算与尾部的验证

- 同一批样本分别在预算 4 / 8 / 核数−1 下跑导入与压缩，记录墙钟、末尾 5% 墙钟、提交/删旧/写线程收尾时间；比较默认核数−1 是否比 8 更差。
- 内存峰值记录到文档；如果 15 线程让大图导入/压缩峰值明显上升，设置建议写“16 核机器可设 8”，但不改默认。
- 不用跨机器墙钟做结论；所有对比在同一台机器、同一构建档完成。

```rust
    access: Access,
}

struct ResourceRequest {
    session_read: bool,
    timeline: Option<Access>,
    content_writer: bool,
    metadata_writer: bool,
    ai_service: bool,
    paths: Vec<PathScope>, // 任务级；运行中的短读锁单独申请
}

struct HolderInfo {
    id: String,
    label: String,
    reason: String, // 用于错误文案：正在读 / 正在写 / 正在处理
}
```

- `ResourceTable::try_acquire(request, holder) -> Result<ResourceGuard, Vec<HolderInfo>>`：一次性检查并占用；失败返回冲突持有者。
- `ResourceTable::acquire(request, holder, deadline, cancel) -> Result<ResourceGuard, WaitError>`：等待版本；每 200 ms 检查取消/超时。
- `ResourceTable::acquire_path_read(folder, holder)`：运行中的短读锁；支持取消/超时；返回 `PathReadGuard`。
- `ResourceTable::is_idle()`：没有任何持有者（含短操作）；生命周期用。
- `ResourceGuard` / `PathReadGuard` 只做 RAII 释放；`Drop` 不回调业务代码。

`TaskBus`：

- `launch` / `begin_queued` 改为构建 `ResourceRequest`；冲突判断用 `ResourceTable`，不再用 `lane.conflicts_with`。
- `TaskHandle` 增加 `resources: ResourceRequest`（内部）或由 bus 保存；`conflicting(request)` 返回任务/短操作标签，用于 `Conflict`。
- 等待者结构增加请求；`cancel` 同时移除等待者；`is_idle` 同时检查表与等待者。
- `TaskKind::lane` 保留，作为排队优先级与快照字段；文档注明它不再决定冲突。

`AppState`：

- `begin_maintenance` 拆成：
  - `begin_folder_change(scopes, kind)`：session 读 + timeline 共享 + 路径写（结构改动用旧/新子树，排序用父/目标子树）；最多等 10 秒；
  - `begin_metadata_write()`：session 读 + timeline 共享 + metadata.writer；立即失败；
  - `begin_content_write(scopes)`：session 读 + timeline 共享 + content.writer + 路径写；用于编辑保存等短内容写；
  - `begin_reader(scope)`：session 读 + 短路径读；查看器/MCP 读图用。
- 打开/创建/关闭图库改用 `session` 写；排队任务计入。
- 文件夹新建/重命名/移动/删除、排序、一次性排序全部走新的入口；MCP `folders_modify` 复用。

`ImageBudget`：

- `acquire(cancel)` / `update_limit(n)`；`pool()` 按当前预算建 rayon 池；移除 `library/mod.rs` 的 `ENCODE_MAX_THREADS` 与 `encode_threads()`。
- 导入的 `request.worker_threads` 不再覆盖全局预算；`ImportRequest` 字段保留用于反序列化兼容，但 `start_import_inner` 不再写它。
- 设置校验仍 1–128；文案改为全局预算。

### 5.2 前端

### 6.2 现有锁序审计结论

- 数据库写锁与包互斥不会互相等待：`ThumbPack::append`、`FeatureStore::append` 内部锁只在调用期间持有，返回后才写数据库；导入/压缩在数据库写锁内调用 `append`，但包锁不会反过来等数据库写锁。因此不需要全局包锁。
- 文件夹重命名/移动在数据库写事务内做磁盘改名；路径写锁会在事务前拿到，读者被挡住，事务提交后才放行。数据库写锁持有时间包含一次目录 rename（同卷 O(1)）与子树路径更新；如果真实库上出现明显停顿，再把磁盘 rename 移到事务外并保留回滚，暂不预做。
- `LiveOperation` / `HistoryRunGuard` 的 Drop 会写数据库；任务收尾必须在数据库写锁之外执行，不能把 guard 声明在 `with_writer` 闭包里。实施时用测试/代码审查确认。
- 取消：导入在文件边界、压缩在张边界、AI 在图片边界、估算在样本边界检查；在飞的编码/HTTP 不强制中断，等它返回后释放许可；任务线程 join 后再释放会话与路径锁。
- 排队任务不占资源；取消后移除等待项，不会在关库/退出后突然启动。
- 临时区清空只在生命周期入口执行；资源表保证没有任务/短操作持有临时路径读锁。

### 6.3 已发现的同步问题

1. **MCP 文件夹操作绕过总线**：本批修复。
2. **文件夹改名与读图窗口**：本批用路径读/写锁修复；读者按 id 重解析路径。
3. **压缩进度 100% 但仍在写**：本批用双缓冲 + 加权进度修复。
4. **导入 processed 早于 written**：本批增加 written 与收尾文案。
5. **缩略图包/数据库锁序不统一**：当前无交叉危险，但实施时要保持“包锁不跨数据库等待”；不要为了并行给包加全局锁。
6. **元数据写入粒度粗**：`metadata.writer` 仍是全局；后续可按图片行细化，本批不做。
7. **导入/压缩与元数据写的并发依赖列级独立**：导入插入图片并附带标签，压缩更新内容列；评分/标签/描述写的是不同列。SQLite 写连接会串行，但列级语义没有专门的约束。实施时要加“导入 attach tags 与标签合并/删除并发”“压缩与评分/描述并发”的测试；出现同列覆盖就把相应操作移回互斥资源。

## 九、自动测试设计

Rust：

- 资源表：
  - 同路径读/读兼容；读/写、写/写冲突；祖先/子孙冲突；不同子树兼容；根读只挡根写/子孙写，不挡子孙读。

## 十、用户手工验收

1. AI 描述/embedding/姿势任务运行时，重命名、移动、删除空文件夹、新建、排序：文件夹操作成功；AI 任务继续，任务摘要没有成批“原图不存在”。
2. AI 任务正在读一个大图时立刻重命名同一文件夹：重命名最多等一两秒后成功，或给出“正在读取该文件夹”的明确提示；不会卡死。
3. 压缩运行时重命名文件夹：被拒绝，文案点名“优化图片空间”和“正在处理图库内容”；不出现笼统的“图库忙”。
4. 导入运行时重命名目标文件夹/其父级：被拒绝并点名“导入”；重命名其他子树：成功。
5. 两个不同文件夹的重命名/排序：都能执行；同一文件夹的连续操作不会互相覆盖。
6. 撤销/重做/清空记录在任意任务运行时：按钮禁用或立即失败，不排队。
7. MCP 同时提交导入与 `folders_modify` 重命名目标：重命名返回冲突；导入结束后再试成功；审计日志有记录。
8. 压缩接近结束：进度从编码平滑进入“正在提交/删旧”，不再停在 100% 不动；结束后任务摘要与已处理张数一致。
9. 导入收尾：显示“正在写入最后一批”，进度在入库完成后才 100%；取消后已完成部分保留、任务状态为已取消。
10. 设置里把工作线程数改成 4/8/自动：导入、压缩、估算都按同一预算变化；大图导入时内存不失控；界面仍可操作。
11. 关闭/切换图库：有任务时按文案拒绝；取消 AI 任务后可以关闭；不会在关库后启动排队任务。

## 十一、边界、风险与后续

不做：

- 不换数据库；不把单写连接改成多写；数据库读命令仍直接走连接池，不占资源锁；只有读原图时按文件夹拿短读锁。
- 不做通用作业调度器/DAG；任务体仍是各自循环。
- 不做每文件一把锁；路径锁只到文件夹子树。
- 不改压缩算法、质量梯子、跳过策略与估算公式（批次 7 处理）。
- 不新增第二套进度通道；批次 6 扩展快照字段。
- 不自动重启 AI 服务；不编译 release；不启动界面或浏览器。

风险：

- **资源表本身可能成为新瓶颈**：每次读图拿一次短读锁；20 万张描述任务会有 20 万次锁操作。锁表用哈希 + 少量活跃键，需在 `perf_path_lock` 中验证；如果开销明显，再按任务批量预取文件夹读锁（仍不按文件）。
- **写者优先可能让读者短暂排队**：AI 任务逐张读，文件夹写者等待时会挡住后续读；这是为了避免重命名饿死。超时与文案必须清楚。
- **压缩仍会挡住所有文件夹操作**：根路径写是真实冲突（候选覆盖全库）；用户可能仍觉得“压缩时不能改名”。文案要说明是压缩正在处理图库，而不是实现没放开。
- **导入目标子树读**：目标子树内的文件夹操作仍被拒绝；其他子树可以并行。若用户认为导入只写新文件、不应挡重命名，可再评估把导入改成“目标只读 + 新文件发布短写锁”，但需要额外验证。
- **metadata.writer 粒度粗**：AI 描述运行时标签/评分仍被挡住；这是保守选择。后续可按图片行拆锁，但要先审计同列/跨列写入语义。
- **默认线程数从 8 变 15**：压缩/估算峰值内存可能上升；设置可降回 8。基准要记录，若 15 明显更差再讨论默认值。
- **更多并发写入**：SQLite 单写连接仍串行，短写之间可能更频繁争用写连接；WAL 读不受影响，但写延迟可能上升。用基准与真实窗口观察。
- **列级并发语义**：导入/压缩与评分/标签/描述并发时，正确性依赖“不同列/不同表”这一审计结论；第 6.3 节第 7 条列出必须补的并发测试。发现同列覆盖就把该操作移回互斥资源，而不是放宽测试。
- **MCP 文件夹操作行为变化**：以前能与导入并行（错误地并行），现在会冲突；这是修复，不是回归。
- **锁顺序审计遗漏**：任何新代码在持有资源锁时调用数据库写/包追加，都可能破坏假设；实施时加断言/测试，代码审查逐项确认。

后续（不阻塞本批）：

- 压缩候选路径集合细化，允许与不相交文件夹的维护并行。
- 图像预算按像素/内存加权，而不是只按线程数。
- 查看器预览缓存的容量与清理（批次 6）。
- 导入按文件大小加权进度与前瞻调度（批次 6/7 视测量结果）。
