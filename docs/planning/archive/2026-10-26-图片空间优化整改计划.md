## 1. 已确认的决策

1. **断电保护保留**。不只保留每张 `sync_all`，还要补齐“文件数据落盘 → 持久化 rename → SQLite 提交持久化 → 再删旧图”的顺序。
2. **统计口径改成漏斗**。环图只按候选池计算“处理 vs 候选内跳过”；“已紧凑 / 已处理 / 透明 / 超 WebP 尺寸”单独列为“未纳入候选”。
3. **抽样滑块改成五档离散值**：50 / 200 / 500 / 1000 / 2000，默认 200。
4. **分两批实施**：
   - 批次 1：内容安全补丁、估算可信度、任务接管、打开延迟、漏斗统计、耗时拆分；不改执行写路径。
   - 批次 2：排队与操作记录收尾、断电安全发布协议、去重复读、阶梯早退、线程与提交/删除优化、最终耗时标定。
5. **动画、多帧与多页源必须排除**：GIF、APNG、动画 WebP、多页 TIFF 不能被替换成单帧静态图。先做安全补丁，估算和执行共用同一条判据。
6. **任务接管必须保存原始范围**：只存 `scopeLabel` 不够；要保留可执行的 `TaskScope`（或完整 `runConfig`），并绑定 `libraryId`，避免换库后接管旧任务。
7. **漏斗必须闭合**：所有 `SkipReason` 都要有落点；取整后 `candidate = process + candidateSkip` 与字节不变量必须严格成立。
8. **导入发布不能直接采纳已有目标文件**：目标已存在时先校验 BLAKE3，匹配才接管；当前实现会先删暂存副本再插行，必须一起修。

## 2. 调查结论

| 编号 | 问题 | 结论 |
| --- | --- | --- |
| 1 | 抽样刻度与实际位置对不上；“约 xx 分钟”是否可靠 | 属实。滑块是 50–2000 线性区间，但刻度按 0/25/50/75/100% 均分；等待时间用硬编码 61 / 12.7 张/秒。结果页耗时是按像素线性外推的实测模型，CPU 差异已被实测吸收，但模型缺项。 |
| 2 | 关闭估算窗口后任务“被抛弃”；重新打开很慢 | 属实。打开时重置 `taskId`，任务中心和内存结果仍在，但对话框找不到；打开前还会先跑完整分面统计，且任务进度每 150ms 让整个工作区重渲染。 |
| 3 | 预计耗时漏掉事务提交、删旧文件、BLAKE3、三个重算开关；极高/高跳过差很多但耗时差不多 | 漏项属实。极高/高耗时接近不一定是 bug：耗时按候选像素算，画质跳过的图同样要解码和阶梯编码；当前阶梯在 PSNR 不达标时还会继续往高质量爬，可能让高档次白试更多次。 |
| 4 | 汇报界面紧凑，但超 WebP 尺寸不进候选却计入跳过，统计口径混乱 | 属实。环图分母是整个范围，`processCount` 是候选内处理数；“候选”又是另一个数字。前置排除和候选内跳过被混在一起。 |
| 5 | `sync_all` 能否去掉；重复读；8 线程是否保守；其他任务如何调度 | `sync_all` 对进程崩溃可去、对断电不可去；重复读属实；8 线程是内存保护而非 CPU 上限；导入、缩略图、AI、撤销等任务的并行方式各不相同。另发现“rename 后、commit 前崩溃”留下的目标文件会被下次执行当成重复内容而永久跳过。 |
| 6 | 动画、多帧、多页源是否会被静态化 | 属实。GIF 可导入；`prefilter` 不排除，`decode` 只返回一帧；JPEG/WebP 输出会丢动画、APNG 帧或多页 TIFF 的其余页。 |
| 7 | 估算节省率是否有上限 | 属实。`stratum_rates` 与 bootstrap 把节省率 `clamp(0.0, MAX_SIZE_RATIO)`，而 0.95 是“新文件必须小于原图 95%”的阈值，不是节省率上限；高压缩比图会被低估。 |
| 8 | 漏斗分类是否闭合 | 属实。解码后 `plan()` 仍可能返回 `Transparent` / `BppLow` / `AlreadyOptimized` / `TooLargeForWebp`，但 `cumulative_skips` 未统计；各桶独立 `round()` 也可能让不变量差几张。 |
| 9 | 任务接管需要哪些字段 | 只存 `scopeLabel` 不够；执行指纹依赖完整 `TaskScope`，且估算运行中改参数会把旧结果套到新设置上。 |
| 10 | 导入发布是否也采纳孤儿 | 是。目标已存在时 `publish` 返回 `false` 并删掉暂存副本，写线程仍会插入行，且不校验目标内容；截断的孤儿会被登记成正常图片。 |
| 11 | 排队、取消排队、线程启动失败如何收尾 | 入队前就 `begin_live`；排队中被取消或 `spawn_worker` 失败时 worker 不会执行，`finish_live` 也不会调用，pending 记录留到下次开库。 |
| 12 | 执行失败清单是否可见 | 否。`OptimizeReport.failures` 只在内存报告里，未转发到 `TaskHandle`；文档却写着“进入任务失败清单”。 |
| 13 | 其他 | 临时文件夹仍可选为优化范围；`LibraryView` 也订阅整包任务上下文；提交事务内有缩略图追加和每张 `metadata`；收益曲线按分层而非单张 bpp 排序；文档口径有过时处。 |

编号 6–13 是第二轮代码复核补充。其中 6、8、10、11 会直接影响内容安全或数据/记录一致性，建议在对应批次开工前先处理。

### 3.0 内容安全前置补丁：动画、多帧与多页源

这个问题与统计/交互无关，但会直接损坏图片，必须先做，并单独提交。

#### 现状

- 导入扫描接受 GIF；`decode::decode` 只返回一个 `DynamicImage`，不保留帧序列或多页。
- `imageops::optimize::prefilter` 只判断 bpp、已处理、透明、WebP 尺寸，没有动画/多页判据。
- 结果：动画 GIF、APNG、动画 WebP、多页 TIFF 会被编码成单帧 JPEG/WebP 并替换原图。

#### 设计

1. 在 `imageops/optimize.rs` 增加 `SkipReason::AnimatedOrMultipage`，并提供 `multiframe_guard(bytes, format) -> Result<(), SkipReason>`：
   - GIF：保守地按 `format = "gif"` 直接跳过；如果实现成本低，再解析 image descriptor 判断是否多帧，静态 GIF 可放行。
   - APNG：PNG 的 `acTL` chunk。
   - 动画 WebP：RIFF 的 `ANIM` chunk。
   - 多页 TIFF：IFD 链多于 1 页。
   - 只读文件头即可判断，不解码全部帧。
2. `prefilter` 增加只依赖数据库列的 GIF 前置桶；APNG/动画 WebP/多页 TIFF 在读取文件后判断，计入候选内跳过。
3. 估算与执行共用同一条判据；估算的漏斗新增对应桶，执行遇到时按跳过处理，不进入编码与发布。
4. 文档在“跳过”一节写清楚：动画/多帧/多页源不参与优化。

#### 测试

- 动画 GIF、APNG、动画 WebP、多页 TIFF：估算计入跳过，执行不替换原图。
- 静态 GIF：如果选择保守跳过，断言计入前置桶；如果解析后放行，断言可正常编码。
- 普通 JPEG/PNG/WebP 不受影响。
- 不需要为了这个补丁改 schema 或导入流程。

### 3.1 抽样滑块与时间提示

#### 现状

- 滑块 `min=50`、`max=2000`、`step=50`，下方标签是 50/200/500/1000/2000，用 `justify-content: space-between` 均分。
- 实际位置：200 在 7.7%，标签在 25%；500 在 23.1%，标签在 50%；1000 在 48.7%，标签在 75%。
- 滑块旁的时间使用硬编码 `SAMPLE_RATE_JPEG = 61`、`SAMPLE_RATE_WEBP = 12.7`，按 `样本数 / 吞吐` 线性计算，不看分辨率、不看本机 CPU/磁盘。
- 当候选张数少于所选样本数时，分配会截到候选数，结果页显示的实际样本数会小于滑块值，但界面上没有解释。

#### 设计

1. 前端定义唯一的五档数组：

   ```ts
   const SAMPLE_CHOICES = [
     { size: 50, label: "50（快）" },
     { size: 200, label: "200（默认）" },
     { size: 500, label: "500" },
     { size: 1_000, label: "1000" },
     { size: 2_000, label: "2000（准）" },
   ];
   ```

   状态仍保存实际张数，滑块内部用索引 0–4；也可以用五个分段按钮，但推荐保留滑块形态。
2. 五个标签等距排列，并与五个停靠点一一对应；默认索引指向 200。
3. 删除 300ms 防抖和 `samplePending`。档位只有五个，且点击“开始估算”才会启动任务，不需要防抖。
4. 删除硬编码吞吐。滑块旁的等待时间改为：
   - 如果本会话已有同一 `(输出格式, 档位, 长边上限)` 的完成估算：`上次样本耗时秒数 / 上次样本张数 × min(当前档位, 候选张数)`；
   - 没有实测：不显示绝对时间，只保留“样本越多越准，也越慢”；
   - 测量值单独保存在会话里，不依赖当前 `estimate` 对象；“返回修改”清空结果后仍可复用上次实测。
5. 后端在估算结果中补 `sampleElapsedMs`（样本编码墙钟时间），供滑块提示和后续校准使用。
6. 结果页在 `sampleCount < 所选档位` 时显示“样本 N 张（候选不足）”，避免看起来是滑块没生效。

#### 边界

- 后端仍接受 50 的倍数；五档只是界面限制，不修改 `sample_size_valid`。
- 如果样本耗时小于 1 秒，界面显示“不到 1 秒”，不显示 0 秒。
- 滑块提示只描述“抽样编码大概要等多久”，不等于结果页的总预计耗时；两者位置和文案要区分。
- 等待时间按 `(输出格式, 档位, 长边上限)` 匹配；只换输出格式或只换档位都不能复用。

#### 验收

- 五个档位的 thumb 与标签对齐，默认 200。
- 首次估算前不出现硬编码的“约 N 分钟”。
- 完成一次 WebP 估算后，切到 WebP 滑块能看到按实测折算的时间；切到 JPEG 时不会误用 WebP 的数值。
- 候选不足时结果页明确显示实际样本数。

### 3.2 关闭窗口后的任务接管

#### 现状

- `OptimizeDialog` 每次 `open` 都把 `taskId`、`executeTaskId`、`estimate` 等全部重置。
- 任务中心仍保留正在运行和已完成的任务；估算结果按 taskId 缓存在后端内存，最近 10 条。
- 对话框只通过自己的 `taskId` 调用 `find`，所以关闭后重新打开看不到进度，也拿不到已完成的结果。
- 任务胶囊能看到“还有任务在跑”，但优化对话框本身无法恢复。

#### 设计

引入一个轻量会话状态，仍放在 `OptimizeDialog` 内部（组件在 `LibraryWorkspace` 中常驻挂载）：

```text
idle / config      没有正在进行的任务，也没有未放弃的结果
estimating         有正在运行或排队的 optimizeEstimate
estimateFailed     估算任务失败
result             已拿到估算结果
executing          有正在运行或排队的 optimize
executionDone      最近一次执行已结束
```

打开窗口时的决策顺序：

1. 有正在运行/排队的 `optimize` → 接管执行进度。
2. 否则有正在运行/排队的 `optimizeEstimate` → 接管估算进度。
3. 否则当前会话已有 `estimate` → 显示结果。
4. 否则有已完成且未放弃的 `optimizeEstimate` → 接管并拉取结果。
5. 否则回到默认配置。

实现要点：

- 任务列表来自 `useTaskCenter().tasks`；优先选择 running/preparing，再按 `startedAt` 取最新。
- 组件常驻，发起时的范围、参数、样本数放在 `runConfig` 中，关闭再打开不丢。
- “返回修改”只清空结果并记住该 taskId 已被放弃，避免下次打开又自动弹回结果；正在运行的任务不允许“返回修改”，只能取消。
- “重新估算”直接以当前配置发起新任务，替换旧 taskId。
- 已完成估算的拉取继续复用现有“5 秒超时 + 重试读取”逻辑；缓存被挤掉时提示“结果已被新的估算覆盖，请重新估算”。
- 应用重启后任务中心列表为空，不承诺跨重启恢复。

#### 后端补字段

为了让结果自描述、接管时不依赖前端内存，给 `OptimizeEstimate` 增加：

- `options: OptimizeOptions`
- `scope: TaskScope`（执行凭证必须能重建原始范围；`scopeLabel` 只用于展示，不能替代）
- `scopeLabel: String`
- `sampleSize: u64`
- `libraryId: String`（或等价的图库标识；接管时和当前库比对，换库后不接管旧任务）

这些字段在 `state::start_optimize_estimate` 拿到结果后补齐再写入缓存；`optimize_estimate::estimate` 本身只负责算法结果。`libraryId` 直接取当前 `LibraryInfo`，不要求改 schema。

实现要点补充：

- `runConfig` 同时保存 `TaskScope`、`options`、`sampleSize` 和打开时的 `BatchTaskContextInfo`；“本次设置”和“确认执行”都从 `runConfig` 取值，不要用当前浏览状态重新拼范围。
- 估算运行中锁定范围与参数（或至少记录发起时的 signature）：任务完成时若当前 signature 已变化，丢弃结果并提示重新估算。现在 `signature` 变化只清空 `estimate`，在飞的旧任务完成时仍会把旧结果写回来，导致结果与设置错配、执行时指纹不符。
- 任务列表保留 50 条、结果缓存保留 10 条；接管时先看缓存是否存在。任务属于别的图库或结果已被淘汰时回到配置页并说明原因。
- 换库、关库、创建库时清空会话里的 `runConfig` 和已放弃 taskId；否则可能接管上一个图库的任务。

#### 验收

- 估算跑到一半关闭窗口，再打开能看到同一任务的进度，可继续等待或取消。
- 估算在关闭期间完成，再打开能自动显示结果。
- 执行压缩期间关闭，再打开能看到执行进度和最终结果。
- 关闭再打开不会重复启动一个新估算。
- 已放弃的估算不会在下次打开时自动弹出。
- 关闭窗口后切换视图/文件夹/图库再打开，不会用新范围执行旧估算；若范围已变，明确提示重新估算。
- 估算运行中改参数，不会显示与当前设置错配的结果。
- 换库后打开优化，不会接管上一个图库的估算或执行任务。

### 3.3 打开窗口的延迟

#### 现状

- 打开优化对话框前，`LibraryView.openOptimize` 会 `await buildTaskContext()`；其中为了拿 `viewTotal` 调用完整的 `getFilterCounts(query)`，会计算文件夹、扩展名、评分、标签四组分面。
- `LibraryWorkspace` 直接订阅整个任务上下文；估算每 150ms 推送一次进度，整个工作区会跟着重渲染。
- 这两项叠加，使“估算运行时打开窗口”明显变慢。

#### 设计

1. 新增/暴露轻量总数命令：
   - Rust 已有 `library::query::query_total`，只做计数，不取分面。
   - 在 `AppState` 增加方法，在命令层注册 `get_query_total`。
   - 前端 `src/modules/library/api.ts` 增加 `getQueryTotal(query)`。
2. `buildTaskContext` 改用 `getQueryTotal`，不再为了一个 total 跑完整分面统计。这个改动同时惠及批量任务对话框。
3. 优化对话框先打开、后补计数：
   - `openOptimize` 立即设置 `viewTotal = null` 的上下文；
   - `LibraryWorkspace` 在弹窗打开后异步取总数，回来再更新 `optimizeContext`；
   - `ScopePicker` 在此期间显示“—”，不阻塞弹窗出现。
4. 拆分任务上下文：
   - 保留 `TaskCenterContext` 给任务胶囊、对话框等需要完整任务列表的组件；
   - 新增 `TaskDataContext`（`dataVersion`、`lastFinished`）给 `LibraryWorkspace`；
   - 新增窄的 `TaskActiveContext`（活动任务数量与标题）给 `LibraryView`、`OperationHistoryPanel` 等只判断“有没有任务在跑”的组件；
   - 工作区和网格都不再因为 `tasks` 数组每 150ms 变化而重渲染；
   - 常驻但隐藏的 `BatchTaskDialog`、`SimilarityGroupsDialog`、`OptimizeDialog` 也应避免订阅整包 `tasks`；至少 `LibraryView` 必须改，否则打开对话框时的卡顿只是从工作区转移到网格。
5. 如果改完仍有明显延迟，再做一次临时计时（只记日志，不驱动 UI），确认是磁盘/CPU 竞争还是渲染；不要凭感觉继续加优化。

#### 验收

- 估算运行时打开对话框，弹窗立即出现，范围计数稍后补齐。
- 打开弹窗不再触发完整分面统计。
- 估算运行期间，切换网格/标签/文件夹的操作没有明显变卡（由用户手工验收）。
- 估算运行期间，`LibraryView` 不随每 150ms 的进度事件重渲染（可由 React DevTools Profiler 或临时日志确认）。

### 3.4 漏斗统计

#### 现状

- 环图分母是 `totalCount - processCount`，也就是整个范围。
- `processCount` 是候选张数减去候选内跳过，`candidateCount` 是候选张数；界面同时出现三个不同分母。
- `skipSegments` 把前置排除（已紧凑、已处理、透明、超 WebP）和候选内跳过（非 sRGB、16 位、画质、省得太少、失败）混在同一份图例里。
- 执行任务的进度总数是候选张数，和环图百分比不一致。

#### 统计定义

| 名称 | 定义 |
| --- | --- |
| 范围 total | 当前范围解析出的未删除图片 |
| 未纳入候选 | 只靠数据库列就能判定的前置跳过：已足够紧凑、已处理、有透明通道、超出 WebP 尺寸、GIF（动画/多帧保守跳过） |
| 候选 candidate | 通过前置判据、会进入解码与编码评估的图片 |
| 候选内跳过 | 解码后才发现不处理：非 sRGB 色彩、16 位源、画质不达标、省得太少、动画/多帧/多页（APNG、动画 WebP、多页 TIFF）、读取/解码失败 |
| 处理 process | 候选减去候选内跳过 |

必须成立的不变量：

```text
totalCount     = prefilterCount + candidateCount
totalBytes     = prefilterBytes + candidateBytes
candidateCount = processCount + candidateSkipCount
candidateBytes = processBytes + candidateSkipBytes
```

其中 `prefilterBytes` 是所有前置桶之和，`candidateSkipBytes` 是所有候选内桶之和（失败用 `failedBytes`；动画/多页、其他未分类原因也必须各有归口）。

#### 分类闭合与取整

1. `cumulative_skips` 必须覆盖 `SkipReason` 的所有变体。解码后的 `Transparent`、`BppLow`、`AlreadyOptimized`、`TooLargeForWebp` 目前会被漏掉，导致 `processCount` 偏高；要么把这几类并入对应前置桶，要么新增“解码后前置跳过/其他”桶，并在图例中单独显示。
2. 不要各桶独立 `round()` 后再用 `saturating_sub` 推 `process`。先算所有跳过桶，再令 `process = candidate - Σskip`，字节同理；或者用最大余数法校正。这样 `candidate = process + skip` 和字节不变量严格成立。
3. 漏斗测试要覆盖：多分层、解码后透明、读取失败、`sampleCount < 档位`、GIF/APNG/多页 TIFF，以及“处理 0 张”的边界。

#### 节省率上限

`MAX_SIZE_RATIO = 0.95` 是“新文件必须小于原图 95%”的阈值，不是节省率上限。`stratum_rates` 和 bootstrap 现在把节省率夹到 0.95，会把 PNG→JPEG 等高压缩比图的收益低估。改成 `clamp(0.0, 1.0)`，并补一张“样本压到原图 2%”的测试；这会改变预估节省、预测体积、曲线和文件夹明细，基准对比要用同一批图重跑。

#### 界面设计

1. 结果头部显示两行短信息：
   - `范围 390,542 张 · 350 GB`
   - `候选 378,000 张 · 340 GB`
2. 环图只展示候选池：
   - 中心百分比 = `processCount / candidateCount`
   - 图例只有“处理”和“候选内跳过”以及候选内全部细分（非 sRGB、16 位、画质、省得太少、动画/多页、失败）。
3. “未纳入候选”单独一组，放在环图下方或右侧，按体积排序，计数为 0 的项不显示：
   - 已足够紧凑
   - 已处理过
   - 有透明通道
   - 超出 WebP 尺寸
   - GIF（动画/多帧保守跳过）
4. 文案统一：
   - 前置排除叫“未纳入候选”，不叫“跳过”；
   - 候选内才叫“候选内跳过”/“跳过”。
5. “预计节省”“体积 total → predicted”“候选张数”保留；不再让“候选”成为孤立的一行。

#### 代码结构

- `OptimizeShareChart` 只接收候选池数据：`processed`、`candidateSkipped`、`candidateBreakdown`。
- `OptimizeDialog` 拆成两个函数：`prefilterSegments(estimate)` 和 `candidateSkipSegments(estimate)`，各自排序、过滤零值。
- 环图的 aria label 用候选池数字，不再用总范围。
- `OptimizeEstimate` 增加 `skipAnimated`（前置 GIF）与 `skipMultiframe`（候选内动画/多页），或合并为一个桶并写清定义。
- 执行报告在批次 2 补 `prefilterSkipped` / `candidateSkipped` / `duplicateSkipped` 字段，让执行完成后的“处理 X / 跳过 Y”也与漏斗一致；批次 1 先保证估算侧自洽。

#### 测试

- 用临时库构造三类图片：低 bpp（前置跳过）、透明图输出 JPEG（前置跳过）、正常可压图（候选）。跑估算后断言四个不变量。
- 再构造 16 位或非 sRGB 源，断言计入候选内跳过而不是未纳入候选。
- 构造解码后才发现的透明/bpp 低/已处理/超 WebP 尺寸样本，断言不会从统计里消失。
- 构造动画 GIF、APNG、多页 TIFF，断言计入跳过且不会进入处理。
- 构造多分层 + 独立取整场景，断言四个不变量严格成立。
- 前端只跑 `tsc`；占比与图例由用户手工验收。

### 3.5 耗时模型（批次 1 部分）

#### 现状公式

```text
cpu = 样本墙钟 × 候选像素 / 样本像素
io  = (候选字节 + 预测结果字节) / (样本字节 × 线程数 / 样本读取时间)
预计 = max(cpu, io) × 1.15
```

它漏掉了：

- BLAKE3
- 临时文件写入与每张 `sync_all`
- 每 1000 张的事务提交
- 提交后删旧原图、删查看器预览
- 三个重算开关（缩略图、pHash、主色）

`1.15` 在基线场景可能刚好盖住写盘/事务（归档计划里这部分约占 7%），但它是固定系数，不会随重算开关、删除量和图片规模变化。

#### 批次 1 要做的

1. 在样本编码中真实执行并计时：
   - BLAKE3（只对成功编码的样本）
   - 缩略图重建（勾选时）
   - pHash（勾选时）
   - 主色（勾选时）
   - 仍然不写文件、不写数据库；重算结果直接丢弃，只保留耗时。
2. 记录每个样本的分段耗时：读取、解码+编码+PSNR、哈希、重算。读取/解码失败也要尽量记录已发生的读取时间；当前 `failed_outcome` 把 `read_secs` 设为 0，会让 IO 模型偏乐观。
3. 增加结果字段：

   ```text
   sampleElapsedMs          样本编码墙钟时间（毫秒）
   estimatedWorkSeconds     编码、读取、哈希、重算
   estimatedWriteSeconds    写盘、fsync、提交（批次 1 用保守模型）
   estimatedFinishSeconds   删旧图、删预览（批次 1 用保守模型）
   estimatedSeconds         = 上述三项之和
   ```

4. 预计耗时的新拆分：

   ```text
   work  = max(样本墙钟按像素外推, 候选读取字节 / 读取带宽)
   write = 预测输出字节 / 写入带宽 + 处理张数 × 每张 fsync 成本
   finish = 批次数 × 每批提交成本 + 处理张数 × 每张删除成本
   total = work + write + finish
   ```

   - `预测输出字节 = processBytes - savingsBytes`（不小于 0）。
   - 批次 1 的写入带宽、fsync、提交、删除先用保守常数，并在结果里标记为估算；批次 2 用真实执行反馈替换。
   - 不再把 `predictedBytes` 整体算进读取/写入字节，避免把未处理的图片重复计入。
   - 缩略图包追加与 `segment_size_bytes` 目前发生在提交事务内，不属于样本阶段；批次 2 的 `write` 应把缩略图写入/事务内 I/O 单独计入，或把追加移出事务。

5. 收益曲线的耗时按分层重新累计：
   - work 按像素；
   - write 按该层的预测输出字节；
   - finish 按该层张数分摊；
   - 不再一律按像素。

6. UI：
   - 主数字仍是“预计耗时”；
   - 下面一行小字显示“其中：编码/重算 X · 写盘/提交 Y · 删除 Z”，为 0 的项省略；
   - 首次没有校准数据时，不承诺精确到分钟。

#### 关于“极高和高耗时差不多”

当前模型按候选像素算，不按最终处理张数算。画质不达标的图片在执行时同样要解码、阶梯编码、回解码、算 PSNR，最后才跳过；只有前置排除的图片才不进候选。所以“跳过张数多”本身不会让耗时按比例下降。

另外，阶梯当前在 PSNR 不达标时不检查体积，即使文件已经缩不到 5%，还会继续往 90/95/97 爬。高从 85 起，可能比极高（95 起）白试更多次。这是批次 2 的“阶梯早退”要修的；修完后两档的耗时差异会更符合直觉。

#### 测试

- 把耗时拆分和累加抽成纯函数，用注入的样本耗时做单测，断言总和、曲线单调、零值处理。
- 集成测试只验证开关打开时估算能正常完成、不写文件、不写库；不要写依赖墙钟的断言。
- 批次 1 不承诺最终精度；批次 2 用复制库实测校准。

## 4. 批次 2：执行写路径、断电保护与性能

> 实施状态（2026-10-26）：4.1–4.6 均已按本节落地。`cargo test --lib` 323 通过、8 ignored；线程、批次与预计/实际基准数字见 [性能基准](2026-10-27-性能实测记录明细.md#图片空间优化写路径2026-10-26)。与本节的差异：全局 `synchronous=FULL` 改为只在压缩提交与释放任务删行时临时 FULL（作用域守卫恢复）；目录 flush 在本机可用，但系统不支持时按“依赖 write-through”处理并在文档里写明边界；没有做拔电注入测试。

### 4.1 断电安全发布协议

#### 现状与风险

当前顺序：

1. 读原图、编码。
2. 写 `.artbank/temp/optimize-*`。
3. 每张 `sync_all`。
4. 1000 张一批：事务内 rename 到目标内容文件、更新行、提交。
5. 提交返回后删旧图与查看器预览。

问题：

- `sync_all` 只保证新文件数据；SQLite 是 `synchronous=NORMAL`，提交不保证断电持久。
- 提交返回后立即删旧图。如果断电丢了 WAL 提交，旧图已经删除，行会指向不存在的旧文件。
- rename 在 commit 之前。如果进程在 rename 后、commit 前崩溃，目标文件成为孤儿：没有行引用，但已经不在 temp 目录，文件守卫不会删。
- 下次执行压缩时，`publish` 看到目标已存在，会当成“内容重复”跳过该行。由于 `content_hash` 唯一且没有行引用这个孤儿，图片会永远保持旧图且不报错。

#### 目标顺序

```text
写 temp
  → 文件数据 fsync
  → 持久化 rename 到目标内容文件
  → 目标目录持久化
  → SQLite 事务提交（持久化）
  → 删除旧图与预览
```

任何一步失败都不进入下一步；提交没有持久化之前，不能删旧图。

#### Windows 实现

1. 新增 `platform/fs.rs`（或 `platform/durable.rs`），提供：

   ```rust
   pub fn rename_durable(from: &Path, to: &Path) -> AppResult<()>;
   pub fn flush_directory(path: &Path) -> AppResult<()>;
   ```

2. Windows 的持久化 rename：
   - 优先 `MoveFileExW`，标志 `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`；
   - 需要新增 `windows-sys` 依赖时，只启用文件系统相关 feature；
   - 如果目标已存在，先走孤儿处理逻辑，再决定替换。
3. 目录持久化：
   - 先做一个小实验验证“打开目录句柄 + `FlushFileBuffers`”在目标 Windows 版本上是否可用；
   - 如果不可用，就依赖 `MOVEFILE_WRITE_THROUGH`，并在文档中写清边界；
   - 如果两者都不可用，停止批次 2 并向用户报告，不静默降级。
4. 每批按目标目录分组，rename 完成后对每个唯一目录只 flush 一次，避免 1000 次目录 flush。
5. 非 Windows 平台使用标准 rename + 目录 fsync（如果继续跨平台）；本计划以 Windows 为准。

#### SQLite 持久化

- 首选把 `schema::configure` 的 `PRAGMA synchronous` 从 `NORMAL` 改为 `FULL`，让所有提交都 fsync WAL。
- 先做基准：普通编辑、标签、导入、MCP 写是否明显变慢。
- 如果全局 FULL 的开销不可接受，改成只在破坏性写任务（压缩、永久删除、清空回收站、释放任务）期间对写连接设置 FULL，任务结束恢复 NORMAL；必须用作用域守卫保证取消/失败也会恢复。
- 无论哪种方式，必须在“提交返回后”才删旧图。

#### 孤儿恢复

在 `commit_batch` 内，把“目标已存在”的判断改成能区分三种情况：

1. 已有其他行引用该 `content_hash`：正常的内容重复，跳过该行。
2. 当前行自己已经指向该 `content_hash`：视为已完成，删 temp，跳过。
3. 没有任何行引用：
   - 目标文件不存在：正常 rename。
   - 目标存在：这是崩溃留下的孤儿。
     - 计算目标文件的 BLAKE3，并与新哈希比较；
     - 匹配：接管该文件（删 temp，按本批发布处理）；
     - 不匹配：删掉孤儿，再持久化 rename temp。

只有在罕见恢复路径才读目标文件算哈希，正常路径不增加成本。接管/替换要写一条 `log::warn!`，方便后续排查。

同一套逻辑应用到导入的发布路径；导入不删原图，但同样可能出现 rename 后、入库前崩溃的孤儿。

#### 永久删除与释放任务

- 全局 FULL 或作用域 FULL 保证“删行提交”持久化后，释放任务才删文件。
- 删除文件本身不需要 fsync；断电后文件可能重新出现，但已经没有行引用，属于孤儿，不影响正确性。
- 如果后续实现孤儿清理任务，再把这类文件纳入清理范围。

#### 这一层不承诺什么

- 不承诺磁盘自身缓存撒谎、文件系统损坏、外部程序改文件时的恢复。
- 不承诺整个库的任意时刻快照一致；只保证优化/删除这类写操作在批次边界上不会出现“行指向坏文件/已删旧图”。
- 不做全库启动扫描；孤儿恢复只在压缩/导入的发布路径上做。

#### 测试与基准

- 单元测试：
  - 目标文件不存在 → 正常发布。
  - 目标文件存在且被其他行引用 → 跳过。
  - 目标文件存在但没有任何行引用，内容匹配 → 接管。
  - 目标文件存在但内容截断/不匹配 → 替换为新文件。
  - 提交失败 → 新文件删除，数据库不变。
- Windows 平台层测试：持久化 rename 成功后文件可见、目录 flush 可调用；记录失败时的错误。
- 基准：在复制库上比较“当前行为 / 新协议”的耗时，报告每张 fsync、每批提交、目录 flush 的开销；用户已接受断电保护的代价，基准用于确认量级和发现异常。
- 不对真实机器做拔电测试；如需，用虚拟机单独验证。

### 4.2 去掉重复读

#### 现状

执行和估算都是：

1. `std::fs::read` 整个文件，用于色彩配置判断和 JPEG 元数据搬运。
2. `decode::decode(&path)` 再打开文件读一遍、解码。

同一张图读两次盘、分配两次完整 buffer。

#### 设计

- 在 `import/decode.rs` 增加从字节解码的入口：

  ```rust
  pub fn decode_bytes(bytes: &[u8], format_hint: Option<&str>) -> AppResult<DecodedImage>
  ```

- `encode_one`、`sample_one` 复用已读 `bytes`，不再传路径。
- 保持现有上限：单边 65535、1 亿像素、512 MB 分配。
- 魔数识别失败时用 `row.format` / `file_ext` 兜底，尤其 TGA。
- 方向处理与当前一致。

#### 测试

- 同一张 PNG/JPEG/TGA 分别从路径和字节解码，尺寸、格式、alpha、方向一致。
- 超大尺寸仍被拒绝。
- 执行与估算的现有测试保持通过。

### 4.3 阶梯编码早退与像素复用

#### 现状

- 每轮先编码，再回解码，算 PSNR；PSNR 达标后才检查是否小 5%。
- 如果当前质量已经缩不到 5%，仍然回解码、算 PSNR，并继续往高质量爬。
- 每轮编码都 `to_rgb8()`/`to_rgba8()` 复制整图，PSNR 比对又复制一次。

#### 早退设计

在阶梯循环内改成：

```text
编码
  → 如果不满足“小 5%”，立即返回“省得太少”
  → 回解码、算 PSNR
  → PSNR 不达标则继续下一档
  → 达标则返回结果
```

理由：同一张图、同一输出格式下，质量越高文件通常越大。当前质量已经不满足 5%，更高只会更大。这样可以省掉回解码和 PSNR 的时间，也避免高质量档白试多轮。

风险与兜底：

- 补一个 JPEG/WebP 质量单调性测试：对多种图片断言 `size(q+1) >= size(q)`。如果发现反例，就把早退条件收紧，例如只在“当前体积已经不小于原图”时早退，或允许再试一档。
- 这会改变跳过分类：原来可能记为“画质不达标”的图，现在可能记为“省得太少”。这更符合实际，但需要同步更新统计、文档和测试。

#### 像素复用

- 在 `encode_ladder` 开始前把 `prepared` 转成一次 RGB8 或 RGBA8 buffer：
  - JPEG 输出用 RGB8；
  - WebP 输出根据 alpha 用 RGB8/RGBA8。
- `encode` 接收像素 buffer，不再每轮 `to_rgb8`/`to_rgba8`。
- PSNR 比对：
  - 原图 buffer 只准备一次；
  - 编码结果解码后转换一次；
  - MSE 用整数累加，最后再转 f64；
  - 不引入嵌套 rayon，避免和外部线程池叠加。
- 内存：预计算 buffer 仍是每线程一份；如果大图内存压力明显，和批次 2 的线程上限/内存预算一起评估。

#### 测试

- 现有阶梯质量测试保持通过。
- 新增早退测试：构造一张在当前质量下无法缩到 95% 的图，断言只编码一次且返回“省得太少”。
- 新增“早退后画质结果不变”的回归测试：能处理的图仍返回原来的质量档。
- 基准：在复制库上比较早退前后的高/极高耗时和跳过分类。

### 4.4 线程与调度

#### 现状

- 优化估算/执行：`min(可用并行度, 8)` 的独立 rayon 池。
- 导入：设置里的 `workerThreads`，空则“核数−1”，上限 128；另有 1 个写线程。
- 缩略图重建：单线程循环。
- AI 描述/姿势/embedding：Rust 侧单线程顺序发 HTTP。
- 撤销/重做/移动/永久删除/释放：单线程分块。
- 任务总线：write 与所有 lane 互斥；ai 与 scan 可以并行；同 lane 串行；每个任务独立 OS 线程；进度 pump 每 150ms。

#### 设计

1. 先做基准，不先改代码：
   - 复制 2–5k 张混合 JPEG/PNG（含大图）。
   - 固定同一批图、同一输出格式/档位，分别跑 4 / 8 / 12 / 核数−1 线程。
   - 记录墙钟、CPU 占用、峰值内存、磁盘吞吐。
2. 根据基准选策略，候选顺序：
   - `min(核数−1, 12)`，留一核给 UI；
   - 如果大图导致内存峰值过高，加内存预算：按候选最大尺寸估算每线程峰值，限制 in-flight 张数；
   - 如果 8 线程已经是吞吐拐点，就保持 8，但在文档里写清理由，不再叫“保守”。
3. 估算与执行共用同一策略；导入暂时保持现有设置，除非基准证明需要统一。
4. 如果新增设置：
   - 复用 `performance.workerThreads` 作为全局图像工作线程上限，或新增独立的图像处理线程字段；
   - 界面文案要说明“0/留空自动”，并给内存风险提示；
   - 设置校验仍在 1–128，但优化侧会再按内存预算夹一次。
5. 缩略图重建是否并行单独评估，不混进本批次必做项。

#### 验收

- 有基准数字和最终选择理由。
- 同一批图在最终线程数下不 OOM，UI 仍可操作。
- 估算/执行不会与导入的线程策略互相踩踏（write lane 已互斥）。

### 4.5 提交与删除优化

1. 删除旧图时不要每张都 canonicalize 根目录和父目录：
   - 每批 canonicalize 一次根目录；
   - 按目标文件夹缓存已校验的 parent；
   - 只对缓存未命中的文件夹做一次 canonicalize；
   - 路径仍来自 `content_path`，保留 `..`/绝对路径校验。
2. 提交后的旧图删除与预览删除并行执行：
   - 不持有数据库写锁；
   - 收集失败项，记日志，不中断已提交批次；
   - 删除失败留待后续维护清理。
3. 每批重复哈希检查改成一次批量查询：
   - 先查本批所有 `new_hash` 是否已有行引用；
   - 批内重复用内存集合处理；
   - 减少 1000 次单条 `SELECT`。
4. 同一批目标目录只 `create_dir_all` 一次。
5. 基准比较 500 / 1000 / 2000 张一批：
   - 更大批次减少提交次数，但增加事务时长和失败回滚范围；
   - 结合 FULL 提交的开销决定最终批次大小。
6. “编码下一批”和“提交当前批”是否重叠，先不做；等基准显示提交占比明显再评估，避免引入复杂的状态机。

### 4.6 最终耗时标定

#### 记录真实执行数据

在 `OptimizeReport` 中增加实际耗时/字节字段（或单独日志），至少包括：

- 编码墙钟
- 哈希耗时
- 重算耗时
- 写盘/fsync 耗时
- 提交耗时
- 删除耗时
- 实际处理字节、输出字节、删除文件数

### 校准方式

优先用“上次执行反馈”校准下次估算，保持估算只读：

- 每次执行结束后，把实测的“每输出字节写盘秒数、每张 fsync 秒数、每 1000 张提交秒数、每张删除秒数”写入本库的校准记录；
- 校准记录可以放在现有 `meta` 表中，不需要改 schema；键名带版本，例如 `optimize.calibration.v1`；
- 估算优先读取本库校准值，没有则用保守常数；
- 换库时使用各自记录；同一库换磁盘后，第一条执行会更新校准。

如果实测误差仍然大，再评估“估算时写一个很小的校准文件”的方案；那会改变“估算不写临时文件”的现有约定，需要单独确认，不在本计划默认范围内。

#### 模型与曲线

- 使用 3.5 的拆分公式，把批次 1 的保守常数替换为校准值。
- 曲线累计：
  - work 按像素；
  - write 按每层预测输出字节；
  - finish 按每层张数分摊；
  - 最后一点的耗时等于总预计耗时。
- UI 继续显示总耗时和三项拆分；不新增大的统计区块。

#### 验证

- 在复制库上跑不同档位、JPEG/WebP、三个重算开关组合，比较预计与实际。
- 先以 ±25% 为目标；如果某项偏差持续过大，单独调该项系数，不改算法。
- 特别验证：
  - 极高与高在阶梯早退后的耗时差异；
  - 重算开关打开后的耗时增长；
  - 全库执行时提交/删除耗时占比；
  - 取消后已完成批次的实际耗时是否被正确记录。

## 7. 风险与待确认

1. **Windows 持久化 rename/目录 flush 的可用性**：需要实验验证；不可用就报告，不静默降级。
2. **全局 `synchronous=FULL` 的性能**：普通编辑、导入、MCP 写都会多一次 WAL fsync；先基准，必要时改成只在破坏性写任务期间 FULL。
3. **阶梯早退的单调性假设**：JPEG/WebP 通常质量越高文件越大，但不是数学保证；用测试兜底，必要时收紧条件。
4. **孤儿接管需要校验哈希**：断电后的孤儿可能截断，不能只看文件名；校验只发生在罕见路径。
5. **耗时模型仍是估算**：即使补齐所有项，也只能做到同机、同参数下的近似；不承诺精确到分钟。
6. **任务接管不跨应用重启**：任务中心只存在内存里；重启后不恢复。
7. **时间校准的存储位置**：优先放现有 `meta` 表，不改 schema；如果实现发现不适合，再单独评估。
8. **线程设置的作用范围**：复用 `performance.workerThreads` 还是新增字段，要看基准和界面文案；不要静默改变导入的现有行为。
9. **真实库只读**：所有执行、断电、耗时基准都在复制库/子库上做。
