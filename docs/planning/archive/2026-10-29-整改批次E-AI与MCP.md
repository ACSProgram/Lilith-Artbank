- 来源：[全量代码审查报告（2026-10-29）](../Lilith-Artbank-全量代码审查报告-2026-10-29.md) 的 T6、T7、T8、T9，以及 Python 服务的两项加固

## 已确认决策

1. **T7 超时**（报告 #13）：单次 120 秒、最多 3 次、总预算 5 分钟；取消能立刻打断请求与重试等待。
2. **T8 执行卡住**（报告 #14）：不自动判失败；10 分钟没有进度标「疑似卡住」，返回当前进度，由 AI 决定继续等还是取消。
3. **T9 关闭 MCP**（报告 #15）：立刻断开已连接的客户端，并让所有工具入口检查服务已关闭。
4. **Python 服务**（本轮对话确认）：只做不动协议的两项——连接/推理并发上限与解码像素上限；`/v1/shutdown` 鉴权要改 Rust 与 Python 之间的启动契约，按报告 #18 留到下一轮。
5. **T7 取消实现**（本轮对话确认）：请求放到旁路线程 + 100 毫秒轮询取消，取消后约 100 毫秒返回；不使用「只在重试之间检查」的方案。

## T6：监督线程改用「代次 + 持有者」交接

问题：`supervising: AtomicBool` 是纯标志。`apply_settings` 先推进代次再 `spawn_supervisor`，但不重置标志：旧监督线程因代次变化提前返回，它的 guard 又因 token 不匹配拒绝清标志；新线程被 `swap(true)` 挡掉。结果是服务启动中（最多 60 秒 + 退避）保存 AI 设置后，自动拉起永久静默失效，只能手动点「启动」。

做法：

- 新增 `SupervisorSlot { generation: AtomicU64, owner: Mutex<Option<u64>> }`，代次与持有者在同一把锁里交接：
  - `invalidate()`：代次前进，作废当前线程；与 `claim` 用同一把锁，避免「读代次 → 改代次」与交接交错；
  - `claim()`：同一代次已有线程在监督时返回 `None`（状态刷新反复调用不会另起线程），否则取新代次并记下持有者；
  - `release(token)`：只释放自己那一代，旧线程退出不会清掉新一代的标记；
  - `is_stale(token)`：线程自己的退出判据。
- `spawn_supervisor` 改成 `claim()` 成功才起线程，`SupervisorGuard` 退出时 `release`；`start_service` / `stop_service` / `shutdown` / `apply_settings` 统一调 `invalidate_supervisor()`。

## T7：单次 120 秒、总预算 5 分钟、取消可打断

问题：describe 单次 300 秒、最多 3 次、退避 250ms/1s，取消只在图片之间检查。服务卡死时单张描述要占 15 分钟，用户点取消后任务长时间停在「取消中」。

做法：

- `AiClient` 收拢成一层 `execute()`（发请求、读响应体）+ 一层 `with_budget()`（按预算切尝试）。单次 120 秒、3 次尝试、总预算 300 秒；`/v1/models/ensure` 单独一份更宽的预算（600 秒 × 2 次、11 分钟）。超预算返回「AI 服务在总时限内没有响应，已停止等待」，不重试。
- `AiError` 增加 `cancelled`：取消与超预算走同一条快速返回路径，不参与重试。
- 取消信号是 `CancelSignal = Arc<dyn Fn() -> bool + Send + Sync>`，由 `AiClient::cancellable` 注入；批量任务传 `TaskHandle::should_cancel`。
- 阻塞客户端没有中断接口，所以带取消信号时请求跑在旁路线程，主线程每 100 毫秒看一次取消；取消后立即返回，旁路线程受单次超时约束自己结束。退避等待也按 100 毫秒切片睡，取消能立刻打断。
- `job.rs` 的逐张循环：错误返回时如果任务已取消，直接 `Ok(())` 收尾，不再把被打断的那张记进失败清单。

## T8：确认队列生命周期闭合

问题：超过 50 条无条件 `pop_front`，会把执行中的记录挤掉；只有 Pending 会过期，Running 的终态只从任务快照临时推导、不落回记录。执行线程 panic 或长跑后卡片永远「执行中」，AI 再查得到「不存在」。

做法：

- `ApprovalRecord` 增加 `last_progress_at` 与 `progress`；`ApprovalView` 增加 `stalled` 与 `progress`。
- 新增 `ApprovalQueue::sync_tasks(&[TaskSnapshot])`，由 `AppState::mcp_approval_views` 在每次读取前调用：进度变了就刷新时间与进度摘要；任务进入终态（完成/失败/部分失败/取消）就把状态回写进记录。任务快照被回收后记录仍然是终态。
- `is_stalled()`：`Running` 且距上次进度超过 10 分钟。只标注，不改状态，不判失败。无头构建可用 `LILITH_MCP_APPROVAL_STALL_MS` 缩短。
- `tasks_get(approvalId)`：`stalled` 视为「这次不用再等」，立即返回 `approval`（含 `stalled`、`progress`）与任务快照，由 AI 决定继续等还是取消。
- `trim_locked`：先淘汰终态记录，再淘汰最老的待确认单；执行中的记录一条都不丢（队列里全是执行中时宁可临时超上限并记一条日志）。

## T9：关闭 MCP 真正断开，工具入口校验开关

问题：`stop` 只 cancel accept 循环，每条连接独立 `tokio::spawn` 且未跟踪；写工具只判 `ReadOnly`。关闭 MCP 后客户端保持的 keep-alive 连接仍可继续调用读工具，完全档下甚至继续写库。

做法：

- `serve_with` 用 `Vec<JoinHandle>` 跟踪每条连接，每条连接内部再 `select!` 监听同一个取消令牌；循环退出后先 `abort` 再逐条 `await`，`serve()` 返回即代表所有连接已关闭（`stop()` 的「端口已释放」判断因此仍然成立）。
- `McpServer::with_context` / `with_state` 是 24 个工具的唯一入口，两处统一调 `ensure_enabled(&state)`：`settings.mcp.enabled` 为 false 时返回「MCP 服务已关闭，请在设置 → MCP 中重新开启后重试」。

## Python 服务：两项加固

- `main.py`：推理并发上限 `MAX_INFERENCE_CONCURRENCY = 4`，用 `BoundedSemaphore` 非阻塞取名额；满了立刻回 503 `server_busy`，不排队（排队只会把显存与内存一起放大）。`/v1/health` 与 `/v1/shutdown` 不占名额，并发推理时也能探活与关闭。
- `image_io.py`：单张解码上限 `MAX_PIXELS = 100_000_000`（与导入解码上限一致），在 `Image.open` 之后、`load()` 之前按 `size` 判断，超过直接 `ImageDecodeError`，路由层映射为 422。

## 前端

- `McpApproval` 类型补 `stalled` 与 `progress`；确认卡片在 `stalled` 时显示一行「10 分钟没有新进度，疑似卡住；任务仍在运行，可以让 AI 继续等或取消。」，样式用 `--warning` 系列（新增 `.mcp-approval-stalled`）。

## 提交前复查整理

- `AiClient::execute` 改为接收 `&str`，去掉三处 `url.clone()`；旁路线程里才转成 `String`。
- `with_budget` 把尝试次数收敛到至少 1，`unreachable!` 不再是可达路径。
- `SupervisorSlot::invalidate` 与 `claim` 共用一把锁，避免「读代次 → 改代次」与交接交错。
- `image_io.py` 两次 `except` 合成一次；超限错误仍原样上抛，不被包成「无法解码」。
- `tasks_get` 的工具描述与 `waitMs` 参数说明补上「长时间没有进度也会立即返回」，否则 AI 不知道 `stalled` 会提前返回。

## 未做与遗留

- `/v1/shutdown` 仍然无鉴权（报告 #18）。要加令牌需要 Rust 生成并随启动参数传给 Python、`AiClient` 带令牌调用、便携包与文档同步改。
- 「疑似卡住」只标注不改状态：真正卡死的任务仍需用户或 AI 主动取消；没有自动超时终止。
- 确认队列的执行中记录若所在任务已被任务总线回收（超过 50 条任务）且没有再次同步，会一直停在 `running`，此时靠 `stalled` 提示；没有「按图库代次清空」之外的兜底。
- T7 的旁路线程在取消后最多再跑完这一次尝试（≤120 秒）才回收，没有真正的 socket 中断。
