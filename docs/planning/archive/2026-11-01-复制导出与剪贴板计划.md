# 复制、导出与剪贴板计划

日期：2026-11-01
来源：本次只读调查（复制路径 150 条、剪贴板 50 百万像素、右键菜单三项并列）
当前能力：[当前状态](current-handoff.md) · 待办：[待办与待决策](todo.md) · 契约：[浏览与查询](../modules/browse-and-query.md)

## 目标

1. **复制路径不再被已加载行数截断**。全选 5 千张就复制 5 千条，与移动、删除、加入集合的行为一致。
2. **右键「复制」只剩两个动作**，语义一致（都写剪贴板）；「导出」明确是任务，不冒充第四种复制。
3. **剪贴板的像素上限说人话**，拒绝时给出路，不再只报「50 百万像素」。

一次做完，不拆批次。

## 现状与根因

| 现象 | 根因 | 证据 |
| --- | --- | --- |
| 复制路径最多 150 条 | `copyPaths` 用 `contextMenu.items`（已加载行），不是 `contextMenu.ids`（完整选择） | `LibraryView.tsx:1302-1321`；`PAGE_SIZE = 150`（`model.ts:14`） |
| 提示「另有 N 张未复制」 | 上面那条的直接后果，代码自己在承认差额 | `LibraryView.tsx:1307-1315` |
| 多选复制图片只得到第一张 | 菜单写「首张」，实际取 `items[0]` | `LibraryContextMenu.tsx:173-177`、`LibraryView.tsx:2252-2256` |
| 右键「复制哈希」与详情面板重复 | 详情面板已有同功能图标按钮 | `ImageInspector.tsx:742` |
| 多选时无法复制哈希 | 批量侧栏没有该入口，右键撤掉后就没有了 | `BatchInspector.tsx:234-457` |
| 剪贴板报「50 百万像素」 | `MAX_CLIPBOARD_PIXELS / 1_000_000` 直译进中文 | `platform/clipboard.rs:29-36` |
| 5000 万像素上限挡住 6100 万像素相机图 | 用 arboard 写原始位图，内存与像素成正比 | `platform/clipboard.rs:9`、`MAX_EDIT_PIXELS`（`imageops/edit.rs:13`） |
| 复制出来的路径不是原图 | `filePath` 是库内副本 `<根>/<文件夹>/<BLAKE3>.<ext>` | `query/sql.rs:632-646` |

已确认**不存在**的问题，不在本计划范围：移动、删除、标签、评分、加入集合都走后端范围解析，上限 100 万张；能力查询 500、状态查询 1000 只被「找相似参考图」调用，而参考图本身上限 100。

## 已定决策

1. **文本由 Rust 拼好再写剪贴板，不回传前端。** 10 万条路径约 20 MB，走 IPC 回传 JSON 没有收益；命令只返回复制了多少条。
2. **两个命令而不是一个带枚举参数的命令**：`copy_image_paths`、`copy_image_hashes`。命令名说明行为。
3. **顺序按传入的 id 顺序**（用户的选中顺序），不是按 id 排序。
4. **右键撤掉「复制哈希」，多选侧栏补上**；多选时隐藏「复制图片」，不做「复制首张」这种隐式行为。
5. **「导出到文件夹…」放「整理」组**，复用现有导出任务，不新写文件复制。
6. **剪贴板上限提到 8000 万像素**，覆盖 6100 万像素全画幅；RGBA 峰值 320 MB，仍在 1.5 GB 图像预算内。

## 改动

### 1 · 后端按 id 取文本

新增 `src-tauri/src/library/query/paths.rs`：

- `paths_for_ids(db, root, ids)`：按 `SQL_CHUNK` 分块查 `content_hash / file_ext / folders.path`，用 `LibraryPaths::content_file` 拼绝对路径
- `hashes_for_ids(db, ids)`：只查 `content_hash`
- 两者都**保持传入顺序**：先建 `HashMap<i64, _>`，再按输入顺序取值；查不到的行跳过
- 返回 `(文本列表, 缺失条数)`，缺失用于提示

命令层（`app/commands.rs`）只做适配，空选择直接报「没有可复制的图片」：

- `copy_image_paths(imageIds: Vec<i64>) -> Result<u64, String>`
- `copy_image_hashes(imageIds: Vec<i64>) -> Result<u64, String>`

### 2 · 前端接线

- `src/modules/library/api.ts` 加两个方法；**不再**在前端拼字符串
- `copyPaths` 改为 `libraryApi.copyImagePaths(contextMenu.ids)`，删掉 `hidden` 差额逻辑；提示「已复制 N 条文件路径」，缺失时补「另有 M 张已不在图库」
- `BatchInspector` 加「复制内容哈希」图标按钮，用 `imageIds`，放在现有 `inspector-inline-actions` 里，与详情面板同款

### 3 · 菜单

- 「复制」组：图片（`menu.items.length === 1` 时渲染）、文件路径

## 风险

1. **复制 10 万条文本约 20 MB 进剪贴板**，个别编辑器粘贴会卡。不做分批——分批会让用户拿到不完整的列表。
2. **保序的实现成本**：`rows_by_ids` 不保证顺序，新函数必须自己回填；写错会变成「按 id 排序」，Shift 选的范围顺序就乱了。
3. **导出入口与维护页重复**：两处都能导出，参数不同（右键固定不附 manifest）。若要求右键也能选 manifest，再把维护页的导出分区抽成共用对话框。
4. **8000 万像素的 320 MB** 要交给系统剪贴板持有，低内存机器上粘贴方可能失败，属平台行为。

## 待决策 · 复制文件引用

把「复制图片」从「写位图」改成「写文件引用」：

- Windows 侧写 `CF_HDROP`（`DROPFILES` + 宽字符路径列表），`windows-sys` 加 `Win32_System_DataExchange` / `Win32_System_Memory`
- 效果：粘贴到资源管理器得到哈希名文件，粘贴到 PS / Word 能直接打开；**不解码，内存几乎为零，像素上限问题自动消失**
- 代价：约 80 行 Windows 专用 unsafe 代码；粘贴到聊天软件会变成「发文件」而不是图片预览
- 与 `todo.md` 待决策里的「拖出到资源管理器（OLE）」是同一类能力，这一条就是把它具体化

做不做、什么时候做都不影响上面的改动。

## 不做

- 复制路径时把文件也写进剪贴板（那是上面的待决策项）
- 「复制首张」这种隐式多选行为
- 把哈希留在右键菜单里（低频、与详情面板重复）
- 提高编辑上限（50 MP 关系到保存耗时与内存，与复制是两件事）
- 为导出新增独立对话框（复用现有任务与目录选择器）
