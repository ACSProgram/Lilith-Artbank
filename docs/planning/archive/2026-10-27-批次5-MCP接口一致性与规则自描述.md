# 使用反馈整改 批次 5：MCP 接口一致性与规则自描述

日期：2026-10-27
状态：已实现并归档；自动检查通过，等待用户手工验收。代码定位、真实库只读测量与决策在准备阶段完成；实现记录见文末“十、实现记录”，正文行号为准备阶段快照。

范围对应《[使用反馈整改计划](../2026-10-27-使用反馈整改计划.md)》的 M1–M5。本批次只改 MCP 只读工具的列表口径、`library_info` 的规则表达、标签筛选模型、标签管理写入与对应界面入口；不改三档权限与 100 张阈值本身，不开放新的破坏性能力，不为了分页放宽单页上限，不动标签计数 SQL 的性能（留给批次 6）。

## 已确认决策

| 问题 | 结论 |
| --- | --- |
| 列表分页用什么游标 | 统一 `offset` 语义的不透明字符串游标，字段名 `cursor` / `nextCursor`。理由：两个列表在 SQL 层都必须先把全部标签/子文件夹聚合完才排序，键集游标省不掉任何扫描；而聚合上的键集条件要把计数子查询写两遍，实测反而更慢（见“四、前置测量”）。offset 与 `image_sheet` 的相似度翻页、`search_images` 的 `pageToken` 同源，AI 只需把 `nextCursor` 原样回传。 |
| 排序与快照口径 | 排序不变（标签按图片数降序、再按名称；子文件夹按 `sortIndex`、再按小写路径）。计数会随写入变化，翻页期间不保证快照一致：返回 `total` 让 AI 判断是否翻完，文档写明“两次翻页之间有写入时可能出现重漏”。不引入事务级快照。 |
| 单页上限 | 保持 500（`tags_list` 默认 100、`folders_list` 默认 200）。分页只是让超过上限的内容可达，不放宽单页。 |
| `history_list` / `collections_list` | `history_list` 不补游标：记录上限等于 `maxSteps`（≤500），一次返回即可，`total` 已给出。`collections_list` 不补游标：集合是用户手工维护的少量对象（真实库 1 个），补游标只增加接口面积。两者都在文档里写明“不分页”的原因。 |
| `library_info` 如何表达阈值 | 用结构化 `approval` 块：`requiredInMode: "ask"`、`appliesToCurrentMode`、`threshold`（只在询问档给出，其它档为 `null`）、`alwaysApproveInAsk`、`queueClearedOnFull`。删掉原来无条件的顶层 `approvalThreshold`，改为 `writeAllowed`（只读档 false）+ 保留 `writeTools`（表示工具已注册，三档都 true）。 |
| 写工具回执是否带确认标记 | 不带。`status: "pendingApproval"` 本身已经说明发生过确认；完全档每次写入都回填 `approval: false` 属于噪声。规则靠 `library_info` 与服务端 instructions 表达。 |
| 标签缺失/排除的字段 | 新增 `tagPresence: any/has/missing`（`has` = 至少一个标签、`missing` = 一个标签都没有）+ `excludeTagIds`（排除拥有其中任一标签的图片）。不扩展 `tagMode: none`：`tagMode` 描述的是 `tagIds` 内部怎么组合，混进“没有任何标签”会让一个字段有两种含义。 |
| 标签筛选的冲突 | `tagPresence=missing` 与 `tagIds` 同时给出直接报错（“没有任何标签”和“含某些标签”互斥）；`missing` 与 `excludeTagIds` 同时给出允许，`excludeTagIds` 在结果恒为空时不起作用，不做额外校验。 |
| 是否同步到浏览界面 | 同步 `tagPresence`：筛选面板标签区加“无标签”开关，与“任一/全部”互斥。`excludeTagIds` 只做后端与 MCP，界面暂不提供反选入口（面板标签列表现在是单选态复选框，加反选要重新设计三态交互）；语义只有一份，界面只是少一个入口，记为后续项。 |
| 分面行为 | 保持“标签分面不应用 `tagIds` / `tagPresence` / `excludeTagIds`”的自排除默认，不改默认。只在 `includeFacets` 为真时多返回一条 `facetsNote` 说明口径，不新增收窄参数。标签分面仍只给 `tagId` 与计数，不带名称：名称请用 `tags_list` 逐页取，避免热路径上多一次 `tags` 连接。 |
| 标签管理工具形态 | 新增单个 `tags_modify`，`action: rename/delete/merge`，与 `folders_modify` 同形。`rename` 与 `delete` 复用 `metadata::rename_tag` / `delete_tag`；`merge` 新增 `metadata::merge_tags`。 |
| 合并的语义 | `sourceId` 的全部图片关系迁移到 `targetId`：目标上已存在的关系只去重不重复插入；迁移完后删除源标签行（关系随外键级联消失）。一次调用一条 `tagMerge` 记录，可撤销。 |
| 合并的撤销 | 撤销时把迁移到目标的关系删掉、按原 id 重建源标签并插回它的全部关系；重做时重新插回目标关系并再次删除源标签。若撤销时已存在同名标签，关系插回那个标签、不重建（与 `tagDelete` 的既有处理一致）。 |
| 合并是否补界面 | 补。`TagManagerDialog` 每行加“合并到…”入口，选定目标后二次确认；只给 AI 用的破坏性能力会让能力边界不可见。 |
| `tags_modify` 的权限 | 只读档拒绝。询问档：`rename` 直接执行；`delete` 与 `merge` 需要用户确认（会成批移除关系）。完全档直接执行。不套用 100 张阈值：标签操作的范围是“整个标签”，与选择集无关。 |
| 数量核对 | `delete` / `merge` 支持 `expectedImages`（源标签当前图片数）：给了且与现状不符就拒绝，避免 AI 按过期数字删错。不做 `confirmedCount`：没有 selector。 |
| 临时区 | 标签操作不区分临时图片：临时图片的标签本来就不写操作记录，但 `image_tags` 关系是一致的。合并会把临时图片上指向源标签的关系一并迁移；撤销同理。不做特判。 |

## 一、现状

### 1.1 列表分页（M1）

- `tags_list` 单页上限 1–500、默认 100，名称搜索路径内部再收到 200，**没有 `total`、没有游标**（`src-tauri/src/mcp/tools/read.rs:284`、`:286`）。默认 100 意味着超出的标签对 AI 完全不可见——真实库有 175 个有图标签，75 个拿不到（见“四、前置测量”）。
- `query::list_tags` 用 `JOIN image_tags` 聚合，只返回有图的标签，`ORDER BY count(images.id) DESC, tags.name`（`src-tauri/src/library/query.rs:656`、`:667`）。`search_tags` 用 `LEFT JOIN` + `LIKE`，上限 200（`:683`、`:692`）。

- `folders_list` 每次都调用 `query::list_folders`，它要全表 `GROUP BY images.folder_id` 拿到直接计数（`query.rs:622`、`:626`）。真实库单次约 1.8 s，翻页会让这个成本线性叠加（见“四”）。
- `history_list` 上限 1–500、默认 100，返回 `total` 与 `maxSteps`（`src-tauri/src/mcp/tools/history.rs:47`、`:57`、`:82`）；操作记录本身被 `maxSteps`（默认 500）限制，因此不需要游标。
- `collections_list` 无上限（`read.rs:305`）；真实库 1 个集合。
- `search_images` / `find_similar` / `image_sheet` 已有游标或 offset，本次不动。

## 二、目标行为

### 2.1 列表翻页

- `tags_list` 增加 `cursor`、`total`、`nextCursor`：
  - 返回当前页的 `tags`、本次命中总数 `total`（有图标签数，与筛选口径一致）、`nextCursor`（还有下一页时给出，否则 `null`）。
  - `limit` 仍 1–500、默认 100；名称搜索路径不再单独收到 200，与其他路径共用同一上限（搜索本身已经把候选收窄）。
  - 排序不变。`cursor` 是不透明字符串，AI 原样回传；解析失败报“游标无效”，不静默回到第一页。
- `folders_list` 增加 `cursor`、`nextCursor`：`total` 已有；`limit` 仍 1–500、默认 200。
- 两个工具都在返回里带 `pagingNote`，一句话说明“两次翻页之间有写入时可能重复或漏掉”。

### 2.3 标签缺失与排除

- 三个字段共同作用在 `images` 上：

  | 字段 | 语义 | SQL |
  | --- | --- | --- |
  | `tagIds` + `tagMode` | 含任一 / 含全部 | 现有 `EXISTS` / 逐标签 `EXISTS` |
  | `tagPresence=has` | 至少一个标签 | `EXISTS (SELECT 1 FROM image_tags WHERE image_id = images.id)` |
  | `tagPresence=missing` | 一个标签都没有 | `NOT EXISTS (...)` |
  | `excludeTagIds` | 不含其中任一标签 | `NOT EXISTS (... tag_id IN (...))` |

- `tagPresence` 与 `excludeTagIds` 都是独立的 AND 条件，与 `tagIds` 叠加。`tagPresence=missing` 与 `tagIds` 同时给出报错。
- 界面：筛选面板标签标题行加“无标签”开关；打开它时清空已选标签，选标签时自动关掉它。`activeFilterCount` 把它算作一项筛选。

### 2.4 分面说明

```json
"facetsNote": "标签分面不应用 tagIds、tagPresence 与 excludeTagIds，选中标签后仍能看到其它标签的计数；文件夹、扩展名、评分分面各自排除自身维度。标签名请用 tags_list 取。"
```

- 不新增收窄参数，不改默认行为。

### 2.5 标签管理

- 新工具 `tags_modify`：

  | action | 输入 | 询问档 | 返回 |
  | --- | --- | --- | --- |
  | `rename` | `tagId`、`name` | 直接执行 | `tag`、`operationId` |
  | `delete` | `tagId`、`expectedImages?`、`dryRun?` | 需确认 | `affected`、`operationId` |
  | `merge` | `tagId`（源）、`targetId`（目标）、`expectedImages?`、`dryRun?` | 需确认 | `moved`、`duplicate`、`affected`、`operationId` |

- 三种动作都写一条操作记录（`tagRename` / `tagDelete` / `tagMerge`），都可撤销；记录标题前加 `AI · `。
- `rename` 撞同名标签直接报错（与界面一致），不做静默合并。
- `merge` 的 `dryRun` 返回源/目标名称、源图片数、其中目标已含的关系数（`duplicate`）、真正要变动的关系数（`willChange`）。
- 临时图片不特判。
- 前端 `TagManagerDialog` 每行加“合并到…”：点开后选择目标标签（列表内筛选，排除自己），确认框写明“把 N 张图片上的「源」换成「目标」，然后删除「源」”，执行后刷新列表并触发 `tagCatalog` 变化。
- `library-changed` 载荷：`{ kind: "tagCatalog", tagAction: "merge", tagId: <源>, targetTagId: <目标> }`；前端在 `tagCatalogPlan` 里把 `merge` 与 `delete` 一样处理（筛选里含源标签时清空选择）。

## 三、数据与接口

### 3.1 分页游标

```rust
/// 不透明游标：十进制偏移量。AI 原样回传，不要在客户端解析。
fn parse_cursor(cursor: Option<&str>) -> AppResult<u32> {
    match cursor.map(str::trim).filter(|text| !text.is_empty()) {
        None => Ok(0),
        Some(text) => text
            .parse::<u32>()
            .map_err(|_| AppError::message(format!("游标无效：{text}"))),
    }
}
```

- `query::list_tags_page(database, search: Option<&str>, limit: u32, offset: u32)`：`search` 为空走按图片数排序，否则走 `LIKE`；两条路径共用 `LIMIT ?/OFFSET ?`。
- `query::count_tags(database, search: Option<&str>)`：`SELECT count(*) FROM tags WHERE EXISTS (...)`；真实库 0 ms（`EXISTS` 短路）。
- `list_tags` / `search_tags` 保留为 `offset = 0` 的薄包装，界面调用点不动。
- `folders_list` 在内存里切片：`children.sort_by(...)` 之后 `.skip(offset).take(limit)`；`total` 仍取排序前的长度。

### 3.2 `library_info` 的 `mcp` 块

- `read::library_info` 需要读 `McpMode`；它已经拿到 `context.settings`，不新增参数。

### 3.4 合并的领域实现

```rust
pub struct MergeReport {
    pub source_images: u64,
    pub moved: u64,
    pub duplicate: u64,
}

pub fn merge_tags_with_id(
    database: &LibraryDb,
    source_id: i64,
    target_id: i64,
) -> AppResult<(MergeReport, Option<i64>)>;
```

事务内步骤：

1. 校验 `source_id != target_id`、两个标签都存在，读出名称。
2. 读源标签的全部 `image_id`（升序）。
3. 逐条检查目标关系：已存在计入 `duplicate`，否则插入并计入 `moved`。
4. `DELETE FROM tags WHERE id = source_id`（关系级联消失）。
5. `draft.json(TagRecord::Merge { source_id, source_name, target_id, images, added })`，`draft.affected(source_images)`。

`TagRecord::Merge` 的撤销/重做：

- 撤销：删除 `added` 里的目标关系 → 保证或重建源标签 → 插回源标签的全部关系。
  - 若同名标签已存在，关系插回那个 id，不重建（记 `redo_removals` 而不是 `redo_deletions`）。
- 重做：插回 `added` 的目标关系 → 删掉重建出来的源关系 → 删除源标签行。
- 复用既有的 `RedoRecord::{TagAdds, TagRemovals, TagDeletions}`，不新增 redo 记录类型。

### 4.2 列表查询耗时

| 查询 | 耗时 |
| --- | --- |
| `list_tags` 现状（含临时区排除，`LIMIT 100`） | 3.58 s（3.58 / 3.88 / 4.16 / 4.17 / 4.63） |
| `list_tags` 现状（`LIMIT 500`） | 4.40 s |
| 同上，去掉临时区排除 | 2.16 s |
| 同上，把临时文件夹 id 改成参数绑定 | 5.57 s |
| 改成 tags 驱动的相关子查询 | 1.56 s |
| 改成 `JOIN` 聚合子查询 | 4.48 s |
| tags 驱动 + `n > 0` 包裹 + `LIMIT/OFFSET` | 2.37 s（首屏）/ 4.00 s（offset 100）/ 3.96 s（offset 200） |
| `count_tags`（`EXISTS` 短路） | 0 ms |
| `search_tags`（`LIKE`，命中 3 个） | 10.6 ms |
| `list_folders` 的直接计数（`GROUP BY folder_id`） | 1.85 s |
| 集合列表 + 计数 | 6.8 ms |

结论：

- 现有 `list_tags` 的 3.6 s 主要来自查询计划从 `images` 侧驱动（`SEARCH images USING INDEX idx_images_active_pixels` + 每次回表取 `image_tags`），而临时区排除的标量子查询再叠一层。候选改写（tags 驱动）在小样本上看到 1.5 s，但在包裹分页后回到 2.4–4.0 s，且波动与磁盘相关，**不足以作为本批次结论**。因此本批次不改标签计数 SQL，只加分页与 `total`；把“标签/分面计数”整体留给批次 6 用基准定案。
- offset 分页不会让单页更便宜（聚合必须全量完成），但它让**总可遍历范围**从 100 条扩大到全部；AI 拿 `total` 就知道要不要继续翻。
- `folders_list` 每次 1.8 s 的成本来自 `GROUP BY images.folder_id` 全表聚合，同样属于批次 6。

### 4.3 筛选与分面耗时（为 M3/M4 校准）

| 查询 | 耗时 |
| --- | --- |
| `tagIds` 任一，1 个标签 | 2.74 s |
| `tagIds` 任一，5 个标签 | 3.40 s |
| `tagIds` 全部，5 个标签 | 3.00 s |
| `tagPresence=missing`（无任何标签） | 2.92 s |
| `excludeTagIds`，1 个标签 | 2.71 s |
| 标签分面，无其它筛选 | 2.79 s |

结论：新增的 `tagPresence` / `excludeTagIds` 与既有 `tagIds` 处在同一量级，不会引入新的量级问题；分面在无筛选时最贵，这与“按需开启 `includeFacets`”的既有设计一致。

### 4.4 数据一致性抽查

- `tags.name` 一条 `UNIQUE COLLATE NOCASE`，`count(DISTINCT name COLLATE NOCASE)` 与 `count(*)` 都是 556，排序键 `(count DESC, name)` 是严格全序 → offset 分页不会出现同值抖动。
- `folders` 有 `path` 唯一索引与 `lower(path)` 唯一索引，`(sort_index, lower(path))` 也是严格全序。
- 0 张标签 381 个：`list_tags` 用 `JOIN` 天然排除；`tags_list` 原本那句 `retain(image_count > 0)` 在分页后会让“本页条数”与 `total` 不一致，实现时已去掉（见 10.1）。

风险与已知边角：

- offset 分页在两次翻页之间有写入时会重漏；已用 `total` 与 `pagingNote` 说明，不做快照。AI 要精确遍历时应先确认库内没有写入。
- `tags_list` 单页仍要 3.6–4.4 s（真实库，现写法未改），翻两页就是两倍；这是批次 6 的性能项，本批次只保证“可遍历”。
- 合并是破坏性写入：源标签行会被删。撤销依赖操作记录，若记录被清空（超过 `maxSteps` 或手动清空）就无法恢复。确认卡与工具描述都写明“源标签会被删除”。
- 合并把临时图片的关系也一起迁移；临时区关闭时这些关系随图片行级联消失，不影响图库。
- `tagPresence=missing` 与 `excludeTagIds` 会与现有标签分面产生“分面不应用该维度”的错觉；已通过 `facetsNote` 说明。搜索与集合视图的分面按命中集统计，那里打开“无标签”后标签分面全是 0，普通视图照常给出计数——界面在两种情况下都列出全部标签。
- 新增 `HistoryKind::TagMerge` 会让旧版本的 `history_list` 客户端看到不认识的 kind；这是 MCP 输出字段的自由扩展，按既有约定不保证向后兼容。

### 10.1 与准备稿的差异
