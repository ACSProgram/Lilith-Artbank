## 一、为什么重写 S8

原 S8 写于 S7 之后，当时的判断是「长期使用的清理、重建、导入导出与快捷键」。之后插入了 20 个批次（单库重构、体验整改 P0–P4、撤销与重做、图片空间优化、MCP、两轮使用反馈、日志与命令记录），S8 的前提变了。在真实库上实测到的事实：

| 项目 | 实测 | 结论 |
| --- | --- | --- |
| 原图完整性 | 396,181 行逐张 `stat`，缺失 0，耗时 19.9 s | 全库快速检查 20 秒就能跑完，做成可取消的任务正好 |
| 孤儿文件 | 磁盘图片文件 396,181 = DB 行 396,181（1 行在回收站、文件仍在原位） | 今天孤儿 0 |
| 缩略图段 | 9 段 9.24 GB，每段 `SUM(thumb_length)` 与 `size − 16` 逐字节相等，`thumb_segment=0` 的图 0 张 | 未引用字节 0，压了也是 0 收益 |
| 特征包 | embedding 1.217 GB = 396,181 × 1536 × 2 + 32；pose 43.1 MB = 81,649 × 132 × 4 + 32 | 每个特征恰好一条，垃圾 0 |
| 僵尸标签 | 556 个标签里 382 个图片数为 0 | 真实脏数据，68.7% |
| 空描述 | 396,180 张可见图里 6,833 张 | 只占 1.7%，且描述生成未实现 |

所以：孤儿与库检查今天跑出来是全绿，它们是保险不是收益；缩略图包今天也是 0 空洞，但那是「还没重建过」，一次全库重建就跳 9 GB，属于不做就会变坏的一条。真正便宜且有立刻可见收益的是界面缺口。

阶段顺序仍按依赖排（检查内核 → 包 → 孤儿与导出 → 界面 → 维护页），因为后面三个阶段的 UI 都要读前三个阶段产出的数据。但阶段 4 的四条是互相独立的界面小改动，任何一条都可以随时插到前面先做、先提交、先验。

## 三、阶段 1：检查内核

### 3.1 一次遍历，四份结果

新增 `src-tauri/src/library/inspect.rs`。核心是一次目录遍历同时产出四类结论，不重复走盘：

1. **快速检查**：DB 行 → 原图是否存在、大小是否一致。
2. **完整校验**：在快速检查基础上重算 BLAKE3 并与 `content_hash` 比较。
3. **孤儿扫描**：磁盘上有、DB 里没有对应行。
4. **缺失原图**：DB 有行、磁盘上没有。

遍历方式：从 `folders` 表取 758 个普通文件夹（不含 `kind='temp'`、不含 `.artbank/`、`recycle/`、`output/`），拼成绝对路径，逐个 `read_dir`。**不做整库递归 `walkdir`**，避免把 `.artbank` 里的 10 GB pack 也数进来。

每个目录内的文件名按 `<64 位小写十六进制>.<ext>` 解析；解析不出来的文件（`desktop.ini`、用户手工放进来的东西）单独计为「非内容寻址文件」，不算孤儿——它们不是本应用写的，移动它们风险高于收益。

### 3.2 判据

DB 侧按文件夹分批取（`WHERE folder_id = ?`），与该目录的文件集在内存里比对，所以内存是 O(最大单文件夹)，不是 O(全库)。

| 情况 | 判定 |
| --- | --- |
| 文件名哈希在该文件夹的行里存在，`file_size` 一致 | 正常 |
| 文件名哈希在该文件夹的行里存在，`file_size` 不一致 | **大小不符**（可能是外部改过，也可能是压缩/编辑中途崩溃） |
| 文件名哈希在 DB 里存在，但在**别的**文件夹 | **孤儿**（同一 `content_hash` 只能有一行，多出来的是散落副本） |
| 文件名哈希在 DB 里完全不存在 | **孤儿** |
| DB 行在该文件夹里，磁盘上没有对应文件 | **缺失原图** |
| 文件名不符合 `<hash>.<ext>` | 非内容寻址文件，只计数 |

`content_hash` 有 `UNIQUE` 约束（实测 396,181 行 = 396,181 个不同哈希），所以哈希是全局主键，可以放心用它判断「这个文件属于谁」。

### 3.3 完整校验的范围与漂移

完整校验按范围（当前选择 / 文件夹 / 集合 / 视图 / 全库）。全库入口保留，但确认框写明：

> 全库约 758 GB，本机 SSD 上预计 25 分钟起，机械盘可能超过 1 小时。期间可以取消。

**不持有路径锁**。理由：25 分钟的根路径读锁会挡住导入、编辑、移动，代价高于收益。改为「容忍漂移」：扫描开始记录时间水位，扫描过程中 `modified_at` 变化过的行跳过并计入「扫描期间变动」，报告里单独列这个数。这与既有口径「不承诺任意时刻的全库快照一致」一致。

快速检查同理，也不持锁。

### 3.4 进度与取消

统一用 `WorkMeter`，单位是**张数**（与压缩、embedding 同口径，不再有第二种计量单位）：

- 准备段（列文件夹、读行）：只给文案「正在准备…」，无百分比。
- 扫描段：`set_total_units(总张数)`，每张 `advance_units(1)`。
- 完整校验在快速检查之后串行执行，同一批单位继续推进，不重置分母。
- 取消：每 256 张检查一次取消标记；已扫描部分的结果保留在报告里，任务相位走「取消中」再落「已取消」。

### 3.5 报告

```rust
struct InspectionReport {
    scanned_rows: u64,
    scanned_files: u64,
    missing: Vec<MissingRow>,        // 最多留 5000 条，其余只计数
    orphans: Vec<OrphanFile>,        // 最多留 5000 条
    size_mismatch: Vec<SizeMismatch>,
    non_content_files: u64,
    changed_during_scan: u64,
    hash_checked: u64,
    hash_mismatch: Vec<HashMismatch>, // 完整校验才有
    elapsed_ms: u64,

}
```

上限 5000 条是为了让 IPC 不炸：39 万行全缺的极端情况下，前端也显示不完。超限时 `truncated = true`，界面显示「只列出前 5000 条，完整清单请导出 CSV」。

报告缓存在 `AppState`，按任务 id 索引，最近 5 条（与压缩估算的 10 条缓存同一个模式）。被挤掉时提示「报告已被新的检查覆盖，请重新扫描」。

## 四、阶段 2：缩略图包垃圾率与空闲回收

### 4.1 垃圾从哪来、涨多快

`ThumbPack::append` 只往段末尾写，`state.offset` 只增不减，段满才开新段，**从不回头找空洞**。所以：

- 编辑一张图 → 旧小图成空洞（约 23 KB）。
- 跑一次全库「重建缩略图」→ 新的 9 GB 写一遍，旧的 9 GB 全成空洞，包从 9.24 GB 变 18 GB。
- 跑五次 → 45 GB 白占。

不是慢慢涨，是跳着涨。实测当前 0 空洞，因为迁移之后没重建过。所以这一条不是「优化」，是「别让一次重建永久吃掉 9 GB」。

### 4.2 垃圾率统计（只读）

新增 `get_pack_stats`，一条 SQL 出全部：

```sql
SELECT s.id, s.file_name, s.size,
       COALESCE(SUM(i.thumb_length), 0) AS used,
       COUNT(i.id) AS blobs
FROM thumb_segments s
LEFT JOIN images i ON i.thumb_segment = s.id
GROUP BY s.id ORDER BY s.id
```

`garbage = size − 16 − used`（16 是段头）。`garbage_ratio = garbage / size`。

特征包同样一条：`feature_blobs` 按 `kind + model + dim + dtype` 聚合 `SUM(length)` 与对应 pack 文件大小。**只显示，不回收**。

实测当前：9 段全部 `garbage = 0`，embedding 与 pose 各 0。界面要能表达「没有可回收空间」，不要显示一个 0 字节的回收按钮让人点。

### 4.3 空闲判定：谁告诉程序「人走开了」

新增 `src-tauri/src/app/activity.rs`：一个 `AtomicI64` 存最后一次用户活动时间，两个方法 `touch()` 与 `idle_for()`。

`touch()` 的落点有三处：

- `trace::read` / `trace::write` / `trace::write_async` 三个包装各加一行，覆盖全部 81 个命令。翻页、改评分、批量操作都会刷新时间戳。
- `thumb://` 与 `img://` 协议处理入口各加一行。用户纯滚动浏览时不发命令，只发缩略图请求；不接这一处，光看不点会被误判成「人走开了」。一次原子写，成本可忽略。
- MCP 请求入口加一行。MCP 调用也是人在操作。

**不监听鼠标键盘，不查窗口是否最小化，不加窗口事件。** 只靠「多久没有命令调用」这一个信号。

动手条件，三条同时满足：

1. `idle_for() >= 3 分钟`；
2. 任务总线没有运行中或排队中的任务；
3. 垃圾率 > 20%。

顺序是有意的：第 1、2 条都是内存判断，零成本；只有它们都满足才去查第 3 条的 SQL。所以平时一次数据库查询都不跑，不会为了「有没有垃圾」每 30 秒扫一遍 39 万行。

### 4.4 空闲循环

新增 `src-tauri/src/app/idle.rs`：`std::thread::Builder` 起一个线程，每 30 秒醒一次（与现有任务线程同一套写法，不引入 tokio）。

- 打开图库时启动，关闭图库时收到停止信号退出。
- 条件满足就提交一个 `TaskKind::PackCompact` 任务，然后回到等待——任务在跑期间第 2 条不满足，自然不会重复提交。
- **不做**「一次空闲窗口只跑一批」的代次计数。任务本身压到干净或被打断就结束，天然自限，不需要再套一层窗口状态。

### 4.5 让位与取消

同一个路径处理两件事：用户回来、用户点取消。

- 每复制 2000 个 blob 检查一次 `idle_for()`。小于 3 分钟说明人回来了 → 放弃当前段。
- 放弃 = 删掉本次新写的段文件，数据库一个字没改，旧段原样保留。
- 因为写的是新文件，中途放弃零副作用，所以让位能在 1–2 秒内响应，不需要等一整段做完。
- 新增 `TaskPhase::Yielded`（终态，前端文案「已让位」）。不复用 `Cancelled`：用户没点取消，胶囊上写「已取消」会误导。
- 摘要写「已让位 · 已回收 N 个段 · 释放 X，剩余部分下次空闲继续」。
- 已提交的段保留，不回退。用户手动点取消仍落 `Cancelled`，两条路径共用一个收尾函数。

### 4.6 一次压多少：不设固定段数

触发阈值 20%，停止阈值 10%。

只要还有段的垃圾率超过 20%，就继续压下一段，直到没有这样的段、或者被打断。所以：

- 离开 10 分钟 → 压 10 分钟的量，剩下的下次继续。
- 离开一小时 → 一次压干净。

「压多少」由用户离开多久决定，不需要额外的加速规则。

关于「跟不上」：压缩本身不产生垃圾，垃圾只来自重建缩略图与编辑。唯一会突增的是全库重建，那种情况一个空闲窗口就会一路压到底。真正会积累的只有「连续做重建且不给空闲时间」，此时维护页的垃圾率数字会上升，旁边有「立即回收」按钮——它提交同一个任务，只是不等空闲条件。

阈值取舍：20% 意味着最坏情况常驻浪费约 1.8 GB（9 GB 的 20%）。再往下压（比如 5%）回收更干净，但每次都要重写接近整个包，写放大会明显变大。10% 的停止阈值是为了避免刚压完、一点小改动又立刻触发。

### 4.7 压缩算法与发布顺序

新增 `src-tauri/src/library/pack_gc.rs`。单段流程：

1. 新建下一个段号的文件（按 1 GiB 上限滚动，与 `append` 同一规则）。
2. 按 `images.id` 升序读该段所有仍被引用的 blob，逐条复制到新段，记录 `(image_id, new_offset, length)`。
3. 每 5000 张一个事务，批量更新 `images.thumb_segment/thumb_offset/thumb_length`，同时更新 `thumb_segments` 的 `size`。
4. 全部提交完成后，延迟 2 秒删旧段文件（见 4.9）。
5. 失败（写失败、事务失败）：删新段文件，数据库不变，旧段保留。

**发布顺序与图片压缩同源**：数据写 → `sync_all` → 事务提交 → 删旧文件。不引入新的断电语义。

### 4.8 失败与残留清理

不需要「失败回退」——发布顺序决定了失败时数据库根本没动过。需要处理的是**留在磁盘上的文件**，三种来源：

- 让位：主动删。
- 提交失败：主动删。
- 进程崩溃：删不掉，只能下次收拾。

一条规则全收：**打开图库时扫一遍 `thumbs/`，凡是不在 `thumb_segments` 表里的 `.pack` 文件直接删。** 9 个段的目录扫描是毫秒级。同一条规则也覆盖 `temp/` 下的压缩中间文件（已有清理，复用）。

### 4.9 与 `ThumbPack` 内存状态的关系

`ThumbPack` 在内存里持有当前段号与写入偏移。压缩后必须让写指针落到新段末尾：

- 压缩任务完成后调用 `ThumbPack::reload_from_disk()`（新增，重新读最新段头）刷新 `state`。
- 互斥：压缩走 `TaskKind::PackCompact` 的 **Write lane**，并申请内容写者 + 根路径**原地替换**（`Access::Replace`），与导入、编辑、重建缩略图互斥——这些正是唯一会 `append` 的路径。所以压缩期间不会有新的 append 进来。
- 查看器与 MCP 拼图读缩略图不受影响（`Access::Replace` 不与读互斥）。

### 4.10 旧段删除的读窗口

存在一个窄竞态：读者在提交前取到旧指针，提交后旧段被删，读请求 404。窗口是「取指针 → 打开文件」之间的几毫秒。

处理：提交后**延迟 2 秒**再删旧段，期间新读请求已全部指向新指针；仍失败的请求由现有的缩略图 404 重试兜底（`thumb://` 已有重试路径）。删除失败不报错，只记日志，留待下次回收。

## 五、阶段 3：孤儿处理与导出

新增 `src-tauri/src/library/maintenance_actions.rs`。

### 5.1 孤儿移入回收站

入口：检查报告里的「移入回收站」按钮。**必须基于一份当次扫描的报告**，不接受任意路径列表——否则就成了「按用户给的路径随便搬文件」的口子。

流程：

1. 目标 `recycle/orphans/<原文件名>`；重名追加 `-1`、`-2`。
2. 逐个 `rename`（跨卷时退化为复制 + 删源），失败的记入失败清单，不中断。
3. 整次操作写**一条**记录，不按 200 个切分——批量操作单条记录是既有约定，撤销也应当一次撤销整次清理。

操作记录新增 kind `orphanMove`，data 是 `moves: Vec<(src_abs, dst_abs)>`。**可撤销**：撤销时按记录把文件从 `recycle/orphans/` 移回原路径；原路径已被占用时跳过该条并计入「无法恢复」。

中途取消时，记录只包含**实际已搬走**的文件，未处理的留在报告里等下次。这样撤销永远不会指向一个没搬的文件。

界面文案必须说清楚：这些文件在数据库里没有对应记录，移走后图库看不到任何变化；撤销可以移回，但清空回收站之后就没有了。

### 5.2 导出到目录

`start_batch_task(kind = "export", scope, targetDir, includeManifest)`。

- 复制原图，保留原文件名（`<content_hash>.<ext>`，因为库里就是这个名字）。
- 流式复制，8 MB 缓冲，不整文件读进内存。
- 目标已存在同名文件：**跳过并计数**，不覆盖、不改名。
- `includeManifest = true` 时写 `manifest.csv`：`content_hash,file_ext,width,height,folder_path,score,description`。不写 JSON——CSV 能被 Excel 和脚本同时吃。
- 占根路径**读锁**（`Access::Read`）：导出期间导入、编辑、移动、删除被拒绝，导出结束后恢复。确认框要写明这一条，因为全库导出会挡很久。
- 进度：张数 + 已复制字节；`ETA` 用 `WorkMeter`。

### 8.2 扩展的命令（3 个）

- `start_batch_task`：`kind` 增加 `checkFast` / `checkFull` / `packCompact` / `export`。
- `preview_batch_task`：同样增加 `checkFast` / `checkFull` / `export`，让范围行显示「范围 N 张」。

### 8.3 新增任务类型（4 个）

| `TaskKind` | lane | 资源 | 可取消 |
| --- | --- | --- | --- |
| `CheckLibrary` | Scan | 无路径锁（容忍漂移） | 是，每 256 张 |
| `Export` | Scan | 根路径读锁 | 是，每张 |
| `OrphanMove` | Write | 根路径原地替换 | 是，每 200 个 |
| `PackCompact` | Write | 内容写者 + 根路径原地替换 | 是，每 2000 个 blob |

`TaskPhase` 增加一个终态 `Yielded`（前端文案「已让位」）。只有 `PackCompact` 会落到它，其余任务的相位集合不变。`tasks_get` 的 `phase` 因此多一个取值，是加法变更。

### 8.4 新增操作记录类型（1 个）

`orphanMove`，可撤销，data 为 `moves`。`releases_files()` 返回 `false`。

### 8.5 设置

两个字段，都在 `#[serde(default)]` 覆盖范围内，**不升 `SETTINGS_VERSION`、不写迁移**，旧文件缺键走默认值：

- `UiSettings.list_columns: Vec<String>`，默认全显示。
- `MaintenanceSettings { auto_compact_thumbs: bool }`，默认 `true`。关掉之后空闲循环不再动手，「立即回收」按钮仍然可用。

### 8.6 新增模块（2 个）

| 模块 | 职责 | 行数 |
| --- | --- | --- |
| `app/activity.rs` | 全局最后活动时间（`AtomicI64`）、`touch()` / `idle_for()` / `reset()`；换库与关库时重置 | ~40 |
| `app/idle.rs` | 空闲循环线程：30 秒轮询、三条条件判定、提交 `PackCompact`、随图库关闭退出 | ~150 |

两个模块都只做调度，不碰像素与数据库。压缩本体在 `library/pack_gc.rs`，这样「什么时候压」与「怎么压」分开，可以各自测试。

### 8.7 不新增的部分

- 不加窗口事件监听、不加最小化判定、不加 tokio 定时器。空闲判定只依赖命令入口的时间戳。
- 不加「一次空闲窗口只跑一批」的代次计数。任务自限，不需要外层窗口状态。
- 不加手动/自动两套压缩实现。两条入口提交同一个 `TaskKind::PackCompact`，区别只在提交前是否等空闲条件。

## 十、风险与边界

- **完整校验的真实耗时没有测过。** 758 GB 按 500 MB/s 是 25 分钟，但 G: 盘的实际顺序读带宽未知，机械盘可能是 1 小时以上。全库入口的确认框必须给区间而不是一个数，且第一次跑完要把实测值写进 `docs/guides/performance.md`。
- **空闲回收会和用户抢磁盘。** 3 分钟阈值意味着用户「开着窗口发呆」也会触发。让位能在 1–2 秒内停手，但已经复制的那部分作废（最多白费一个段的 IO，约 1 GiB）。实际用起来觉得烦就把阈值调到 5 分钟，或在设置里关掉自动回收。
- **「立即回收」不检查空闲条件**，用户点它就是要跑；但它仍受任务互斥，有导入在跑时会排队，界面上要显示「排队中」而不是看起来没反应。
- **压缩的读窗口**：延迟 2 秒删旧段是缓解不是消除。极端情况（读者卡住超过 2 秒）仍可能 404，由缩略图重试兜底。
- **孤儿判定依赖文件名规范**。用户在资源管理器里改过名的图片文件会被判成「非内容寻址文件」而不是孤儿，因为改过名就无法确认它对应哪一行。这是有意的：不猜。
- **移入回收站不可逆的部分**：清空回收站之后文件真的没了，而数据库里本来就没有它们的记录，所以「图库统计」看不出任何变化。界面必须写清楚。
- **导出挡写**。全库导出期间不能导入/编辑/移动/删除，可能持续很久。确认框写明，且进度条要有「取消」。
- **382 个僵尸标签一次删除**：一条记录带 382 个标签名，撤销要重建全部关系。真实库上验证撤销耗时。
- **`?` 键与输入框**：必须在输入框、文本域、contenteditable 内不触发，否则中文输入会误触。
- **本批次不解决验收欠账**。`todo.md` 现在挂着 76 条待真实窗口验收；S8 会再往上加约 10 条。这是这一批最大的隐性成本——代码交付了但没验，等于账没结。

### 11.1 检查

4. 从资源管理器往测试库某个文件夹里手工复制一个图片文件，改名为 64 个 `0` + `.jpg`，再跑一次快速检查：孤儿 1，路径正确。
