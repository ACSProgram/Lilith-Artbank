# 整改批次 G：内存预算

- 日期：2026-10-29
- 来源：[全量代码审查报告（2026-10-29）](../Lilith-Artbank-全量代码审查报告-2026-10-29.md) 的 P1 第 10 项与第 8 节批次 G
- 范围：查看器预览、空间优化、压缩估算、AI 输入解码与 MCP 拼图接入统一字节预算。不做清理与文档（批次 H），不改资源表、查询与前端

## 做法

1. **一份额度全进程共用**：原来 `AppState` 里的导入字节预算改名为 `image_memory`，同一个 `Arc<ImageMemoryBudget>` 交给导入、`AiRuntime`、MCP `ReadContext`、查看器、压缩与估算；上限仍是 1.5 GiB，不随设置变化。
2. **估算口径沿用导入**：非压缩解码按“像素 × 5 字节 + 8 MiB”，压缩与估算样本按“像素 × 16 字节 + 源文件大小 + 8 MiB”；MCP 拼图按“画布 32 MiB + 最大一格解码”一次性申请（逐格解码的峰值就是画布加一张），不逐格排队。
3. **申请顺序统一**：先拿线程许可（`ImageBudget`），再拿字节额度；查看器、AI 与样本估算都在原图字节读完后才申请，拼图整盘只占一个线程许可、逐格使用非阻塞读锁。单张估算超过上限时走独占，等当前占用归零后放行，避免大图永远排不到。同一段工作里最多持有一份额度，不嵌套申请。
4. **取消**：任务路径用各自的取消闭包（导入 job、压缩/估算 reporter、AI 任务句柄），等待额度可中断；查看器与 MCP 拼图没有取消入口，等待不可中断，与已有的线程许可一致。

## 各路径

| 文件 | 变化 |
| --- | --- |
| `concurrency/budget.rs` | 文档改为“全进程共用”，`DEFAULT_MEMORY_LIMIT` 与 `estimate_working_bytes` 说明覆盖范围；准入逻辑不变 |
| `app/state.rs` | `import_memory` → `image_memory`，访问器 `memory()`；构造 `AiRuntime`、`ReadContext`、导入源与查看器命令都传同一份 |
| `ai/runtime.rs`、`ai/job.rs`、`ai/input.rs` | `AiRuntime`/`JobContext` 增加 `memory`；`small_bytes`/`description_bytes` 在解码原图前按行宽高申请额度（读缩略图包时不申请） |
| `library/viewer.rs` | `source` 与 `ensure_preview_file` 在生成预览前申请；预估用行宽高 |
| `library/optimize.rs` | 每张编码在线程许可之后申请；预估按压缩口径含源文件字节 |
| `library/optimize_estimate.rs` | 样本编码同样申请；申请发生在读完原图、记录读取耗时之后，不污染 IO 外推 |
| `mcp/context.rs`、`mcp/sheet.rs` | `ReadContext` 增加 `memory`；拼图按画布 32 MiB 加最大一格的原图估算一次申请，整盘只占一个线程许可，逐格解码不各自排队 |

## 未做与遗留

- 编辑保存与缩略图重建仍只受线程许可约束：两者都占内容写者，与导入、压缩互斥，编辑另有 5000 万像素上限；若下一步要完全统一，需要把 `memory` 传进 `edit::save` 与 `thumbs::rebuild`。
- 查看器与 MCP 拼图的额度等待不可取消；若真实窗口里出现“切图等额度”的卡顿，再补超时或降级策略，而不是让交互路径绕过预算。
- 多任务并行时的峰值内存与吞吐仍未在真实库实测，记在[性能基准](../../guides/performance.md)与[待办](../todo.md)。
