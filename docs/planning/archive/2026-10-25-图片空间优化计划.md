## 0. 已确认的决策

| 项 | 决定 |
| --- | --- |
| 默认档位 | **高**（PSNR ≥ 40 / 无损源 36） |
| 撤销 | **不可撤销**。原图替换后直接删除，空间立即释放 |
| 输入格式 | **所有格式一视同仁**：JPEG / PNG / TIFF / BMP / WebP 全部进入候选 |
| 输出格式 | **只有 JPEG 与 WebP**，不提供 PNG 输出 |
| 估算 | **强制前置步骤**。没估算过不能执行 |
| 流程 | 两步：配置 → 估算 → 确认执行 |

预估收益：全库 679.6 GB，**约省 350–400 GB**（输出 JPEG）；若选 WebP 约 420–460 GB。

## 2. 判据与算法

### 2.1 bpp 只能初判

149 张全库分层抽样（JPEG），bpp 与 q90 节省率相关性 **+0.716**。但同一 bpp 桶内跨度极大：

| bpp 桶 | p10 | 中位 | p90 | 跨度 |
| --- | --- | --- | --- | --- |
| 0.15–0.22 | −16% | +9% | +33% | 49 pt |
| 0.22–0.32 | −13% | +40% | +65% | **78 pt** |
| 0.32–0.50 | +12% | +49% | +74% | 62 pt |

结论：bpp 阈值统一取 **0.12**，只负责"值不值得试"。

### 2.2 阶梯算法（所有格式共用）

```text
if bpp < 0.12: 跳过
if optimized_at > 0 且未勾"重新优化": 跳过
if 有 alpha 且输出 JPEG: 跳过（装不下透明通道）

q = tier.start            // 由估算标定的 (格式组, bpp 桶) 查表得出，缺省才用档位基准值
loop:
    (bytes, psnr) = 编码并比对
    if psnr >= tier.floor_for(源格式):
        if bytes < old_bytes * 0.95: 替换
        else: 跳过（省得太少）
        break
    q = 下一个更高的 q     // 75 → 82 → 85 → 90 → 95 → 97
    没有更高的 q: 跳过（压不动）
```

### 2.3 ⚠️ 实测发现的矛盾：PSNR 底线不能对两种源用同一个数

**PNG 转 JPEG 的实测（20 张画作 PNG，全分辨率）：**

| 编码 | 节省 | 平均 PSNR | 最大局部坏点占比 |
| --- | --- | --- | --- |
| JPEG q85 | **89.6%** | **38.2 dB** | 39.9% |
| JPEG q90 | 86.7% | 39.6 dB | 37.0% |
| WebP q90 | 90.1% | 39.9 dB | 31.5% |

按 JPEG 的"高"档底线 40 dB，**绝大多数 PNG 会被直接放弃**——141 GB 白搭。

原因不是编码器不行，而是**起点不同**：

- JPEG → JPEG 是"在已有损失上再加一点"，40 dB 是合理门槛。
- PNG → JPEG 是"从无损变有损"，38 dB 已经是"从零到有损"的第一次，用同一个数字衡量不公平。

而且实测发现 PSNR 与内容细节强相关：

| 内容细节（detail） | 典型 PSNR@q85 | 局部坏点 |
| --- | --- | --- |
| 1.2–3.0（平滑/厚涂） | 40–47 dB | 0.1–3.5% |
| 3.0–6.0 | 37–43 dB | 3–7% |
| 7.0–12.0（细节密集） | **30–33 dB** | **20–40%** |

detail 高的 PNG 转 JPEG 确实会明显掉细节，这类图应该被 PSNR 底线拦住（或者升到 q95 仍不达标就放弃）。detail 低的 PNG 转得很安全。

**解法：底线按"源是否无损"分两套，算法完全一样。**

| 档位 | 有损源（JPEG / WebP） | 无损源（PNG / TIFF / BMP） |
| --- | --- | --- |
| 极高 | PSNR ≥ 45 | PSNR ≥ 42 |
| **高（默认）** | **PSNR ≥ 40** | **PSNR ≥ 36** |
| 中 | PSNR ≥ 36 | PSNR ≥ 32 |

这不算"格式歧视"：**算法、阶梯、保底、bpp 门槛全部一致**，只是承认"已压过的图"和"无损图"的质量起点不同。用同一把尺子量两种起点，本身就是不公平的。

预期效果：约一半的 PNG（细节较少的）能过 36 dB 被压缩，细节密集的会被拦下并计入"跳过：画质不达标"。

### 2.4 三档的实际收益（JPEG 部分，实测标定）

| 档位 | 起始 q | 全库 JPEG 约省 |
| --- | --- | --- |
| 极高 | 95 | 106 GB |
| **高（默认）** | **85** | **319 GB** |
| 中 | 75 | 417 GB |

对照：固定 q85 省 398 GB，但 49/149 张 PSNR 低于 40 dB、8% 低到 26–33 dB。多花 23 GB 换"一张都不压坏"。

### 2.5 保底

`new_bytes < old_bytes × 0.95` 才替换。这保证功能在任何情况下都不会让图库变大。

### 2.6 bpp 与质量的 U 形关系

- bpp 0.15–0.45：越浪费越能用低质量
- bpp > 0.6：反而要用高质量（多是近无损存储，q85 会把 PSNR 打到 26–33 dB）

阶梯算法天然处理。标定时不要以为"高 bpp 图用了 q95"是 bug。

## 3. 格式转换规则

所有输入格式走同一条管线，差异只在"输出格式能不能装下"：

| 输入 | 输出 JPEG | 输出 WebP | 备注 |
| --- | --- | --- | --- |
| JPEG | ✓ | ✓ | 二次压缩，PSNR 底线 40 |
| PNG 无 alpha | ✓ | ✓ | 色带风险，靠 PSNR/局部坏点拦 |
| PNG 有 alpha | **跳过** | ✓ | JPEG 装不下透明通道，不自动合成白底 |
| TIFF 8-bit | ✓ | ✓ | |
| TIFF 16-bit | **跳过**（v1） | 跳过 | 降位深会有色阶损失，需单独处理 |
| BMP | ✓ | ✓ | |
| WebP | ✓ | ✓ | 已是最优格式，收益通常很小 |

### 3.1 关于 alpha

输出 JPEG 时，有 alpha 的图（PNG 35,481 张 / 81.2 GB）全部跳过，计入"跳过：有透明通道"。不自动合成白底——那是改变画面内容，不是压缩。

用户想处理这批图，就把输出格式切到 WebP。

### 3.2 关于色带

PNG 平涂/线稿转 JPEG 会出色带，而 PSNR 对色带不敏感。实测中"局部坏点占比"（单通道差值 > 6 的像素比例）能反映色带，但还不够精确。

v1 靠三道防线：PSNR 底线、保底的 5%、以及**用户手工抽检**。如果实测发现有明显色带漏网，v2 再加"平坦区域专用检测"。

## 4. 不可撤销的写入语义

### 4.1 空间怎么释放

**旧原图在每批事务提交后立即删除**，空间当场释放。

```text
压缩前           100 GB
压缩后            40 GB（旧图已删）      ← 立刻省 60 GB
峰值增量         ≈ 单批新文件（200–400 MB）
```

**不用为撤销留旧图，所以磁盘只减不增。**

### 4.2 操作记录

写一条 `operations` 记录（`kind = 'optimize'`），**不写 `operation_chunks`**。

- 记录面板能看到"优化图片空间 · 处理 268,400 张 · 省 319 GB"。
- 不显示撤销按钮；后端撤销命令遇到该 kind 返回"压缩操作不可撤销，原图已删除"。
- `operations` 表已有 `kind` 列，不需要改表结构。

### 4.3 防重复压缩（必须做）

**实测：同一质量重压几乎是无损的。**

5 张样本连压三次 q85，每次都跟"上一次的结果"比：

| 第 2 次 vs 第 1 次 | 第 3 次 vs 第 2 次 | 第 3 次 vs 原图 | 文件大小 |
| --- | --- | --- | --- |
| 65.8–74.5 dB | 69.5–85.8 dB | 40.6 dB（与第 1 次相同） | 不变 |

原因：量化是幂等的——JPEG 第一次编码后，DCT 系数已经落在 q85 量化表的网格上，再用同一张表量化，值基本不变。

所以**同档位重跑无害，而且因为文件大小不变，会被"必须小 5%"的保底规则自动跳过**。

但**换更低档位重跑会累积损失**（q85 的结果再用 q75 压，等于在已损失的图上再粗量化一次）。这种情况保底规则挡不住，因为确实会变小。

**结论：标记必须有，但它的作用不是防"二次掉质"，而是：**

1. 防止用户换更低档位重跑造成的累积损失
2. 不白跑一遍（33 万张 × 0.6 秒 = 55 核·小时）
3. 让估算数字对应"这次真能干多少"

**schema v6：`images` 表加 `optimized_at INTEGER NOT NULL DEFAULT 0`。**

- 优化成功写入时间戳，**和文件替换在同一个事务里**。
- 用时间戳而不是布尔值：以后能按"什么时候压的"筛选、统计累计省了多少，布尔值做不到。
- SQLite 的 `ADD COLUMN` 只改 schema 不重写表，39 万行也是毫秒级，不阻塞打开图库。
- 默认跳过已优化的图，UI 上是一个默认勾选的选项（见 §8.1）；取消勾选才会重新处理。
- 估算默认排除，数字才对得上"这次真能干多少"。

**判据能不能代替标记？不能。** 因为判据比较的是"新结果 vs 当前文件"，已压过的图再压，这个 PSNR 是 65–74 dB，判据会愉快放行；只有保底规则在同档位时偶然挡住，换档位就挡不住。必须用显式标记。

迁移：`ALTER TABLE images ADD COLUMN optimized_at INTEGER NOT NULL DEFAULT 0`，不回填，按现有链式迁移写 v5 → v6。

### 4.4 中途取消会不会造成二次压缩

不会。标记和文件替换在同一个事务里，三个状态都安全：

| 状态 | 结果 |
| --- | --- |
| 已提交的批次 | `optimized_at` 已写，重跑跳过 |
| 未提交的批次 | 文件还在 temp、DB 没改，重跑重做 |
| 正在处理的那一张 | 要么完成提交，要么回滚（删除已发布的新文件） |

顺序固定为：编码到 temp → 事务开始 → 发布（rename）→ UPDATE 行 → 提交 → 删旧图。任一步失败都回滚到"没动过这张图"。

提交成功但删旧图失败时，图已是压缩后的状态、标记已写，重跑会跳过，旧文件成了孤儿留给维护任务清理。

### 4.5 崩溃后的残留

- 每 1000 张一个事务，提交后立刻删旧图。
- 未提交批次的临时文件由 `TempFile::Drop` 清理。
- 取消后已处理的图保持压缩状态（不可撤销），`optimized_at` 已写，重跑自动跳过。
- 提交后删旧图失败：图已是压缩状态、标记已写，重跑跳过，旧文件留作孤儿由维护任务清理。

`content_hash`、`file_ext`、`file_size`、`format`、（仅长边上限时）`width` / `height`、`optimized_at`。

### 绝对不能动

| 列 / 表 | 原因 |

| `phash` / `colors4` / `colors8` | 压缩不改构图与配色 |

`image` crate 重编码不写 EXIF/ICC。非 sRGB 的 ICC 丢失会变色。

- 转 WebP 时不搬，UI 说明"会丢失拍摄信息"。

## 6. 两步流程：估算 → 执行

### 6.1 为什么强制估算

压缩不可撤销，用户必须在"看到真实数字"之后才能按执行。

后端也要保证：**没有有效的估算凭证，执行命令直接拒绝**，不能只靠前端禁用按钮。

### 6.2 估算凭证（后端强制）

估算完成时服务端在内存登记：

```text
EstimateGrant {
    task_id:             估算任务 id（作为凭证）
    scope_fingerprint:   hash(scope JSON + OptimizeOptions)
    candidate_count:     候选张数
    candidate_bytes:     候选总体积
    created_at:          i64
}
```

执行请求必须带 `estimateId`，后端校验：

1. 凭证存在（缓存最近 5 条）→ 否则"请先估算"。
2. `scope_fingerprint` 与当前参数一致 → 否则"参数已变化，请重新估算"。
3. 重新 resolve 候选集，张数或体积与凭证相差 > 10% → "图库内容已变化，请重新估算"。

前端：任何影响结果的参数改动后立即清空估算结果，"确认执行"重新置灰。关闭对话框不清凭证。

### 6.3 估算任务

`TaskKind::OptimizeEstimate`，**lane = Scan**，不写库、不进操作记录、不改任何文件。

**抽样必须分层 + 体积加权**（否则系统性低估）：

```text
① SQL 按 bpp 分 6 桶，统计每桶张数 / 体积 / 像素
② 样本量按体积份额分配，每桶至少 3 张
③ 桶内随机抽，真实编码
④ 桶内节省率 = Σ新大小 / Σ原大小
⑤ 全量节省 = Σ(桶体积 × 桶节省率)
```

随机抽 100 张会低估：数量最多的是 bpp < 0.15 的图（31%），它们压不动；而体积 48% 在 bpp ≥ 0.5 的图里，随机抽到概率只有 22%。

**样本量**（bootstrap 300 次）：100 张 ±3.5 pt（±22 GB），300 张 ≈±2 pt（±13 GB）。默认 200 张。

> 分桶时要按格式拆：JPEG 和 PNG 的 bpp 分布完全不同，混在一个桶里会让估算失真。实际按 `(格式组, bpp 桶)` 交叉分层——格式组只有"有损源 / 无损源"两类。

### 6.4 估算输出

```text
样本 200 张 · 覆盖 3.1% 的候选体积

  处理      268,400 张
  跳过       78,000 张   已足够紧凑 54,000 · 已处理过 12,000 · 有透明通道 8,000 · 画质不达标 4,000
  节省      372 GB  ± 26 GB          680 GB → 308 GB
耗时      约 8 小时
质量分布   q85 58% · q90 24% · q95 13% · 放弃 5%
```

### 6.5 收益曲线

| 处理进度 | 覆盖字节 | 累计节省 | 折合耗时（JPEG 档） |
| --- | --- | --- | --- |
| 10% | 25% | 67 GB | 40 分钟 |
| **20%** | **41%** | **147 GB** | **1.3 小时** |
| 30% | 52% | 192 GB | 2 小时 |
| 50% | 72% | 257 GB | 3.2 小时 |
| 100% | 100% | 319 GB | 6.3 小时 |

**跑 20% 就能拿到 46% 的收益。**

### 6.6 时间估算

```text
t_cpu = 样本实测耗时 × (候选总像素 / 样本总像素)
t_io  = (候选总体积 + 预估新体积) / 实测读带宽
t     = max(t_cpu, t_io) × 1.15
```

PNG 解码比 JPEG 慢（无损解码），估算采样里要分别统计，不能混算。

### 6.7 分文件夹明细

展开后每行可以单独点"只处理这个文件夹"，直接切范围并保留其余参数（但需要重新估算）。

## 7. 执行任务

```text
start_batch_task(kind = optimize, scope, optimize, estimateId)
  → state.rs::start_optimize_task
      ① 校验 estimateId 与指纹，失败直接拒绝
      ② scope.resolve(&db) 拿 id
      ③ 过滤：bpp < 0.12 / optimized_at > 0 / 有 alpha 且输出 JPEG / 16-bit TIFF
      ④ 按 bpp 降序排序
      ⑤ TaskHandle::new(Optimize) + tasks.launch(write lane)
      ⑥ 建 operation（kind='optimize'，无 chunk）
      ⑦ 线程池：解码 → 阶梯编码 → PSNR 裁决 → 每 1000 张事务 + 删旧图
      ⑧ task-progress 推进度，可取消
```

1. **按 bpp 降序执行**，随时取消都拿到最大收益。
2. **lane = Write**，与导入/编辑/移动互斥。
3. **每 1000 张一个事务**。
4. **连续失败 5 张自动停止**。
5. **内存**：线程数 × 110 MB，8 线程约 880 MB。

### 7.1 时间花在哪

单张 12 MP JPEG 的账：

| 步骤 | 耗时 | 占比 |
| --- | --- | --- |
| 解码原图 | 0.12 s | 20% |
| 编码（平均 1.15 次） | 0.29 s | 48% |
| 回解码编码结果 | 0.12 s | 20% |
| PSNR + 局部坏点比对 | 0.03 s | 5% |
| 写文件 / 事务 | 0.04 s | 7% |
| **合计** | **约 0.6 s** | |

8 线程跑 334,668 张 JPEG ≈ **7 小时**；加 PNG 约 8 小时。

"回解码 + 比对"这 25% 不是浪费——它挡住了 8% 会严重掉质的图（PSNR 26–33 dB 那批）。因为**不可撤销**，这钱必须花。

### 7.2 能省的两处

1. **起始 q 由估算标定**（已写进方案）：估算跑完后，每个 (格式组, bpp 桶) 都有一个实测的"最低达标 q"。执行时直接从这个值开始，平均编码次数从 1.4 降到 1.15，省约 8% 时间。
2. **同档位重跑几乎零成本**：实测二次压缩的 PSNR 是 65–74 dB、文件大小不变，保底规则会直接跳过，不会白编码。

不建议砍掉逐张复核：估算只保证"这一桶中位数达标"，桶内仍有离群值，而压缩不可撤销。

### 13.3 画质

阶梯落点：q85 5407 张、q90 1221 张、q95 338 张、q97 48 张。

| 指标 | p1 | p5 | 中位 | 最差 |
| --- | --- | --- | --- | --- |
| PSNR | 37.14 | 40.08 | 41.52 | 34.77 |
| SSIM | 0.9581 | 0.9722 | 0.9920 | 0.9278 |
| 平坦区 PSNR | 42.12 | 43.16 | 46.87 | 37.14 |

- 有损源（JPEG/WebP）**没有一张低于 40 dB** 底线。
- SSIM < 0.96 共 85 张，< 0.97 共 270 张；平坦区 PSNR < 40 共 11 张（无色带迹象，最低 37.14）。
- 无损源 29 张按 RGB 三通道复算落在 34.77–35.97，低于名义的 36 dB。**这不是画质问题，是量法问题**：全透明像素底下的颜色数据编码器可以随便填，人看不见，却会把"只看颜色"的 PSNR 拉得很低。同库实测（一张 2048×2048 透明 PNG，q85）：全图 RGB **18.09 dB**、仅不透明区 **38.00 dB**、alpha 通道 99 dB —— 20 dB 的差距全来自看不见的像素。程序 `compare()` 按 RGBA 四通道算，alpha 近乎无损会把分数抬回 36 以上，这 29 张因此通过；它们的 SSIM 在 0.982–0.999、平坦区 PSNR 40+，肉眼无差别。**含义**：透明图的 PSNR 只能当参考，验收看 SSIM 与平坦区 PSNR。若要收紧，正确做法是"只在不透明区算分"（合成到背景后比），而不是改通道数。
- 最激进的几张：`1348`（600×584 PNG，省 93.6%，SSIM 0.9943）、`6983`（1019×1014 PNG，省 95.8%，SSIM 0.9278）、`7052`（1000×1500 PNG，省 94.9%，SSIM 0.9328）。

### 13.5 与计划的偏差

1. **收益 41.0%，低于第 10 节按主库估的 45%**，但远高于纯 JPEG 的 21%。差距来自测试库 bpp 分布：4536 张 bpp ≥ 1.5 的近无损图贡献了绝大部分收益，其余 60% 再压省不到 5%。
2. **必须选 WebP 才能拿到这个数字**：336 张带 alpha 的 PNG 在 JPEG 下整类跳过，这 296 MB 是 WebP 独有的收益。
3. **WebP 不保留 EXIF/ICC**：本批次新增的色彩配置判据已挡住会偏色的图（229 张），代价 82 MB。EXIF 丢失不影响查看。
4. **WebP 单边上限 16383**：本批次已加尺寸判据与 `catch_unwind`，全库 1 张（`391×17799`）按设计跳过，未再 panic。
5. **编码速度 12.7 张/秒**（JPEG 61 张/秒），全库约 12 分钟，为主库预估时要按 5 倍时长算。
