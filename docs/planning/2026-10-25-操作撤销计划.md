# 图库操作撤销计划

日期：2026-10-25
状态：计划中，尚未开始实现

目标：为图库增加持久化的操作记录与手动撤销。工具栏打开最近记录，选择一条后回到该操作之前；关闭并重新打开同一图库后仍可撤销；设置可限制保留步数。批量操作算一条记录。

## 已确认的决策

- **线性回退**：选中第 N 条记录 = 依次撤回 N 之后的所有记录，再撤回 N。不做任选单条的独立回滚。
- **覆盖全部图库内容修改**：导入、编辑、图片移动、文件夹、回收站、永久删除、评分、标签、描述、集合都进入记录。派生数据与界面状态不进入。
- **延迟释放**：永久删除与清空回收站不立即删除文件和数据库行，只标记为待释放；记录超出最大步数或用户清空操作记录时才真正删除。
- **取消边界**：撤销本身是 write lane 任务；取消只在记录之间生效，单条记录必须完整撤完。
- **不做重做，不绑定 `Ctrl+Z`**。图片没有原始文件名，因此不存在图片重命名；重命名只涉及文件夹、标签、集合。
- 历史保存在当前图库的 SQLite 中，换库看到的是对应图库自己的历史；最大步数是全局设置。

## 范围

### 纳入记录

| 类别 | 操作 |
| --- | --- |
| 导入 | 新增、重复合并、取消后已提交的批次 |
| 编辑 | 几何编辑保存 |
| 图片 | 移动、移入回收站、恢复、永久删除、清空回收站 |
| 文件夹 | 创建、重命名、移动、删除空文件夹、同级排序 |
| 元数据 | 单张/批量评分、描述（手工与 AI 生成）、标签设置/增删/重命名/删除 |
| 集合 | 创建、重命名、删除、排序、加入/移出、并集/交集/差集、相似分组保存集合 |

### 不纳入记录

- 设置、图库名称、图库路径、图库创建/打开/关闭。
- 缩略图重建、embedding/pose 生成、feature pack 维护、相似分组扫描本身。这些是派生数据或后台计算；编辑撤销不恢复 embedding/pose。
- 浏览历史、排序、筛选、选择、窗口状态等界面状态。
- 复制路径、复制图片等只读动作。
- 缩略图包与特征包内部的追加、压缩细节；它们不是用户可见内容。

## 核心设计

### 线性时间线与记录状态

- 每条记录代表一次用户动作，批量操作只记一条。
- 记录按 `id` 递增排列，最新记录对应当前状态。
- 撤销成功后，被撤销的记录从可撤销列表移除；第一版没有重做。若以后需要审计，再增加只读历史表。
- 记录失败时保留该记录并停止回退；更新的记录如果已经成功撤回，则保持已撤回状态。用户重试成功后才能继续向更早记录回退。

### schema v5

新增表：

```sql
CREATE TABLE operations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    kind TEXT NOT NULL,
    label TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    status TEXT NOT NULL,              -- applied / undoing / undo_failed
    task_id TEXT,
    affected INTEGER NOT NULL DEFAULT 0,
    error TEXT NOT NULL DEFAULT '',
    undone_at INTEGER
) STRICT;

CREATE TABLE operation_chunks (
    operation_id INTEGER NOT NULL REFERENCES operations(id) ON DELETE CASCADE,
    seq INTEGER NOT NULL,
    format TEXT NOT NULL,              -- json / i64
    data BLOB NOT NULL,
    PRIMARY KEY (operation_id, seq)
) STRICT;

CREATE TABLE undo_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    target_operation_id INTEGER NOT NULL,
    state TEXT NOT NULL,               -- running / completed / failed / cancelled
    started_at INTEGER NOT NULL,
    finished_at INTEGER
) STRICT;
```

`images` 增加两列：

```sql
ALTER TABLE images ADD COLUMN purge_operation_id INTEGER;
ALTER TABLE images ADD COLUMN origin_operation_id INTEGER;

CREATE INDEX idx_images_purge
    ON images(purge_operation_id)
    WHERE purge_operation_id IS NOT NULL;
```

- `operations.id` 使用 `AUTOINCREMENT`，避免记录清理后 id 复用，撞上 `.artbank/undo/<id>/` 目录或残留的 `purge_operation_id`。
- `purge_operation_id` 与 `origin_operation_id` 不建外键：记录行会在释放后删除，但标记需要继续用于启动时的清理扫描。
- 大列表用原始 `i64` BLOB 存放在 `operation_chunks`，避免几十万 id 写成几十 MB 的单个 JSON。
- schema v4 → v5 只新增表、列与索引，不改现有数据。

### 设置 v5

```text
settingsVersion 5
history { maxSteps: 100 }
```

- `maxSteps` 范围建议 10–500，默认 100。
- 降低上限时立即裁掉最旧记录，并触发对应的释放清理。
- 每个图库的历史独立；设置本身是全局的。

### 延迟释放：永久删除与清空回收站

永久删除和清空回收站不再立即删除数据库行和原图：

1. `deleted_at` 保持不变，写入 `purge_operation_id = <operationId>`。
2. 回收站视图、回收站计数与“全库搜索包含回收站”的情况统一排除 `purge_operation_id IS NOT NULL`。
3. 撤销时清除 `purge_operation_id`，图片回到回收站。
4. 记录被裁掉或用户清空操作记录时，才按 `purge_operation_id` 分块删数据库行、再删原图文件。复用现有永久删除的分块逻辑。
5. 启动时扫描“操作记录已不存在、但仍有 `purge_operation_id`”的图片，继续完成释放；这同时覆盖释放中途崩溃。
6. 历史面板显示待释放图片数量与字节数；提供“清空操作记录并立即释放文件”，红色确认，且不可撤销。

必须接受的后果：

- 清空回收站后磁盘空间不会立即下降。
- 待释放图片仍占用内容哈希，重新导入同一文件会按重复跳过，直到记录过期或手动释放。
- 待释放图片仍会挡住其所在文件夹的删除，直到释放完成。
- 这些是持久撤销与立即释放无法同时满足的必然代价，必须在确认文案和历史面板里写清楚。

### 编辑保存的旧原图

编辑保存不再立即删除旧原图：

1. 保存时把旧原图移到 `.artbank/undo/<operationId>/<contentHash>.<ext>`。
2. 事务里记录旧的内容列、旧文件位置与修改时间。
3. 撤销时确认当前哈希：
   - 已经是旧哈希：跳过；
   - 是这条记录的新哈希：把旧文件搬回当前文件夹，恢复内容列，重新生成缩略图并递增 `thumb_version`，删除当前新文件与预览缓存；
   - 其他哈希：记录失败，要求人工处理。
4. 编辑撤销只恢复像素内容相关字段；评分、标签、描述、集合保持当前值，embedding/pose 保持清除状态。
5. 记录被裁掉时删除 `.artbank/undo/<operationId>/`；启动时清理没有对应记录的撤销目录。

### 导入

- 一个导入任务一条记录。开始任务时创建记录，之后每个写批次在同一个事务里追加 `operation_chunks`，并给新增图片写入 `origin_operation_id`。
- 取消的导入仍保留已提交批次的记录；取消只停止后续工作，不回滚已入库图片。
- 崩溃后启动时，`running` 的导入记录按已提交批次标为可撤销；没有任何批次时删除空记录。
- 撤销导入：
  - 按 `origin_operation_id` 分块删除新增图片行与原图文件；
  - 恢复重复合并前的评分、标签、修改时间；
  - 尝试删除本次导入新建且已经为空的文件夹和标签；非空则保留。
- 导入的重复检测仍会把待释放的回收站图片视为已存在，这是延迟释放的已知后果。

### 撤销引擎

一次撤销的流程：

1. 检查 write lane；任何写入、导入、AI/扫描任务在进行时直接拒绝并提示。
2. 读取目标记录，计划为“所有 `id >= target` 且状态为 applied 的记录”，从新到旧执行。
3. 创建 `undo_runs`，保存目标记录；崩溃后据此续做。
4. 对每条记录：
   - 标记 `undoing`；
   - 执行该类型的逆操作；
   - 成功后删除记录与其 chunks；
   - 记录之间检查取消标记；单条记录内部不响应取消。
5. 失败时把该记录恢复为 applied 或标为 `undo_failed`，保留错误信息并停止。已经完成的更新记录保持已撤销。
6. 全部成功后删除 `undo_runs` 完成项，清空有序 id 缓存、使 AI 相似度状态失效，并让前端刷新。

逆操作必须可重复执行：

- 移动撤销先看图片当前文件夹：已经在源文件夹就跳过，仍在目标文件夹才移动。
- 编辑撤销先看当前哈希。
- 导入撤销按 `origin_operation_id` 删除剩余行。
- 释放任务按 `purge_operation_id` 删除剩余行与文件。
- 文件夹撤销先看当前路径是旧路径、新路径还是其他状态。

### 任务总线

- 新增 `TaskKind::Undo` 与 `TaskKind::ReleaseGarbage`，都在 write lane。
- 撤销任务立即失败而不是排队，避免用户误以为已经撤销。
- 计划包含多条记录时，任务可取消；取消在记录边界生效。只剩一条记录时任务标记为不可取消。
- 释放任务幂等、可分块，不提供随时取消；崩溃后下次启动继续。
- 进度同时显示“已完成记录 / 总记录”和“当前记录内已完成项 / 总项”。
- 撤销成功后与导入收尾一样递增前端刷新令牌，刷新计数、文件夹、标签与集合；查看器中被删除或内容变化的图片关闭。

## 逆操作矩阵

| 操作 | 记录内容 | 撤销动作 |
| --- | --- | --- |
| 导入 | `origin_operation_id`、合并前的评分/标签/修改时间、新建文件夹/标签 | 删除新增行和文件；恢复合并项；清理已空的本次新建项 |
| 编辑保存 | 旧内容列、旧文件在 `.artbank/undo/<id>/`、旧修改时间 | 搬回旧文件、恢复行、重建缩略图、递增 `thumb_version`、删除新文件 |
| 图片移动 | 每张图的源/目标文件夹与修改时间 | 逐张移回并恢复 `folder_id` / `modified_at` |
| 移入回收站 | 图片 id、原 `modified_at` | 清空 `deleted_at`，恢复 `modified_at` |
| 恢复 | 图片 id、原 `deleted_at` 与 `modified_at` | 恢复原 `deleted_at` 与 `modified_at` |
| 永久删除 / 清空回收站 | `purge_operation_id` | 清除标记，回到回收站 |
| 文件夹创建 | 文件夹 id/路径、`sort_index` | 仅在仍为空时删除数据库行和物理目录 |
| 文件夹重命名/移动 | id、旧路径、新路径、旧/新 `sort_index` | 反向修改目录与整棵子树路径 |
| 删除空文件夹 | 路径、`created_at`、`sort_index` | 重建目录与数据库行 |
| 文件夹同级排序 | 受影响同级的 `id → sort_index` | 恢复旧排序位 |
| 评分 | 每张图旧评分与 `modified_at` | 恢复旧值 |
| 描述 | 旧描述、来源、模型、`modified_at` | 恢复旧值；FTS 由既有触发器同步 |
| 标签设置/增删 | 每张图旧关系集合、操作中新建的标签 | 精确恢复关系；删除已无引用的本次新建标签 |
| 标签重命名 | 旧名称 | 改回旧名称 |
| 标签删除 | 标签名、全部关联图片 id | 重建标签与关系 |
| 集合创建 | 集合 id、名称、排序位 | 删除集合 |
| 集合重命名 | 旧名称 | 改回旧名称 |
| 集合删除 | 集合名、全部条目与位置 | 重建集合与条目 |
| 集合排序 | 受影响集合的旧 `sort_order` | 恢复旧顺序 |
| 集合加入/移出 | 受影响条目的旧位置与集合末尾位置 | 恢复条目与位置并重新编号 |
| 集合运算 | 新建的集合 | 当作集合创建撤销；源集合不变 |
| 相似分组保存集合 | 本次创建的全部集合 | 当作一条集合创建记录撤销 |
| AI 生成描述 | 每张图旧描述、来源、模型、`modified_at` | 作为一个批量任务恢复 |

## 三个批次

三批是合适的。再少会让“基础层、文件逆操作、元数据与收尾”挤在一起，验收边界会变模糊。每批结束都必须通过自动检查并形成可独立验收的状态。

### 批次 1：基础层、回收站与历史面板

目标：先把最危险的删除链路做成完整闭环。

交付：

- schema v5 迁移与设置 v5。
- `library/history.rs`：记录读写、chunks、裁剪、状态机、撤销引擎骨架、`undo_runs`。
- `TaskKind::Undo` / `TaskKind::ReleaseGarbage` 与任务总线接入。
- 回收站：移入、恢复、永久删除、清空回收站全部进入记录。
- 延迟释放：标记、视图/计数排除、记录过期释放、手动释放、启动清理。
- 操作记录面板、最大步数设置、撤销确认、刷新联动。
- 测试：schema 迁移、回收站撤销、释放、重启后仍可撤销、write lane 冲突、记录之间取消。

退出条件：

- 移入回收站 → 清空 → 重启 → 撤销，图片回到回收站；磁盘文件在记录过期前仍存在。
- 清空操作记录后文件被真正释放，且不能再撤销。
- `npm run typecheck`、`npm run build`、`cargo fmt --check`、`cargo check`、`cargo test`、`git diff --check` 通过。

估算：10–12 个工作日。

### 批次 2：导入、编辑、移动与文件夹

目标：覆盖所有会移动文件或改变原图内容的操作。

交付：

- 导入记录：`origin_operation_id`、批次 chunks、合并快照、取消/崩溃后的部分导入、新建文件夹/标签清理。
- 编辑保存：旧原图暂存、内容快照、撤销、缩略图重建、记录过期后的暂存清理。
- 图片移动：源/目标文件夹与修改时间记录、逐张幂等撤销。
- 文件夹：创建、重命名、移动、删除、同级排序的记录与撤销。
- 文件类逆操作的中断续做；启动时清理无主撤销目录。
- 测试：导入撤销（新增/合并/取消）、编辑撤销、移动撤销、文件夹子树撤销、线性链组合、中断后续做。

退出条件：

- 导入、编辑、移动、文件夹操作都能在重启后撤销。
- 撤销中断后再次打开图库可以继续，不留下用户可见的孤儿文件。
- 上述自动检查通过。

估算：12–14 个工作日。

### 批次 3：元数据、标签、集合与收尾

目标：补齐全部内容修改，并完成可靠性、性能与验收收尾。

交付：

- 评分、描述、标签设置/增删/重命名/删除、集合 CRUD/排序/成员/运算、相似分组保存集合、AI 描述任务记录。
- 精确的关系恢复；导入撤销时的空文件夹/空标签清理。
- 待释放数量与字节数展示、撤销失败状态、部分撤销提示、按钮禁用原因。
- 全类型线性链测试、待释放与裁剪测试、390k 规模数据量与耗时基准。
- 模块文档更新、实施记录、当前交接更新；计划完成后归档。

退出条件：

- 全部纳入操作可撤销；跨类型线性回退结果正确。
- 数量/计数/缩略图/搜索在撤销后一致。
- 自动检查通过；真实窗口由用户手工验收。

估算：8–10 个工作日。

总计约 30–36 个工作日（单人，含测试与文档；真实窗口手工验收另计）。

## 验收清单

- 关闭软件再打开，历史仍在，且能撤销导入、编辑、移动、回收站、元数据与集合操作。
- 导入 → 编辑 → 移动 → 移入回收站 → 清空回收站，依次撤销到每一层，文件、行、标签、集合关系都正确。
- 批量操作只出现一条记录；取消的导入能撤销已提交部分。
- 永久删除/清空回收站后文件仍在；记录过期或清空记录后文件真正消失。
- 撤销过程中取消，停在记录边界；再次撤销可继续。
- 撤销失败时记录保留并显示原因，不会把后续状态伪装成成功。
- 20 万级批量记录与待释放标记不显著拖慢现有查询；历史列表打开不触发全库扫描。
- 现有查询、缩略图、搜索、编辑、导入、集合、回收站测试不回归。
- 界面文案只写后果与范围，不解释实现。

## 风险与边界

- 文件与数据库无法总是原子提交；依靠幂等逆操作、启动续做与孤儿清理保证最终一致。
- 编辑旧原图会占用磁盘，最大步数直接决定上限；需要在设置与历史面板里能看见。
- 待释放图片会暂时占内容哈希并挡住文件夹删除，这是延迟释放的已知后果。
- 撤销失败会阻止向更早记录回退；不提供“跳过失败记录”，避免伪造一致状态。
- 批次 3 的表面最多；实施中不再增加第四批，必要时只在第三批内部按子阶段提交。
- 不编译 release、不启动开发服务器、不做浏览器/UI 自动化；真实窗口由用户验收。
