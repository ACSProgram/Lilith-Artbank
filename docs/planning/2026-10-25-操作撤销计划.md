## 1. 已确认的决策

- **线性回退**：选中第 N 条记录 = 依次撤回 N 之后的所有记录，再撤回 N。不做任选单条的独立回滚。
- **覆盖全部图库内容修改**：导入、编辑、图片移动、文件夹、回收站、永久删除、评分、标签、描述、集合都进入记录。派生数据与界面状态不进入。
- **延迟释放**：永久删除与清空回收站不立即删除文件和数据库行，只标记为待释放；记录超出最大步数或用户清空操作记录时才真正删除。
- **取消边界**：撤销本身是 write lane 任务；取消只在记录之间生效，单条记录必须完整撤完。
- **撤销后保留记录并可重做**（批次 2 增补，替代原“不做重做”决策）：撤销成功的记录变灰留在列表，新的图库写入才清空灰色分支。仍不绑定全局 `Ctrl+Z`/`Ctrl+Y`；查看器内部的几何撤销栈不受影响。图片没有原始文件名，因此不存在图片重命名；重命名只涉及文件夹、标签、集合。
- 历史保存在当前图库的 SQLite 中，换库看到的是对应图库自己的历史；最大步数是全局设置。

## 4. 数据模型

### 4.1 schema v5

`SCHEMA_VERSION` 从 4 升到 5。新建库直接包含以下结构；v4 库执行一次迁移。

```sql
CREATE TABLE operations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    kind TEXT NOT NULL,
    label TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    status TEXT NOT NULL,              -- pending / applied / undoing / undone / redoing / undoFailed
    task_id TEXT,
    affected INTEGER NOT NULL DEFAULT 0,
    error TEXT NOT NULL DEFAULT '',
    undone_at INTEGER
) STRICT;

CREATE TABLE operation_chunks (
    operation_id INTEGER NOT NULL REFERENCES operations(id) ON DELETE CASCADE,
    seq INTEGER NOT NULL,
    format TEXT NOT NULL,              -- ids / triples / moves / json / redo
    data BLOB NOT NULL,
    PRIMARY KEY (operation_id, seq)
) STRICT;

CREATE TABLE undo_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    target_operation_id INTEGER NOT NULL,
    state TEXT NOT NULL,               -- running / completed / failed / cancelled
    started_at INTEGER NOT NULL,
    finished_at INTEGER
) STRICT;

ALTER TABLE images ADD COLUMN purge_operation_id INTEGER;
ALTER TABLE images ADD COLUMN origin_operation_id INTEGER;

CREATE INDEX idx_images_purge
    ON images(purge_operation_id)
    WHERE purge_operation_id IS NOT NULL;
```

要点：

- `operations.id` 使用 `AUTOINCREMENT`：记录清理后 id 不复用，避免撞上 `.artbank/undo/<id>/` 或残留的 `purge_operation_id`。
- `purge_operation_id`、`origin_operation_id` 不建外键：记录行删除后标记要继续用于释放扫描。
- `operation_chunks.format` 的编码：
  - `ids`：连续的 little-endian `i64`。
  - `triples`：连续的 `(i64, i64, i64)`，用于 id + 两个旧值。
  - `moves`：连续的 `(id, from_folder_id, to_folder_id, old_modified_at)`。
  - `json`：`serde_json`，用于描述、标签关系、单张快照等可读结构。
  - `redo`：撤销时写入的 `serde_json` 快照（`RedoRecord`），只描述撤销前状态；原始逆数据保持不动。
- 大列表不写 JSON：几十万 id 用 `ids`/`triples` 原始 BLOB，避免日志膨胀。
- v4→v5 只新增表、列与索引，不改现有行；迁移前后 schema 版本同时写 `PRAGMA user_version` 与 `meta.schemaVersion`。

### 5.1 `library/history.rs`

```rust
pub enum HistoryKind {
    Import, Edit, Move, Trash, Restore, PermanentDelete, EmptyTrash,
    FolderCreate, FolderRename, FolderMove, FolderDelete, FolderReorder,
    Score, Description, TagSet, TagAdd, TagRemove, TagRename, TagDelete,
    CollectionCreate, CollectionRename, CollectionDelete, CollectionReorder,
    CollectionAdd, CollectionRemove, CollectionCombine, SimilarityGroups,
    AiDescription,
}

pub enum OperationStatus { Pending, Applied, Undoing, Undone, Redoing, UndoFailed }

pub struct NewOperation<'a> {
    pub kind: HistoryKind,
    pub label: Cow<'a, str>,
    pub task_id: Option<&'a str>,
}

pub struct OperationDraft { /* id, affected, chunks */ }

impl OperationDraft {
    pub fn id(&self) -> i64;
    pub fn affected(&mut self, n: u64);
    pub fn triples(&mut self, rows: &[(i64, i64, i64)]);
    pub fn moves(&mut self, rows: &[(i64, i64, i64, i64)]);
    pub fn json<T: Serialize>(&mut self, value: &T) -> AppResult<()>;
}

/// 同步操作：事务内执行 work；work 里用 draft.id() 写 purge/origin 标记。
/// affected 为 0 时回滚，不留下空记录。
pub fn write<T>(
    database: &LibraryDb,
    op: NewOperation<'_>,
    work: impl FnOnce(&Transaction<'_>, &mut OperationDraft) -> AppResult<T>,
) -> AppResult<T>;

/// 长任务（导入、AI 描述）：先建 pending 记录，再按批次追加。
pub fn begin_live(database: &LibraryDb, op: NewOperation<'_>) -> AppResult<i64>;
pub fn finish_live(database: &LibraryDb, op_id: i64, error: &str) -> AppResult<()>;
/// 写入内容的导入批次在同一个事务里调用，删除 undone / redoing 记录开启新时间线。
pub fn discard_redo_in_tx(tx: &Transaction<'_>) -> AppResult<()>;

/// 已经持有写事务时使用，避免在 flush 里再次加写锁造成死锁。
pub fn append_live_in_tx(
    tx: &Transaction<'_>,
    op_id: i64,
    format: ChunkFormat,
    data: &[u8],
) -> AppResult<()>;
pub fn add_live_affected_in_tx(tx: &Transaction<'_>, op_id: i64, n: u64) -> AppResult<()>;

pub fn list(database: &LibraryDb) -> AppResult<Vec<HistoryEntry>>;
pub fn pending_summary(database: &LibraryDb) -> AppResult<(u64, u64)>;
pub fn trim(database: &LibraryDb, max_steps: u32) -> AppResult<Vec<EvictedOperation>>;
pub fn recover_on_open(database: &LibraryDb) -> AppResult<RecoveryPlan>;

pub fn run_undo(
    database: &LibraryDb,
    root: &Path,
    thumbs: &ThumbPack,   // 编辑撤销要重新编码并追加缩略图
    target_id: i64,
    task: Arc<TaskHandle>,
) -> AppResult<()>;

pub fn run_redo(
    database: &LibraryDb,
    root: &Path,
    thumbs: &ThumbPack,
    target_id: i64,
    task: Arc<TaskHandle>,
) -> AppResult<()>;

pub fn run_release(
    database: &LibraryDb,
    root: &Path,
    task: Arc<TaskHandle>,
) -> AppResult<()>;
```

`write` 的固定顺序：

1. `transaction_with_behavior(Immediate)`。
2. 插入 `operations` 行，`status='pending'`，拿到 `draft.id()`。
3. 执行闭包；闭包内完成实际更新，并用 `draft` 收集逆数据。
4. `affected == 0` 且没有 chunks：回滚，不保留记录。
5. 更新 `status='applied'`、`affected`；插入 chunks；提交。

`begin_live` 用于导入/AI 描述：先建 `pending` 行；每批写入时在同一个写事务里用 `*_in_tx` 更新 `affected` 并插入 chunks；任务结束后 `finish_live` 改为 `applied`。崩溃后 `pending` 行在下次打开时按已提交内容转为可撤销。

### 5.2 `AppState` 与命令

`AppState` 增加 `app: AppHandle`（在 `lib.rs` 用 `application.handle().clone()` 构造），用于从写操作内部安排后台释放任务。`AppState::new(settings, app)`；`lib.rs:58` 是唯一构造点。

`mutate` 是所有会写历史的操作的统一收口：成功后清空 id 列表缓存并调用 `after_history_write`。当前 `create_collection`、`rename_collection`、`reorder_collections` 等尚未走 `mutate` 的写方法要一并补上，否则这些操作不会触发最大步数裁剪。

```rust
impl AppState {
    pub fn history_page(&self) -> AppResult<HistoryPage>;
    pub fn undo_to(&self, target_id: i64) -> AppResult<TaskStartResult>;
    pub fn clear_history(&self) -> AppResult<TaskStartResult>;
    fn after_history_write(&self);   // trim + 安排释放；失败只记日志
    fn schedule_release(&self);      // 队列外待释放批次
}
```

新增命令，注册到 `commands.rs:734`：

| 命令 | 输入 | 输出 |
| --- | --- | --- |
| `get_operation_history` | — | `HistoryPage` |
| `undo_to_operation` | `{ targetId }` | `TaskStartResult` |
| `redo_to_operation` | `{ targetId }` | `TaskStartResult` |
| `clear_operation_history` | — | `TaskStartResult` |

`HistoryPage`：

```text
entries: HistoryEntry[]
maxSteps: number
pendingPurgeCount: number
pendingPurgeBytes: number
canRun: boolean
blockedReason: string | null
```

`HistoryEntry`：`id`、`kind`、`label`、`createdAt`、`affected`、`status`（`applied` / `undone` / `redoing` / `undoFailed`）、`error`。撤销记录标为 `undone` 保留在列表里供重做；`redoing` 只在任务进行/崩溃时出现。

`undo_to` / `clear_history` 使用 `tasks.launch(..., ConflictPolicy::Fail, ...)`；write lane 忙时直接返回冲突，不排队，避免用户误以为已撤销。`run_release` 可以用 `ConflictPolicy::Queue`，因为它是清理任务，不应阻塞用户操作。

导入与 AI 描述的收尾线程在 `finish_live` 后调用 `AppState::after_history_write()`，确保后台任务也受最大步数裁剪约束；该调用失败只记日志，不影响任务结果。

### 5.3 `TaskHandle`

### 6.1 回收站与永久删除

`metadata.rs:587` 的 `delete_internal` 不再直接删行删文件。拆成两条路径：

- `mark_for_purge(database, image_ids: Option<&[i64]>, reporter)`：
  - 只接受 `deleted_at IS NOT NULL AND purge_operation_id IS NULL` 的行；
  - `delete_images` 的目标里只要有一张不在回收站，整批拒绝，避免命令绕过 UI 把正常图片隐藏；
  - `empty_trash` 传 `None`，`delete_images` 传选中 id；
  - 用 `history::write` 记录一条 `PermanentDelete` / `EmptyTrash`；
  - 在事务里 `UPDATE images SET purge_operation_id = op.id()`；
  - 返回 `DeleteReport { deleted: affected, files_removed: 0, deferred: true, failures: [] }`。
- `purge_by_operation(database, root, op_id, reporter)`：
  - 只被释放任务调用；
  - 沿用现有 400 张一块的“先删行、再删文件”逻辑；
  - 可以按 `purge_operation_id` 过滤，也支持一次清理多个 op id。

`DeleteReport` 增加 `deferred: bool` 字段；前端通知改为“已从回收站移除，文件会在记录过期后释放”。`metadata::empty_trash` 的查询条件和 `db.counts` 的回收站计数都加 `purge_operation_id IS NULL`。

`query.rs:929` 的 `PreparedQuery::new` 在视图分支之前统一加入：

```text
images.purge_operation_id IS NULL
```

这样普通视图、回收站视图和“全库搜索包含回收站”都不会看到待释放行；`rows_by_ids` 也加同一条件，避免过期会话按 id 取回待释放图片。

实际实现（批次 1）：`purge_operation_id IS NULL` 只加在回收站视图与全库搜索；普通视图与集合视图的 `deleted_at IS NULL` 已经挡住待释放行（它们一定在回收站里）。无条件加这条会让排序 id 列表失去覆盖索引，20 万行文件夹排序首页从 39 ms 涨到 81 ms。

### 6.2 编辑保存与撤销

`edit.rs:145` 的 `save` 保持公开签名，内部改为：

1. `resolve` 读取旧行；生成新内容到 temp；冲突检查与 `has_changes` 不变。
2. 打开写事务，插入 `operations` 行（`history::write` 的闭包形式），拿到 `op.id()`。
3. 把旧原图**硬链接**到 `.artbank/undo/<op.id()>/<oldHash>.<ext>`，不先移走原文件；硬链接失败时退化为复制。这样在事务提交前崩溃，原路径仍然有效。
4. 发布新文件、追加缩略图、更新 `images` 行、删除 `feature_blobs`，与现在一致。
5. 把旧内容列快照写入 chunk；`affected=1`；提交。
6. 提交成功后再删除旧原图的原路径（暂存链接继续保留）；失败时不删原路径，删除新文件与暂存链接。
7. 提交成功后删除旧哈希的预览缓存。

需要新增的输入数据：旧行的 `content_hash/file_ext/file_size/width/height/format/has_alpha/phash/colors4/colors8/modified_at`。`content.rs:11` 的 `ContentRow` 不含 phash/colors/modified_at，新增一个 `EditBefore` 查询或扩展 `ContentRow`。

撤销 `edit`：

1. 读 JSON 快照；读当前行。
2. 当前哈希等于旧哈希：已经恢复，删除记录即可。
3. 当前哈希不等于新哈希：报错，不猜测。
4. 先用暂存旧文件重新编码缩略图并 `pack.append`（在事务外，失败直接返回）。
5. 事务内：把暂存文件复制/链接回当前文件夹（目标已存在则复用）；更新内容列与 `modified_at`；更新缩略图指针并 `thumb_version + 1`；删除该图 `feature_blobs`；删除 operation 行与 chunks。
6. 提交后删除当前新内容文件与该哈希的预览缓存；暂存目录内的旧链接随记录删除。

embedding/pose 不恢复；删除是为了避免旧特征与新内容不一致。缩略图重建失败不阻止内容恢复，但记录会保留错误并显示占位，后续维护可重建。

记录被裁掉时删除 `.artbank/undo/<op>/`；启动时扫描该目录，删除没有对应 `operations.id` 的目录。

### 6.3 导入

`AppState::start_import`（`state.rs:101`）在 `tasks.launch` 的执行闭包里、拿到 write lane guard 之后：

1. `history::begin_live` 创建 `Import` 记录，label 使用输入路径数/目标文件夹。
2. 把 `operation_id` 放进 `ImportSource`（`import/mod.rs:109`）或 `WriterOptions`（`pipeline.rs:49`）。
3. 这样任务冲突返回 `Conflict` 时不会留下空记录；线程启动失败时由闭包/收尾删除空记录。

`pipeline.rs:507` 的 `flush` 在同一个写事务里：

- `repository::insert_image` 增加 `origin_operation_id`：新行写入 `op.id`；
- 合并重复项时，在 `resolve_existing` 之前抓取旧评分、旧标签、旧 `modified_at`，写入 JSON chunk；
- `ensure_folder` / `ensure_tags` 返回“本次是否新建”，新建的 path/tag id 写入 chunk；
- `history::add_live_affected_in_tx` 更新操作行（与插入处在同一个事务里）；

任务结束后在 `import::start` 的收尾线程调用 `history::finish_live`（含取消/失败）；没有任何新增/合并时删除空记录。崩溃留下的 `pending` 导入记录在下次打开时按 `origin_operation_id` 判断：有行则转为 `applied`，没有行则删除。

撤销导入：

1. 按 `origin_operation_id` 分块查询新增行，删除行并记录文件路径；提交删行后再删文件。
2. 恢复合并项快照：评分、标签关系、`modified_at`。
3. 对本次新建的文件夹，若仍为空则删目录与行；对本次新建的标签，若无关系则删除。
4. 全部成功后删除 operation 行；中断则保留 `undoing`，下次按剩余 origin 行继续。

重复检测仍会把待释放的回收站行视为已存在，这是延迟释放的已知后果。导入撤销只删除本次新增行，不删除用户源文件。

## 7. 撤销引擎

### 7.1 流程

1. `AppState::undo_to` 校验目标记录存在且为 `applied`；计算 `id >= target` 的 applied 记录，最新的在前。目标上方已经 `undone` 的记录不会再次处理。
2. 建立 `undo_runs` 行（`running`），创建 `TaskKind::Undo` 任务，`ConflictPolicy::Fail`。
3. `history::run_undo`：
   - 设置 total 为记录数；
   - 每条记录开始前检查取消标记；
   - 从 `applied` 进入撤销时清掉旧的 `redo` chunks，再标记 `undoing`；
   - 调用该类型的逆操作，并把撤销前状态写成 `redo` chunks；
   - 成功后标记 `undone` 与 `undone_at`，**不删除 operation 行与 chunks**；
   - `task.inc_completed()`，message 显示当前记录内进度；
   - 失败时标记 `undoFailed`，把 `undo_runs` 标为 `failed`，停止。
4. 全部成功后 `undo_runs` 标为 `completed`；清空查询 id 缓存、使 AI 相似度缓存失效；前端随任务完成刷新。
5. 取消发生在记录之间：`undo_runs` 标为 `cancelled`，已完成的记录保持 `undone`，未完成的记录保持 `applied`。

### 7.2 重做

1. `AppState::redo_to` 校验目标为 `undone` / `redoing`；从目标向下取连续的 `undone` / `redoing` 记录，直到遇到 `applied` / `undoFailed`。
2. 创建 `TaskKind::Redo` 任务，`ConflictPolicy::Fail`；`history::run_redo` 在开始处理前把整批记录标为 `redoing`。
3. 按 id 升序执行；每条从 `redo` chunks 恢复撤销前状态，成功后标回 `applied`、清空 `undone_at`。
4. 取消或失败时，把尚未处理的 `redoing` 记录恢复为 `undone`；失败记录保留 `error`，可以再次重做。存在重做失败的灰色记录时，`undo_to` 拒绝继续向更早记录回退。
5. 新的图库写入（`history::write` / `begin_live`）在同一个事务里删除 `undone` / `redoing` 记录，重做分支失效。

### 7.3 崩溃恢复

- `recover_on_open`：
  - `pending` 导入/AI 记录：有已提交内容则转 `applied`，否则删除；
  - `undoing` 记录与 `running` undo_run：保留，启动后安排一次 Undo 任务续做（最小 `undoing` id）；逆操作必须幂等；
  - `redoing` 记录：保留，启动后安排一次 Redo 任务，从最大 `redoing` id（本次用户选择的目标）续做；
  - `.artbank/undo/<id>` 没有对应记录：删除；
  - `purge_operation_id` 没有对应记录：加入待释放。
- 续做时已经恢复的行/文件再次执行会走“已完成”分支跳过。
- 启动恢复在 `AppState::open_library` 内做 DB 部分；后台任务在 `application.manage(state)` 之后安排，避免启动时在未注册状态上取 `AppState`。

### 7.4 裁剪与释放

- `history::trim(database, max_steps)`：
  - 只考虑 `applied` / `undoFailed`；`pending` / `undoing` / `undone` / `redoing` 不参与裁剪；
  - 按 id 倒序保留最新 `max_steps` 条；
  - 删除更旧的 operations 与 chunks；
  - 返回被裁掉的 `EvictedOperation { id, kind }`。
- `AppState::after_history_write`：
  - 每次成功写入后读取当前设置的 `maxSteps`，调用 `trim`；
  - 被裁掉的有编辑记录：删除对应 `.artbank/undo/<id>`；
  - 被裁掉的有永久删除/清空记录：安排 `ReleaseGarbage`；
  - 失败只记日志，不影响用户操作。
- `ReleaseGarbage`：
  - `history::orphan_purge_batches` 找 `purge_operation_id` 已无对应 operations 行的批次；
  - 调 `metadata::purge_by_operation` 分块删行、删文件；
  - 不提供用户取消；可重复执行。
- `clear_operation_history`：
  - 删除全部 operations/chunks；
  - 删除全部 `.artbank/undo` 目录；
  - 安排 ReleaseGarbage 删除所有待释放行与文件；
  - 红色确认，明确“立即释放且不能再撤销”。

- 撤销过程中取消，停在记录边界；再次撤销可继续。
- 撤销失败时记录保留并显示原因，不会把后续状态伪装成成功。
- 20 万级批量记录与待释放标记不显著拖慢现有查询；历史列表打开不触发全库扫描。

## 12. 风险与已知后果

- 文件与数据库无法总是原子提交；依靠幂等逆操作、启动续做与孤儿清理保证最终一致。
- 永久删除/清空回收站后磁盘不会立即释放；重新导入同一文件会按重复跳过，待释放图片也会暂时挡住文件夹删除。
- 编辑旧原图暂存会占用磁盘，最大步数直接决定上限；历史面板显示待释放量。
- 撤销失败会阻止向更早记录回退；不提供“跳过失败记录”。
- `origin_operation_id` 在导入记录过期后仍留在行上，但没有记录引用，属于无害旧标记；如担心误解，可在发布任务中清理。
- AI 描述服务当前未实现；描述撤销代码先按 live operation 预留，不改变现有 UI 置灰。
- 撤销编辑会删除该图当前 `feature_blobs`，包括编辑之后重新生成的 embedding/pose；特征是派生数据，保持为空比保留与新内容不一致的旧向量更安全。
- 未来新增的写路径（描述回填、维护任务、新的批量编辑）必须接入 `history::write` 或 live operation，否则会破坏“线性时间线 = 当前状态”的约定。
- 批次 3 的表面最多；实施中不再增加第四批，必要时只在第三批内部按子阶段提交。
- 不编译 release、不启动开发服务器、不做浏览器/UI 自动化；真实窗口由用户验收。
