# 使用反馈整改计划（第三轮）

日期：2026-10-29
状态：**批次 1 已实施，批次 2、3 待实施**。只界定问题、根因、方案与三个批次；三个批次都完成后把本文件与批次记录一起移入 `archive/`，验收条目写进 `todo.md`。

本轮四条反馈：

1. 图片详情里增加“跳转到所在文件夹”。
2. 导入：标签会消失；进度增加写入体积（压缩后按最终体积）与预计完成时间；2.8 万张导入占用约 4 GB 内存是否正常。
3. 删除文件夹必须先清空子文件夹，清空回收站后仍不能删；回收站要能直接接收文件夹，并用树状结构展示图片与多级文件夹。
4. 大规模移动、导入结束后 UI 卡顿一两秒。

## 已确认的决策

- **回收站树复用现有文件夹树语义**：父节点下可以有子文件夹，也可以有“直属图片”；单独移入回收站、原文件夹仍在图库中的图片挂在回收站根节点的“散图”下，不混进正常文件夹路径。
- **删除文件夹 = 整棵子树移入回收站**：文件夹与全部子文件夹立即从正常树中消失，树内图片一起进入回收站；可整目录恢复或整目录永久删除。空文件夹也走同一语义，不再保留“只能删除空文件夹”的特例。
- **导入内存按解码内存动态限流**：大图少并发、小图多并发，峰值压到约 1.5–2 GB；吞吐允许略降。
- **标签消失修根因，不加“重新打开恢复草稿”之类的补丁**：见下面的 `<label>` 结论。

## 一、根因与代码定位

### 1. 详情跳转文件夹

现状：详情侧栏的“文件夹”区只显示路径与“移动”控件，没有跳转入口（`src/modules/library/Inspector.tsx:762-813`）。浏览视图已有 `showFolder`，会把 `filters.folderIds` 设为该文件夹（`src/modules/library/LibraryView.tsx:1739-1756`）；文件夹树在选中项变化时会自动展开祖先（`src/modules/library/FolderTree.tsx:154-172`）。

结论：缺的只是一个入口与回调，不需要新查询。跳转后应退出回收站/临时视图、清空搜索与其它筛选（沿用 `showFolder` 的既有行为），并让树滚动到目标行。

### 2. 导入标签消失（根因已确认）

不是导入逻辑清空标签，也不是建议列表覆盖。根因是 **HTML `<label>` 包裹了多个可聚焦控件**：

- `Field` 组件把整个字段渲染成 `<label>`（`src/shared/components/Field.tsx:10-17`）。
- 导入对话框的“初始标签”用 `Field` 包住 `TagInput`（`src/modules/import/ImportDialog.tsx:480-490`）。
- `TagInput` 先渲染已有 chip，再渲染输入框；每个 chip 里都有一个删除 `<button>`（`src/shared/components/TagInput.tsx:123-137`、`src/shared/components/TagChip.tsx:80-89`）。
- `<label>` 没有 `for` 时，浏览器把它的第一个可聚焦后代当作被标注控件；这里第一个就是第一个 chip 的删除按钮。
- 因此点击字段标签文字、提示文字、chip 的名字区域或字段内任意非交互空白，浏览器都会把点击转发给第一个 chip 的删除按钮。每点一次就删掉一个已确定的标签；只有一个标签时看起来就是“点一下别处标签就没了”。

同一个问题也存在于其它“一个 `Field` 里放了多个按钮/控件”的位置，例如导入的“输出格式”两个按钮（`ImportDialog.tsx:559-589`）、批量任务/空间优化的“处理范围”（`BatchTaskDialog.tsx:361`、`OptimizeDialog.tsx:969`）：点击提示文字可能误触第一个选项。

### 3. 导入进度缺少体积与 ETA

后端导入快照只有文件数、耗时与压缩省下的字节（`src-tauri/src/import/job.rs:85-110`、`:441-462`），没有“本次新增的最终体积”，也没有速度/预计剩余。写入线程已经拿得到每张最终入库的 `file_size`（`Prepared.file_size`，`src-tauri/src/import/pipeline.rs:87-107`、`:681-700` 附近），只是没有汇总。

任务总线本身已有统一的速度/ETA 算法（`src-tauri/src/app/tasks.rs:467-495`）；导入也挂在任务总线上，可以直接复用同一套口径，不需要另造滑窗。

### 4. 2.8 万张导入约 4 GB 内存

不是泄漏，是当前“按线程数、不按字节数”的预算模型在大图 + 导入压缩下的正常峰值。

- 默认图像预算 = 逻辑核数 − 1（`src-tauri/src/concurrency/budget.rs:107-112`）；本机 16 逻辑核，即 15 个导入工作线程（`src-tauri/src/import/pipeline.rs:261-264`）。
- 每个线程处理一张图时会同时持有：
  - 解码后的全尺寸 `DynamicImage`（`src-tauri/src/import/decode.rs:73`）；
  - 缩略图/pHash/主色都从这张图计算，计算期间原图不释放；
  - 勾选压缩时，再把整个源文件读进内存（`pipeline.rs:522`）；
  - `PixelBuffer::from_image` 再复制一份全尺寸 RGB/RGBA（`src-tauri/src/imageops/optimize.rs:583`、`:621-628`）；
  - 每个质量档编码后还会 `image::load_from_memory` 解码一份用于 PSNR（`optimize.rs:593`），编码结果也留在内存里。
- 单张 20 MP 图在压缩路径下的峰值约为 12–16 字节/像素，再加源文件字节；即 240–320 MB。15 个线程同时处理大图就是 3.6–4.8 GB，正好对应观察到的 4 GB。
- 不勾压缩时只剩解码图与特征计算，单张约 4–5 字节/像素，峰值通常低一个量级；这次日志里 `set_import_optimize` 后紧接着导入，属于压缩路径。

结论：4 GB 在现有模型下可解释，但不应作为正常目标。修法是给图像工作加“字节预算”，在解码前按图片尺寸申请内存额度，而不是只数线程。

### 5. 删除文件夹与回收站

现状：

- `delete_folder` 只允许删除“没有子文件夹、没有图片、磁盘目录为空”的文件夹（`src-tauri/src/library/folders.rs:812-876`、`:924-979`）。
- 图片移入回收站只是写 `deleted_at`，文件仍在原目录（`src-tauri/src/library/metadata.rs` 的回收站实现）；清空回收站只写 `purge_operation_id` 待释放标记，真正删行删文件要等记录过期或清空操作记录（`docs/modules/browse-and-query.md` 的“回收站”）。
- 所以“图片都进回收站了，文件夹仍然不是空的”不是 bug，而是两套生命周期没有接上：数据库行还在、文件也还在，空目录判据自然失败。

目标语义：

- 删除文件夹时，整棵子树（含所有子文件夹与图片）进入回收站；正常树立即不再显示。
- 回收站左侧是树：根节点“回收站”，下面是已删除文件夹的多级结构；每个文件夹可以有“直属图片”行；单独删除、原文件夹仍在图库中的图片放在根节点“散图”下。
- 可整目录恢复、整目录永久删除；清空回收站同时处理文件夹与图片。

数据上不需要把文件搬到 `recycle/` 目录：保留原路径与文件，用 `folders.trashed_at` 表示文件夹被删除、`images.deleted_at` 表示图片在回收站；永久删除仍走现有“待释放标记 + 释放任务”。这样恢复不需要搬文件，磁盘释放仍遵守现有延迟释放协议。

### 6. 大规模操作后 UI 卡顿

日志证据（`D:\Lilith\Lilith Artbank\logs\lilith-artbank.log`）：

- 导入/回收站操作后 `get_feature_summary` 多次耗时 2.0–2.6 秒；00:37:50 一次达到 10.2 秒。
- `get_feature_summary` 是 5 条全库子查询（`src-tauri/src/library/capability.rs:88-121`），对 39.6 万行与 feature_blobs 做聚合；而每次导入/回收站变化都会把 `features` 置真并重查（`src/modules/library/dataChange.ts:243-259`、`src/modules/library/LibraryView.tsx:705-719`）。
- 主线程还有一个确定的平方级循环：`selectionAfterChange` 用 `change.ids!.includes(id)` 过滤选择集（`src/modules/library/dataChange.ts:415-433`、`:454-457`、`:460-490`）。大规模移动/回收站时，选中 2 万张、变化 id 也是 2 万张，就是约 4 亿次比较，正好对应“结束后卡一两秒”。
- `applyChanges` 串行等待列表刷新、文件夹重取、图库计数（`src/modules/library/LibraryView.tsx:584-645`），进一步把这段卡顿拉长。

结论：卡顿至少由“主线程平方级选择过滤 + 导入后全库特征统计 + 串行刷新”三部分叠加，不是单一原因。

#### 1.2 标签消失的根因修复

- 所有“一个字段里不止一个可聚焦控件”的地方改用 `plain`：

  - 批量任务/空间优化的“处理范围”（`ScopePicker` 内多个按钮/单选框）；
  - 其它含按钮组、滑块+按钮的 `Field`。
- 单输入框字段继续用 `<label>`，保留点击标签聚焦输入框的可访问性。

#### 1.3 导入进度：最终体积与 ETA

后端：

- `ImportJob` 增加 `written_bytes: AtomicU64` 与 `processing_started_at: Mutex<Option<i64>>`（或直接复用 `TaskHandle` 的 `run_started_at`）。
- 写线程每批提交后，把本批新增行（不含重复、不含合并）的 `Prepared.file_size` 求和，累加到 `written_bytes`。压缩成功的行 `file_size` 已经是压缩后字节，因此口径天然是“最终增加的体积”。
- `ImportProgress` 增加：
  - `writtenBytes`：已入库新图片的最终字节总和；
  - `ratePerSecond: number | null`：进入 processing 后，按“已写入张数 / 已运行秒数”计算；
  - `etaSeconds: number | null`：`(total − written) / rate`，未开始或样本不足时为空；终态为空。
- 不建议复用 `optimizedBytes` 当体积：它是“省下的字节”，不是新增体积。

### 批次 2：导入内存与刷新收敛

#### 2.1 导入内存字节预算

- 在 `concurrency/` 增加字节预算（`MemoryBudget` 或给 `ImageBudget` 增加 `acquire_bytes`），记录当前占用字节与上限；等待可取消，释放用 RAII。
- 导入在 `decode` 前先探测尺寸（`ImageReader` 读头，不解码像素），估算：
  - 不压缩：`像素数 × 5 字节 + 固定开销`；
  - 压缩：`像素数 × 16 字节 + 源文件大小 + 固定开销`。
  系数先用保守值，实测后再校准。
- 预算上限初值 1.5 GiB；单张图片估算超过上限时允许“独占”一个许可，避免大图永远排不到。
- 许可在 `process_one` 里、解码前获取；解码、特征与压缩结束就释放，不等写线程，写通道积压不再额外占解码内存。
- 顺带降低压缩路径的单线程峰值：
  - `encode_ladder` 尽量消费已解码的 `DynamicImage`，避免 `PixelBuffer` 再复制一份全尺寸像素；
  - 源文件字节只保留到 ICC/EXIF 判断与必要元数据搬运，随后尽快释放。
- 在调试构建里记录每个导入任务的峰值估算与并发数（不需要新增系统信息依赖）；真实峰值用任务管理器复核。

#### 2.2 刷新收敛

- `get_feature_summary` 改为“标记过期、按需读取”：
  - 导入/回收站/文件夹变化只递增一个 `featureSummaryStale` 标记；
  - 只有筛选面板打开、或用户打开“有描述/有 embedding/有 pose”相关界面时才请求；
  - 失败保留旧值，显示加载态，不让它进入导入收尾的关键路径。
- `applyChanges` 中互不依赖的刷新并行化：列表刷新、文件夹重取、图库计数、集合读取分到 `Promise.all`；状态更新用一次批量提交。非紧急的界面更新（文件夹树、统计）放进 `startTransition`，保持滚动与点击响应。
- 导入、回收站、恢复这三类变化已知数量时，优先用增量更新图库计数，不再每次做全库 `count(*)`；无法确定时再回退到计数查询。
- 加调试计时：在 `applyChanges` 里按阶段打 `performance.mark`，只有超过阈值才输出；配合现有 Rust `command slow` 日志定位剩余长任务。

#### 2.3 验收与数字

- 用复制出的 2.8 万张样本（不写真实库）分别跑“不压缩 / 压缩”导入，记录峰值内存、总耗时、导入速度与 UI 是否可操作。
- 同一批样本跑一次 2 万张移动、回收站、恢复，记录操作结束到列表稳定的时间。
- 结果写进 `docs/guides/performance.md`，不在本计划里留数字。

**不做**：不改变导入管线（不引入新的解码器、不改成多进程）；不降低默认线程数来“掩盖”问题；不为了省内存牺牲缩略图/pHash/主色精度；不把导入改成可关闭窗口。

**退出标准**：2.8 万张压缩导入峰值约 1.5–2 GB；不压缩导入峰值明显更低；导入结束不再触发全库特征统计；大选择移动/回收站在结束后 200 ms 内恢复交互（以用户实际观感与 Performance 长任务为准）。

### 批次 3：文件夹回收站树

#### 3.1 Schema v10

`folders` 增加：

- `trashed_at INTEGER`：NULL 表示正常；非空表示整棵子树在回收站。
- `purge_operation_id INTEGER`：文件夹级待释放标记；永久删除后先从回收站树隐藏，释放完成后再删行与目录。

迁移 v9→v10 只做 `ALTER TABLE ADD COLUMN`，不重写旧行；旧 `folderDelete` 历史记录仍按原逻辑撤销/重做。

查询：

- 正常 `list_folders` 排除 `trashed_at IS NOT NULL` 与 `purge_operation_id IS NOT NULL`；正常文件夹树、概览、任务范围、导入目标都看不到回收站文件夹。
- 新增 `list_trash_folders`：返回已删除文件夹的 id/路径/父路径/直属回收站图片数/子树回收站图片数；另返回根节点“散图”计数（`deleted_at IS NOT NULL` 且所属文件夹 `trashed_at IS NULL` 的图片）与回收站总图片数。
- 回收站图片查询复用 `view=trash`，增加 `filters.trashLoose`：选中“散图”时只匹配正常文件夹里的回收站图片；选中已删除文件夹时沿用 `folderIds` 子树匹配。
- 为 `images(deleted_at)`、`folders(trashed_at)` 补必要索引，并用 `EXPLAIN QUERY PLAN` 测试确认不退化。

#### 3.2 删除、恢复、永久删除

- `delete_folder` 语义改为“整树移入回收站”（保留命令名以减少前端改动，文档与按钮文案改为“移入回收站”）：
  - 事务内把子树所有文件夹 `trashed_at = now`，所有未删除图片 `deleted_at = now`；
  - 写一条 `FolderTrash` 记录，chunk 里保存文件夹 id/路径与图片旧状态（`deleted_at`、`modified_at`）；
  - 不移动、不删除物理文件与目录；返回子树 id 供前端从正常树剔除。
- `restore_folder(folderId)`：清空子树 `trashed_at`，只恢复“这次文件夹删除时仍为正常”的图片；删除文件夹之前就已经单独在回收站的图片保持删除状态，随后归到“散图”。写一条 `FolderRestore` 记录，撤销时重新移入回收站。
- 已删除文件夹下的图片不提供单张恢复：它们属于整目录删除，恢复入口在文件夹层。要只保留其中几张，先恢复整个文件夹，再把不要的图片移入回收站。单张恢复只用于“散图”与正常文件夹里的回收站图片。
- `delete_folder_permanently(folderId)`：只接受回收站文件夹；给子树图片写 `purge_operation_id`（与现有永久删除一致），给子树文件夹写 `purge_operation_id`；写一条 `FolderPurge` 记录。文件夹立即从回收站树消失。
- `empty_trash` 同时处理图片与回收站文件夹：图片沿用现有逻辑；文件夹写 `purge_operation_id`。
- 释放任务：删完图片行与文件后，自底向上删除 `purge_operation_id` 非空、已无图片、已无子文件夹的文件夹行与空目录；非空目录不强行递归删除，记录警告留待下次。
- 撤销/重做：扩展 `HistoryKind` 与 undo/redo 分发；旧 `FolderDelete`（空文件夹物理删除）保留解析与撤销能力，不做数据迁移。
- 临时文件夹仍禁止删除/恢复/永久删除；根目录禁止。

写入边界：

- 新建/重命名/移动/导入目标/移动图片到文件夹时，目标路径若落在回收站文件夹（`trashed_at` 非空），返回明确错误：“该文件夹在回收站中，请先恢复或永久删除”。
- MCP `folders_modify` 的 delete 同步改为“移入回收站”，dryRun 输出图片张数、子文件夹数与“可恢复”；`folders_list` 默认不返回回收站文件夹。
- 真实库只读；迁移与删除测试全部在复制样本或临时库进行。

#### 3.3 回收站树 UI

- 回收站视图左侧改为树（复用 `FolderTree` 的行渲染与展开逻辑，增加 `mode="trash"` 或抽一个只读树组件）：
  - 根节点“回收站” + “散图 N”；
  - 已删除文件夹按路径层级嵌套；
  - 每个文件夹下保留现有“直属图片 N”虚拟行（`docs/modules/browse-and-query.md` 的“直属图片”）；
  - 选中节点过滤右侧图片列表；面包屑显示“回收站 / 路径”。
- 右键/工具栏操作：
  - 文件夹：恢复、永久删除；
  - 散图/图片：恢复、永久删除；
  - 不允许新建、重命名、移动、拖动排序或把正常图片拖进回收站文件夹。
- 正常树的“删除文件夹”菜单项去掉“只能删除空文件夹”的禁用条件与文案，确认框写明“文件夹及 N 张图片移入回收站，可恢复”；删除后若当前筛选正是该文件夹，切回全部。
- 空回收站按钮同时处理文件夹；确认文案说明文件延迟释放，不能撤销。
- 回收站计数仍用图片数；树节点计数用回收站图片数，不把正常图片算进去。

**不做**：不把物理目录搬到 `recycle/`；不新增第二套回收站；不在回收站树里显示正常文件夹；不改变图片内容寻址与缩略图 pack；不开放 MCP 的永久删除/清空回收站（沿用现有三档权限）。

**退出标准**：`cargo fmt --check`、`cargo check --all-targets`、`cargo clippy --all-targets`、`cargo test`、`npx tsc --noEmit`、`npm run test:web`、`npm run build` 通过；用户手工验收下面的场景。

## 四、用户手工验收步骤

### 批次 1

1. 选中任意图片，点详情“转到所在文件夹”：视图切到该文件夹，树自动展开并滚动到该行，图片仍在网格里。
2. 在查看器侧栏点同一按钮：查看器关闭，回到该文件夹。
3. 打开导入对话框，添加 2–3 个标签；依次点击“初始标签”文字、提示文字、chip 名字、目标文件夹输入框、目录层级按钮、重复内容按钮。标签必须全部保留；点某个 chip 的 X 只删掉那一个。
4. 导入时勾选压缩，观察进度：显示已写入体积（最终压缩后）、速度与预计还需；完成页的新增体积与资源管理器里目标文件夹增加的字节大致一致。
5. 选中 2 万张图片移入某个文件夹，或移入回收站：操作结束后立即点击/滚动界面，不再出现约 1–2 秒的无响应；查看器打开也正常。
6. 文件夹树双视图：点标题栏加号左侧的按钮拆成上下两格；上面滚到 A、下面滚到 F；把 A 里选中的图片或 A 文件夹直接拖到下方 F，操作正常；拖动中间分隔条改变高度；重启应用后开关与高度保持。
7. 不选图片、选中“全部图片”根行：右侧显示“图库概览”，图片数、文件夹数与总大小和侧栏计数一致，类型/评分/常见标签有数据；空库时显示“图库里还没有图片”。

### 批次 2

1. 用复制出的 2.8 万张样本做一次压缩导入：任务管理器峰值约 1.5–2 GB；导入期间缩放窗口、切换文件夹不卡死。
2. 不压缩再导入同一批：峰值明显更低，吞吐不低于改动前太多。
3. 导入结束时不打开筛选面板：日志里不出现新的 `get_feature_summary` 慢查询；打开筛选面板后才刷新特征可用性。
4. 大规模移动/回收站/恢复结束后，Performance 面板没有超过 200 ms 的主线程长任务（或只剩可解释的一次列表刷新）。

### 批次 3

1. 建 `父/子` 两级文件夹，各放几张图片；右键父文件夹删除：确认框显示子树张数；正常树立即消失；回收站树出现 `父 → 子` 结构，直属图片行计数正确。
2. 在回收站树选中 `子`：右侧只显示该子树的回收站图片；选中“散图”：只显示单独删除、原文件夹仍在的图片。
3. 恢复整个 `父`：文件夹与全部图片回到正常树，路径不变；回收站树对应节点消失。
4. 再次删除 `父`，在回收站树永久删除：节点立即从回收站消失；清空操作记录/等待释放后，磁盘上的目录与数据库行都被清理；未清空记录前文件仍在，界面文案要说明这一点。
5. 单独把某张图片移入回收站：它出现在“散图”，不出现在正常文件夹节点下；恢复后回到原文件夹。
6. 在回收站树选中 `父/子`：右侧图片可查看，但没有单张“恢复”入口，只提供恢复整个文件夹；文件夹恢复后，删除前就已单独在回收站的图片仍留在回收站，并归到“散图”。
7. 尝试新建/移动/导入到已被删除的文件夹路径：被拒绝并提示先恢复或永久删除。
8. MCP `folders_modify` 删除一个非空文件夹：dryRun 返回张数与可恢复说明；实际执行后文件夹进入回收站，可在界面恢复。
9. 关闭并重开图库：回收站树、散图、文件夹隐藏状态与计数都保持。

## 五、风险与约束

- **Schema v10**：迁移只加列，但真实库 39.6 万行，升级前用复制库验证打开耗时；不读取旧 `.data`。
- **历史兼容**：旧 `folderDelete` 记录必须继续可撤销；新记录类型要能在旧数据上安全解析。
- **回收站树与查询计划**：`散图` 需要 `images JOIN folders` 过滤 `folders.trashed_at IS NULL`，必须用 20 万/39.6 万行样本检查计划，避免退化为全表回表。
- **恢复语义**：只恢复文件夹删除时仍正常的图片；删除前已单独在回收站的图片不会被一起复活，恢复后落到“散图”。UI 文案要说明这一点。
- **内存预算的吞吐代价**：大图导入会变慢；用真实样本确认典型图（小/中尺寸）不受明显影响，必要时只对大图收紧。
- **刷新收敛的陈旧感**：特征摘要改为按需读取后，筛选面板首次打开可能有短暂加载；保留旧值并显示“更新中”，不要闪空。
- **代理边界**：不启动应用、不截图、不驱动窗口、不编译 release；界面与观感由用户验收。
