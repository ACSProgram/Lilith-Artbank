## 已确认的决策

- 批量裁剪使用**统一画布 + 矩形裁剪**；不做非矩形蒙版。
- 旋转与裁剪合并在同一个批量编辑面板，沿用单图编辑的操作顺序；只想旋转时可以不画裁剪框。
- 同一批使用同一套 recipe；不做逐张不同裁剪、逐张旋转覆盖。方向不一致的图片先分组处理。
- 所选图片在翻转/旋转后宽高完全一致时，额外允许“同一像素矩形”作为快捷模式，不重采样。
- 批量编辑整批只写一条操作记录，可按快照逐张撤销/重做；**可撤销上限 2000 张**（按选中集计）。
- 超过 2000 张时只给两个动作：返回并缩小选择、分多次处理（推荐）；或明确确认后整批继续，但本次不保留撤销副本，只写一条不可撤销记录。不自动拆任务。
- 输出质量可调，但默认按格式：JPEG 90、WebP 85、PNG 无损；不默认 95。质量用可空值表示“按输出格式取默认”，否则混合格式的“保持原格式”会把 WebP 误改成 90。
- 批量编辑复用现有批量任务总线（`BatchTaskKind` / `start_batch_task` / `preview_batch_task`）与长任务 `LiveOperation`，不新增 `start_batch_edit` 命令。
- MCP 只新增一个只读 `library_sql`，导出作为它的参数；不新增多个导出/脚本工具，不开放数据库文件。
- `library_sql` 与导出只出元数据，不出原图像素；像素继续走 `image_sheet`、查看器与应用内编辑。
- `library_sql` 的导出格式只有 **JSONL 与 CSV**，不做 SQLite 结果副本；模型需要 SQLite 时用自己的 Python 从 JSONL/CSV 建库。
- 导出结果返回真实文件路径，不是不透明句柄；模型用自己的 Python 处理，应用不跑脚本。
- `mcp_*` 稳定视图在专用只读连接上以 `TEMP VIEW` 创建，不占 schema 版本；字段口径只写在 `library_info.sql`，`library_sql` 工具描述只列视图名与用法，不单建 `mcp_schema` 视图。
- 新增 MCP 工具的门槛：只有当某个计算无法由 SQL、文件导出、现有相似与写入动作组合完成时才加；不按工作流造工具。
- 批量标签保留“一次提交、一条记录”的语义，但把输入后的 chip 明确标成“待添加”，按钮改为“保存 N 个标签”。
- 文件夹回收站采用“搬入仓库”模型：移入回收站时把整棵子树同盘 rename 到 `.artbank/trash/`，原路径立即释放；图片单独移入回收站仍留在原地。
- 仓库根用数字 id，不镜像完整原路径：`.artbank/trash/<trashed_at>/<根文件夹id>`；子树内部保留原目录名，只做一次根目录 rename，不逐级改名。原路径只存 `original_path`。
- 回收站恢复遇到原路径已被占用时默认拒绝，不做自动合并或自动改名；用户先重命名或移走新文件夹再恢复。
- v10 已有的回收站文件夹保持“原地”语义，迁移不搬文件；新删除的文件夹才进入仓库。
- “其它批量操作能否撤销”的口径：缩略图、AI、检查、导出不改图库内容，没有撤销；压缩改内容但按设计不可撤销；评分/标签/移动/回收站已经一条记录、可撤销；本次只给批量编辑补多快照撤销。

## 一、现状与代码定位

### 1. 单图编辑已有完整管线，批量编辑没有内容任务

- 当前批量面板 `src/modules/library/BatchInspector.tsx` 只支持评分、标签、移动、回收站与集合，不提供像素编辑。
- 批量任务总线、资源锁、图像预算都已存在：`BatchTaskKind` / `BatchTaskRequest` 在 `src-tauri/src/app/tasks/mod.rs:409`，统一入口是 `start_batch_task` / `preview_batch_task`，前端走 `src/app/taskApi.ts`；任务快照已有 `failures` 与 `skip_breakdown`，不需要为批量编辑另造任务系统或报告文件。

### 2. 单图编辑历史不能直接承接批量快照

- `edit::save` 每张图写一条 `HistoryKind::Edit` 记录（`src-tauri/src/library/edit.rs:203`）。
- 单图撤销 `src-tauri/src/library/history/undo/edit.rs:26` 只读取一个 `EditSnapshot`；重做用 `RedoRecord::EditState` 存单张状态。
- 批量如果沿用单图保存，会产生 N 条记录；如果整批一条记录，撤销/重做必须支持多个快照。这是批次 1 的主要改造点。
- 长任务已有 `history::LiveOperation`（`src-tauri/src/library/history/mod.rs:946`）：先建 record 为 `pending`，在每批真正写入的事务里用 `append_live_in_tx` 追加逆数据、`add_live_affected_in_tx` 累加影响数，结束统一 `finish_live`。批量编辑直接复用它，不需要新的“跨事务操作记录”机制。
- 撤销入口 `run_undo` 在有任务运行时由 `history_page` 置灰，因此批量编辑运行期间不会被用户撤销；但评分/标签等元数据短写仍可与长任务交错，它们会拿到更晚的 record id，撤销顺序仍按 id 从晚到早。

### 3. MCP 目前只有浏览/检索原语，没有分析接口

- 24 个工具；`search_images` 每页 50、`images_get` 每次 50、`image_sheet` 最多 25 格（`src-tauri/src/mcp/tools/read.rs:31-35`）。新增 `library_sql` 后是 25 个。
- 没有全量元数据、聚合、随机抽样或 SQL；模型的复杂检索只能靠多次调用，或绕过 MCP 直接读库。
- `library_info` 返回 `library.path` 与 `tempFolder.path`，`images_get` 返回 `filePath`；这正是需要收掉的部分。其它工具与任务消息也要一起审计，不能只改这两个字段。
- 现有读连接是 `READ_WRITE + query_only`（`src-tauri/src/library/db.rs:29-41`），不能只靠 `query_only` 作为 SQL 沙箱；数据库是 WAL，新增连接必须单独用 `SQLITE_OPEN_READ_ONLY`，不能复用连接池。
- 当前没有 schema 视图；`mcp_*` 视图若在专用连接上建成 `TEMP VIEW`，就不需要 schema 版本，也不会和批次 4 的 v11 抢版本号。
- 应用已经有相似分组任务，但 MCP 没有入口；本轮不预先把它做成 MCP 工具。embedding/pose 本体在 feature pack，不在 SQLite 里。

### 4. 批量标签的暂存状态看起来像已生效

- `BatchInspector.tsx:47` 用 `tagAdd` 暂存；`:121` 的 `applyAddTags` 只有在点按钮时才写库；`:266-279` 的按钮文案是“添加”，并提示“将添加 N 个标签”。
- `TagInput` 的 chip 只有一种外观（`src/shared/components/TagInput.tsx`），批量侧栏的待添加 chip 与已有标签看起来一样，用户会以为已经保存；实际还要再点一次。`TagInputHandle.commitPending()` 已能把输入框里未回车的文本一起提交，按钮数量口径要按“已提交 chip + 输入框文本”算，不能只看 `tagAdd.length`。

### 5. 文件夹删除仍是“原地回收站”

- `folders` 的 `path` 是全局唯一键，`trashed_at` 只做标记，磁盘目录留在原路径（`src-tauri/src/library/schema.rs:16`、`src-tauri/src/library/folders/trash.rs:21`）。
- 删除文件夹后原路径仍被占用，用户不能建同名文件夹；恢复也默认回到原路径，冲突时只能失败。
- `.artbank` 是保留运行时目录，导入/检查扫描会跳过；`normalize_stored_folder` 目前只额外允许临时文件夹 `.artbank-temp`（`src-tauri/src/library/paths.rs:111`），没有仓库前缀。
- 用户文件夹路径上限 512 字符（`paths.rs:124`）；仓库路径必须在落盘前按内部上限单独校验，不能复用用户输入规则。
- 已有 `folders/undo.rs`、`FolderRow` 与 `FileJournal` 可复用，但 `FolderRow` 还没有 `original_path` 与删除时间戳，撤销/重做要补字段；旧 chunk 缺字段时按“原地回收站”处理。

`BatchEditOptions` 的字段固定为：`rotate`、`flipHorizontal`、`flipVertical`、`mode: canvas | samePixel`、`canvas { width, height, fit: cover | contain }`、`crop: CropRect | null`（画布坐标）、`outputFormat: "keep" | "jpeg" | "png" | "webp"`、`quality: number | null`、`reversible: boolean`。预检响应在现有 `total` / `willProcess` 之外补 `skipBreakdown`、`estimatedOutputBytes` 与 `availableBytes`；其它任务不需要这些字段。

把单图 `edit::save` 拆成两段，单图与批量共用：

1. **准备**：解码、应用方向、翻转/旋转/画布适配/裁剪、编码到临时文件、计算哈希、生成缩略图/pHash/主色；
2. **提交**：发布新内容、更新图片行、追加历史快照。

批量任务逐张“准备 + 提交”，每张一个独立事务；整批共用一个 `LiveOperation` id。已在事务里的提交用 `append_live_in_tx` 写 `EditSnapshot`、用 `add_live_affected_in_tx` 累加影响数，任务结束 `finish_live` 收尾；不要在长任务中一直持有单个 SQLite 写事务。第一批真正写入时调用一次 `history::discard_redo_in_tx`，开启新时间线并清掉可重做分支；后续批次不重复调用。

#### 1.4 裁剪与画布语义

- 统一画布的目标 W×H 是**参考尺寸**，不是强制输出尺寸：每张图按 cover（默认）或 contain 适配到画布，再套同一个矩形裁剪框；最终输出 = 裁剪框的像素尺寸，未画裁剪框时输出 = 画布 W×H。
- cover：等比放大到填满画布，超出画布的部分居中裁掉；contain：等比缩放到完整放入画布，剩余区域补底。
- 补底颜色：输出 PNG/WebP 且原图有 alpha 时用透明；输出 JPEG 或原图无 alpha 时用白色。JPEG 输出统一压到白底，不保留透明。
- 同一像素矩形：仅当所选图片在翻转/旋转后宽高完全一致时可用；裁剪框按原图像素坐标应用到每张图，不缩放、不重采样，输出 = 裁剪框尺寸。该模式下画布尺寸只用于预览，不参与输出。
- 操作顺序固定为：翻转 → 旋转 → 画布适配（或同一像素矩形直通）→ 矩形裁剪 → 编码。前两步与单图一致；画布适配是批量新增的一步，插在裁剪之前。
- 目标尺寸、裁剪框与输出尺寸必须通过 50MP / 单边 65535 校验；recipe 是声明式的，后端按每张图的原始尺寸计算各自的 `EditRequest`，不是把一组固定坐标直接发给所有图。

#### 1.5 输出

- 格式：保持原格式（默认）/ JPEG / PNG / WebP；整批一套。保持原格式时，JPEG/PNG/WebP 各自保持，GIF/TIFF/TGA/BMP 按单图 `OutputFormat::parse` 的现有规则落到 PNG 或 JPEG。
- 质量：`quality: number | null`；`null` 表示按每张图的输出格式取默认（JPEG 90、WebP 85、PNG 无损），用户手动拖动后才写具体值。这样混合格式的“保持原格式”不会把 WebP 误按 JPEG 的 90 重编码。
- 调整质量时显示基于抽样的体积估算；确认页的额外磁盘占用按“新文件总量”估算，撤销副本的老原图用硬链接，不重复计体积。
- 跳过并报告：动画 GIF、回收站/临时区图片、缺原图、解码后超过 50MP、输出与当前内容完全相同（无变化）。
- 单张失败继续并列入失败清单：编码失败、输出哈希与库内另一张图片相同（现有单图编辑也拒绝这种重复内容）、文件夹在任务期间被移动且复核失败。
- 明确提示：旋转/裁剪会重新编码，JPEG/WebP 有一次性画质损失；当前编辑路径不保留原文件 EXIF/ICC。

#### 1.6 任务、历史与资源

- 资源：整批占一个内容写资源；逐张申请该图所在文件夹的路径写锁，提交后释放，不一次性持有所有文件夹锁。每张提交前复核文件夹路径与内容哈希（与单图 `begin_edit` 同一套路），复核失败列为单张失败。与导入、压缩、移动冲突时按现有规则拒绝或排队。
- 逐张解码，使用现有图像预算；不要整批同时解码。
- 预检：总张数、可处理数、按原因细分的跳过数与预计额外磁盘占用；所需空间超过可用空间时直接拒绝，不进入队列。
- 可撤销上限 2000 张：不超过时整批一条 `HistoryKind::BatchEdit` 记录，每张一个 `EditSnapshot` 快照；撤销按逆序、重做按顺序逐张恢复。
- 超过 2000 张：确认页只给“返回并缩小选择（推荐，分多次处理）”与“继续，本次不可撤销”。后者仍写一条 `BatchEdit` 记录（含 `reversible: false` 元数据），不保存逐张快照，旧原图在提交后删除；撤销时明确返回“本次批量编辑未保留撤销副本”，不静默跳过。
- 取消保留已完成部分；单张失败继续并写入任务 `failures`，跳过写入 `skip_breakdown`；全部失败或全部无变化时不产生空记录（`finish_live` 已按 affected/chunks 为空删除）。
- 可撤销批次：旧原图硬链接进 `.artbank/undo/<operationId>/`（失败退化为复制），清空记录后按现有释放路径处理。不可撤销批次：提交成功后删除旧原图，不建撤销暂存。
- 撤销/重做：`undo_batch_edit` 读全部 `Json` 快照，逆序逐张恢复并写 `RedoRecord::EditStates`；重做正序。`run_undo`/`undo_record` 需要按 kind 把 `total` 设为快照张数并逐张 `inc_completed`（重做同理），不要让整条批量记录只占 1 个进度单位，且要响应取消；单张内容已被其他操作改变时中止并标 `undoFailed`，重试时按“已恢复的哈希”续做。撤销/重做期间仍独占时间线。
- 编辑后重建缩略图、哈希、pHash、主色，清空 embedding/pose；标签、评分、描述、集合与图片 id 保持不变。

### 批次 2：MCP 查询与导出

#### 2.1 范围

- 只补一个分析出口：只读 `library_sql`，导出是它的参数；不新增 `export_csv` / `export_json` / `run_script`。工具总数从 24 变 25。
- `library_sql` 与导出只出元数据，不出原图像素；像素继续走 `image_sheet`、查看器和应用内编辑。
- 模型不接触数据库文件、图库路径或内部表；SQL 在应用进程内的专用只读连接上执行。
- 应用不跑 Python 或脚本；它只负责执行 SQL、把结果写成文件并返回路径，脚本由模型自己的环境运行。
- 本轮不固定“相似分组 / 姿势 / 采样 / 统计”等专用工具。它们只有在无法由 SQL、文件导出、现有相似与写入动作组合出来时才评估新增；不按工作流造工具。

#### 2.2 SQL 边界

- 专用连接用 `SQLITE_OPEN_READ_ONLY` 打开同一个 `library.db`，不放在连接池里，也不加 `query_only`：它需要在连接自己的 temp 库里建 `TEMP VIEW`；主库只读由打开标志保证。连接带 `busy_timeout`，应用关库/换库时中断正在跑的查询。
- 只接受单条 `SELECT` 或以 `WITH` 开头的单条查询（先去掉前导空白与 SQL 注释再判定）；用 `prepare` 后检查 tail 为空，拒绝 `EXPLAIN`、`PRAGMA`、`ATTACH`/`DETACH`、DDL/DML、事务/Savepoint。CTE、子查询、join、聚合、窗口函数、`ORDER BY`/`LIMIT` 都允许。
- SQLite authorizer 白名单：只允许读 `mcp_*` 视图；直接查 `images`、`feature_blobs`、`sqlite_master` 拒绝。利用视图展开时 authorizer 的 `SQLITE_READ` 携带 view/trigger 名称区分“经视图读取”与“直表读取”；不带表名的 `SELECT 1` 允许。`sqlite_temp_master` 也拒绝。
- 函数策略：内置的普通标量/聚合/窗口函数（`lower`、`hex`、`json_extract`、`printf` 等）放行，视图定义里的 `hex()` 也走同一规则；显式拒绝加载扩展、文件读写与虚拟表函数（`load_extension`、`readfile`、`writefile`、`fsdir`、`zipfile`、`sqlite_dbpage` 等）以及 `PRAGMA` 表值函数。实现为“内置函数放行 + 危险函数名拒绝”两层，测试覆盖允许与拒绝两侧；不逐个枚举内置函数，避免升级 SQLite 时误杀新函数。
- 并发与资源：同一时刻只跑一条 SQL；行数、字节数、执行时间都有上限，超时用 `progress_handler` 中断，不靠模型猜。初始值：内联 200 行 / 256 KiB / 5 秒，导出 1,000,000 行 / 512 MiB / 60 秒；实测后再调，数字只在 `docs/modules/mcp.md` 维护一份。`truncated` 必须明确提示“不是全量”，并在截断前多取一行确认确实还有数据。
- 结果列名必须唯一；重复列名或空列名直接报错，避免 JSON 行对象静默丢列。

#### 2.3 稳定视图

视图在专用只读连接上以 `TEMP VIEW` 创建（首次使用时建一次，连接关闭即消失），不写进 schema，也不占版本号。不单建 `mcp_schema` 视图：字段、类型、单位与说明只写进 `library_info.sql`；`library_sql` 工具描述只列视图名与用法，避免同一份字段表维护两处。

只开放这些视图：

- `mcp_images`：正常图片，含 id、文件夹、格式、宽高、字节、评分、pHash、主色、导入/修改时间；
- `mcp_trash_images`：回收站图片；
- `mcp_temp_images`：临时区图片；
- `mcp_folders` / `mcp_trash_folders`：正常/回收站文件夹；批次 2 先落地时显示路径用 `path`，批次 4（v11）落地后改为 `COALESCE(original_path, path)`，不能引用尚不存在的列；
- `mcp_tags` / `mcp_image_tags`：标签与正常图片的标签关系；
- `mcp_collections` / `mcp_collection_items`：集合与成员；
- `mcp_features`：是否有 embedding/pose、模型、维度，不含 pack 名与偏移。

字段口径：`rating` 代替 `score`；时间用 `_ms`；大小用 `_bytes`；pHash/主色用 `hex()` 输出十六进制；不暴露绝对路径、仓库路径、pack 名、内部表、向量本体与待释放细节。pHash/主色给出来，模型可以在 Python 里自己算距离和分组；向量与 pose 原始数据不出库。视图字段只增不减，改名视为破坏性变更。

#### 2.4 导出

- 小结果内联返回；大结果写成文件，格式只有 JSONL（默认，适合 Python 逐行读）与 CSV。不做 SQLite 结果副本。
- **返回真实文件路径**，不是不透明句柄；模型拿路径就能用自己的 Python 处理。
- 值映射统一：`NULL` → JSON `null` / CSV 空字段；`INTEGER` 原样；`REAL` 用最短可往返表示，非有限值写成字符串（`NaN` / `Infinity`）；`TEXT` 原样；`BLOB` 用 base64 字符串（JSONL 直接是字符串，CSV 同样 base64，不加 `base64:` 前缀但工具描述写明）。
- JSONL：一行一个对象，键是列名；CSV：UTF-8、无 BOM、首行列名、按 RFC 4180 加引号；以 `= + - @`、Tab 或 CR 开头的单元格前加 `'`，防止表格公式注入。
- 导出目录固定在系统临时目录下的应用专属子目录（例如 `std::env::temp_dir()/lilith-artbank/mcp-export/`），随机文件名，TTL 24 小时；启动、每次导出和空闲回收时清理过期文件。**不使用程序根目录**（`settings.json` 与 `mcp-runtime.json` 在那里，路径会间接暴露图库与口令），也不使用图库目录。不接受模型指定任意路径写入；模型要固定位置时自己复制。
- 流式写文件，不把整个结果集读进内存；导出用比内联预览更宽的行数/字节上限，超过时同样明确 `truncated`，不悄悄截断。
- 返回预览 20 行、总行数、`truncated`、实际路径与格式。
- 导出文件名不包含图库名、文件夹名、查询内容或图片 id；响应、错误与导出内容都不含图库绝对路径；导出内容里的文件夹仍是相对路径。
- 只导出查询结果，不导出原库；导出文件同样不含图库绝对路径。
- 导出走审计日志，记录 SQL 摘要（可截断）、行数、字节数与结果路径。

#### 2.5 路径隐藏

- `library_info` 去掉 `library.path` 与 `tempFolder.path`（保留 `available` / `count` / 说明）；`images_get` 去掉 `filePath`。
- 审计所有工具的返回与错误，不只这两个字段：`folders_list` / `search_images` 只给库内相对路径；`image_sheet`、`find_similar`、`history_list`、`tasks_get` 的消息与 `currentFile` 不得出现库根或程序根；`import_start` 回显的 `missingPaths` 只回显客户端自己传入的输入路径，不回显库内路径。
- 在 MCP 工具边界加一个统一脱敏器：替换图库根、程序根、临时目录、`.artbank` 绝对路径与 `file://` 形式的库 URL；所有工具响应与错误都经过它，不靠各工具自觉。审计日志可以保留完整路径，便于本机排查。
- 脱敏器必须跳过本次返回的导出文件路径及其父目录：导出文件本来就在系统临时目录下，按“临时目录一律替换”会把它一起抹掉；只对其它字段脱敏。
- 不提供数据库文件路径、`sqlite_master` / `sqlite_temp_master`、pack 文件名或任意文件读取函数。
- 导出文件路径是例外：它是模型的工作文件，必须返回；它不是图库路径。
- 仍可见的目录信息只有：系统临时目录、OS 用户名（如果临时目录带用户名）与库内相对文件夹路径；库根、程序根、数据库文件路径不出现在工具响应、错误或导出内容里。程序根不通过导出路径暴露，避免模型顺着路径读到 `settings.json` / `mcp-runtime.json`。

注意：路径隐藏只对“只通过 MCP 访问”的客户端有效；如果客户端同时有 shell/文件读取能力，仍可能从设置或磁盘找到图库。真正的隔离要靠沙箱/独立账户。

### 批次 4：文件夹回收站搬入仓库

#### 4.1 范围与目标

- 文件夹移入回收站时，把整棵子树同盘 rename 到 `.artbank/trash/<trashed_at>/<根文件夹id>/`，**原路径立即释放**；用户可以马上在原位置新建同名文件夹。
- 仓库根用根文件夹 id，子树内部保留原目录名：只做一次根目录 rename，不逐级改名，也不把完整原路径再拼进磁盘路径。
- 回收站树仍按原路径展示；恢复时把仓库目录搬回原路径；永久删除/清空回收站只处理仓库内容。
- 单张图片移入回收站仍留在原文件夹，不搬文件；图片文件名是 BLAKE3 内容哈希，不存在同名冲突。
- v10 已有的回收站文件夹保持原地语义，迁移不搬目录；新删除的文件夹才进入仓库。

#### 4.2 数据模型（schema v11）

- `folders` 增加 `original_path TEXT`：
  - 正常行：`path` 是用户路径，`original_path` 为 `NULL`；
  - 新回收站行：`path` 是仓库内部路径，`original_path` 保存用户原路径（每一行都存，恢复与展示不必反推）；
  - 旧回收站行（v10 迁移）：`original_path` 为 `NULL`，表示“原地回收站”，恢复/释放沿用旧语义。
- 仓库内部路径仍保存在 `path`，继续满足 NOCASE 唯一索引；`trashed_at` 仍是删除单元时间戳。
- 仓库路径：根行 `.artbank/trash/<trashed_at>/<根id>`，后代行 `.artbank/trash/<trashed_at>/<根id>/<相对原路径>`；子树 LIKE 查询继续可用。
- `.artbank/trash` 加入运行时目录；导入/检查扫描本来就跳过 `.artbank`，仓库不会被当成图库内容。
- `normalize_stored_folder` 额外允许 `.artbank/trash/<正整数>/<正整数>/...` 这一种内部前缀；该路径长度按内部上限（例如 1024 字符）校验，不复用用户路径的 512 上限；`normalize_folder` 与用户输入仍拒绝 `.artbank`。
- `LibraryPaths::content_file` / `folder_dir` 继续用 `folders.path`，因此查看器、缩略图重建、检查、优化与释放读图不需要新增“仓库路径”分支；所有展示、面包屑与历史标题改用 `original_path`。

#### 4.3 删除（移入回收站）

- 在写事务内读取子树行与图片；用 `next_trash_stamp` 生成删除单元时间戳，计算仓库根。时间戳必须在所有回收站单元之间唯一：现有实现只查当前子树；改为同时查 `MAX(folders.trashed_at)` 与图片的 `MAX(deleted_at)`，或在目标路径已存在时递增重试。
- 先 `rename` 原目录到仓库根，再改写 `folders.path`（保留根后的相对原路径）、`original_path`、`trashed_at` 与仍正常图片的 `deleted_at`；rename 记入 `FileJournal`，事务失败时逆序撤回目录。已在图片回收站里的行不改 `deleted_at`，避免恢复文件夹时把它们一起复活。
- 源目录不存在、目标已存在、rename 失败：整次删除失败，不留“行已改、目录未搬”的半截状态。
- 空文件夹同样搬移；子树里更早的回收站单元已经在别的仓库目录，不并入本次单元。
- 子树里未纳管的文件随目录一起搬入仓库；释放时删不掉就保留行与标记，日志记录完整仓库路径，界面只说明“仓库里还有未纳管文件”，不显示内部路径。
- `FolderChange` 的 `removedIds`、`affectedImages` 与计数逻辑保持不变。

#### 4.4 恢复

- 以 `trashed_at` 与仓库根定位整个删除单元；恢复范围仍是“最外层文件夹及其子树”。
- 恢复前检查原路径在正常树与磁盘上是否空闲；被占用时拒绝，提示先重命名或移走占用的文件夹，不做自动合并/自动改名。v10 原地行同样检查原路径。
- 恢复顺序：rename 仓库根回原路径 → 对根与全部后代写回 `path = original_path`（后代保留相对结构）、`original_path = NULL`、`trashed_at = NULL` → 本次单元图片 `deleted_at = NULL`；任何一步失败都回滚数据库与磁盘。
- 旧 v10 行 `original_path IS NULL`：不搬目录，只清 `trashed_at` 与本次单元图片的 `deleted_at`，保持兼容。

#### 4.5 永久删除、清空与释放

- 永久删除/清空仍只写 `purge_operation_id`；行立即从回收站树、普通视图与全库搜索消失。
- 释放任务按 `folders.path`（仓库内部路径）删原图，再自底向上删空目录与行；**原路径不受影响**。
- `has_orphan_purge`、`folder_dir_state`、释放失败清单继续用仓库路径判断；目录里还有未纳管文件时保留行与标记，等下次清空回收站或手动释放重试。
- 本批次不改变“清空记录本身不自动触发释放”的现有策略；只补一个人工入口（记录面板的“释放待删文件”对纯文件夹待释放也可见），不改变释放时机与语义。

#### 4.6 撤销/重做与历史

- `folderTrash`：逆数据保存子树原路径、排序位与删除时间戳；撤销 = 恢复并搬回原路径，重做 = 用新时间戳重新搬入仓库。撤销时原路径被占就失败，可重试或跳过；重做时原路径仍空才搬，否则失败。
- `folderRestore`：撤销 = 重新搬入仓库（原路径必须仍空），重做 = 搬回原路径。
- `folderPurge`：逆数据保存待释放 id；撤销只清标记，仓库内容仍存在才可恢复；释放已经删掉的目录按现有“过期后不可撤销”协议失败。
- `FolderRow` / chunk 需要增加 `original_path` 与删除时间戳（或显式仓库路径）；旧 chunk 缺字段时按“原地回收站”处理，不能把 `NULL` 当空字符串。
- 历史标题、回收站树、面包屑、恢复提示一律使用 `original_path`；日志可同时记录仓库路径便于排查。旧 v10 行 `original_path` 为 NULL 时回退到 `path`。
- 恢复/撤销/重做的搬移都走 `FileJournal`，失败时数据库与目录一起回滚；进程崩溃窗口由启动对账兜底（见 4.9）。

#### 4.7 前端与查询

- 回收站列表的行需要同时提供显示路径（`original_path`）与稳定结构键（文件夹 id；内部 `path` 只用于子树定位）。`TrashFolders` 的树结构与计数按内部路径/id 建，展示与面包屑用 `original_path`，不能按原路径合并两代同名节点。
- 同名文件夹被删除多次时，回收站里是按 `trashed_at` 区分的多个删除单元；节点按 id 区分，界面可附加删除时间说明。
- 新建、导入、移动的目标校验只看正常树，不再命中回收站行；删除后同名创建直接成功。
- 所有删除确认与 MCP `folders_modify delete` 的文案从“文件留在原路径”改成“目录搬入回收站仓库，原路径立即释放”；恢复冲突提示写清“先重命名或移走占用原路径的文件夹”。同步改 `docs/modules/mcp.md` 与 `docs/modules/library.md` 里的旧说法。
- MCP 的 `mcp_trash_folders` / `mcp_images.folder` / `mcp_folders` 显示路径改用 `COALESCE(original_path, path)`，仓库内部路径不出现在工具响应、错误或导出内容里（跨批次依赖见第二节）。
- 顺带修两个已暴露的刷新问题（可拆成独立提交）：清空回收站后回收站树没有立即重取；纯文件夹待释放时记录面板没有“释放待删文件”入口（只补入口，不自动释放）。

#### 4.8 自动检查与验收

- 自动：v10→v11 迁移；删除后原路径不存在、同名创建成功；仓库目录存在且内容完整；恢复搬回；恢复冲突；嵌套子树与多次同名删除；删除单元时间戳唯一；已在图片回收站的行不被文件夹恢复复活；旧 v10 回收站行恢复/释放；永久删除后释放只删仓库；未纳管文件的释放失败与重试；撤销/重做搬移；崩溃窗口对账；内部路径长度上限；MCP 视图显示 `original_path` 且不含 `.artbank/trash`；回收站树计数与全库搜索不变。
- 运行：按 `docs/guides/validation.md` 的允许命令执行，不把命令清单另抄一份到本计划。
- 用户真实窗口：删除文件夹后资源管理器里原目录立即消失、可建同名文件夹；回收站树仍显示原路径；恢复后目录回到原位；先建同名再恢复会明确拒绝；清空回收站后原路径仍可用；清空记录并释放后仓库目录消失；撤销/重做回收站操作；重启后旧回收站行仍可恢复。

#### 4.9 风险与实施约束

- **崩溃一致性（实施前先写对账测试）**：rename 与数据库提交之间进程退出会留下“仓库有目录、数据库还是正常行”或相反状态。启动对账规则固定为“让磁盘与数据库一致”：
  - 扫 `.artbank/trash/<stamp>/<rootId>`；若 `folders.id = rootId` 的行仍是正常行且原路径为空，把仓库根搬回 `path`（撤销未提交的删除）；原路径已被占用时不要覆盖，记为待处理并提示。
  - 若该行是回收站行但仓库根不存在、`original_path` 存在，把原目录搬回仓库根（补完未提交的删除）；原目录也不在时保留行并标记，等用户恢复或永久删除时再报错。
  - 恢复/撤销中断同理：数据库仍是回收站行就搬回仓库，数据库已恢复正常行就搬回原路径。对账只处理 `.artbank/trash` 下的单元，不遍历全库；无法判定时只报告，不删数据。
- **路径长度**：仓库根只增加固定前缀与 id，但原路径本身可能接近 512；落盘前按内部上限校验，超限时在确认框就拒绝，说明“文件夹路径过长，请先缩短路径”，不要等 rename 失败。
- **同名多代**：同一原路径可以被删除多次，回收站树与恢复单元必须按 id/时间戳区分，不能继续假设 path 全局唯一；`original_path` 只做展示，不作为键。
- **旧数据行为不一致**：v10 回收站行仍占原路径，直到恢复或永久删除；这是迁移期的已知过渡，验收时要确认用户能接受。
- **删除变慢与失败面**：文件夹删除现在包含一次真实 rename；网络盘、占用、权限错误会直接让删除失败，需要有清楚的错误与回滚。盘符不同或跨卷不会发生（仓库在库根下），但仍要处理共享盘 rename 失败。
- **释放触发**：清空记录后不自动释放、纯文件夹待释放无入口仍然存在；本批次只补人工入口并消除“原路径被占”，释放时机不自动改变。
- **未纳管文件**：仓库目录里可能有非内容寻址文件；释放失败时保留行与标记，不把原目录重新建出来，也不在界面上暴露仓库路径。

## 四、风险与约束

- **批量撤销**：现有单图撤销只读一个快照；先复用 `LiveOperation` 做多快照格式、逐张续做与 2000 张边界测试。超过上限的不可撤销分支必须明确确认，不能静默降级。
- **裁剪语义**：统一画布的 cover/contain 会改变构图；预览必须让用户看到裁掉了什么，不能在保存后才发现。
- **重编码**：JPEG/WebP 旋转/裁剪会再编码一次；WebP 默认 85，避免 95 造成的体积膨胀。当前编辑路径不保留原文件 EXIF/ICC，文案要说明。
- **磁盘与锁**：批量编辑会同时保留新旧文件并占用内容写资源；开始前估算空间，任务期间挡住导入/压缩/移动。2000 张 4K 的输出文件可能到数 GB，必须让用户在确认页看到估算。
- **压缩撤销不在本轮**：压缩后旧原图已被删除，保留撤销副本会额外占一份旧图体积，优化期间磁盘先涨后降，与“立即省空间”冲突；维持 `Optimize` 不可撤销，只把提示写清。
- **SQL 安全**：只读连接、authorizer、视图白名单与函数策略必须一起用；不能靠关键词匹配或提示词。错误要可读、限时、限行，不自动重试。
- **导出隐私**：导出的是查询结果，不是原图；导出路径可见是刻意的，图库路径仍然隐藏。只在用户开启 MCP 后可用，并保留审计与 TTL。
- **导出路径的暴露面**：路径只暴露系统临时目录与 OS 用户名，不暴露图库根或程序根；如果连用户名也不想给，需要客户端指定导出目录或改用 MCP 资源传输，代价更大。客户端若有 shell/文件读取能力，仍可自行扫描磁盘，路径隐藏不是沙箱。
- **工具膨胀**：不按工作流加工具；新增前先证明“SQL + 文件导出 + 现有相似/写入动作”组合不出来。否则模型的任务越多样，工具越难维护。
- **跨批次口径**：批次 2 的 MCP 视图与批次 4 的 `original_path` 必须同步；后落地的批次负责改视图并补“响应里没有 `.artbank/trash`”的断言。
