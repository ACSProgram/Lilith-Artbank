### 批次 4：后台任务健壮性与并发

已实现并归档，自动检查通过，等待用户手工验收。代码定位、真实库只读测量、已确认决策、接口约定、实现记录与验收口径见[批次 4 记录](archive/2026-10-27-批次4-后台任务健壮性与并发.md)。

- 终态必然收尾：任务线程 panic、线程起不来、任务体提前返回都进入失败终态并释放 lane；release 移除 `panic = "abort"`，加全局 panic hook。
- 长任务的操作记录由 `LiveOperation` 守卫，撤销/重做由 `HistoryRunGuard` 守卫；强杀进程仍由下次打开图库恢复。
- 并发改为“长任务排队”：同 lane 先来先得，`write` 优先，`ai` / `scan` 可并行；评分、标签、描述、编辑保存、回收站等短写以及撤销/重做/清空记录仍快速失败。

- 不做：不改 SQLite 单写连接；不引入外部任务队列；不把长写任务拆成无协调的并行写；不实现 AI 服务崩溃自动重启；不新增任务中心清空入口。

### 批次 5：MCP 接口一致性与规则自描述

已实现并归档，自动检查通过，等待用户手工验收。代码定位、真实库只读测量、决策与实现记录见[批次 5 记录](archive/2026-10-27-批次5-MCP接口一致性与规则自描述.md)。

- `history_list` 与 `collections_list` 不加游标：前者受 `maxSteps`（≤500）限制且已返回 `total`，后者是用户手工维护的少量对象。
- 规则自描述：`library_info` 的 `mcp` 块改为 `writeAllowed` + `approval{requiredInMode, appliesToCurrentMode, threshold, alwaysApproveInAsk, queueClearedOnFull, timeoutMinutes}`，阈值只在询问档给出；服务端 instructions 改为三档逐条说明。写工具回执不加确认标记。

- 分面：保持“标签分面不应用标签维度筛选”的自排除默认，`includeFacets` 时额外返回 `facetsNote` 说明；不加收窄参数，不给分面带名称。
- 标签管理：新增 `tags_modify`（`rename` / `delete` / `merge`），三种动作都走操作记录、都可撤销；`delete` / `merge` 支持 `expectedImages` 核对，询问档需确认。界面标签管理器补“合并到…”，新增 `tagMerge` 记录类型。
- 不做：不改变三档权限模型与 100 张阈值本身；不开放永久删除、清空回收站、压缩、像素编辑或普通图库批量 AI；不为了分页放宽单页上限；不重写标签/文件夹计数 SQL。
- 退出标准：超过 500 个标签/子文件夹可以完整遍历；AI 能正确复述完全档与询问档的差别；标签缺失/排除过滤有明确语义；标签管理写入进入操作记录并可撤销。

### 批次 6：性能专项

已实现并归档：代码定位、查询计划、库副本上的索引 A/B、SigLIP 分段、决策记录与实现记录见[批次 6 记录](archive/2026-10-27-批次6-性能专项.md)。收尾后在空闲环境补跑了 20 万行合成库的聚合与均值基准（`list_folders` 3.3×、`list_tags` 13.5×、均值 9.8×；`counts` 与 `filter_counts` 在合成库上不具代表性）；真实库复测与真实窗口验收仍待做。

- 已定位：620–1 815 ms 的聚合（`counts`、`list_folders`、`list_tags`、`filter_counts`）都不是 SQL 写法问题，而是缺少“可见性 + 分面列”的覆盖索引，39 万次随机回表；真实库加索引后 `counts` 19.7 ms、`list_folders` 27.1 ms，索引只多占 7.0 MB、建一次 533 ms。
- 已定位：`list_tags` 是驱动方向问题，改成“`image_tags` 覆盖聚合 + 回连 `tags`”后 1 162.7 → 23.7 ms，结果逐行相同；`filter_counts` 剩 620–824 ms 是标签分支的交集地板，有筛选时 160 ms。
- 已定位：这些命令都是 Tauri 同步命令，Windows 下卡在窗口事件循环；索引只缩短卡的时间，**不卡窗口靠异步化**（D2 已确认）。
- 已定位：语义搜索冷启动的大头是依赖导入——空闲环境 7.7–8.0 s（RSS 420 MB），非空闲环境同一脚本 17 s；`ensure` 只 mmap 权重（RSS 499 MB），首次 forward 还要 2.37 s 把 2.83 GB 拉进内存。用户澄清没有观察到空闲卸载导致的反复加载，慢的是进程冷启动。
- 已定位：均值在开库时无条件后台计算，但 `ensure_mean` 在 `Computing` 时不等后台、而是同步再算一遍（多花 1–3 s）；`mean` 是单线程标量循环。
- 已定位：移动图片本身 0.169 ms/张，慢在移动后的收尾（重拉文件夹 683 ms + 状态计数 621 ms + 整页刷新）。
- 方案分四组：P1 命令线程模型与增量返回、P2 schema v8 覆盖索引与查询形状、P3 导入预热 + warmup forward + 均值等待/并行、P4 前端刷新截断与预览缓存上限。
- 已定：D1 接受覆盖索引；D2 接受异步化；D3 不改卸载策略、改为“启动预热导入 + ensure 末尾 warmup forward”（420 MB RSS，可关）；D4 均值仍在开库时算，但后台算、不阻塞打开、`Computing` 等待不重算、`rayon` 并行，不做持久化。
- 不做：不提前上 ANN；不做全量内存化；不引入增量计数表；不用跨机器墙钟比较。

### 批次 7：压缩估算准确性

## 跨批次原则

1. 先测量，后优化。批次 1、6、7 都先留基线，再决定缓存、索引或抽样策略。
2. 数据变化必须回答“谁失效、谁保留”。不允许以“全量刷新”作为默认答案。
3. 所有暂存/快照都要有代次、版本或指纹；没有的，至少在执行/展示前复核对象仍存在且范围未变。
4. 前端模块边界、Tauri 薄命令、SQLite 单写、真实库只读等既有约束不变。
5. 每批结束：自动检查、同步模块文档、用户真实窗口验收；代理不启动界面。
6. 不把“计划实现”写成“已经验收”；未完成事项继续写 `todo.md`。

## MCP 反馈评估：值得改与保持不动

| 编号 | 结论 | 说明 |
| --- | --- | --- |
| M1 | 值得改 | `tags_list` 与 `folders_list` 的 500 条硬上限没有游标，超过上限的内容对 AI 完全不可达；这是能力缺口，不是有意的安全边界。保留排序默认与单页上限，只补稳定游标。`history_list` 的上限与操作记录最大步数相同，`collections_list` 的数据量通常较小，二者可按一致性补游标，但优先级低。 |
| M2 | 值得改，但不改权限行为 | 三档模型与“询问档超过 100 张需确认”是既定行为，应保持；问题在于 `library_info` 把 `approvalThreshold` 无条件展示，AI 会误以为完全档也受它约束。只改说明与返回字段，不改实际拦截逻辑。 |
| M3 | 值得改 | 标签缺失/排除是真实筛选能力缺口。需要先定语义并同步到浏览界面，否则 MCP 与界面会出现两套标签筛选。保留 `tagMode: any/all` 的既有行为。 |
| M4 | 不建议改默认 | 分面计数对自身维度排除当前筛选是标准分面搜索行为，改掉会让“选了一个标签后继续看其它标签计数”失效。应补文档与输出说明；确需收窄时增加显式参数，而不是改默认。 |
| M5 | 部分值得改 | 重命名/删除在界面已有，补 MCP 平价是合理的；合并连界面都没有，先定语义并决定是否同时补界面，避免出现只有 AI 能用的破坏性能力。 |

保持不动的 MCP 特性：

- 三档权限模型与“询问档超过 100 张需确认”的阈值本身；完全档不弹确认，只读档拒绝写入。
- 永久删除、清空回收站、图片空间优化、像素编辑、普通图库批量 AI 生成不开放；临时区特征生成是唯一例外。
- `dryRun` / `confirmedCount` 数量核对、一次调用一条历史记录、MCP 写入在进程内串行。
- `search_images` 单页 50、`images_get` 50 张、选择器上限、拼图格数等安全上限；分页不意味着放宽单页。
- `tags_list` 默认按图片数从高到低、不返回 0 张标签；`find_similar` 的单结果槽与 token 失效规则。
- 只读档不隐藏写工具，避免客户端缓存的 `tools/list` 因切档失效。

## 待决策

这些问题会实质影响行为或架构，进入对应批次前需要用户拍板；已确认项保留为决策索引，具体执行口径见对应批次归档记录。

1. **并发策略（已确认）**：长任务冲突时自动排队（同 lane FIFO、`write` 优先、`ai`/`scan` 可并行），短写与撤销/重做/清空记录仍快速失败；不合并同类请求。见[批次 4 记录](archive/2026-10-27-批次4-后台任务健壮性与并发.md)。
2. **任务历史缓存（已确认）**：指操作记录/撤销数据，不是任务中心的内存快照；操作记录面板显示记录数与占用，清空入口沿用现有“清空记录”，不新增任务中心清空入口。见[批次 4 记录](archive/2026-10-27-批次4-后台任务健壮性与并发.md)。
3. **虚拟直属图片入口（已确认）**：放在文件夹树内作为虚拟子行，仅在文件夹同时有子文件夹与直属图片时显示；只对单文件夹生效，多选时不提供。见[批次 3 记录](archive/2026-10-27-批次3-文件夹树与会话状态.md)。
4. **一次性文件夹排序（已确认）**：依据只保留名称与图片数（含子文件夹），可升降序；递归时逐层排序，不把所有后代混成一层；一次操作一条可撤销记录。见[批次 3 记录](archive/2026-10-27-批次3-文件夹树与会话状态.md)。
5. **描述编辑（已确认）**：只点保存才写入；AI 生成直接写入并退出编辑；空描述显示“还没有描述”；草稿按图片暂存，取消即丢弃。见[批次 2 记录](archive/2026-10-27-批次2-详情与批量编辑.md)。
6. **批量标签（已确认）**：同时列共同标签与部分拥有的标签并显示 `拥有数/选中数`；允许创建新标签；详情单图 64 个、批量添加一次 64 个、导入 32 个。见[批次 2 记录](archive/2026-10-27-批次2-详情与批量编辑.md)。
7. **抽样与误差**：是否接受“绝对张数档位”继续作为默认，还是改成比例档位？估算结果是否需要显示误差区间/置信提示？
8. **窗口持久化（已确认）**：使用 Tauri 窗口状态插件，状态跟随系统应用配置目录；只保存位置、大小、最大化，启动后校验屏幕可见性并回退。见[批次 3 记录](archive/2026-10-27-批次3-文件夹树与会话状态.md)。
9. **多选文件夹拖动（已确认）**：一次拖动一条操作记录，撤销整体回退；父子同时选中只移动最外层父。见[批次 3 记录](archive/2026-10-27-批次3-文件夹树与会话状态.md)。
10. **MCP 分页语义（已确认）**：offset 语义的不透明字符串游标，字段 `cursor` / `nextCursor`；聚合必须先算完才能排序，键集条件省不掉扫描且实测更慢。`history_list` / `collections_list` 不加游标。见[批次 5 记录](archive/2026-10-27-批次5-MCP接口一致性与规则自描述.md)。
11. **MCP 标签排除（已确认）**：`tagPresence: any/has/missing` + `excludeTagIds`，不扩展 `tagMode: none`；界面只同步“无标签”，反选入口记为后续项。同上记录。
12. **MCP 标签管理（已确认）**：`rename` / `delete` / `merge` 都做进 `tags_modify` 并同步补界面“合并到…”；合并迁移关系后删除源行，撤销按原 id 重建源标签并插回关系。同上记录。
13. **MCP 标签分面（已确认）**：保持自排除默认，只在 `includeFacets` 时返回 `facetsNote` 说明；不新增收窄参数。同上记录。
14. **MCP 规则呈现（已确认）**：`library_info.mcp` 改为 `writeAllowed` + 结构化 `approval`（阈值只在询问档给出）；写工具回执不加 `confirmationRequired`。同上记录。
15. **性能：覆盖索引（已确认）**：schema v8 只加一张 `(deleted_at, purge_operation_id, folder_id, file_ext, score)` 覆盖索引。实测 `counts` 620.9 → 19.7 ms、`list_folders` 683.4 → 27.1 ms，代价只有库 +7.0 MB、建索引 533 ms、1000 行 `UPDATE` 无可见退化。见[批次 6 记录](archive/2026-10-27-批次6-性能专项.md)的 D1。
16. **性能：命令线程模型（已确认）**：所有重读命令改为异步执行，写命令不再返回整棵文件夹树。代价是并发读最多占满 4 条读连接、命令错误语义需逐一复核。同上 D2。
17. **性能：文本塔驻留（已否决原方案）**：用户澄清实际没有观察到空闲卸载导致的反复加载，慢的是进程冷启动；因此不改卸载策略，改为服务启动后**预热依赖导入**（7.7–8.0 s、RSS 420 MB，可关设置）+ `ensure` 末尾做一次 warmup forward（把首次 forward 的 2.37 s 折进“加载模型”阶段）。同上 D3。
18. **性能：均值策略（已否决持久化）**：均值仍在开库时计算，但后台算、不阻塞打开；`Computing` 时等待后台结果而不是同步重算；`embedding::mean` 改 rayon 并行。不做持久化。同上 D4。

## 风险

- 批次 1 触及全局刷新与失效，回归面最大；需要先把“变化类别 → 失效对象”列全，否则容易修好闪烁、引入过期数据。
- 批次 3 的多选文件夹拖动与排序会同时影响选择、拖放、操作记录与撤销；需要先定一次提交的语义。
- 批次 4 若改变并发策略，可能把“快速失败”变成“长时间排队”，需要前端明确展示排队状态。
- 批次 6 的缓存/索引若没有基准支撑，容易把内存换成另一种卡顿。
- 批次 7 的抽样调整会改变用户看到的估算数字；需要同时解释误差，而不是只追求更接近实际。
- 窗口位置持久化在多显示器/远程桌面下容易恢复出屏幕外窗口，需要可见性回退。
- MCP 列表分页在标签计数/文件夹数量变化时可能出现重漏；需要稳定 tie-break 与明确的快照口径。
- MCP 标签合并是破坏性写入；批次 5 已同时补界面入口与确认，合并会删除源标签行，撤销依赖操作记录（超 `maxSteps` 或清空后无法恢复），确认卡与工具描述都写明这一点。
- 批次 5 的分页不解决 `tags_list` / `folders_list` 的单页耗时（真实库 2.4–4.4 s / 1.8 s），性能留给批次 6。批次 6 已定位并给出方案：`list_tags` 换驱动方向后 1 162.7 → 23.7 ms，`list_folders` 加覆盖索引后 683.4 → 27.1 ms，`tags_list` / `folders_list` 因此不再需要专门优化。
