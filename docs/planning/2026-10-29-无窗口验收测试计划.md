# 无窗口验收测试补齐计划

日期：2026-10-29

状态：B1 已完成（2026-10-29）；B2–B3 待实施。实施完成后，本计划与批次记录移入[规划归档](archive/README.md)，表层只保留已自动化的结论。

## 一、目标

把 `todo.md`「待验收」里**所有不依赖真实窗口、真实渲染、真实 AI 模型与外部数据的条目**，改成可在后台运行的无窗口测试；剩下必须真人看的，收敛成一条短冒烟清单。

完成标准：

1. 每条待验收都能回答“由哪个测试覆盖”或“为什么只能手工”。
2. 无窗口套件不创建窗口、不加载 WebView、不经过 IPC、不模拟键鼠、不截图。
3. 测试不读取 `G:\Lilith Image Library`、`G:\Lilith Test Library`、`python_embeded`、模型目录或任何外部服务。
4. 裸 `cargo test` 行为不变；无窗口测试只在显式 feature/命令下运行。
5. 默认套件在普通桌面机上可以后台跑，CPU/磁盘/内存有明确上限；超过上限的场景必须先向用户请示。

## 二、参考实现

`F:\Programs\Lilith Artworks` 已经有一套成熟做法，直接借鉴其结构：

- 无头入口：`src-tauri/src/headless.rs`，由空 feature `headless` 门控；`src-tauri/src/main.rs` 在 Tauri 初始化之前拦截 `--headless`。入口只做参数解析、状态装配与领域函数调用，不创建窗口、托盘或 WebView。
- 进程边界：压力测试 `src-tauri/tests/stress_*.rs` 启动**真实可执行文件**，只通过命令行、stdin、JSON 结果与磁盘事实断言，不读取被测进程内部状态。
- 门控纪律：所有会启动子进程的测试目标以 `#![cfg(feature = "headless")]` 开头；`tests/gate_guard.rs` 扫描并强制这一行，防止裸 `cargo test` 拉起 GUI。
- 共享助手：`tests/stress_support/mod.rs` 统一工作区、进程编排、报告、账本、磁盘预算与档位。
- 成本分层：便宜组进 CI/日常，昂贵组只在显式请求时跑；产物统一落在 `<target>/stress/`，随 `cargo clean` 清掉。
- 可观测性：每个场景一行 JSON，记录耗时与峰值工作集；昂贵场景另有磁盘账本。

本计划只借结构，不复制 Artworks 的 12 组压力场景。Artbank 的验收重点是图库状态与文件事实，不是大文件吞吐。

## 四、总体方案

### 4.1 Feature 与入口

`src-tauri/Cargo.toml` 增加空 feature：

```toml
[features]
headless = []
```

`src-tauri/src/main.rs` 在 `run()` 之前拦截：

```rust
#[cfg(feature = "headless")]
{
    let arguments = std::env::args().skip(1).collect::<Vec<_>>();
    if arguments.first().map(String::as_str) == Some("--headless") {
        std::process::exit(lilith_artbank_lib::run_headless(&arguments[1..]));
    }
}
```

`src-tauri/src/lib.rs` 增加：

```rust
#[cfg(feature = "headless")]
mod headless;

#[cfg(feature = "headless")]
pub fn run_headless(args: &[String]) -> i32 {
    headless::run(args)
}
```

约束：

- 该 feature 不进 default，不进发布产物；不带 feature 时 `--headless` 不存在，行为与现在完全一致。
- `--mcp-stdio` 保持现状，与 `--headless` 是两个入口：前者是 MCP 小桥，后者是验收适配器。
- 无头入口不调用 `lilith_artbank_lib::run()`，不创建用户可见窗口、不建托盘、不加载 WebView、不经过 IPC。B0 实测 tao 会建立一个 15×15、无标题、无任务栏入口的事件循环窗口，见 4.2 的 B0 记录。

### 4.2 无窗口启动与状态装配

无头进程需要 `AppState` 才能覆盖任务总线、资源锁、MCP、AI 与撤销恢复。启动顺序：

1. 测试通过子进程环境变量把 `LILITH_ARTBANK_ROOT` 指向本次工作区；无头进程不再自行改写环境变量。
2. 用 `tauri::Builder::default().build(tauri::generate_context!())` 建一个**没有窗口、随后不调用 `run()`** 的应用，只取 `AppHandle`。
3. 从 `<root>/settings.json` 载入或创建设置；无头模式**不自动打开上次图库**，由命令显式打开。
4. `AppState::new(settings, app.handle().clone())`，`app.manage(state)`；按需调用与 GUI 相同的 `after_manage` / 开库逻辑。
5. 执行一条命令或一个场景，写结果 JSON，调用 `shutdown`、`ai.shutdown`、`mcp.stop`，退出。

**决策门（B0）**：先做 `--headless ping` 尖刺，确认三件事：

- 应用能在不创建用户可见窗口的情况下 build 并拿到 `AppHandle`；
- `AppState`、任务事件、MCP 事件不依赖窗口存在；
- 进程能在 5 秒内正常退出，不残留 WebView2 子进程。

**B0 实测（2026-10-29）**：

- `cargo build --features headless` 成功；`--headless ping` 退出码 0，输出 JSON；`settings.json` 只落在 `LILITH_ARTBANK_ROOT`，仓库根的 `settings.json` 未被触碰。
- 没有 Tauri 主窗口，没有新增 `msedgewebview2.exe`，没有直接子进程。
- `EnumWindows` 只看到 tao 事件循环的 `Tao Thread Event Target`：15×15、位于 (0,0)、无标题、owner=0、`visible=true`；另有一个隐藏的 IME 窗口。任务栏与 Alt-Tab 无入口，用户确认没有看到新增窗口。
- 结论：按“用户不可见”接受当前方案，B1 继续用最小 Tauri 应用装配 `AppState`。若后续要求严格“零顶层窗口”，必须走下面的回退 1/2，不能在产品路径里硬隐藏。

若尖刺失败，按以下顺序回退，并在实施前向用户说明改动范围：

1. **优先**：在 `AppState`、任务总线、MCP 审批、AI 事件处引入最小事件出口 trait（GUI 用 `AppHandle`，无头用空实现）。只改推送出口，不改领域逻辑。
2. **次选**：让状态类型对 `tauri::Runtime` 泛型化，无头用 `tauri::test::mock_app`。改动面更大，只有在方案 1 不可行时采用。
3. **最后**：无头只覆盖领域函数，任务/MCP/AI 的端到端项退回手工。这会明显降低覆盖率，不推荐。

### 4.3 命令面

无头入口是命令层的第二适配器：解析参数、取当前图库、调用与命令相同的 `AppState`/领域函数、输出 JSON。业务判断不写进 `headless`。

按待验收需要，第一批命令面如下（名称可微调，语义与 Tauri 命令一致）：

| 域 | 命令 |
| --- | --- |
| 图库 | `library create/open/open-configured/close/info/counts/inspect-path` |
| 设置 | `settings get/save` |
| 查询 | `query images/ids/stats/folders/tags/detail/states/selection-tags` |
| 元数据 | `metadata score/description/tags/move/trash/restore/delete/empty-trash` |
| 文件夹 | `folder create/rename/move/delete/reorder/place/order/apply` |
| 集合 | `collection list/create/rename/delete/add/remove/combine/reorder` |
| 历史 | `history list/undo/redo/clear` |
| 导入 | `import run/start/cancel` |
| 任务 | `task list/cancel/wait` |
| 查看器/编辑 | `viewer source`、`edit save/estimate` |
| 维护 | `inspect run/report`、`orphan move`、`export run`、`pack stats/gc` |
| 优化 | `optimize estimate/execute` |
| AI | `ai status/semantic/similar/pose/embedding` |
| MCP | `mcp serve` |
| 场景 | `scenario <name>` |
| 夹具 | `fixture corpus/seed-db/write-image` |

命令约定：

- 参数用 `--request <json-file>` 或 `--request-json <inline>` 传 DTO；复杂请求不塞进命令行。
- `--root` 可显式指定程序根目录，但测试优先用 `LILITH_ARTBANK_ROOT` 子进程环境变量，避免进程内改环境。
- `--result <file>` 写结果；stdout 保持单行 JSON，便于测试解析。
- 退出码：`0` 成功、`1` 失败、`2` 取消。
- 结果统一含 `command`、`ok`、`elapsedMs`、`peakWorkingSetBytes`、`data`、`error`。

### 4.4 场景与长任务

一次性命令无法覆盖任务排队、取消、锁冲突、审批、空闲回收与进程重启恢复，用 `scenario` 在同一进程内编排：

| 场景 | 覆盖 |
| --- | --- |
| `task_queue_cancel` | 同资源排队、取消排队任务、取消运行中任务、终态与资源释放 |
| `task_panic` | 任务体 panic 后的失败态、操作记录不停在 pending、资源释放 |
| `close_during_task` | 有任务时关闭/切换图库被拒绝，取消后允许 |
| `folder_lock` | 导入/压缩期间文件夹重命名/移动的拒绝与放行 |
| `ai_lock` | AI 任务期间元数据写入不被整库挡住，压缩期间拒绝 |
| `idle_gc` | 短空闲间隔下的自动回收、垃圾率下降 |
| `idle_yield` | 回收中有人操作时的“已让位”、稍后继续 |
| `undo_interrupt` | 撤销/重做跨进程中断后重开图库续做 |
| `mcp_ask` | 询问档待确认、批准/拒绝、过期、换库清空 |
| `settings_restart` | 保存设置后进程退出，再启动读取同一份设置 |
| `log_rotation` | 等级、行格式、命令记录、4MB 轮转与归档份数 |

场景只做编排，断言仍放在 `tests/` 的集成测试里；场景输出事实 JSON，测试判断对错。

长任务（导入、压缩、检查、回收）默认在场景内同步跑完；需要取消的用 `--cancel-after-ms`。所有场景必须设置超时，避免后台挂死。

纪律与 Artworks 一致：

- 工作区统一由 `acceptance_support::Workspace` 创建在 `<target>/acceptance/workspaces/`，不落 `%TEMP%`，不散到仓库其他位置。

- 产物路径从 `CARGO_TARGET_TMPDIR` 反推，不硬编码 `src-tauri/target`。
- 每个场景记录：目标条目、耗时、峰值工作集、生成文件数/字节、断言结果。

档位：

| 档位 | 默认 | 内容 |
| --- | --- | --- |
| `cheap` | 是 | 设置、查询、元数据、文件夹、集合、回收站、撤销、日志、AI stub、MCP 协议 |
| `default` | 是 | 导入小样本、查看器/编辑、维护、包统计、短时任务场景 |
| `heavy` | 否 | 规模合成库、压缩估算/执行、全量检查、20k 文件操作、大图 |

通过 `LILITH_ACCEPT_TIERS=cheap|default|heavy` 选择；`heavy` 必须显式打开。任何超过第五部分预算的场景，默认不跑。

### 4.6 后台运行

提供 `tools/acceptance/run.ps1`（或 `.mjs`）作为唯一入口：

- 用 Windows Idle 优先级启动，隐藏窗口；
- 默认 `--test-threads=1`，限制 `RAYON_NUM_THREADS=2`；
- 默认只跑 `cheap+default`，`heavy` 需要 `-Tier heavy` 或环境变量；
- 结束后打印报告路径与失败条目，不弹出任何窗口。

不常驻、不注册计划任务；需要后台跑时由用户或代理显式启动，跑完退出。

## 五、测试数据策略

### 5.1 硬约束

- 不读取 `G:\Lilith Image Library`、`G:\Lilith Test Library`、`G:\Lilith Image Library Failed`。
- 不启动 `python_embeded`，不加载 `resources/models`，不访问外部网络；AI 只连测试进程内的 `127.0.0.1` 假服务。
- 不把真实图库路径写进测试或基准。
- 所有测试数据在临时工作区内生成，结束回收。

### 5.2 按操作类型选择最小数据形态

| 测试类型 | 数据形态 | 说明 |
| --- | --- | --- |
| 查询、筛选、选择、统计、计数、分页 | 直接向 SQLite seed 行，不生成图片文件 | 复用 `library/perf.rs` 的合成行种子；规模测试首选 |
| 文件夹移动、回收站、恢复、永久删除、撤销 | seed 行 + 0–1 字节占位文件，文件名按实际内容哈希 | 这些路径只做文件搬移/存在性检查，不解码 |
| 导入、缩略图、查看器、几何编辑 | 16×16 到 64×64 的渐变/纯色 PNG/JPEG/WebP/GIF/TIFF/TGA/BMP | 体积很小，生成快；覆盖格式、透明、动画、EXIF 方向 |
| 压缩估算/执行 | 少量 256×256 或 512×512 纹理图 | 需要可压缩内容，不能用纯色 |
| 大图/超限 | 单张 6000×6000 纯色 PNG | 文件小但解码内存高；单独标记 |
| 维护检查、孤儿、包统计 | 小文件 + 人工构造的孤儿/截断/同名文件 | 不需要真实美术图 |
| 日志 | 临时根目录 + 4MB 日志写入 | 不需要图片 |

这样把“大量图片”拆成“大量数据库行 + 极少量真实文件”，避免逐个生成大图。

### 5.3 预算与请示线

默认套件单场景预算：

- 生成文件 ≤ 200 个；
- 生成数据 ≤ 50 MB；
- 峰值内存 ≤ 1 GB；
- 磁盘 ≤ 2 GB；
- 墙钟 ≤ 60 秒。

超过任一项，或整轮预计超过 10 分钟，必须先向用户请示，说明规模、耗时、内存、磁盘与替代方案。

### 5.4 已知的重场景（默认不跑）

| 场景 | 建议规模 | 预计耗时 | 峰值内存/磁盘 | 说明 |
| --- | --- | --- | --- | --- |
| 20 万行查询/筛选/排序基准 | 合成 DB，无文件 | 1–5 分钟 | 数百 MB / 数百 MB | 已有 `perf_metadata_200k`，优先复用，不新增 |
| 39 万行合成库 | 合成 DB，无文件 | 5–15 分钟 | 1–2 GB / 约 1 GB | 只证明规模曲线；真实库首次打开仍需手工 |
| 1,000 张极小图导入 | 16×16 PNG/JPEG/WebP/BMP | 10–60 秒 | <500 MB / <50 MB | 覆盖导入管线与进度/取消 |
| 9,455 个文件的全量检查 | 1 字节文件 + 正确哈希名 | 30–120 秒 | <500 MB / <100 MB | 需要用户确认是否值得造这么多文件 |
| 20,000 个文件移动/回收站 | 1 字节占位文件 + seed 行 | 1–5 分钟 | <1 GB / <100 MB | 文件系统条目多，可能拖慢整机 |
| 300 张 512×512 压缩估算/执行 | 纹理图 | 1–5 分钟 | <1 GB / 100–300 MB | 估算准确性需要可压缩内容 |
| 4K/50MP 单图保存 | 单张大图 | 数秒 | 100–300 MB / 小 | 只跑一次，验证上限与原子性 |
| 日志轮转 | 4MB 日志 | 数秒 | 小 | 无需大图 |

这些场景全部放在 `heavy` 档，默认不启用；是否实现、是否运行，按用户后续决定。

## 六、覆盖矩阵

“自动”=无窗口测试可覆盖；“手工”=必须真人/真窗口/真实模型。部分条目拆成自动的后端断言与手工的界面观感。

| 组 | 自动覆盖 | 仍手工 |
| --- | --- | --- |
| 1 图库生命周期与设置 | `acceptance_settings`：创建/打开/关闭、路径检查、设置落盘与重启、`settings.json` 原子替换、自动打开上次图库（无头 `library open-configured`）；`acceptance_logs`：启动横幅 | 主库/测试库真实观感（1、2）；欢迎页与设置页布局（3、5）；真实窗口位置/大小/最大化/离屏回退（4）；真实库首次打开耗时（6） |
| 2 导入 | `acceptance_import`：导入小样本、平铺/保留源目录、目标文件夹、临时文件夹、取消保留、临时清理、导入中关闭/切换被拒、重复策略、失败清单 | 文件/目录选择器、拖放、进度与结果面板观感（1、2）；真实样本吞吐（4）；247 条超大图（5） |

## 八、长耗时/高占用与请示点

用户已确认的默认策略：单次生成不超过 **1,000 个文件、200 MB** 的重档场景可以自动跑，不逐项请示；超过这条线，或预计单场景超过 5 分钟、峰值内存超过 1 GB、磁盘超过 2 GB，必须先说明规模与替代方案。

1. **9,455 文件全量检查**：默认用 500 文件覆盖逻辑；9,455 超出自动线，需单独同意。
2. **20,000 文件移动/回收站**：默认用 2,000 文件 + 合成 DB 行；20,000 超出自动线，需单独同意。
3. **396,000 行合成库**：只证明规模曲线，不证明真实库；磁盘约 1 GB、内存 1–2 GB、5–15 分钟，需单独同意。保留 200,000 行现有基准；真实库首次打开仍手工。
4. **300 张 512×512 压缩估算/执行**：需要可压缩纹理图，磁盘 100–300 MB、1–5 分钟；生成量在自动线内可直接跑，超过 200 MB 再请示。
5. **4K/50MP 单图**：单张解码内存 100–300 MB，用于上限与原子性；只跑一次。
6. **日志轮转**：写入 4MB 日志，成本低，默认跑。

## 九、风险与边界

- **逻辑通过不等于界面通过**：无窗口测试证明数据、文件、状态、资源与协议，不证明布局、动画、手感、WebView2 渲染。历史上拖放曾在浏览器预览里全好、真实 WebView2 里从未工作，这类问题只能真人验收。
- **性能数字不可跨环境比较**：无头套件的耗时只用于发现数量级退化，不作为用户感知性能；真实库与真实窗口的耗时仍手工记录。
- **AI 是假服务**：stub 只验证协议与错误路径，不验证模型质量、显存、加载耗时。
- **MCP 是进程内/桥接测试**：不替代真实第三方客户端与便携包联调。
- **无断电验证**：强杀进程不等于断电；断电持久性仍为手工/声明项。
- **测试夹具会腐化**：命令面、场景与测试钩子需要随产品契约维护；新增命令或改变资源语义时必须同步更新对应测试。
- **不写真实库、不编译 release、不驱动窗口**：这是红线，无窗口套件也不破例。
