# 语义特征基的归属、身份与自动准备计划（批次 1）

日期：2026-11-01
前置：[特征检索扩展计划](archive/2026-11-01-特征检索扩展计划.md)（语义描述子代码已落地，真实基拟合未做）
当前能力：[当前状态](current-handoff.md) · 待办：[待办与待决策](todo.md)

## 问题

2026-11-01 主库上点「生成语义特征」得到“缺少构图白化基 spp_basis.npz；请先用 server/tools/fit_basis.py 生成”，任务在准备阶段直接失败。查完的结论不是脚本忘了跑，而是三处结构性问题：

1. **归属错配**：基放在模型目录（全局一份），描述子存在库内 `.artbank/features/`。两个东西生命周期不同——基删了、换了，库里的描述子还在。
2. **没有身份**：`pack.rs` 的 `pack_name` 只含 kind/model/dim/dtype，`image_features.BASIS_VERSION` 写死为 1，`load_basis` 也只校验版本号。换基后新描述子会追加进同一个包，新旧混在一起，既分辨不出也无法回滚，检索质量会静默下降。
3. **缺基没有退路**：`clip_cache._load_locked` 把缺基转成 `CapabilityUnavailable` → `/v1/models/ensure` 422 → 任务失败；`/v1` 没有拟合端点，`fit_basis.py` 只吃路径清单，不认识图库这个概念。

现状数据（只读核对）：主库 424,218 张，`embedding` 424,218 条、`pose` 96,158 条、`spp` / `maxsim` **0 条**；测试库 9,456 张，同样 0 条。所以本批次不是“换基”，是**首次建基**，没有任何现存描述子会失效。全局 embedding 与基无关，换基不影响语义搜索与找相似的粗筛。

## 目标

语义描述子的产出与校验不再依赖人工跑脚本；换基变成可回滚的常规操作；多图库互不污染。出口条件：

- 缺基的库打开后自动就绪，不需要用户知道 `fit_basis.py` 存在。
- 换基只切换指针，旧描述子在新包补齐前仍可服务，出错能切回。
- `embedding` / `pose` 的包名与记录一个字节都不动。

## 已定决策

1. **基跟着描述子走**，存库内 `.artbank/basis/<clip_model>/`。模型目录里那份降级为「通用兜底」，只在小库凑不够样本时复制过去用。
2. **`basis_id` 同时写进库与包名**：`meta` 一条记录管校验，包名管物理隔离。两者都只在 `spp` / `maxsim` 上生效。
3. **缺基自动准备，但绝不自动替换已有的基**。自动流程只在“从来没有基”时介入；想换基只能显式操作。
4. **不做增量滚动更新**。基一变就要全库重算描述子，“边积累边更新基”等于常年在重算，收益为零。
5. **拟合走带状态的端点，读图留在 Rust**。不把 3 000 个路径交给 Python 自己读——那同时破坏“文件读写只走 Rust”和进度上报。
6. **不涉及 schema 版本变更**（`meta` 是键值表），也不改特征包 MAGIC 与 VERSION。

## 步骤 A · 归属

- 基路径：`<库>/.artbank/basis/<clip_model>/{spp_basis,maxsim_basis}.npz`，文件格式不变（仍有 `version`、`samples`、`scale`）。
- 记 `meta` 之前先定位：`app/` 层新增基目录解析（`clip_model_path` 相对库根），`ai/` 加载时优先库内、其次模型目录。
- `clip_cache` 的 `_LoadedTower` 记录当前 `basis_id`；`/v1/models/ensure` 请求体增加可选 `basis`：`{"dir": "...", "id": "..."}`，缺省仍按 `--model-dir` 读取（兼容现有调用）；`basis_id` 变化即重载塔（约 36 s，只在换库或换基时发生）。
- 库内没有基、模型目录有基：复制到库内再加载，`meta.source=universal`。

## 步骤 B · 身份

- `basis_id` = 两份 npz 字节 + 模型名的 blake3 前 16 位，由 Python 算出返回；Rust 侧用同一个函数校验（`blake3` 已是依赖）。
- 库 `meta` 增加 `feature_basis`，值是一个 JSON：`{model, id, samples, source: library|universal, fitted_at}`。
- `pack_name(kind, model, dim, dtype)` 增加 `basis_id` 入参，并拼进 blake3 的输入；`embedding` / `pose` 传 `None`，哈希输入保持原样，**存量包名不变**。
- 换基流程：新 `basis_id` → 新包 → 批量任务按 `PendingFilter::Features` 补齐 → 补完写 `meta` 指向新基 → 旧包标记待释放，走既有释放任务延迟删除。中途取消或失败：`meta` 不动，旧包继续服务。
- 校验：批量任务预览、任务启动与检索入口都读 `meta.feature_basis`，与当前基不一致的 `spp` / `maxsim` 记录按“缺”处理，自动进入待处理清单——不再需要人工清表。

## 步骤 C · 触发

打开库或首次需要图片塔时按三种情况分流：

| 情况 | 动作 |
| --- | --- |
| 库内有基 | 直接加载 |
| 无基，有效率 ≥ 1500 | 自动分层抽样拟合，走任务面板，可取消 |
| 无基，有效率 < 1500 | 复制通用基，任务消息写明来源 |

拟合端点（带累积器状态，Python 侧只在内存里攒统计量）：

- `POST /v1/basis/start`：`{model, kinds:["spp","maxsim"], maxsimSample}` → 建累积器，返回 `sampleId`。
- `POST /v1/basis/add`：图片字节，逐张调用；返回已累积张数。每张一次请求，进度天然可见，取消即停。
- `POST /v1/basis/finish`：返回两份 npz 的 base64 与 `basis_id`，Rust 落盘并写 `meta`。
- `POST /v1/basis/cancel`：丢弃累积器。

拟合失败或取消：不写 `meta`，任务里显示原因，功能维持“无基”状态而不是把库里数据标脏。

## 验收

自动覆盖：`cargo test --lib` 覆盖 `pack_name` 的 `basis_id` 分支与存量包名不变、`meta.feature_basis` 读写、`basis_id` 不一致时的待处理过滤、`/v1/basis/*` 累积器用合成特征拟合出可读的基；Python 侧 `py_compile` 与「合成特征跑通 start/add/finish/cancel」。

- [ ] 有基的库：`/v1/health` 的 `imageEmbedding.ready=true`，`/v1/embed/image?features=spp,maxsim` 返回两条记录，长度 8192 / 2048。
- [ ] 小库兜底：测试库（9,456 张）删掉库内 `basis/` 后打开，自动复制通用基，任务消息写明来源，能直接生成语义特征。
- [ ] 大库首次：主库打开后出现“正在准备语义特征基”任务，进度按张数推进、可取消；完成后 `meta.feature_basis` 有 id、样本数与 `source=library`。
- [ ] 换基演练：手工替换库内基 → 批量任务预览把已有 `spp` / `maxsim` 全算进“将处理 M” → 跑完切到新包名、旧包被释放；中途取消后旧包仍可服务。
- [ ] 存量不动：`embedding` 424,218 条、`pose` 96,158 条的包名与记录数不变。
- [ ] 换库不串味：在测试库与主库之间切换后，各自用自己的基，`health` 与检索都正常。

## 不做

- 自动重拟合已有基；导入或库变动后自动重拟合。
- 增量累积充分统计量并滚动更新基（等于常年重算）。
- 为一个库准备多份基再按查询挑选。
- 保留“缺基硬失败”。
- 界面上的基管理入口（拟基、换基仍然由“首次缺基”与显式操作触发，不新增设置页）。
